# 🐧 Linux Fondamentals — Cours Complet

## À propos de ce cours

**Public visé :** toute personne qui veut passer d'une utilisation superficielle de Linux à une vraie maîtrise du terminal et de l'administration de base — sans prérequis autre que savoir installer un logiciel.

**Comment l'utiliser :**
- Ouvre un vrai terminal Linux pendant que tu lis. **Tape** chaque commande, ne te contente pas de lire.
- **Choisis bien ta machine d'entraînement.** Pour la Partie 1, un simple `docker run -it ubuntu bash` ou WSL2 suffit. À partir de la Partie 2, il te faut un **vrai système avec systemd** (services, cron, SSH, pare-feu) : une VM, un conteneur système LXD, ou le lab du projet fil rouge ([projet-fil-rouge/lab](projet-fil-rouge/lab/README.md)), qui fonctionne sur ton VPS comme sur ton PC. Un conteneur Docker ordinaire n'a ni systemd ni cron : la moitié des commandes y échouerait pour de mauvaises raisons.
- Progresse dans l'ordre : chaque module s'appuie sur le précédent.
- Fais les exercices avant de regarder la solution — c'est là qu'est l'apprentissage réel.
- Une commande que tu ne comprends pas ? `man <commande>` ou `<commande> --help` est ton meilleur ami dès le Module 1.

**Structure :** 23 modules (numérotés 0 à 22) répartis en 5 parties, du "qu'est-ce qu'un shell" jusqu'à la mise en service d'une application derrière nginx et un projet de synthèse.

**Conventions utilisées dans tout le cours :**
- Les blocs de code sont donnés **sans prompt** (`$` ou `#`) pour être copiables directement.
- `sudo` apparaît partout où les droits root sont nécessaires. Si tu travailles déjà en root, retire-le.
- Les exemples supposent **Debian/Ubuntu** (testés sur Ubuntu 24.04 LTS). Les équivalents RHEL/Fedora sont signalés quand ils diffèrent, ainsi que les écarts entre Debian et Ubuntu (par exemple, Debian 12 n'installe plus `rsyslog` : pas de `/var/log/syslog` ni de `/var/log/auth.log`, tout est dans `journalctl`).
- ⚠️ signale une commande destructive ou risquée, 💡 une astuce de terrain, 🪤 un piège classique.

**Place dans le parcours :** ce cours est l'**étape 1 sur 3**, suivie de *Linux Intermédiaire* (étape 2) puis *Linux Expert* (étape 3).

**Projet fil rouge :** les trois étapes sont accompagnées d'un projet unique, [projet-fil-rouge](projet-fil-rouge/README.md) : mettre en production une vraie application (Marché, une plateforme de commande en ligne) sur des serveurs Ubuntu, du premier compte utilisateur jusqu'à une infrastructure haute disponibilité reconstruite par Ansible. Le Palier 1 du projet correspond à ce cours ; le terminer seul, avec le correcteur au vert, prouve la maîtrise des fondamentaux.

# Partie 1 — Bases du terminal

## Module 0 — Qu'est-ce que Linux ?

### Le concept
Linux n'est **pas** un système d'exploitation complet à proprement parler : c'est un **noyau (kernel)**, créé par Linus Torvalds en 1991. Ce que tu utilises au quotidien (Ubuntu, Debian, Fedora, Arch...) est une **distribution** : ce noyau + des outils GNU + un gestionnaire de paquets + parfois une interface graphique.

### Les familles de distributions
| Famille | Exemples | Gestionnaire de paquets |
|---|---|---|
| Debian | Debian, Ubuntu, Linux Mint | `apt` |
| Red Hat | RHEL, Fedora, CentOS, Rocky | `dnf` / `yum` |
| Arch | Arch Linux, Manjaro | `pacman` |

Ce cours utilise la syntaxe **Debian/Ubuntu** (`apt`), la plus répandue, mais les concepts sont identiques partout.

### Philosophie Unix (à garder en tête tout le cours)
- **Tout est fichier** — y compris les périphériques matériels, les processus, les sockets.
- **Des petits outils, bien faits, combinables** — plutôt qu'un gros outil qui fait tout. C'est ce qui rend les pipes (`|`) si puissants.
- **Pas d'interface graphique obligatoire** — tout peut se faire en ligne de commande, ce qui rend le système scriptable et automatisable.

### Architecture en une image mentale
```
Matériel
   ↓
Noyau Linux (gestion mémoire, CPU, périphériques, réseau)
   ↓
Shell (interprète tes commandes : bash, zsh...)
   ↓
Applications (ls, apt, nginx, ton code...)
```

### Exercice 0.1

<details><summary>💡 Solution</summary>

Alternative plus courte : `lsb_release -a` (pas toujours installé par défaut).
</details>

### Exercice 0.2
Trouve la version du noyau Linux que tu utilises.

<details><summary>💡 Solution</summary>


</details>

## Module 1 — Le terminal et le shell

### Le concept
- **Terminal (ou émulateur de terminal)** : la fenêtre/application qui affiche du texte et capte ton clavier.
- **Shell** : le programme qui interprète ce que tu tapes et l'exécute. Le plus courant : **bash** (Bourne Again SHell).
- Ces deux mots sont souvent confondus dans le langage courant — ce n'est pas grave, mais sache faire la distinction.

### Anatomie du prompt
```
juvanio@serveur:~/projets$
   │        │      │      └─ symbole ($ = utilisateur normal, # = root)
   │        │      └──────── répertoire courant (~ = home)
   │        └─────────────── nom de la machine (hostname)
   └──────────────────────── utilisateur connecté
```

### Commandes essentielles pour se situer
| Commande | Rôle |
|---|---|
| `whoami` | affiche ton nom d'utilisateur |
| `hostname` | affiche le nom de la machine |
| `date` | date et heure système |
| `uptime` | depuis combien de temps la machine tourne |
| `clear` (ou `Ctrl+L`) | nettoie l'écran |
| `history` | historique des commandes tapées |
| `!!` | rejoue la dernière commande |
| `Ctrl+R` | recherche interactive dans l'historique |
| `Ctrl+C` | interrompt la commande en cours |
| `Ctrl+D` | ferme le shell / signale une fin d'entrée |

### L'autocomplétion : le réflexe numéro un
La touche **`Tab`** complète automatiquement commandes, chemins et noms de fichiers.
- `Tab` une fois → complète s'il n'y a qu'une possibilité.
- `Tab` deux fois → affiche toutes les possibilités s'il y en a plusieurs.

Ce n'est pas un gain de confort, c'est un **filet de sécurité** : si `Tab` ne complète pas un chemin, c'est qu'il n'existe pas. Tu évites ainsi la moitié des fautes de frappe — y compris sur un `rm`.

### Éditer la ligne de commande sans les flèches
| Raccourci | Action |
|---|---|
| `Ctrl+A` / `Ctrl+E` | aller au début / à la fin de la ligne |
| `Ctrl+W` | supprimer le mot précédent |
| `Ctrl+U` | effacer toute la ligne |
| `Ctrl+K` | effacer du curseur jusqu'à la fin de la ligne |
| `Alt+B` / `Alt+F` | reculer / avancer d'un mot |

### Se documenter tout seul
C'est la compétence la plus rentable du cours : aucun administrateur ne connaît toutes les options par cœur, il sait les retrouver en dix secondes.

```bash
man ls              # manuel complet ("q" pour quitter, "/mot" pour chercher dedans)
ls --help           # aide courte, souvent suffisante et plus rapide à lire
apropos réseau      # cherche une commande par mot-clé quand tu ne connais pas son nom
type ll             # dit si c'est un alias, une fonction, un builtin ou un binaire
which python3       # chemin du binaire qui sera réellement exécuté
```

Les manuels sont découpés en **sections** numérotées. La même page peut exister dans plusieurs :
```bash
man 1 passwd        # section 1 = la commande passwd
man 5 passwd        # section 5 = le format du fichier /etc/passwd
man man             # la liste des sections
```

> 💡 Si tu tombes sur une commande inconnue dans un script ou un tutoriel, le réflexe est `man <commande>` **avant** de la lancer — surtout si elle commence par `sudo`.

### Exercice 1.1
Retrouve dans ton historique la dernière commande contenant le mot "apt" sans faire défiler manuellement.

<details><summary>💡 Solution</summary>

`Ctrl+R` puis taper `apt` — bash propose la dernière occurrence, `Ctrl+R` à nouveau pour remonter aux occurrences plus anciennes.
</details>

### Exercice 1.2
Exécute une commande qui échoue volontairement (ex : `frmo /tmp/test`), puis rappelle-la et corrige juste la faute de frappe sans la retaper entièrement.

<details><summary>💡 Solution</summary>

Variante utile au quotidien : `^frmo^rm^` rejoue la dernière commande en remplaçant la première occurrence de `frmo` par `rm`.
</details>

### Exercice 1.3
Tu lis un tutoriel qui utilise `ss -tulpn` et tu ne sais pas ce que fait l'option `-u`. Trouve la réponse sans quitter ton terminal et sans moteur de recherche.

<details><summary>💡 Solution</summary>

```bash

```
Ou, pour un simple rappel : `ss --help`.
</details>

## Module 2 — Navigation dans le système de fichiers

### Le concept : la hiérarchie FHS
Linux organise tout dans **une seule arborescence** commençant à `/` (racine) — pas de "C:\" et "D:\" séparés comme sous Windows.

| Répertoire | Contenu |
|---|---|
| `/` | racine de tout le système |
| `/home` | répertoires personnels des utilisateurs |
| `/etc` | fichiers de configuration système |
| `/var` | données variables (logs, bases de données, mails) |
| `/usr` | programmes et bibliothèques installés |
| `/bin`, `/sbin` | exécutables essentiels (système/admin) |
| `/tmp` | fichiers temporaires (effacés au reboot) |
| `/root` | home de l'utilisateur root |
| `/dev` | fichiers représentant le matériel (disques, terminaux...) |
| `/proc` | informations virtuelles sur les processus en cours |

### Chemins absolus vs relatifs
- **Absolu** : commence par `/` → `/home/juvanio/projets`
- **Relatif** : part d'où tu es → `projets/backend`
- `.` = répertoire courant | `..` = répertoire parent | `~` = ton home | `-` = répertoire précédent (avec `cd`)

### Commandes de navigation
| Commande | Rôle | Exemple |
|---|---|---|
| `pwd` | affiche le répertoire courant | `pwd` |
| `ls` | liste le contenu | `ls -lah` |
| `cd` | change de répertoire | `cd /var/log` |
| `tree` | affiche l'arborescence (à installer) | `tree -L 2` |

**Options `ls` à connaître par cœur :** `-l` (format détaillé), `-a` (fichiers cachés, commençant par `.`), `-h` (tailles lisibles : Ko/Mo/Go), `-t` (trié par date), `-R` (récursif).

### Retrouver un fichier : `find`
`find` parcourt réellement l'arborescence à chaque appel — toujours à jour, mais plus lent sur un gros disque. C'est l'outil de recherche le plus utilisé en administration.

```bash
find . -name "*.log"                 # par nom, depuis le répertoire courant (sensible à la casse)
find . -iname "*.LOG"                # -iname = insensible à la casse
find /etc -type f -name "*.conf"     # -type f = fichiers, -type d = répertoires, -type l = liens
find /var/log -size +100M            # plus gros que 100 Mo (-100M = plus petit que)
find /var/log -mtime -7              # modifiés il y a moins de 7 jours (+7 = il y a plus de 7 jours)
find . -maxdepth 1 -type d           # ne descend pas dans les sous-répertoires
find /home -user juvanio             # appartenant à un utilisateur donné
```

`-exec` permet d'agir sur chaque résultat — `{}` est remplacé par le fichier trouvé, `\;` termine la commande :
```bash
find /tmp -name "*.tmp" -exec rm {} \;      # supprime chaque fichier trouvé
find . -name "*.sh" -exec chmod +x {} +      # "+" groupe les résultats : bien plus rapide que "\;"
```

> ⚠️ Avant tout `find ... -exec rm`, lance **la même commande sans `-exec`** pour voir exactement quels fichiers seront touchés. C'est la seule protection qui existe.

### Retrouver un fichier vite : `locate`
```bash
sudo apt install plocate    # non installé par défaut sur la plupart des distributions
locate nginx.conf           # réponse quasi instantanée
sudo updatedb               # rafraîchit l'index (sinon un fichier créé à l'instant reste introuvable)
```
`locate` interroge un **index** mis à jour périodiquement : très rapide, mais potentiellement en retard sur la réalité. `find` est lent mais toujours exact — on utilise `locate` pour explorer, `find` pour être sûr.

### Retrouver une commande
```bash
which nginx       # chemin du binaire qui sera exécuté (cherche dans $PATH)
type -a ls        # toutes les définitions connues : alias, builtin, binaire
whereis nginx     # binaire + sources + pages de manuel associées
```

## Module 3 — Gestion des fichiers et répertoires

### Créer et copier
| Commande | Rôle | Exemple |
|---|---|---|
| `mkdir` | créer un répertoire | `mkdir projet` |
| `mkdir -p` | créer une arborescence complète d'un coup | `mkdir -p a/b/c` |
| `touch` | créer un fichier vide / mettre à jour sa date | `touch notes.txt` |
| `cp` | copier | `cp source.txt dest.txt` |
| `cp -r` | copier un répertoire (récursif) | `cp -r dossier/ backup/` |

### Déplacer, renommer, supprimer
| Commande | Rôle | Exemple |
|---|---|---|
| `mv` | déplacer **ou** renommer (c'est la même commande !) | `mv old.txt new.txt` |
| `rm` | supprimer un fichier | `rm fichier.txt` |
| `rm -r` | supprimer un répertoire et son contenu | `rm -r dossier/` |
| `rm -rf` | comme au-dessus, sans confirmation — **dangereux** | `rm -rf /tmp/build` |
| `rmdir` | supprimer un répertoire **vide uniquement** | `rmdir dossier_vide` |

> ⚠️ **Il n'y a pas de corbeille sous Linux en ligne de commande.** `rm -rf` est irréversible. Ne l'exécute jamais sans être sûr à 100% du chemin, et **jamais** avec une variable non vérifiée dans un script (`rm -rf $VAR/*` avec `$VAR` vide = catastrophe sur `/*`).

**Trois habitudes qui évitent le drame :**
1. `ls` d'abord, `rm` ensuite — avec **exactement** le même chemin. Si `ls` n'affiche pas ce que tu attends, `rm` ne supprimera pas ce que tu crois.
2. `cp -i`, `mv -i`, `rm -i` demandent confirmation avant d'écraser ou de supprimer. Sur une machine de production, c'est un réflexe rentable.
3. Compose le chemin avec `Tab` plutôt qu'à la main : si la complétion ne sort rien, le chemin n'existe pas.

### Inspecter un fichier avant d'y toucher
```bash
file archive.bin      # devine le vrai type de contenu (l'extension peut mentir)
stat notes.txt        # taille, permissions, inode, dates d'accès/modification/changement
wc -l notes.txt       # nombre de lignes, pour jauger un fichier avant un "cat"
```

### Liens
Pour comprendre les liens, il faut savoir qu'un fichier, c'est un **inode** (les données et les métadonnées : taille, droits, dates) et un ou plusieurs **noms** qui y mènent. Le nom n'est qu'une entrée dans un répertoire.

| | Lien symbolique `ln -s cible lien` | Lien physique `ln cible lien` |
| --- | --- | --- |
| Ce que c'est | un petit fichier qui contient un **chemin** | un **second nom** pour le même inode |
| `ls -li` | inode différent, `lien -> cible` | **même numéro d'inode**, compteur de liens à 2 |
| Si on supprime la cible | le lien est **cassé** (pointe dans le vide) | les données restent, accessibles par l'autre nom |
| Vers un répertoire ? | oui | non |
| Entre deux systèmes de fichiers ? | oui | non (un inode appartient à un seul système de fichiers) |

```bash
echo "v1" > original.txt
ln original.txt dur.txt           # lien physique
ln -s original.txt symbolique.txt # lien symbolique
ls -li original.txt dur.txt symbolique.txt   # comparer les numéros d'inode
rm original.txt
cat dur.txt          # v1 : les données existent toujours
cat symbolique.txt   # erreur : le lien pointe vers un nom qui n'existe plus
```

> 💡 Les liens symboliques sont partout en administration : `/etc/nginx/sites-enabled/site -> ../sites-available/site`, `/opt/app/current -> releases/1.4.2` (Palier 2 du projet). Changer la cible d'un lien avec `ln -sfn` est la façon **atomique** de basculer d'une version à l'autre.

### Wildcards (globbing)
| Motif | Signifie |
|---|---|
| `*` | n'importe quelle suite de caractères |
| `?` | un seul caractère |
| `[abc]` | un caractère parmi a, b, c |
| `[0-9]` | un chiffre |

Exemple : `rm *.log` supprime tous les fichiers finissant par `.log` dans le répertoire courant.

### Exercice 3.2

</details>

### Exercice 3.3
Crée un lien symbolique nommé `logs` pointant vers `/var/log`, puis vérifie qu'il fonctionne.

<details><summary>💡 Solution</summary>

```bash

```
</details>

### Exercice 3.4
Explique pourquoi supprimer un fichier de log de 10 Go avec `rm` peut ne libérer **aucun** espace disque, alors que le fichier a bien disparu de `ls`.

<details><summary>💡 Solution</summary>

`rm` supprime un **nom**. L'inode et ses données ne sont libérés que lorsque plus aucun nom ne les référence **et** plus aucun processus ne garde le fichier ouvert. Un service qui écrit encore dans ce log garde un descripteur ouvert : l'espace reste occupé jusqu'à son redémarrage. On le vérifie avec `sudo lsof +L1` (Module 9). La bonne façon de vider un log en cours d'écriture : `truncate -s 0 fichier.log` (ou `: > fichier.log`), qui vide l'inode sans le supprimer.
</details>

## Module 4 — Lire et éditer des fichiers

### Lire sans éditer
| Commande | Rôle |
|---|---|
| `cat fichier` | affiche tout le contenu d'un coup |
| `less fichier` | affiche page par page, navigable (`q` pour quitter, `/mot` pour chercher) |
| `head -n 20 fichier` | affiche les 20 premières lignes |
| `tail -n 20 fichier` | affiche les 20 dernières lignes |
| `tail -f fichier` | suit un fichier en temps réel (indispensable pour les logs) |

### Éditer en ligne de commande
**nano** — simple, débutant-friendly, raccourcis affichés en bas de l'écran (`^O` = sauver, `^X` = quitter).

**vim** — plus puissant, courbe d'apprentissage plus raide, mais présent par défaut sur presque tous les serveurs. Le strict nécessaire pour survivre :

| Touche(s) | Action |
|---|---|
| `i` | passer en mode **insertion** (pour taper du texte) |
| `Échap` | revenir en mode **normal** |
| `:w` | sauver |
| `:q` | quitter |
| `:wq` ou `ZZ` | sauver et quitter |
| `:q!` | quitter **sans** sauver |
| `dd` | supprimer la ligne courante |
| `/mot` puis `Entrée` | chercher "mot" |

> 💡 Anecdote classique : la première chose que tout le monde cherche un jour, c'est "comment quitter vim". Réponse : `Échap` puis `:q!`.

### Comparer et observer
```bash
diff ancien.conf nouveau.conf        # lignes qui diffèrent (< ancien, > nouveau)
diff -u ancien.conf nouveau.conf     # format « unifié », celui des correctifs et de git
diff -rq dossier1/ dossier2/         # quels fichiers diffèrent entre deux arborescences
less +F /var/log/syslog              # comme tail -f, mais Ctrl+C permet ensuite de remonter et chercher
watch -n 2 'df -h /'                 # relance la commande toutes les 2 s (Ctrl+C pour sortir)
```

> 💡 Avant de modifier un fichier de configuration : `sudo cp -a fichier fichier.bak`. Après : `diff -u fichier.bak fichier`. Tu sais exactement ce que tu as changé, et tu peux revenir en arrière en une commande.

### Écrire un fichier d'un coup : le heredoc
Pour créer un fichier de plusieurs lignes sans éditeur (dans un script, une documentation, une session SSH), on utilise un **heredoc** : tout ce qui est entre `<< 'EOF'` et la ligne `EOF` est envoyé sur l'entrée standard de la commande.

```bash
cat > notes.txt << 'EOF'
Serveur : web1
Rôle : application Marché
Variable non remplacée : $HOME
EOF
```

| Écriture | Effet |
| --- | --- |
| `<< 'EOF'` (guillemets) | le texte est pris **tel quel** : `$HOME` reste `$HOME` — le choix par défaut |
| `<< EOF` (sans guillemets) | les variables et `$(…)` sont **remplacées** avant l'écriture |
| `<<- EOF` | retire les tabulations en début de ligne (pour indenter dans un script) |

Pour écrire un fichier appartenant à root, on combine avec `sudo tee` (la redirection `>` ne passe pas sous `sudo`, voir Module 6) :
```bash
sudo tee /etc/motd > /dev/null << 'EOF'
Serveur de production — toute intervention est journalisée.
EOF
```

🪤 La ligne de fin doit être **exactement** `EOF`, seule, sans espace avant ni après : sinon le heredoc ne se termine jamais et le shell attend (`>` en début de ligne). `Ctrl+C` pour s'en sortir.

# Partie 2 — Administration système de base

## Module 5 — Permissions et propriété

### Le concept
Chaque fichier a **un propriétaire**, **un groupe**, et **des permissions** pour trois catégories : le propriétaire (u = user), le groupe (g = group), et tout le monde (o = others).

### Lire `ls -l`
```
-rwxr-xr--  1 juvanio  devs  4096  15 sept 10:00  script.sh
│└┬┘└┬┘└┬┘  │    │      │      │        │            │
│ u  g  o   │    │      │      │        │            └─ nom
│           │    │      │      │        └────────────── date de dernière modification
│           │    │      │      └─────────────────────── taille en octets
│           │    │      └────────────────────────────── groupe propriétaire
│           │    └───────────────────────────────────── utilisateur propriétaire
│           └────────────────────────────────────────── nombre de liens physiques
└─ type de fichier (- = fichier normal, d = répertoire, l = lien symbolique)
```
- `r` (read = 4) : lire un fichier / lister un répertoire
- `w` (write = 2) : modifier un fichier / créer-supprimer dans un répertoire
- `x` (execute = 1) : exécuter un fichier / **traverser** un répertoire (`cd`, ou accéder à ce qu'il contient)

> 🪤 **Le piège qui fait perdre le plus de temps :** pour lire `/a/b/c/fichier`, il ne suffit pas d'avoir `r` sur `fichier` — il faut aussi `x` sur `/a`, `/a/b` **et** `/a/b/c`. Un "Permission denied" alors que `ls -l` montre des permissions correctes sur le fichier vient presque toujours d'un répertoire parent sans `x`. Vérifie toute la chaîne d'un coup avec `namei -l /a/b/c/fichier`.

> 🪤 Corollaire inverse : sur un répertoire, `w` autorise à **supprimer n'importe quel fichier qu'il contient**, même un fichier qui ne t'appartient pas et sur lequel tu n'as aucun droit. C'est précisément la raison d'être du sticky bit sur `/tmp` (détaillé à l'étape 2).

### Modifier les permissions
**Notation symbolique :**
```bash
chmod u+x script.sh      # ajoute l'exécution au propriétaire
chmod go-w fichier.txt   # retire l'écriture au groupe et aux autres
chmod a+r fichier.txt    # lecture pour tout le monde (a = all)
```

**Notation numérique (octale)** — chaque chiffre = somme de r(4)+w(2)+x(1) pour u/g/o :
```bash
chmod 755 script.sh   # rwxr-xr-x : propriétaire tout, les autres lecture+exécution
chmod 644 fichier.txt # rw-r--r-- : propriétaire lit/écrit, les autres lisent seulement
chmod 600 secret.key  # rw------- : seul le propriétaire peut lire/écrire
```

### Propriété
```bash
chown juvanio fichier.txt          # change le propriétaire
chown juvanio:devs fichier.txt     # change propriétaire ET groupe
chgrp devs fichier.txt             # change seulement le groupe
chown -R juvanio:devs dossier/     # récursif sur tout un répertoire
```

### `umask`
Détermine les permissions par défaut des nouveaux fichiers/répertoires. C'est un **masque de retrait**, pas une permission : le système part de `666` pour un fichier et `777` pour un répertoire, puis soustrait la `umask`.

| `umask` | Nouveau fichier | Nouveau répertoire |
|---|---|---|
| `022` (défaut courant) | `644` (`rw-r--r--`) | `755` (`rwxr-xr-x`) |
| `027` | `640` (`rw-r-----`) | `750` (`rwxr-x---`) |
| `077` (le plus strict) | `600` (`rw-------`) | `700` (`rwx------`) |

```bash
umask           # affiche la valeur courante
umask 027       # la change pour la session ; à mettre dans ~/.bashrc pour la rendre permanente
```
Un fichier n'est **jamais** créé exécutable, quelle que soit la `umask` — c'est volontaire : `chmod +x` reste un geste explicite.

</details>

## Module 6 — Utilisateurs et groupes

### Le concept
Linux est multi-utilisateur par nature. Trois fichiers clés :
- `/etc/passwd` — liste des utilisateurs (nom, UID, home, shell...)
- `/etc/shadow` — mots de passe chiffrés (lisible root uniquement)
- `/etc/group` — liste des groupes

### Commandes essentielles
| Commande | Rôle |
|---|---|
| `id` | affiche ton UID, GID, et groupes |
| `whoami` | ton nom d'utilisateur |
| `sudo useradd -m nom` | crée un utilisateur avec un home (`-m`) |
| `sudo passwd nom` | définit/change son mot de passe |
| `sudo usermod -aG groupe nom` | ajoute l'utilisateur à un groupe (`-a` = append, ne pas oublier sinon ça écrase les groupes existants) |
| `sudo userdel -r nom` | supprime l'utilisateur et son home |
| `sudo groupadd nom` | crée un groupe |
| `groups nom` | liste les groupes d'un utilisateur |

> 🪤 **`useradd` n'est pas `adduser`.** `useradd` est l'outil bas niveau : sur Debian/Ubuntu il ne crée pas de home sans `-m`, et attribue par défaut un shell inutilisable (`/bin/sh` ou aucun). Pense à `-s` :
> ```bash
> sudo useradd -m -s /bin/bash stagiaire    # home + shell utilisable
> ```
> `sudo adduser stagiaire` (Debian/Ubuntu uniquement) est un assistant interactif qui fait tout ça correctement et demande le mot de passe — c'est le plus sûr en usage manuel. `useradd` reste le bon choix dans un script, parce qu'il n'est pas interactif.

> 🪤 **Un ajout de groupe ne s'applique pas à une session déjà ouverte.** Après `usermod -aG docker juvanio`, la commande `groups` montre le nouveau groupe mais les processus en cours ne l'ont pas. Il faut se déconnecter/reconnecter (ou `newgrp docker` pour le shell courant). C'est la cause numéro un des "permission denied" juste après un ajout de groupe.

### `sudo` — le principe
`sudo` permet d'exécuter **une commande** avec les droits root, sans se connecter en root en permanence (bonne pratique de sécurité). La configuration se fait dans `/etc/sudoers`, à éditer **toujours** avec `sudo visudo` (jamais un éditeur classique — `visudo` valide la syntaxe avant d'enregistrer, et une erreur de syntaxe non détectée peut te priver définitivement de tout accès root).

Quelques usages qui reviennent sans arrêt :
```bash
sudo -i                     # ouvre un shell root complet (à réserver aux sessions de maintenance)
sudo -u deploy commande     # exécute la commande en tant qu'un AUTRE utilisateur que root
sudo !!                     # rejoue la dernière commande en ajoutant sudo (le classique de la journée)
sudo -l                     # liste ce que tu es autorisé à exécuter via sudo
```

> 🪤 `sudo echo "texte" > /etc/fichier` **échoue** avec "Permission denied" : `sudo` élève `echo`, mais la redirection `>` est effectuée par ton shell, qui n'est pas root. Les deux solutions correctes :
> ```bash
> echo "texte" | sudo tee /etc/fichier          # tee écrit, et lui est bien sous sudo
> sudo sh -c 'echo "texte" > /etc/fichier'      # le shell entier passe sous sudo
> ```

**Donner un droit précis plutôt que tout `sudo` : `/etc/sudoers.d/`.** On ne modifie pas `/etc/sudoers` lui-même : on dépose un fichier par besoin dans `/etc/sudoers.d/`, toujours via `visudo` :
```bash
sudo visudo -f /etc/sudoers.d/deploy
# contenu : l'utilisateur deploy peut redémarrer UN service, sans mot de passe, et rien d'autre
deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart marche-gateway
```
```bash
sudo visudo -c                  # vérifie la syntaxe de TOUS les fichiers sudoers
sudo -l -U deploy               # ce que deploy a le droit de faire
```
🪤 Une erreur de syntaxe dans un fichier de `/etc/sudoers.d/` : avec le sudo d'Ubuntu 22.04/24.04 (1.9.x), sudo affiche l'erreur à **chaque** appel et **ignore la ligne fautive** — si c'était ta règle, tu as perdu `sudo` (vérifié). Sur les systèmes plus anciens (sudo 1.8 : Ubuntu 20.04, RHEL 8), c'est pire : `sudo` refuse de fonctionner **pour tout le monde**. `visudo -f` refuse d'enregistrer un fichier invalide ; un éditeur ordinaire, non. Si c'est déjà fait : `pkexec visudo -f …`, ou la console.

**Clé SSH et mot de passe n'ont pas le même rôle.** Quand l'authentification SSH par mot de passe est désactivée (Module 20), la clé sert à *se connecter* ; le mot de passe du compte sert encore à **`sudo`**. Un administrateur créé sans mot de passe se connecte parfaitement… et ne peut rien faire avec `sudo`.

**État des comptes :**
```bash
sudo passwd -S awa              # P = mot de passe défini ; L = verrouillé OU jamais défini (cas d'un useradd seul)
sudo usermod -L awa             # verrouiller (départ, suspicion) ; -U pour déverrouiller
sudo chage -l awa               # expiration du compte et du mot de passe
who ; w                         # qui est connecté maintenant, et ce qu'il fait
last -n 10                      # les dernières connexions (lastb : les tentatives échouées, en root)
```

## Module 7 — Processus et gestion système

### Le concept
Chaque programme en cours d'exécution est un **processus**, identifié par un **PID** (Process ID).

### Observer les processus
| Commande | Rôle |
|---|---|
| `ps aux` | liste tous les processus du système |
| `top` | vue temps réel, triable, consomme peu de ressources |
| `htop` | équivalent en plus lisible/interactif (à installer) |
| `pgrep nom` | trouve le PID d'un processus par son nom |

### Premier/arrière-plan
```bash
longue_commande &     # lance en arrière-plan
jobs                  # liste les tâches en arrière-plan du shell courant
fg %1                 # ramène la tâche 1 au premier plan
bg %1                 # relance la tâche 1 en arrière-plan (après un Ctrl+Z)
nohup commande &       # continue même après fermeture du terminal
```
`Ctrl+Z` met en pause la tâche au premier plan.

> 🪤 `commande &` seule **ne survit pas** à la fermeture du terminal : le shell qui part envoie `SIGHUP` à ses enfants. Pour une tâche longue lancée par SSH, il faut `nohup commande &`, ou `disown %1` après coup — et idéalement `tmux` (vu à l'étape 2), qui est la vraie réponse à ce besoin.

### Terminer un processus
```bash
kill PID          # envoie SIGTERM (demande poliment de s'arrêter) — signal par défaut
kill -9 PID       # envoie SIGKILL (force l'arrêt, brutal, dernier recours)
killall nginx     # tue tous les processus dont le nom est exactement "nginx"
pkill -f "python3 app.py"   # tue par motif sur la ligne de commande complète (-f)
pgrep -af python3            # À FAIRE D'ABORD : montre ce que pkill toucherait
```

> ⚠️ **Toujours `pgrep` avant `pkill`.** Un motif trop large (`pkill -f python`) peut emporter des processus que tu ne visais pas. `pgrep -af <motif>` affiche exactement la liste sans rien tuer.

**Pourquoi ne pas commencer par `-9` :** `SIGTERM` (défaut) demande au programme de s'arrêter, ce qui lui laisse le temps de vider ses tampons d'écriture, fermer ses connexions et retirer ses fichiers temporaires. `SIGKILL` (`-9`) est traité par le noyau, le programme n'en est même pas informé — d'où les fichiers corrompus et les verrous orphelins. Ordre correct : `kill` → attendre quelques secondes → `kill -9` seulement si le processus est réellement bloqué.

### Priorité
```bash
nice -n 10 commande     # lance avec une priorité plus basse (0 = normal, 19 = min, -20 = max, root requis pour négatif)
renice 5 -p PID          # change la priorité d'un processus déjà lancé
```

### Les deux chiffres à savoir lire : charge et mémoire
**La charge (load average)** — les trois nombres de `uptime` et du haut de `top` :
```
load average: 0.52, 0.71, 1.05      ← moyennes sur 1, 5 et 15 minutes
```
C'est le nombre moyen de processus **qui veulent travailler** (en cours d'exécution ou en attente). Il se lit **par rapport au nombre de cœurs** (`nproc`) : 2,0 sur 4 cœurs = machine à moitié occupée ; 8,0 sur 4 cœurs = des processus font la queue. La tendance compte : `1 min > 15 min`, ça monte ; l'inverse, ça redescend. (L'étape 2 montre que le disque aussi fait monter la charge.)

**La mémoire** — `free -h` :
```
               total        used        free      shared  buff/cache   available
Mem:           3,8Gi       1,1Gi       312Mi        12Mi       2,4Gi       2,5Gi
```
🪤 La colonne à regarder est **`available`**, pas `free`. Linux utilise la mémoire inutilisée comme cache disque (`buff/cache`) et la rend instantanément quand une application en a besoin. Un `free` proche de zéro sur un serveur qui tourne depuis des jours est **normal et souhaitable** ; un `available` proche de zéro, lui, annonce des problèmes.

**Dans `top`** : `P` trie par CPU, `M` par mémoire, `1` détaille chaque cœur, `k` envoie un signal, `q` quitte. La ligne `%Cpu(s)` décompose le temps : `us` (applications), `sy` (noyau), `wa` (attente disque), `id` (inactif).

### Exercice 7.3
Ta machine a 2 cœurs, `uptime` affiche `load average: 3.90, 2.10, 0.80` et `free -h` indique `free 150Mi, available 1,9Gi` sur 4 Gi. Que se passe-t-il, et faut-il s'inquiéter de la mémoire ?

## Module 8 — Gestion des paquets

### Debian/Ubuntu — `apt`
| Commande | Rôle |
|---|---|
| `sudo apt update` | rafraîchit la liste des paquets disponibles (à faire avant tout install) |
| `sudo apt upgrade` | met à jour les paquets installés |
| `sudo apt install nom` | installe un paquet |
| `sudo apt remove nom` | désinstalle (garde les fichiers de config) |

|---|---|

`apt` et `dnf` sont des sur-couches conviviales autour de `dpkg` (Debian) et `rpm` (Red Hat), qui gèrent les paquets bas niveau (fichiers `.deb`/`.rpm`) mais **sans résoudre les dépendances automatiquement** — d'où l'intérêt d'`apt`/`dnf`.

Installe `tree`, vérifie qu'il fonctionne, puis désinstalle-le complètement (y compris sa config).

<details><summary>💡 Solution</summary>

```bash
sudo apt update

```

Une commande est absente de ta machine (`ss`, par exemple). Trouve quel paquet il faut installer pour l'obtenir, **sans** procéder par essais successifs.

<details><summary>💡 Solution</summary>

## Module 9 — Disques et systèmes de fichiers

### Observer l'espace disque
| Commande | Rôle |
|---|---|
| `df -h` | espace disque par partition (format lisible) |
| `du -sh dossier` | taille totale d'un dossier |
| `du -sh */` | taille de chaque sous-dossier du répertoire courant |
| `lsblk` | liste les disques et partitions détectés |

### Quand « disque plein » ne vient pas de l'espace disque
Deux causes classiques d'un `No space left on device` alors que `df -h` affiche de la place :

**1. Les inodes sont épuisés.** Un système de fichiers a un nombre fini d'inodes (un par fichier). Des millions de petits fichiers peuvent l'épuiser alors que les octets sont loin d'être consommés :
```bash
df -i           # colonne IUse% : si elle est à 100%, c'est ça
```

**2. Un fichier supprimé est toujours ouvert par un processus.** L'espace n'est libéré que quand le dernier descripteur se ferme. Un log de 40 Go supprimé pendant que le service y écrit encore ne rend **rien** :
```bash
sudo lsof +L1         # liste les fichiers supprimés mais encore ouverts
```
La solution n'est pas de supprimer davantage, mais de redémarrer (ou recharger) le service qui détient le fichier.

> 💡 Autre écart courant : `du` et `df` ne s'accordent pas. `du` additionne ce qu'il **voit** dans l'arborescence, `df` interroge le système de fichiers. Un fichier caché sous un point de montage, ou supprimé-mais-ouvert, n'est compté que par `df`.

### Montage
```bash
sudo mount /dev/sdb1 /mnt/usb    # monte une partition sur un point de montage
sudo umount /mnt/usb             # démonte (« target is busy » : un processus y travaille → lsof +D /mnt/usb)
findmnt                          # arborescence de tout ce qui est monté, avec les options
findmnt -T /var/lib/postgresql   # sur quel système de fichiers vit ce répertoire ? (-T : n'importe quel chemin)
```

### Monter au démarrage : `/etc/fstab`
Chaque ligne décrit un montage automatique : **quoi**, **où**, **type**, **options**, `dump`, **ordre de vérification**.
```bash
sudo blkid /dev/sdb1             # UUID="3f1c…" TYPE="ext4"
```
```
# /etc/fstab
UUID=3f1c6a8e-…  /srv/donnees  ext4  defaults,nofail  0  2
```
- **Toujours l'UUID, jamais `/dev/sdb1`** : les noms `sdX` peuvent changer d'un démarrage à l'autre (ordre de détection des disques), l'UUID est inscrit dans le système de fichiers lui-même.
- `nofail` : si ce disque manque, le démarrage continue au lieu de s'arrêter en mode secours. Indispensable pour tout disque qui n'est pas vital au système.

⚠️ **Une erreur dans `/etc/fstab` peut empêcher la machine de redémarrer** (mode secours, console requise). Teste **toujours** avant de redémarrer :
```bash
sudo findmnt --verify            # vérifie la syntaxe et que chaque source existe
sudo systemctl daemon-reload     # systemd génère des unités de montage à partir de fstab
sudo mount -a                    # monte tout ce qui est déclaré et pas encore monté : une erreur ici = une erreur au boot
```

### Types de systèmes de fichiers (repère rapide)
- **ext4** : standard Linux, fiable, le plus courant
- **xfs** : performant sur gros volumes, utilisé par défaut sur RHEL
- **btrfs** : snapshots natifs, encore en progression sur certaines distros
- **vfat/exfat** : compatibilité Windows/clés USB

Et pour le cas classique où l'espace n'est pas le vrai problème :

</details>

## Module 10 — Variables d'environnement et configuration du shell

### Le concept
Les **variables d'environnement** sont des paires clé=valeur **héritées** par tous les processus lancés depuis le shell.

```bash
echo "$HOME"             # affiche une variable (les guillemets évitent les surprises si elle contient des espaces)
MA_VAR="valeur"          # variable de SHELL : visible dans ce shell uniquement
export MA_VAR="valeur"   # variable d'ENVIRONNEMENT : héritée par les processus enfants
printenv                 # liste les variables d'environnement (équivalent de env)
unset MA_VAR             # supprime une variable
```

**La distinction compte en pratique :** sans `export`, un script que tu lances ne verra pas la variable. C'est la cause fréquente d'un « pourtant je l'ai définie » :
```bash
MA_VAR="test"
bash -c 'echo "vu par lenfant : $MA_VAR"'    # vide
export MA_VAR
bash -c 'echo "vu par lenfant : $MA_VAR"'    # test
```

L'héritage ne va que du parent vers l'enfant, **jamais** l'inverse. Un script ne peut donc pas modifier l'environnement du shell qui l'appelle — c'est exactement la raison d'être de `source` (ou `.`), qui exécute le fichier **dans** le shell courant au lieu d'en démarrer un nouveau :
```bash
./config.sh      # s'exécute dans un sous-shell : ses exports disparaissent avec lui
source config.sh # s'exécute dans le shell courant : ses exports restent
```

### `PATH` — la variable la plus importante
`PATH` liste les répertoires où le shell cherche les exécutables, dans l'ordre.
```bash
echo $PATH
# /usr/local/bin:/usr/bin:/bin:/usr/local/games
export PATH="$HOME/scripts:$PATH"   # ajoute un dossier perso en priorité
```
C'est pour ça que `./script.sh` fonctionne mais pas `script.sh` tout seul si le répertoire courant n'est pas dans `PATH` (et il ne devrait jamais l'être, pour des raisons de sécurité).

### Fichiers de configuration du shell
| Fichier | Chargé quand |
|---|---|
| `~/.bashrc` | à chaque nouveau terminal interactif (le plus utilisé au quotidien) |
| `~/.bash_profile` / `~/.profile` | à la connexion (login shell) |
| `/etc/environment` | variables globales pour tous les utilisateurs |
| `/etc/skel/` | modèles copiés dans le home de chaque nouvel utilisateur créé |

> 🪤 Une variable définie dans `~/.bashrc` n'est **pas** disponible dans une commande SSH non interactive (`ssh serveur 'echo $MA_VAR'`) ni dans une tâche cron : `~/.bashrc` sort immédiatement en mode non interactif. Pour ces contextes, place la variable dans `/etc/environment`, ou définis-la explicitement dans le script. C'est la même racine de problème que le `PATH` minimal de cron (Module 15).

### Alias
```bash
alias ll='ls -lah'
# à mettre dans ~/.bashrc pour qu'il persiste entre les sessions
```

## Module 11 — Redirections et pipes

### Le concept : les 3 flux standards
Chaque commande a trois flux :
- **stdin** (0) : entrée standard (clavier par défaut)
- **stdout** (1) : sortie standard (écran par défaut)
- **stderr** (2) : sortie d'erreur (écran par défaut aussi, mais séparée de stdout)

### Redirections
| Syntaxe | Effet |
|---|---|
| `commande > fichier` | redirige stdout vers un fichier (écrase) |
| `commande >> fichier` | redirige stdout en ajoutant à la fin (append) |
| `commande < fichier` | utilise un fichier comme entrée |
| `commande 2> fichier` | redirige seulement les erreurs |
| `commande > fichier 2>&1` | redirige stdout **et** stderr vers le même fichier |
| `commande &> fichier` | raccourci équivalent au-dessus |
| `commande 2>/dev/null` | jette les erreurs (les ignore silencieusement) |

### Le pipe `|`
Chaîne la sortie d'une commande vers l'entrée de la suivante — le cœur de la philosophie Unix.
```bash
ps aux | grep nginx | wc -l
# liste les processus → filtre "nginx" → compte les lignes
```

### `tee` — dupliquer un flux
```bash
commande | tee fichier.log        # affiche à l'écran ET écrit dans le fichier
commande | tee -a fichier.log     # -a = ajoute au lieu d'écraser
commande | sudo tee /etc/conf     # LA solution pour écrire en root dans un fichier protégé (cf. Module 6)
```

> 🪤 **L'ordre compte dans `> fichier 2>&1`.** `2>&1` signifie « envoie stderr là où va stdout *en ce moment* ». Donc :
> ```bash
> commande > fichier 2>&1     # correct : stdout vers le fichier, PUIS stderr suit vers le fichier
> commande 2>&1 > fichier     # piège : stderr part vers l'écran (où allait stdout), stdout seul va au fichier
> ```

### `xargs` — transformer une sortie en arguments
Un pipe alimente l'**entrée** de la commande suivante. Mais beaucoup de commandes (`rm`, `chmod`, `cp`...) attendent des **arguments**, pas une entrée. `xargs` fait la conversion :

```bash
find . -name "*.log" | xargs rm              # supprime tous les fichiers trouvés
find . -name "*.log" -print0 | xargs -0 rm   # version robuste : gère les noms avec espaces
cat serveurs.txt | xargs -I{} ssh {} uptime  # -I{} = place chaque ligne à l'endroit voulu
find . -name "*.txt" | xargs -P 4 gzip       # -P 4 = 4 traitements en parallèle
```

> 💡 `xargs -0` avec `find -print0` est la combinaison à mémoriser : un fichier nommé `mon rapport.log` casse un `xargs` classique (deux arguments au lieu d'un), alors que la version `-print0`/`-0` sépare les noms par un caractère nul et fonctionne toujours.

## Module 12 — Traitement de texte

### `grep` — chercher dans du texte
| Option | Effet |
|---|---|
| `-i` | insensible à la casse |
| `-r` | récursif (dans tout un dossier) |
| `-v` | inverse (lignes qui NE contiennent PAS le motif) |
| `-n` | affiche le numéro de ligne |
| `-c` | compte les correspondances |
| `-E` | regex étendue |

Options complémentaires qu'on utilise en réalité tous les jours :

| Option | Effet |
|---|---|
| `-A 3` / `-B 3` / `-C 3` | affiche 3 lignes après / avant / autour de chaque correspondance |
| `-w` | mot entier (`grep -w ssh` ne trouve pas "sshd") |
| `-l` | affiche seulement les **noms de fichiers** correspondants |
| `-o` | affiche seulement la partie qui correspond, pas toute la ligne |
| `--exclude-dir=.git` | ignore un répertoire lors d'une recherche récursive |

```bash
grep -in "erreur" app.log
grep -r "TODO" ./src
grep -v "^#" config.conf              # ignore les lignes de commentaire
grep -C 5 "Exception" app.log         # le contexte autour d'une erreur : LE réflexe de débogage
grep -rl "mot_de_passe" /etc 2>/dev/null   # quels fichiers en parlent (sans afficher le contenu)
```

> 💡 `grep -C` est probablement l'option la plus rentable du lot : une stack trace ou un message d'erreur n'a presque jamais de sens sur sa seule ligne.

### `sed` — remplacer du texte
```bash
sed 's/ancien/nouveau/' fichier.txt        # remplace la 1ère occurrence par ligne, affiche le résultat
sed 's/ancien/nouveau/g' fichier.txt       # remplace TOUTES les occurrences (g = global)
sed -i 's/ancien/nouveau/g' fichier.txt    # modifie le fichier directement (-i = in-place)
sed -i.bak 's/ancien/nouveau/g' fichier    # idem, en gardant une copie fichier.bak
```

> ⚠️ **`sed -i` est destructif et silencieux.** Lance toujours la commande **sans** `-i` d'abord : la sortie à l'écran te montre exactement ce qui va changer. Sur un fichier de configuration système, utilise `-i.bak` plutôt que `-i` tout court.

> 💡 Le séparateur n'est pas obligatoirement `/`. Pour remplacer des chemins, `sed 's|/usr/local|/opt|g'` évite d'avoir à échapper chaque slash.

### `awk` — traiter des colonnes
```bash
awk '{print $1}' fichier.txt        # affiche la 1ère colonne (séparateur = espace par défaut)
awk -F: '{print $1}' /etc/passwd    # -F pour changer le séparateur (ici ":")
df -h | awk '{print $1, $5}'        # combine avec un pipe
```

### Autres outils indispensables
| Commande | Rôle |
|---|---|
| `cut -d: -f1 fichier` | extrait une colonne selon un délimiteur |
| `sort` | trie des lignes (`-n` numérique, `-r` inverse) |
| `uniq` | supprime les doublons **consécutifs** (donc souvent après `sort`) |
| `wc -l` | compte les lignes (`-w` mots, `-c` caractères) |
| `tr 'a-z' 'A-Z'` | transforme des caractères (ex : minuscule → majuscule) |

</details>

### Exercice 12.2
Dans un fichier de log, remplace toutes les occurrences de "ERROR" par "🔴 ERROR" directement dans le fichier.

## Module 13 — Scripting shell — les bases

### Structure minimale
```bash
#!/bin/bash
# Le shebang ci-dessus indique quel interpréteur utiliser

echo "Bonjour depuis un script !"
```
Rendre exécutable puis lancer :
```bash
chmod +x script.sh
./script.sh
```

### Variables et arguments
```bash
nom="Juvanio"
echo "Bonjour $nom"

# Arguments passés au script :
echo "Premier argument : $1"
echo "Tous les arguments : $@"
echo "Nombre d'arguments : $#"
echo "PID du script : $$"
echo "Code de sortie de la dernière commande : $?"
```

### Substitution de commandes — capturer une sortie dans une variable
```bash
date_du_jour=$(date +%F)              # 2026-09-18
nb_fichiers=$(ls -1 | wc -l)
echo "Sauvegarde du $date_du_jour : $nb_fichiers fichiers"

archive="backup-$(hostname)-$(date +%F).tar.gz"
```
La forme `$(...)` remplace l'ancienne syntaxe à accents graves `` `...` `` : elle s'imbrique correctement et se lit mieux. Utilise-la systématiquement.

### Les guillemets : la source d'erreur numéro un des scripts
```bash
fichier="mon rapport.txt"
rm $fichier      # ⚠️ le shell découpe sur l'espace : essaie de supprimer "mon" ET "rapport.txt"
rm "$fichier"    # ✅ un seul argument, celui attendu
```

Trois règles qui suffisent à éviter la quasi-totalité des bugs :
1. **Toujours entourer une variable de guillemets doubles** : `"$var"`, `"$1"`, `"$(commande)"`.
2. Les guillemets **doubles** substituent les variables, les **simples** ne substituent rien :
   ```bash
   echo "Le home est $HOME"      # Le home est /home/juvanio
   echo 'Le home est $HOME'      # Le home est $HOME
   ```
3. Pour parcourir une liste, `"$@"` (avec guillemets) préserve les arguments contenant des espaces, `$*` les écrase.

### Codes de sortie
Toute commande renvoie un code : **0 = succès**, toute autre valeur = échec. C'est ce que testent `if`, `&&` et `||`.
```bash
if grep -q "erreur" app.log; then echo "Des erreurs présentes"; fi   # -q = silencieux, on ne veut que le code

mkdir /tmp/travail && cd /tmp/travail     # le "cd" ne s'exécute QUE si le mkdir a réussi
commande_risquee || echo "Échec détecté"  # exécuté seulement en cas d'échec

exit 0     # dans un script : signale un succès
exit 1     # signale une erreur (toute valeur non nulle convient)
```

> 💡 Un script qui ne renvoie jamais de code d'erreur est inutilisable dans une chaîne automatisée (cron, CI, `&&`) : l'appelant croira que tout va bien. Soigner ses `exit` fait partie du travail.

### Conditions
```bash
if [ -f "fichier.txt" ]; then
    echo "Le fichier existe"
elif [ -d "fichier.txt" ]; then
    echo "C'est un dossier"
else
    echo "N'existe pas"
fi
```
Tests courants : `-f` (fichier existe), `-d` (dossier existe), `-e` (existe, quel que soit le type), `-r`/`-w`/`-x` (lisible/inscriptible/exécutable), `-z` (chaîne vide), `-n` (chaîne non vide), `-eq`/`-ne`/`-lt`/`-gt` (comparaisons numériques), `=`/`!=` (comparaison de chaînes), `!` (négation : `if [ ! -d "$dir" ]`).

> 💡 En bash, préfère la double paire de crochets `[[ ... ]]` à `[ ... ]` : elle ne se casse pas sur une variable vide ou contenant des espaces, et accepte `&&`, `||` et la comparaison de motifs.
> ```bash
> if [[ -f "$fichier" && "$nom" == juv* ]]; then echo "OK"; fi
> ```
> `[ ]` (alias de la commande `test`) reste nécessaire uniquement pour un script devant tourner sous un shell POSIX strict (`#!/bin/sh`).

### Boucles
```bash
# for
for i in 1 2 3; do
    echo "Itération $i"
done

# while
compteur=0
while [ $compteur -lt 5 ]; do
    echo "Compteur : $compteur"
    compteur=$((compteur + 1))
done
```

### Fonctions
```bash
saluer() {
    echo "Bonjour $1"
}
saluer "Juvanio"
```

### Lire une saisie et choisir selon une valeur : `read` et `case`
```bash
read -r -p "Nom du service : " service       # -r : ne pas interpréter les antislashs
case "$service" in
    gateway|orders|payments) echo "Service connu : $service" ;;
    "")                      echo "Rien saisi" >&2; exit 1 ;;
    *)                       echo "Service inconnu : $service" >&2; exit 1 ;;
esac
```
`read` sert aussi à lire un fichier ligne par ligne, **la** bonne façon de le faire (une boucle `for` découperait sur les espaces) :
```bash
while IFS= read -r ligne; do
    echo "→ $ligne"
done < /etc/hostname
```

### Le mode strict : arrêter le script à la première erreur
Par défaut, bash **continue** après une commande qui échoue : un script de sauvegarde dont le `cd` a échoué exécutera tranquillement la suite… dans le mauvais répertoire. Trois options changent ce comportement :
```bash
#!/bin/bash
set -euo pipefail
# -e : arrêt dès qu'une commande échoue
# -u : arrêt si une variable non définie est utilisée (faute de frappe → erreur, pas chaîne vide)
# -o pipefail : un pipe échoue si N'IMPORTE QUELLE commande échoue (pas seulement la dernière)
```
Sans `pipefail`, `pg_dump base | gzip > sauvegarde.gz` réussit **toujours** (c'est `gzip` qui a le dernier mot) : une base injoignable produit une sauvegarde vide et un script « vert ».

🪤 Le revers de `pipefail` : une commande coupée volontairement en cours de route est aussi un « échec ». `tr -dc 'a-z' < /dev/urandom | head -c 20` fait mourir `tr` d'un SIGPIPE quand `head` a fini, et le script s'arrête **sans aucun message**. Préfère une source finie : `head -c 15 /dev/urandom | base64`. L'étape 2 approfondit ces angles morts.

## Module 14 — Archivage et compression

### `tar` — l'archiveur standard
```bash
tar -cvf archive.tar dossier/        # créer (c), verbeux (v), fichier (f)
tar -xvf archive.tar                 # extraire
tar -czvf archive.tar.gz dossier/    # créer + compresser en gzip (z)
tar -xzvf archive.tar.gz             # extraire une archive gzip
tar -tvf archive.tar                 # lister le contenu sans extraire
```
Astuce mnémotechnique : **`tar -xzvf`** est la combinaison la plus tapée au monde — beaucoup la retiennent par la formule *"eXtract Ze Vile File"*.

> 💡 **Les versions récentes de `tar` détectent seules la compression** : `tar -xf archive.tar.gz` fonctionne sans le `z`, tout comme `.tar.bz2`, `.tar.xz` ou `.tar.zst`. Le `z` reste nécessaire à la **création**, pour indiquer quel format tu veux.

> ⚠️ **Le piège de la « tar bomb » :** rien n'oblige une archive à contenir un répertoire racine. Extraite dans ton home, elle peut y déverser des centaines de fichiers en vrac, voire écraser des fichiers existants. Le réflexe est d'inspecter avant d'extraire :
> ```bash
> tar -tf archive.tar.gz | head        # tout part-il d'un même dossier ?
> mkdir extraction && tar -xf archive.tar.gz -C extraction   # sinon, isole l'extraction
> ```

**Choisir son format de compression :**
| Format | Option | Profil |
|---|---|---|
| gzip | `-z` | rapide, universellement disponible — le défaut raisonnable |
| bzip2 | `-j` | compresse mieux, nettement plus lent |
| xz | `-J` | meilleur taux, très lent à compresser — bon pour une archive écrite une fois et lue souvent |
| zstd | `--zstd` | quasi aussi rapide que gzip, compresse presque comme xz — le choix moderne |

Dans un script, retire le `v` : `tar -czf` suffit, et tu évites des milliers de lignes de sortie dans tes logs.

### Compression seule (sans archivage)
```bash
gzip fichier.txt        # produit fichier.txt.gz, supprime l'original
gunzip fichier.txt.gz   # décompresse
zip archive.zip fichier1 fichier2
unzip archive.zip
```

<details><summary>💡 Solution</summary>

```bash

```
</details>

### Exercice 14.2
Extrais `projet.tar.gz` dans un nouveau dossier `restauration/`.

<details><summary>💡 Solution</summary>


(`-C` change le répertoire de destination avant d'extraire)

## Module 15 — Planification de tâches (cron)

### Le concept
`cron` exécute des commandes automatiquement à intervalles réguliers, définis dans une **crontab**.

### Éditer sa crontab
```bash
crontab -e     # éditer sa propre crontab
crontab -l     # lister ses tâches planifiées
crontab -r     # supprimer toute sa crontab (attention)
```

### Syntaxe cron
```
* * * * * commande
│ │ │ │ │
│ │ │ │ └─ jour de la semaine (0-6, 0=dimanche)
│ │ │ └─── mois (1-12)
│ │ └───── jour du mois (1-31)
│ └─────── heure (0-23)
└───────── minute (0-59)
```

Exemples :
```bash
0 3 * * *     /home/juvanio/scripts/backup.sh      # tous les jours à 3h
*/15 * * * *  /home/juvanio/scripts/healthcheck.sh # toutes les 15 minutes
0 0 * * 0     /home/juvanio/scripts/weekly.sh      # tous les dimanches à minuit
```

### 🪤 Les trois pièges de cron (la cause de 90 % des « ça marche à la main mais pas en cron »)

**1. L'environnement de cron est presque vide.** Pas de `~/.bashrc`, et un `PATH` réduit à `/usr/bin:/bin`. Un script qui appelle `docker`, `node` ou un binaire de `/usr/local/bin` échouera silencieusement.
```bash
# Solution 1 : chemins absolus partout dans le script
/usr/bin/docker compose -f /opt/app/compose.yml restart

# Solution 2 : déclarer le PATH en tête de crontab
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
0 3 * * * /opt/scripts/backup.sh
```

**2. La sortie disparaît.** Par défaut cron envoie stdout/stderr par mail local — que personne ne lit. Redirige explicitement, **sans** jeter les erreurs :
```bash
0 3 * * * /opt/scripts/backup.sh >> /var/log/backup.log 2>&1
```
`>/dev/null 2>&1` (courant dans les tutoriels) fait taire jusqu'aux messages d'erreur : le jour où la tâche casse, tu n'as plus aucune trace.

**3. Le `%` doit être échappé.** Dans une crontab, `%` a une signification spéciale. `date +%F` doit s'écrire `date +\%F`, sinon la ligne est tronquée.

**Pour déboguer une tâche cron qui ne part pas :**
```bash
grep CRON /var/log/syslog        # cron journalise chaque lancement
journalctl -u cron --since today  # équivalent systemd
```
Et le test qui reproduit fidèlement les conditions de cron :
```bash
env -i /bin/bash --noprofile --norc /opt/scripts/backup.sh
```

### Alternative moderne : les timers systemd
Sur les systèmes récents, `systemd` propose des **timers** comme alternative à cron, avec plus de fonctionnalités (dépendances entre services, rattrapage des exécutions manquées, logs centralisés via `journalctl`). Vu au Module 16, et approfondi à l'étape 2.

### Où vivent les tâches planifiées
| Emplacement | Usage |
|---|---|
| `crontab -e` | tâches de **ton** utilisateur |
| `sudo crontab -u deploy -e` | tâches d'un autre utilisateur |
| `/etc/crontab` et `/etc/cron.d/` | tâches système — une colonne **utilisateur** en plus avant la commande |
| `/etc/cron.{hourly,daily,weekly}/` | scripts exécutés à intervalle fixe, sans syntaxe cron à écrire |

> 🪤 Dans `/etc/cron.d/`, la ligne comporte un champ supplémentaire : `0 3 * * * root /opt/script.sh`. Oublier l'utilisateur est l'erreur classique, et la tâche ne part jamais.

# Partie 4 — Services, réseau et sécurité

## Module 16 — systemd et gestion des services

### Le concept
`systemd` est le système d'initialisation utilisé par la majorité des distributions modernes (Ubuntu, Debian, Fedora, RHEL...). Il démarre le système, gère les **services** (appelés "unités"), et centralise les logs.

### Commandes essentielles
```bash
sudo systemctl start nginx      # démarrer un service
sudo systemctl stop nginx       # arrêter
sudo systemctl restart nginx    # redémarrer
sudo systemctl reload nginx     # recharger la config sans coupure (si supporté)
sudo systemctl status nginx     # état actuel + derniers logs
sudo systemctl enable nginx     # démarrage automatique au boot
sudo systemctl disable nginx    # désactive le démarrage automatique
systemctl list-units --type=service   # liste tous les services
```

### Créer un service personnalisé (aperçu)
Un fichier `.service` minimal dans `/etc/systemd/system/mon-app.service` :
```ini
[Unit]
Description=Mon application
After=network.target

[Service]
ExecStart=/usr/bin/python3 /opt/mon-app/app.py
Restart=on-failure
User=juvanio

[Install]
WantedBy=multi-user.target
```
Puis : `sudo systemctl daemon-reload && sudo systemctl enable --now mon-app`.

> 🪤 **`daemon-reload` n'est pas optionnel.** systemd garde les unités en cache : après toute création ou modification d'un fichier `.service`, sans `daemon-reload` tu relances l'**ancienne** version sans le savoir. Et ne confonds pas les trois :
> - `systemctl reload <svc>` → demande au **service** de relire sa propre config (nginx, sshd...).
> - `systemctl daemon-reload` → demande à **systemd** de relire les fichiers d'unités.
> - `systemctl restart <svc>` → arrêt puis démarrage du service (coupure brève).

**Inspecter et modifier proprement une unité :**
```bash
systemctl cat nginx           # affiche le fichier d'unité réel + tous ses overrides
systemctl show nginx           # tous les paramètres effectifs, valeurs par défaut incluses
sudo systemctl edit nginx      # crée un override dans /etc/systemd/system/nginx.service.d/
systemctl list-dependencies nginx   # ce dont le service dépend pour démarrer
```

> 💡 **Ne modifie jamais un fichier de `/lib/systemd/system/`** : il appartient au paquet et sera écrasé à la prochaine mise à jour. `systemctl edit` crée un fichier d'*override* dans `/etc/`, qui survit aux mises à jour et ne contient que tes différences. Même principe que `/etc/` qui prime sur les valeurs livrées par la distribution.

**Configurer un service sans y mettre de secret :**
```ini
[Service]
Environment=SERVICE_NAME=orders          # valeur non sensible, en clair dans l'unité
EnvironmentFile=/etc/monapp/secrets.env  # fichier root:<groupe du service> 640 : DATABASE_URL=…
```
Le fichier d'unité est lisible par tous (`systemctl cat` le montre à n'importe qui) ; le fichier d'environnement, lui, garde des droits stricts. systemd le lit **en root**, avant de passer à l'utilisateur du service.

```bash
systemctl kill -s SIGKILL mon-app    # simuler un crash brutal : Restart=on-failure doit le relancer
systemctl show mon-app -p User -p Restart -p MainPID
```

### Identité et heure de la machine
Deux petits outils systemd qu'on utilise à chaque mise en service :
```bash
hostnamectl                                  # nom, OS, noyau, type de machine (VM, conteneur…)
sudo hostnamectl set-hostname web1           # renommer la machine (pense aussi à /etc/hosts)
timedatectl                                  # heure, fuseau, et surtout « System clock synchronized: yes »
timedatectl list-timezones | grep Africa
sudo timedatectl set-timezone Africa/Lome
```
> 🪤 **Une horloge fausse casse des choses sans rapport apparent** : certificats TLS « pas encore valides », jetons expirés, logs impossibles à corréler entre machines, sauvegardes datées de travers. Vérifie `System clock synchronized: yes` ; la synchronisation NTP est assurée par `systemd-timesyncd` (ou `chrony` sur RHEL et les serveurs exigeants).

## Module 17 — Réseau de base

### Diagnostiquer sa configuration réseau
```bash
ip a                  # interfaces réseau et leurs IP (remplace l'ancien ifconfig)
ip -br a              # même chose en une ligne par interface : bien plus lisible
ip route              # table de routage (la ligne "default via ..." est la passerelle)
hostname -I           # juste les IP de la machine, sans le reste
ping 8.8.8.8          # teste la connectivité (Ctrl+C pour arrêter)
ping -c 4 google.com  # 4 paquets seulement, avec résolution DNS
```

### La méthode : diagnostiquer de bas en haut
Face à un « ça ne marche pas », ne teste pas au hasard. Remonte les couches dans l'ordre : la **première** étape qui échoue désigne le problème, et rend inutile de tester les suivantes.

| # | Question | Commande | Si ça échoue |
|---|---|---|---|
| 1 | L'interface est-elle active avec une IP ? | `ip -br a` | problème local : câble, DHCP, configuration |
| 2 | La passerelle répond-elle ? | `ping -c2 $(ip route \| awk '/default/{print $3}')` | problème de réseau local ou de routage |
| 3 | Internet répond-il par IP ? | `ping -c2 1.1.1.1` | problème de routage ou de pare-feu sortant |
| 4 | La résolution DNS fonctionne-t-elle ? | `dig +short google.com` | problème DNS uniquement — le réseau lui-même va bien |
| 5 | Le service distant répond-il ? | `curl -sv https://exemple.com` | problème applicatif, TLS, ou port filtré |

> 💡 « Le réseau est en panne » est presque toujours, en réalité, l'étape 4 : le DNS. Le symptôme caractéristique est `ping 1.1.1.1` qui fonctionne alors que `ping google.com` échoue.

### Requêtes HTTP en ligne de commande
```bash
curl https://api.exemple.com               # affiche la réponse
curl -I https://exemple.com                # seulement les en-têtes (HEAD)
curl -L https://exemple.com                # suit les redirections 301/302
curl -o fichier.html https://exemple.com   # sauvegarde la réponse dans un fichier
curl -O https://exemple.com/fichier.zip    # conserve le nom de fichier distant
curl -sv https://exemple.com               # -s silencieux + -v verbeux : DNS, TLS, en-têtes échangés
curl -w '%{http_code}\n' -o /dev/null -s https://exemple.com   # juste le code HTTP
wget https://exemple.com/fichier.zip       # téléchargement (gère mieux la reprise, avec -c)
```

> 💡 `curl` sans `-L` affiche une page vide sur un site qui redirige — c'est le premier réflexe à avoir quand une réponse semble anormalement courte. Et `curl -sv` est l'outil de diagnostic HTTP/TLS le plus direct qui existe : il montre la résolution DNS, la négociation du certificat, et les en-têtes dans les deux sens.

### Ports, TCP et UDP en deux minutes
Une connexion réseau vise une **adresse IP** (la machine) et un **port** (le programme sur cette machine). Les ports sous 1024 sont réservés à root. Quelques ports à connaître : 22 (SSH), 53 (DNS), 80/443 (HTTP/HTTPS), 5432 (PostgreSQL), 3306 (MySQL), 6379 (Redis).

| | TCP | UDP |
| --- | --- | --- |
| Principe | connexion établie, données acquittées et ordonnées | datagrammes envoyés sans connexion |
| Usages | SSH, HTTP, bases de données | DNS, NTP, VPN WireGuard, voix |
| Tester | `nc -zv hôte port` (répond « succeeded » ou « refused ») | pas de « connexion » à tester : on observe la réponse du service |

Une adresse d'écoute dit **qui** peut se connecter : `127.0.0.1:8000` → seulement la machine elle-même ; `0.0.0.0:80` → toutes les interfaces, donc potentiellement Internet.

### Connexions et ports ouverts
```bash
ss -tulpn      # remplace netstat : liste les ports en écoute (t=TCP, u=UDP, l=listening, p=process, n=numérique)
ss -tan        # toutes les connexions TCP et leur état (ESTAB, LISTEN, TIME-WAIT…)
nc -zv 10.10.10.21 5432    # le port 5432 de cette machine est-il joignable depuis ici ?
```

> 🪤 « Connection **refused** » et « connection **timed out** » ne veulent pas dire la même chose. *Refused* : la machine a répondu, mais rien n'écoute sur ce port (service arrêté, mauvais port). *Timed out* : aucune réponse du tout (pare-feu qui jette les paquets, machine éteinte, mauvaise route). Le message te dit déjà où chercher.

### Résolution de noms
| Fichier | Rôle |
|---|---|
| `/etc/hosts` | résolution de noms manuelle (ex : forcer une IP pour un domaine) |
| `/etc/resolv.conf` | serveurs DNS utilisés |

```bash
nslookup exemple.com     # résout un nom de domaine
dig exemple.com          # équivalent plus détaillé
```

## Module 18 — SSH et accès distant

### Se connecter
```bash
ssh utilisateur@serveur              # connexion simple
ssh -p 2222 utilisateur@serveur      # port personnalisé
ssh -i ~/.ssh/ma_cle utilisateur@serveur   # avec une clé spécifique
```

### Authentification par clé (bien plus sûre qu'un mot de passe)
```bash
ssh-keygen -t ed25519 -C "mon-email@exemple.com"   # génère une paire de clés
ssh-copy-id utilisateur@serveur                     # copie la clé publique sur le serveur
```
Après ça, `~/.ssh/id_ed25519` (privée, **jamais** partagée) et `~/.ssh/id_ed25519.pub` (publique, à distribuer) permettent une connexion sans mot de passe.

> 🪤 **SSH refuse silencieusement les permissions trop larges** — c'est de très loin la première cause d'échec d'une authentification par clé. SSH ignore purement et simplement une clé privée ou un `authorized_keys` lisible par d'autres, **sans message explicite**. Les valeurs correctes :
> ```bash
> chmod 700 ~/.ssh
> chmod 600 ~/.ssh/id_ed25519        # clé privée
> chmod 644 ~/.ssh/id_ed25519.pub    # clé publique
> chmod 600 ~/.ssh/authorized_keys   # sur le SERVEUR
> ```
> Le home de l'utilisateur ne doit pas non plus être inscriptible par le groupe (`chmod 755 ~` au maximum).

**Quand une connexion par clé échoue, `-v` donne toujours la réponse :**
```bash
ssh -v utilisateur@serveur      # montre quelles clés sont proposées et pourquoi elles sont rejetées
ssh -vvv utilisateur@serveur    # encore plus détaillé, rarement nécessaire
```
Côté serveur, la vérité définitive est dans les logs : `sudo journalctl -u ssh -f` pendant la tentative de connexion.

### Transférer des fichiers
```bash
scp fichier.txt utilisateur@serveur:/chemin/distant/     # copie simple
scp -r dossier/ utilisateur@serveur:/chemin/              # récursif
scp utilisateur@serveur:/chemin/fichier.txt .             # dans l'autre sens : du serveur vers ici
rsync -avz dossier/ utilisateur@serveur:/chemin/          # ne transfère que les différences
rsync -avz --dry-run dossier/ utilisateur@serveur:/chemin/   # simulation : à faire systématiquement d'abord
```

> 🪤 **La barre oblique finale de `rsync` change tout :**
> - `rsync -a source/ dest/` copie le **contenu** de `source` dans `dest`.
> - `rsync -a source dest/` copie le **répertoire lui-même**, donnant `dest/source/`.
>
> C'est l'erreur la plus fréquente avec `rsync`, et elle est silencieuse. `--dry-run` la révèle immédiatement.

> 💡 `rsync` est préférable à `scp` dès que le transfert est répété : il ne recopie que ce qui a changé, reprend un transfert interrompu, et préserve les permissions. Approfondi à l'étape 2.

### Configuration pratique : `~/.ssh/config`
```
Host monserveur
    HostName 192.168.1.190
    User juvanio
    Port 22
    IdentityFile ~/.ssh/id_ed25519
```
Ensuite, une simple `ssh monserveur` suffit.

### Rebondir et créer des tunnels
**Rebond (`ProxyJump`)** : atteindre une machine qui n'a pas d'accès direct depuis Internet, en passant par une machine qui en a un — typiquement les machines d'un réseau privé derrière ton VPS.
```
Host vps
    HostName vps.exemple.tg
    User juvanio

Host web1
    HostName 10.10.10.21        # IP privée, invisible depuis Internet
    User juvanio
    ProxyJump vps               # la connexion passe par le VPS, chiffrée de bout en bout
```
```bash
ssh web1                        # rebond transparent ; scp et rsync en profitent aussi
ssh -J vps juvanio@10.10.10.21  # même chose, sans fichier de configuration
```

**Tunnel local (`-L`)** : rendre un port distant accessible sur ta machine, à travers SSH.
```bash
ssh -N -L 8080:10.10.10.21:80 vps     # http://localhost:8080 sur ton PC → port 80 de web1, via le VPS
ssh -N -L 5433:127.0.0.1:5432 web1    # la base PostgreSQL de web1 (qui n'écoute qu'en local) sur ton port 5433
```
`-N` : pas de shell, juste le tunnel. C'est la bonne façon d'administrer une interface web ou une base **sans jamais ouvrir son port sur Internet**.

**Agent SSH** : si ta clé privée est protégée par une phrase de passe (recommandé), `ssh-add` la déverrouille une fois par session au lieu de la redemander à chaque connexion.
```bash
eval "$(ssh-agent -s)" && ssh-add ~/.ssh/id_ed25519
```

> 🪤 « **REMOTE HOST IDENTIFICATION HAS CHANGED** » : la clé du serveur ne correspond plus à celle enregistrée dans `~/.ssh/known_hosts`. Si tu viens de réinstaller ou recréer la machine, c'est attendu : `ssh-keygen -R web1` retire l'ancienne entrée. Si tu n'as rien changé, **ne te connecte pas** : c'est exactement le symptôme d'une interception (attaque « de l'homme du milieu »).

## Module 19 — Logs et monitoring

### Où trouver les logs
| Emplacement | Contenu |
|---|---|
| `/var/log/syslog` (Debian) ou `/var/log/messages` (RHEL) | logs système généraux |
| `/var/log/auth.log` | tentatives de connexion, sudo |
| `/var/log/nginx/`, `/var/log/apache2/` | logs applicatifs (exemples) |
| `journalctl` | logs centralisés par systemd, y compris ceux avant le dernier reboot |

### `journalctl` — le couteau suisse des logs modernes
```bash
journalctl                        # tous les logs
journalctl -u nginx               # logs d'un service précis
journalctl -f                     # suivi en temps réel (comme tail -f)
journalctl --since "1 hour ago"   # filtre temporel
journalctl -p err                 # seulement les erreurs
journalctl -b                     # logs depuis le dernier démarrage
```

### `dmesg` — messages du noyau
```bash
dmesg | tail        # derniers messages matériel/noyau (disque, périphérique USB, OOM killer...)
dmesg -T | tail     # -T : horodatage lisible au lieu des secondes depuis le démarrage
dmesg -l err,warn   # seulement les erreurs et avertissements
```

> 💡 Quand un processus disparaît sans explication, `dmesg -T | grep -i -e oom -e "killed process"` révèle si le noyau l'a tué par manque de mémoire. C'est un diagnostic qu'aucun log applicatif ne donnera.

### Empêcher les logs de remplir le disque
Un disque saturé par ses propres logs est un incident classique. Deux mécanismes s'en chargent, et il faut savoir lequel gère quoi :

**`logrotate`** pour les fichiers de `/var/log/` (nginx, applicatifs...) :
```bash
cat /etc/logrotate.d/nginx            # exemple de politique par service
sudo logrotate -d /etc/logrotate.conf  # -d = simulation, n'effectue aucune rotation
```

**`journald`** pour le journal systemd, qui a sa propre comptabilité :
```bash
journalctl --disk-usage                   # taille actuelle du journal
sudo journalctl --vacuum-time=30d         # ne garder que les 30 derniers jours
sudo journalctl --vacuum-size=500M        # ou plafonner à 500 Mo
```
Pour rendre la limite permanente, `SystemMaxUse=500M` dans `/etc/systemd/journald.conf` (détaillé à l'étape 2).

## Module 20 — Sécurité de base

### Pare-feu simplifié : `ufw` (Ubuntu)
```bash
sudo ufw status verbose          # état actuel et politiques par défaut
sudo ufw allow 22/tcp            # autorise SSH — À FAIRE AVANT d'activer le pare-feu
sudo ufw enable                  # active le pare-feu
sudo ufw allow 80,443/tcp        # autorise HTTP/HTTPS
sudo ufw allow from 192.168.1.0/24 to any port 22   # SSH restreint au réseau local
sudo ufw limit 22/tcp            # autorise SSH mais bride les tentatives répétées
sudo ufw deny 23                 # bloque un port
sudo ufw status numbered         # numérote les règles, pour pouvoir les supprimer sans ambiguïté
sudo ufw delete 3                # supprime la règle n°3
```

> ⚠️ **`ufw enable` sur un serveur distant sans avoir autorisé SSH d'abord te déconnecte immédiatement et définitivement.** La politique par défaut de `ufw` est de tout bloquer en entrée ; ta propre session SSH en fait partie. L'ordre correct n'est pas négociable :
> ```bash
> sudo ufw allow 22/tcp     # 1. autoriser
> sudo ufw status           # 2. VÉRIFIER que la règle est bien là
> sudo ufw enable           # 3. seulement maintenant
> ```
> Si tu travailles sur une machine à laquelle tu n'as pas d'accès physique ou console de secours, `sudo ufw limit 22/tcp` avant l'activation est le minimum. Et garde une seconde session SSH ouverte pendant l'opération : elle reste active si tu te bloques, et te permet de corriger.

Sur RHEL/Fedora, l'équivalent est `firewalld` (`firewall-cmd --add-service=ssh --permanent`, puis `firewall-cmd --reload`). Le même avertissement s'applique mot pour mot.

### Principes de base à respecter
- **Moindre privilège** : ne jamais travailler en root en permanence, utiliser `sudo` au cas par cas.
- **Mises à jour régulières** : `sudo apt update && sudo apt upgrade` doit être une habitude, pas une exception.
- **Authentification par clé SSH**, désactiver la connexion root par mot de passe (`PermitRootLogin no` et `PasswordAuthentication no` dans `/etc/ssh/sshd_config`).
- **Fermer les ports inutiles** — n'ouvre que ce dont tu as réellement besoin.
- **Ne jamais stocker de secrets en clair** dans des fichiers avec des permissions trop larges (voir Module 5 : `chmod 600`).

### Mises à jour de sécurité automatiques
Un serveur exposé sur Internet ne peut pas attendre que tu penses à faire `apt upgrade`. Ubuntu fournit `unattended-upgrades`, qui installe chaque jour **les correctifs de sécurité** (pas les nouvelles versions) :
```bash
cat /etc/apt/apt.conf.d/20auto-upgrades              # les deux lignes doivent valoir "1" (défaut sur Ubuntu Server)
sudo apt install unattended-upgrades                 # sinon : installer…
sudo dpkg-reconfigure -plow unattended-upgrades      # …et activer
sudo unattended-upgrade --dry-run --debug | tail     # ce qui serait installé
ls /var/run/reboot-required 2>/dev/null && echo "Un redémarrage est nécessaire (noyau, libc…)"
```

### Deux surprises d'ufw à connaître
- 🪤 **ufw refuse deux règles de même correspondance.** `sudo ufw insert 1 deny 80/tcp` alors qu'il existe `allow 80/tcp` affiche `Skipping inserting existing rule` et **ne fait rien** : ufw considère la règle comme déjà présente. Pour bloquer une source précise tout en gardant le port ouvert, sois spécifique : `sudo ufw insert 1 deny from 203.0.113.7 to any port 80 proto tcp`. Et relis toujours `ufw status numbered` après une modification.
- ⚠️ **Docker contourne ufw.** Un conteneur publié avec `-p 8080:80` est joignable depuis Internet **même si ufw bloque 8080** : Docker insère ses propres règles dans la chaîne `DOCKER`, évaluée avant celles d'ufw. Sur un VPS, publie les ports sur la boucle locale (`-p 127.0.0.1:8080:80`) et expose-les via nginx, ou n'exporte rien et passe par un tunnel SSH.

### Vérifier les tentatives de connexion suspectes
```bash
sudo grep "Failed password" /var/log/auth.log | tail
sudo journalctl -u ssh | grep "Failed password"
```

## Module 21 — Héberger une application : nginx en reverse proxy

### Le concept
Une application (Python, Node, Java…) écoute sur un port local, par exemple `127.0.0.1:8000`. On ne l'expose **pas** directement : on place devant elle un **reverse proxy**, nginx, qui reçoit les requêtes des clients sur le port 80 (et 443) et les relaie à l'application.

```
Client ──HTTP :80──▶ nginx ──▶ 127.0.0.1:8000 (application)
```

Ce qu'on y gagne : un seul point d'entrée (les ports des applications restent fermés), les journaux d'accès au format standard, la possibilité de bloquer des chemins sensibles, de servir les fichiers statiques, et plus tard le chiffrement TLS (étape 2) et la répartition de charge (étape 3).

### Installer et s'y retrouver
```bash
sudo apt install nginx
systemctl status nginx
curl -I http://127.0.0.1          # « Server: nginx » : la page par défaut répond
```

| Chemin | Rôle |
| --- | --- |
| `/etc/nginx/nginx.conf` | configuration générale (on y touche rarement) |
| `/etc/nginx/sites-available/` | un fichier par site, **disponible** |
| `/etc/nginx/sites-enabled/` | liens symboliques vers les sites **actifs** |
| `/var/log/nginx/access.log`, `error.log` | journaux par défaut |

### Un site en reverse proxy
```nginx
# /etc/nginx/sites-available/monapp
server {
    listen 80;
    server_name _;                               # « n'importe quel nom »

    access_log /var/log/nginx/monapp.access.log;
    error_log  /var/log/nginx/monapp.error.log;

    location /admin/ {
        deny all;                                # ce chemin ne sort jamais de la machine
    }

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host            $host;
        proxy_set_header X-Real-IP       $remote_addr;               # l'IP du vrai client, pour l'application
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```
```bash
sudo ln -s /etc/nginx/sites-available/monapp /etc/nginx/sites-enabled/monapp
sudo rm /etc/nginx/sites-enabled/default        # le site par défaut répondrait à sa place
sudo nginx -t                                    # TOUJOURS valider avant d'appliquer
sudo systemctl reload nginx                      # relit la configuration sans couper les connexions
```

> 🪤 **`nginx -t` avant chaque `reload`.** Un `reload` avec une configuration invalide est refusé : nginx continue avec l'ancienne (et le signale dans `journalctl -u nginx`). Un `restart` avec une configuration invalide, lui, **arrête nginx et ne le redémarre pas** : le site tombe.

### Lire les erreurs
| Code vu par le client | Signification | Où chercher |
| --- | --- | --- |
| **502 Bad Gateway** | nginx n'a pas pu joindre l'application (arrêtée, mauvais port) | `systemctl status` de l'application, `ss -tlpn`, `error.log` de nginx |
| **504 Gateway Timeout** | l'application n'a pas répondu à temps | lenteur de l'application ou de sa base |
| **403 Forbidden** | refus volontaire (`deny`) ou droits de fichiers | configuration, `namei -l` sur les fichiers servis |
| **404 Not Found** | chemin inconnu (de nginx ou de l'application) | quel `server` a répondu ? le site par défaut est-il encore actif ? |

```bash
sudo tail -f /var/log/nginx/monapp.error.log   # « connect() failed (111: Connection refused) » = application arrêtée
```

### Exercice 21.1
Mets le service `mini-web` de l'exercice 16.4 derrière nginx, sur le port 80, en refusant l'accès à `/prive/`. Vérifie que `curl localhost/` affiche la page, et que `curl -I localhost/prive/` renvoie 403.

<details><summary>💡 Solution</summary>

```bash
sudo tee /etc/nginx/sites-available/mini-web > /dev/null << 'EOF'
server {
    listen 80 default_server;
    server_name _;
    location /prive/ { deny all; }
    location / { proxy_pass http://127.0.0.1:8080; }
}
EOF
sudo ln -sfn /etc/nginx/sites-available/mini-web /etc/nginx/sites-enabled/mini-web
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx
curl -s localhost/
curl -sI localhost/prive/ | head -1       # HTTP/1.1 403 Forbidden
```
</details>

## Module 22 — Projet final : mets tout bout à bout

### Le brief
Sur une VM ou un serveur de test (jamais sur un système de prod tant que tu débutes), réalise ce scénario complet :

1. Crée un utilisateur `deploy` dédié à une application, sans mot de passe root, ajouté au groupe `sudo`.
2. Crée un dossier `/opt/monitoring` appartenant à `deploy:deploy`, avec permissions `750`.
3. Écris un script bash `/opt/monitoring/healthcheck.sh` qui :
   - écrit la date, l'usage disque (`df -h`) et la mémoire libre (`free -h`) dans `/opt/monitoring/health.log` ;
   - s'arrête avec un message d'erreur clair si le dossier `/opt/monitoring` n'existe pas.
4. Rends-le exécutable uniquement par `deploy`.
5. Planifie ce script pour qu'il tourne toutes les 10 minutes via cron (sous l'utilisateur `deploy`).
6. Configure `ufw` pour n'autoriser que SSH.
7. Génère une paire de clés SSH pour `deploy` et vérifie la connexion par clé (pas par mot de passe).
8. Après une heure de fonctionnement, utilise `grep`/`tail` pour vérifier que `health.log` se remplit correctement, et `journalctl` pour vérifier qu'aucune tentative de connexion SSH suspecte n'a eu lieu.

### Pourquoi ce projet
Il traverse volontairement : gestion utilisateurs (M6), permissions (M5), scripting (M13), cron (M15), réseau/sécurité (M20), SSH (M18), et lecture de logs (M19, M12). Si tu le termines seul sans revenir aux modules, tu maîtrises les fondamentaux.

### Critères de réussite — vérifie-les un par un
Le projet n'est pas terminé quand les commandes sont passées, mais quand **ces huit affirmations sont vérifiables** :

- [ ] `id deploy` montre l'appartenance au groupe `sudo`.
- [ ] `ls -ld /opt/monitoring` affiche `drwxr-x---` et `deploy deploy`.
- [ ] `sudo -u deploy /opt/monitoring/healthcheck.sh` s'exécute sans erreur et alimente `health.log`.
- [ ] Le même script, lancé sur un répertoire cible absent, sort avec un code non nul (`echo $?` renvoie 1) et un message sur stderr.
- [ ] `sudo crontab -u deploy -l` montre la ligne planifiée, avec des chemins absolus.
- [ ] Après 20 minutes, `health.log` contient **au moins deux** blocs horodatés distincts — la preuve que cron l'exécute réellement, et pas seulement toi à la main.
- [ ] `sudo ufw status` affiche `active` avec uniquement le port 22 autorisé.
- [ ] `ssh -i ~/.ssh/deploy_key deploy@serveur` fonctionne, et la connexion par mot de passe est refusée.

> 💡 Le sixième point est le plus instructif : si `health.log` ne se remplit qu'en exécution manuelle, tu viens de rencontrer en vrai l'un des trois pièges de cron du Module 15. C'est l'exercice le plus formateur du cours.

<details><summary>💡 Solution guidée (grandes lignes)</summary>

```bash
# 1-2. Utilisateur et dossier
sudo useradd -m -s /bin/bash deploy
sudo usermod -aG sudo deploy
sudo mkdir -p /opt/monitoring
sudo chown deploy:deploy /opt/monitoring
sudo chmod 750 /opt/monitoring

# 3-4. Script (à écrire en tant que deploy, ou via sudo -u deploy)
sudo -u deploy tee /opt/monitoring/healthcheck.sh > /dev/null << 'EOF'
#!/bin/bash
set -uo pipefail

CIBLE=/opt/monitoring
if [ ! -d "$CIBLE" ]; then
    echo "Erreur : $CIBLE introuvable" >&2
    exit 1
fi
{
    echo "--- $(date '+%F %T') ---"
    df -h
    free -h
} >> "$CIBLE/health.log"
EOF
sudo chmod 700 /opt/monitoring/healthcheck.sh
sudo chown deploy:deploy /opt/monitoring/healthcheck.sh

# Tester le script AVANT de le planifier — sinon tu déboguerais à l'aveugle toutes les 10 minutes
sudo -u deploy /opt/monitoring/healthcheck.sh && sudo tail /opt/monitoring/health.log

# 5. Cron pour deploy (chemins absolus, sortie conservée : cf. les pièges du Module 15)
sudo crontab -u deploy -l 2>/dev/null > /tmp/ct
echo '*/10 * * * * /opt/monitoring/healthcheck.sh >> /opt/monitoring/cron.log 2>&1' >> /tmp/ct
sudo crontab -u deploy /tmp/ct && rm /tmp/ct
sudo crontab -u deploy -l      # vérifier

# 6. Firewall
sudo ufw allow 22/tcp
sudo ufw enable

# 7. Clé SSH (depuis ta machine locale)
ssh-keygen -t ed25519 -f ~/.ssh/deploy_key
ssh-copy-id -i ~/.ssh/deploy_key.pub deploy@serveur

# 8. Vérification
tail -f /opt/monitoring/health.log
sudo journalctl -u ssh | grep "Failed password"
```
</details>

## Glossaire

| Terme | Définition |
|---|---|
| **Kernel (noyau)** | cœur du système, gère matériel, mémoire, processus |
| **Shell** | interpréteur de commandes (bash, zsh...) |
| **Daemon** | processus qui tourne en arrière-plan, souvent un service système (nginx, sshd...) |
| **PID** | identifiant unique d'un processus |
| **Inode** | structure de données décrivant un fichier (permissions, taille, emplacement sur le disque) — pas son nom |
| **FHS** | Filesystem Hierarchy Standard, la norme d'organisation des répertoires Linux |
| **Signal** | message envoyé à un processus (SIGTERM, SIGKILL, SIGHUP...) |
| **Unit (systemd)** | brique de configuration gérée par systemd (service, timer, socket...) |
| **Root** | super-utilisateur, tous les droits sur le système |
| **Shebang** | première ligne d'un script indiquant l'interpréteur (`#!/bin/bash`) |
| **Pipe** | mécanisme reliant la sortie d'une commande à l'entrée d'une autre (`\|`) |
| **stdin / stdout / stderr** | les trois flux de toute commande : entrée (0), sortie (1), erreurs (2) |
| **Code de sortie** | entier renvoyé par une commande : 0 = succès, toute autre valeur = échec (`$?`) |
| **Variable d'environnement** | variable `export`ée, donc héritée par les processus enfants |
| **umask** | masque de retrait appliqué aux permissions des fichiers nouvellement créés |
| **Login shell** | shell démarré lors d'une connexion : il lit `~/.profile`, pas seulement `~/.bashrc` |
| **Globbing** | expansion des jokers (`*`, `?`, `[...]`) par le shell **avant** l'exécution de la commande |
| **Heredoc** | bloc de texte multi-lignes passé sur l'entrée standard d'une commande (`<< 'EOF'`) |
| **Compte de service** | compte système sans shell de connexion, sous lequel tourne un démon (`www-data`, `postgres`) |
| **Reverse proxy** | serveur (nginx) qui reçoit les requêtes des clients et les relaie à une application locale |
| **UUID (système de fichiers)** | identifiant stable inscrit dans un système de fichiers, à utiliser dans `/etc/fstab` |
| **Load average** | nombre moyen de processus prêts à s'exécuter (ou bloqués en I/O) sur 1, 5, 15 min, à comparer au nombre de cœurs |
| **Tunnel SSH** | transport d'un port réseau à travers une connexion SSH chiffrée (`-L`, `ProxyJump`) |
