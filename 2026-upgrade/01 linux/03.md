# Partie 1 — Le noyau et l'authentification sous le capot

## Module 1 — PAM et NSS

### Le concept
**PAM** (Pluggable Authentication Modules) intercepte **toute** demande d'authentification système — connexion, `sudo`, SSH, changement de mot de passe — et la fait passer par une pile de modules empilables et configurables, service par service, dans `/etc/pam.d/`. **NSS** (Name Service Switch) détermine **où** le système va chercher utilisateurs, groupes et noms d'hôtes (fichiers locaux, LDAP, DNS...) via `/etc/nsswitch.conf`.

### Lire une pile PAM
```bash
cat /etc/pam.d/sshd
cat /etc/pam.d/common-auth     # Debian/Ubuntu : pile d'authentification partagée entre plusieurs services
```
Chaque ligne a la forme `type contrôle module [arguments]` :
- **type** : `auth` (authentifie), `account` (vérifie que le compte est valide/non expiré), `password` (gestion du mot de passe), `session` (actions au début/fin de session).
- **contrôle** : `required` (doit réussir, mais continue d'évaluer la pile), `requisite` (doit réussir, arrête immédiatement sinon), `sufficient` (suffit à valider si réussi), `optional`.

### Exemple concret : verrouillage après échecs répétés
```
auth required pam_faillock.so preauth silent deny=5 unlock_time=900
auth [default=die] pam_faillock.so authfail deny=5 unlock_time=900
account required pam_faillock.so
```
```bash
sudo faillock --user juvanio          # consulte les tentatives échouées
sudo faillock --user juvanio --reset   # réinitialise le compteur
```

> 🪤 **Le module diffère selon la distribution.** `pam_faillock` est le standard sur RHEL/Fedora et arrive sur les Debian/Ubuntu récents ; les versions antérieures utilisent `pam_tally2` (déprécié, retiré depuis). Vérifie ce qui est réellement disponible avant d'écrire la règle :
> ```bash
> ls /usr/lib/x86_64-linux-gnu/security/ | grep -E 'faillock|tally'
> ```
> Sur Debian/Ubuntu, la configuration se pose dans `/etc/security/faillock.conf` et s'active via `/etc/pam.d/common-auth` — et `pam-auth-update` est le mécanisme prévu pour ne pas éditer ce fichier à la main (il est régénéré par le gestionnaire de paquets).

> ⚠️ **Une pile PAM cassée verrouille la machine pour tout le monde, root compris** — y compris ta propre session SSH suivante, et `sudo`. Ce n'est pas un risque théorique : c'est la manière la plus rapide de perdre définitivement une VM distante. Le protocole :
> 1. Sauvegarde le fichier : `sudo cp -a /etc/pam.d/common-auth{,.bak}`.
> 2. Garde **une session root déjà ouverte** (`sudo -i`) pendant toute la manipulation : elle est déjà authentifiée et survit à une pile cassée — c'est ta seule voie de réparation sans console.
> 3. Ouvre une console de secours (hyperviseur, IPMI, console cloud) **avant** de modifier quoi que ce soit.
> 4. Teste depuis un second terminal, jamais en fermant le premier.
>
> En cas de blocage sans console : démarrer sur un live USB, monter la racine, restaurer le `.bak`. C'est un incident d'une heure, contre dix secondes de sauvegarde préalable.

> 💡 `pamtester` (paquet `pamtester`) permet de tester une pile PAM **sans** se déconnecter :
> ```bash
> sudo pamtester sshd juvanio authenticate
> ```

### `/etc/nsswitch.conf`
```
passwd: files systemd
group:  files systemd
hosts:  files dns
```
Ordre de résolution de gauche à droite : `hosts: files dns` cherche d'abord dans `/etc/hosts`, puis interroge le DNS seulement si rien n'est trouvé.

## Module 2 — Namespaces et cgroups : les fondations des conteneurs

### Le concept
Deux primitives du noyau Linux, combinées, sont **tout ce dont Docker, LXC et Kubernetes ont besoin en dessous** :
- **Namespaces** : isolent ce qu'un processus **voit** (PID, réseau, points de montage, hostname/UTS, IPC, utilisateurs).
- **Cgroups** (control groups) : limitent ce qu'un processus **peut consommer** (CPU, mémoire, I/O disque).

### Explorer les namespaces
```bash
lsns                              # tous les namespaces actifs sur le système
ls -l /proc/self/ns/                # les namespaces du processus courant
sudo unshare --pid --fork --mount-proc bash    # crée un nouveau PID namespace, lance bash dedans
# À l'intérieur : "ps aux" ne montre QUE les processus de ce namespace, bash y est PID 1
```

### Cgroups v2 en pratique
```bash
mount | grep cgroup                        # vérifier qu'on est bien en cgroup v2 (type "cgroup2")
cat /sys/fs/cgroup/cgroup.controllers      # contrôleurs disponibles (cpu, memory, io...)
```

> 🪤 **Un contrôleur doit être délégué au parent avant d'être utilisable dans un enfant.** C'est la différence de fond avec cgroup v1, et la raison pour laquelle la séquence « naïve » échoue : `cpu.max` et `memory.max` **n'existent pas** dans un cgroup fraîchement créé tant que le parent ne les a pas délégués. Le symptôme est un `tee: ... No such file or directory` déroutant, alors que le répertoire vient d'être créé.
>
> Nuance : sur une machine gérée par systemd, la **racine** délègue déjà les contrôleurs usuels (`cat /sys/fs/cgroup/cgroup.subtree_control` → `cpuset cpu io memory hugetlb pids rdma` sur Ubuntu 24.04) ; un cgroup créé directement sous `/sys/fs/cgroup` a donc ses `cpu.max`/`memory.max`. Le piège frappe dès qu'on crée un **sous-arbre** (`/sys/fs/cgroup/labo/enfant`) : il faut alors `echo "+cpu +memory" > /sys/fs/cgroup/labo/cgroup.subtree_control` avant de créer l'enfant.

La séquence correcte :
```bash
# 1. Déléguer les contrôleurs voulus depuis le parent (ici la racine)
echo "+cpu +memory +io" | sudo tee /sys/fs/cgroup/cgroup.subtree_control

# 2. Créer le cgroup — les fichiers cpu.max / memory.max apparaissent alors
sudo mkdir -p /sys/fs/cgroup/mongroupe
ls /sys/fs/cgroup/mongroupe/          # cpu.max, memory.max... sont désormais présents

# 3. Poser les limites
echo "50000 100000" | sudo tee /sys/fs/cgroup/mongroupe/cpu.max    # 50 ms par période de 100 ms = 50 % d'un cœur
echo 104857600      | sudo tee /sys/fs/cgroup/mongroupe/memory.max  # 100 Mo
echo 209715200      | sudo tee /sys/fs/cgroup/mongroupe/memory.high # 200 Mo : freine avant de tuer

# 4. Y placer un processus (son PID, ou $$ pour le shell courant)
echo $$ | sudo tee /sys/fs/cgroup/mongroupe/cgroup.procs
```
Une fois le shell courant dans ce groupe, tout ce qu'il lance hérite des mêmes limites.

> 🪤 **La règle « pas de processus dans un nœud interne ».** En cgroup v2, un cgroup ne peut pas à la fois contenir des processus et déléguer des contrôleurs à ses enfants. Sur un système géré par systemd — c'est-à-dire tous — écrire directement à la racine de `/sys/fs/cgroup` entre en conflit avec sa propre hiérarchie. Pour un usage durable, passe par systemd, qui fait exactement la même chose proprement :
> ```bash
> sudo systemd-run --scope -p CPUQuota=50% -p MemoryMax=100M stress-ng --vm 1 --vm-bytes 200M
> ```
> Et pour un service existant, sans toucher à `/sys` : `sudo systemctl set-property nginx.service MemoryMax=512M`.

**Observer ce que les limites produisent réellement :**
```bash
cat /sys/fs/cgroup/mongroupe/memory.current   # consommation instantanée
cat /sys/fs/cgroup/mongroupe/memory.events     # compteurs "high", "max", "oom", "oom_kill"
cat /sys/fs/cgroup/mongroupe/cpu.stat           # dont throttled_usec : temps passé bridé
systemd-cgtop                                    # vue temps réel par cgroup, façon "top"
```

> 💡 `memory.max` déclenche l'OOM killer ; `memory.high` ralentit le processus par une pression de récupération **sans** le tuer. En production, `memory.high` un peu en dessous de `memory.max` donne un amortisseur plutôt qu'une falaise — c'est ce que fait Kubernetes avec ses `requests`/`limits`.

### Exercice 2.3
Crée un cgroup limitant un processus à 100 Mo de mémoire, lance quelque chose qui en consomme davantage, et **prouve** que c'est bien le cgroup qui l'a tué (et non un échec du programme).

<details><summary>💡 Solution</summary>

```bash
# Déléguer le contrôleur memory AVANT de créer le cgroup — sinon memory.max n'existe pas
echo "+memory" | sudo tee /sys/fs/cgroup/cgroup.subtree_control
sudo mkdir -p /sys/fs/cgroup/test
echo 104857600 | sudo tee /sys/fs/cgroup/test/memory.max

# Placer un shell dedans, puis y consommer plus que la limite
sudo bash -c 'echo $$ > /sys/fs/cgroup/test/cgroup.procs; exec stress-ng --vm 1 --vm-bytes 200M --timeout 20'
```

```bash

```

```bash
sudo rmdir /sys/fs/cgroup/test
```

```bash
sudo systemd-run --scope -p MemoryMax=100M stress-ng --vm 1 --vm-bytes 200M --timeout 20
```
</details>

## Module 3 — Paramètres noyau avancés et compilation

### `sysctl` au-delà de `swappiness`
```bash
sysctl -a | less                             # tous les paramètres noyau actuels
sudo sysctl net.ipv4.ip_forward=1              # active le routage IP (nécessaire pour un routeur/VPN Linux)
sudo sysctl net.core.somaxconn=1024              # augmente la file d'attente des connexions TCP en attente d'accept()
sudo sysctl net.ipv4.tcp_syncookies=1             # protection contre les attaques SYN flood
sudo sysctl fs.file-max=100000                      # nombre max de descripteurs de fichiers pour tout le système
```
Persistance :
```bash
echo "net.ipv4.ip_forward=1" | sudo tee /etc/sysctl.d/99-custom.conf
sudo sysctl --system      # recharge tous les fichiers sysctl.d
```

### Limites par utilisateur/session : `ulimit`
```bash
ulimit -n              # limite actuelle de descripteurs de fichiers
ulimit -n 4096           # l'augmente pour la session courante
```
Persistance dans `/etc/security/limits.conf` (appliqué par `pam_limits`, voir Module 1) :
```
juvanio soft nofile 4096
juvanio hard nofile 8192
```

> 🪤 **`limits.conf` ne s'applique PAS aux services systemd.** C'est le piège classique du « j'ai augmenté `nofile` mais nginx plante toujours sur *Too many open files* » : `limits.conf` passe par PAM, donc uniquement par les **sessions de connexion** (login, SSH, `su`). Un démon démarré par systemd ne traverse jamais PAM. Pour un service, la limite se pose dans l'unité :
> ```ini
> [Service]
> LimitNOFILE=65535
> ```
> ou globalement dans `/etc/systemd/system.conf` (`DefaultLimitNOFILE=`). Et la vérité se lit toujours sur le processus lui-même, pas sur le fichier de configuration :
> ```bash
> cat /proc/$(pgrep -o nginx)/limits        # limites RÉELLEMENT appliquées au processus
> systemctl show nginx -p LimitNOFILE
> ```

> 🪤 De même, `sysctl -w` (ou `sysctl param=valeur`) ne survit pas au redémarrage, et un fichier dans `/etc/sysctl.d/` n'est pas appliqué tant que `sysctl --system` n'a pas été lancé. Fais systématiquement les deux, puis **relis la valeur** pour confirmer :
> ```bash
> echo "net.core.somaxconn=1024" | sudo tee /etc/sysctl.d/99-custom.conf
> sudo sysctl --system
> sysctl net.core.somaxconn        # la seule vérification qui vaille
> ```
> L'ordre de lecture est alphabétique : `99-` passe après les fichiers de la distribution, donc gagne. Un `50-` risque d'être écrasé.

### Compilation d'un noyau (aperçu conceptuel)
Rarement nécessaire aujourd'hui, mais comprendre les étapes reste fondamental :
```bash
make menuconfig             # configuration interactive des options du noyau
make -j$(nproc)               # compilation parallèle sur tous les cœurs disponibles
sudo make modules_install
sudo make install
sudo update-grub
```

<details><summary>💡 Solution</summary>

## Module 4 — Débogage bas niveau

### `perf` — profiler le système en direct
```bash
sudo perf top                          # vue temps réel du CPU, FONCTION par fonction (noyau et userspace)
sudo perf top -p $(pgrep -o nginx)     # restreint à un processus
sudo perf record -g -- commande        # enregistre un profil avec la pile d'appels complète
sudo perf record -g -p PID -- sleep 30 # profile un processus déjà lancé, pendant 30 s
sudo perf report                        # analyse interactive du profil enregistré
sudo perf stat -- commande              # compteurs matériels : cycles, cache-miss, branchements manqués
```

> 🪤 **`perf` répond « quelle fonction consomme le CPU », pas « quel processus ».** Pour la seconde question, `top`/`htop`/`pidstat` suffisent et coûtent infiniment moins cher. On sort `perf` quand on sait *déjà* qu'un processus sature un cœur et qu'on veut savoir **où** dans le code — ou quand la consommation est dans le noyau et qu'aucun outil userspace ne la voit.

> 🪤 **Sans symboles, le profil est illisible** : `perf report` affiche des adresses hexadécimales ou `[unknown]` au lieu de noms de fonctions. Il faut les paquets de débogage de la cible (`-dbgsym` sous Debian, `debuginfo` sous RHEL), et pour le noyau, `linux-image-$(uname -r)-dbgsym`. Pour un binaire compilé par toi, `-g -fno-omit-frame-pointer` est nécessaire, sinon `-g` de `perf` ne remonte aucune pile.

> 🪤 `perf` peut être refusé même sous `sudo`, selon un réglage noyau — fréquent dans un conteneur ou sur une VM cloud durcie :
> ```bash
> cat /proc/sys/kernel/perf_event_paranoid    # 2 ou 3 = restreint ; il faut -1 pour tout tracer
> sudo sysctl -w kernel.perf_event_paranoid=-1
> ```

> 💡 Un profil `perf record -g` se lit beaucoup mieux sous forme de **flame graph** : `perf script | stackcollapse-perf.pl | flamegraph.pl > profil.svg` (scripts de Brendan Gregg). La largeur d'une barre est le temps CPU passé dans la fonction — le point chaud saute aux yeux en une seconde.

### Core dumps et `gdb`
```bash
ulimit -c unlimited                     # autorise la génération de core dumps pour la SESSION courante
cat /proc/sys/kernel/core_pattern        # qui récupère les core dumps, et sous quel format
coredumpctl list                          # liste les core dumps collectés par systemd
coredumpctl info                           # détails du plus récent (signal, exécutable, pile)
coredumpctl gdb 1234                        # ouvre gdb sur le core dump de ce PID
coredumpctl dump 1234 -o /tmp/core          # extrait le fichier pour l'analyser ailleurs
```

> 🪤 **Pour un service systemd, `ulimit -c unlimited` dans ton shell ne sert à rien** : le démon n'hérite pas de ta session. Il faut `LimitCORE=infinity` dans l'unité, et `Storage=external` dans `/etc/systemd/coredump.conf`. Vérifie aussi que `core_pattern` pointe bien vers `systemd-coredump` — sinon les dumps sont écrits dans le répertoire de travail du processus, voire nulle part.

> 🪤 Un core dump sans symboles de débogage ne donne qu'une pile d'adresses. Installe le `-dbgsym` correspondant **à la version exacte** du binaire qui a planté, sinon la pile est fausse plutôt qu'absente — ce qui est pire, car crédible.
Dans `gdb` :
```
(gdb) bt        # backtrace : la pile d'appels au moment du crash
(gdb) info registers
```

### `ltrace` — tracer les appels de bibliothèque
```bash
ltrace commande       # trace les appels aux bibliothèques (libc, etc.) — complémentaire de strace (Module Intermédiaire M5) qui trace les appels SYSTÈME
```

### Exercice 4.1
Utilise `perf top` pour identifier le processus qui consomme le plus de CPU sur ta machine en ce moment.

<details><summary>💡 Solution</summary>

`perf top` répond en réalité à une question plus fine : quelle **fonction** consomme le CPU. Pour le processus, l'outil adapté est plus simple :
```bash
ps aux --sort=-%cpu | head -n 5      # ou: top, htop, pidstat 1
```
Puis, une fois le coupable identifié, `perf` dit **où** dans son code le temps part :
```bash
sudo perf top -p $(pgrep -o <nom_du_processus>)
```
Si la colonne de gauche affiche des adresses hexadécimales au lieu de noms de fonctions, les symboles de débogage manquent (paquet `-dbgsym`).
</details>

# Partie 2 — Stockage résilient et haute disponibilité

## Module 5 — RAID logiciel avec `mdadm`

### Les niveaux de RAID, en un tableau
| Niveau | Principe | Tolérance de panne | Disques min. | Capacité utile |
|---|---|---|---|---|
| RAID 0 | répartition (stripe), aucune redondance | **aucune** — un disque perdu = tout perdu | 2 | 100 % |
| RAID 1 | miroir complet | tous sauf un | 2 | 50 % (sur 2 disques) |
| RAID 5 | stripe + parité répartie | 1 disque | 3 | (n-1)/n |
| RAID 6 | stripe + double parité | 2 disques | 4 | (n-2)/n |
| RAID 10 | miroir puis stripe | 1 par miroir (selon disposition) | 4 | 50 % |

> ⚠️ **Le RAID n'est pas une sauvegarde.** Il protège de la panne *matérielle* d'un disque, et de rien d'autre : une suppression accidentelle, un `rm -rf`, un rançongiciel ou une corruption applicative sont répliqués instantanément et fidèlement sur tous les disques. Le RAID sert la **disponibilité** (le service continue malgré un disque mort), la sauvegarde sert la **récupération**. Les deux sont nécessaires, et aucun ne remplace l'autre.

> 🪤 **La reconstruction est le moment le plus dangereux de la vie d'un RAID.** Pendant la resynchronisation, chaque bloc des disques restants est lu intégralement, sous charge, pendant des heures — précisément les conditions qui révèlent une seconde défaillance. Sur des disques du même lot, du même âge, ayant subi la même sollicitation, la panne simultanée est un scénario courant, pas une malchance improbable. Conséquences pratiques :
> - Un RAID 5 de gros disques (plusieurs téraoctets) a une fenêtre de reconstruction qui se compte en dizaines d'heures ; c'est la raison pour laquelle le RAID 6 (ou le RAID 10) est recommandé au-delà d'une certaine taille.
> - Surveille la reconstruction (`cat /proc/mdstat`) et évite de charger la machine pendant ce temps.
> - Lance des `scrub` réguliers (`echo check > /sys/block/md0/md/sync_action`) : ils détectent les secteurs illisibles **avant** qu'une reconstruction n'en dépende.

> ⚠️ **Sans surveillance, un RAID dégradé passe inaperçu jusqu'au second disque.** Un tableau en mode dégradé fonctionne normalement : aucun ralentissement, aucun message visible. Active les notifications :
> ```bash
> sudo apt install mdadm            # fournit le service de surveillance mdmonitor
> sudo nano /etc/mdadm/mdadm.conf    # renseigner MAILADDR
> sudo mdadm --monitor --scan --test --oneshot    # vérifier que l'alerte part bien
> ```

### Créer et surveiller un RAID
```bash
sudo mdadm --create /dev/md0 --level=1 --raid-devices=2 /dev/sdb1 /dev/sdc1   # RAID 1 (miroir)
cat /proc/mdstat                            # état du RAID en temps réel
sudo mdadm --detail /dev/md0                  # détails complets (disques, état, UUID)
sudo mdadm --create /dev/md0 --level=5 --raid-devices=3 /dev/sdb1 /dev/sdc1 /dev/sdd1  # RAID 5
```

### Remplacer un disque défaillant
```bash
sudo mdadm /dev/md0 --fail /dev/sdb1 --remove /dev/sdb1
sudo mdadm /dev/md0 --add /dev/sde1
cat /proc/mdstat     # observer la reconstruction (resync) en cours
```

### Rendre la configuration persistante
```bash
sudo mdadm --detail --scan | sudo tee -a /etc/mdadm/mdadm.conf
sudo update-initramfs -u
```

## Module 6 — Btrfs / ZFS : snapshots, checksums, auto-réparation

### Le concept
Les systèmes de fichiers modernes comme Btrfs et ZFS intègrent nativement ce que RAID + LVM devaient combiner péniblement : **snapshots instantanés**, **checksums de chaque bloc de données** (détectent la corruption silencieuse — un bit qui change sur le disque sans que le disque lui-même s'en aperçoive), et de l'**auto-réparation** si une copie redondante existe.

### Btrfs
```bash
sudo mkfs.btrfs /dev/sdb1
sudo mount /dev/sdb1 /mnt/data
sudo btrfs subvolume create /mnt/data/sousvolume
sudo btrfs subvolume snapshot /mnt/data/sousvolume /mnt/data/snapshot-2026-09-16
sudo btrfs subvolume list /mnt/data
sudo btrfs scrub start /mnt/data      # vérifie et corrige les checksums en arrière-plan
sudo btrfs scrub status /mnt/data
```

### ZFS
```bash
sudo zpool create monpool /dev/sdb /dev/sdc      # crée un pool à partir de deux disques
sudo zfs create monpool/data
sudo zfs snapshot monpool/data@avant-maj
sudo zfs rollback monpool/data@avant-maj            # revient instantanément à l'état du snapshot
sudo zpool status                                      # état de santé, y compris auto-réparation en cours
```

### Sauvegarde hors site, chiffrée et dédupliquée : restic
Snapshots Btrfs/ZFS, RAID, LVM : tout cela vit **sur la même machine**. Un incendie, un rançongiciel, une erreur d'administration les emporte avec les données. La règle 3-2-1 (étape 2, M11) exige une copie **ailleurs** — et une copie ailleurs doit être **chiffrée avant de partir** : la machine qui stocke ne doit rien pouvoir lire.

`restic` fait exactement cela : il découpe les fichiers en blocs, ne stocke chaque bloc qu'une fois (déduplication), chiffre tout **côté client**, et parle à de nombreux stockages (dossier local, `sftp:`, S3, B2, `rest:`…).
```bash
sudo apt install restic
export RESTIC_REPOSITORY=sftp:sauvegarde@10.20.0.1:/srv/restic/app    # un serveur distant, par SSH
export RESTIC_PASSWORD_FILE=/etc/restic/mdp                            # 600, root — JAMAIS sur le serveur distant
restic init                                        # une fois
restic backup --tag app /var/lib/app-dump/app.dump
restic snapshots                                   # ID, date, machine, étiquettes
restic forget --tag app --keep-last 24 --keep-daily 7 --keep-weekly 4 --prune   # rétention
restic check                                       # intégrité du dépôt (régulièrement)
restic restore latest --tag app --target /tmp/restauration
```
Mesuré (restic 0.16, Ubuntu 24.04) : trois sauvegardes successives d'un dossier de 5 Mo où seul un petit fichier change occupent **6,1 Mo** dans le dépôt, pas 15 ; et un mauvais mot de passe donne `Fatal: wrong password or no key found` — sans le mot de passe, le dépôt n'est que du bruit.

🪤 **Ne sauvegarde pas une base de données en direct dans un tube.** `pg_dump app | restic backup --stdin` semble élégant, mais si `pg_dump` meurt en route, restic enregistre quand même un instantané — tronqué, et marqué comme réussi. Dump **sur disque**, vérifié (`pg_restore -l dump >/dev/null`), puis `restic backup` du fichier.

🪤 **Le compte de dépôt sur le serveur distant** ne doit servir qu'à ça : dans son `authorized_keys`, `restrict,command="internal-sftp" ssh-ed25519 AAAA…` (sftp seulement, pas de shell, pas de redirection). Idéalement joignable seulement par un tunnel (WireGuard, M10).

### Plan de reprise : RPO, RTO, et l'exercice qui compte
- **RPO** (*Recovery Point Objective*) : la perte de données acceptable. Sauvegarde horaire → au pire une heure perdue.
- **RTO** (*Recovery Time Objective*) : la durée d'indisponibilité acceptable. Elle ne se déclare pas, elle se **mesure** : machines neuves livrées, chronomètre lancé, runbook suivi, service rétabli.
- Un plan de reprise **jamais joué** échoue sur des détails : une clé SSH d'hôte qui a changé, un mot de passe qui n'était que dans la tête de quelqu'un, un ordre d'étapes implicite, une dépendance oubliée (le tunnel doit exister avant la restauration)…
- 🪤 Le piège le plus sournois : sur une base **reconstruite**, la sauvegarde planifiée tourne avant la restauration, et l'instantané « le plus récent » devient… la base neuve. Et elle n'est presque jamais **vide** : dès que les serveurs d'application la joignent, ils y écrivent. **Vérifié dans le lab du projet** : un garde-fou « refuser une base vide » a laissé passer une base de 22 commandes (contre 73 000 dans le dépôt), sauvegardée puis « restaurée » comme dernier instantané. Le bon garde-fou compare : chaque instantané porte son volume (`restic backup --tag commandes=73665 …`), et le script refuse une base nettement plus petite que le dernier instantané. Pendant la reprise, l'application reste **arrêtée** jusqu'à la restauration ; et la restauration choisit son instantané en connaissance de cause (`restic snapshots`, puis `restic restore <ID>`).

Le Palier 3 du projet fil rouge se termine exactement par cet exercice : deux machines détruites, reconstruction par Ansible, restauration depuis le dépôt restic, en moins de 30 minutes.

## Module 7 — Clustering : Pacemaker + Corosync

### Le concept
Un cluster Pacemaker/Corosync fait basculer automatiquement un service d'un nœud défaillant vers un nœud sain, **sans intervention humaine** — la base de la haute disponibilité.

```bash
sudo apt install pacemaker corosync pcs

# 1. Le démon pcsd doit tourner sur TOUS les nœuds, et le compte hacluster avoir un mot de passe
sudo systemctl enable --now pcsd
echo "hacluster:unMotDePasseSolide" | sudo chpasswd

# 2. Authentifier les nœuds entre eux — ÉTAPE OBLIGATOIRE, oubliée une fois sur deux
sudo pcs host auth node1 node2 -u hacluster

# 3. Seulement maintenant, créer le cluster
sudo pcs cluster setup mon_cluster node1 node2
sudo pcs cluster start --all
sudo pcs cluster enable --all      # redémarrage automatique du cluster au boot
sudo pcs status                     # état complet du cluster
```

> 🪤 **`pcs cluster setup` échoue sans `pcs host auth` préalable** — et le message ne le dit pas : avec pcs 0.11 (Ubuntu 24.04), on obtient `At least 1 and at most 8 addresses must be specified for a node, 0 addresses specified for node 'node2'` (vérifié). Il faut aussi que les nœuds se résolvent mutuellement par leur nom : renseigne `/etc/hosts` sur chacun, car une dépendance DNS pour la communication interne d'un cluster est un point de faillite de plus.

> 🪤 **Sur Debian/Ubuntu, le paquet `corosync` démarre un cluster par défaut** (`Cluster name: debian`, un seul nœud) dès l'installation. `pcs cluster setup` refuse alors : `Some nodes are already in a cluster`. Sur **chaque** nœud, avant le setup : `sudo pcs cluster destroy` (sans risque sur une machine neuve ; destructeur sur un vrai cluster).

> ⚠️ **Un cluster à 2 nœuds n'a pas de quorum possible** — c'est un cas particulier, pas une configuration ordinaire. Avec deux nœuds, la majorité stricte est de 2 : la perte d'un seul nœud fait perdre le quorum et arrête les ressources, ce qui est l'inverse de l'effet recherché. `pcs cluster setup` pose donc automatiquement `two_node: 1` dans `corosync.conf`, qui contourne le calcul de quorum — **mais ce contournement rend le fencing absolument obligatoire**, car plus rien n'empêche les deux nœuds de se croire seuls survivants.
>
> Trois nœuds (ou deux nœuds plus un `qdevice` arbitre) est la configuration réellement saine. Vérifie l'état du quorum avec :
> ```bash
> sudo pcs quorum status
> sudo corosync-quorumtool -s
> ```

### Créer des ressources gérées par le cluster
```bash
sudo pcs resource create mon_ip ocf:heartbeat:IPaddr2 ip=192.168.1.100 --group mon_groupe
sudo pcs resource create mon_service systemd:nginx --group mon_groupe
```
Les deux ressources dans le même groupe basculent **ensemble** sur le même nœud en cas de panne.

### Le fencing (STONITH) — éviter le split-brain
Dans un cluster à 2 nœuds, si la communication entre eux est coupée (mais que les deux tournent toujours), **chacun peut croire être seul survivant** et activer les mêmes ressources en double — un "split-brain" dangereux (ex : deux nœuds qui écrivent sur le même disque partagé simultanément). Le **fencing** (STONITH — "Shoot The Other Node In The Head") force l'extinction physique/électrique du nœud suspect avant tout basculement, éliminant ce risque.

Le fencing n'est pas une option de confort : sans lui, Pacemaker **refuse de basculer** une ressource dont il ne peut pas garantir qu'elle est arrêtée ailleurs. Le symptôme classique est un cluster qui laisse les ressources `Stopped` après une panne, au lieu de les migrer.

```bash
sudo pcs stonith list                       # agents de fencing disponibles
sudo pcs property config stonith-enabled     # doit rester à true en production
sudo pcs stonith status
```
Les agents dépendent de l'infrastructure : `fence_ipmilan` sur du matériel physique, `fence_vmware_rest` / `fence_kvm` en virtualisé, `fence_aws`/`fence_gce` dans le cloud, `fence_sbd` (watchdog + disque partagé) quand aucune interface de gestion n'est accessible.

> ⚠️ **`stonith-enabled=false` est le raccourci qu'on trouve dans tous les tutoriels — et la cause de toutes les corruptions de données en cluster.** C'est acceptable sur une maquette d'apprentissage, jamais sur un cluster qui détient des données partagées. Si tu le désactives pour avancer dans ce module, note-le explicitement comme dette à reprendre : sur un cluster sans fencing, un simple incident réseau de quelques secondes suffit à faire écrire deux nœuds sur le même volume.

### Exercice 7.1

<details><summary>💡 Solution</summary>

</details>

## Module 8 — Répartition de charge : HAProxy et keepalived

### HAProxy — répartir le trafic entre plusieurs serveurs
```
# /etc/haproxy/haproxy.cfg
frontend web
    bind *:80
    default_backend serveurs

backend serveurs
    balance roundrobin
    server web1 192.168.1.10:80 check
    server web2 192.168.1.11:80 check
```
```bash
sudo systemctl restart haproxy
echo "show stat" | sudo socat stdio /run/haproxy/admin.sock    # statistiques en temps réel
```
`check` active un contrôle de santé automatique : un serveur qui ne répond plus est retiré de la rotation sans intervention manuelle.

### keepalived (VRRP) — éliminer le point de faillite unique du load balancer lui-même
Un seul HAProxy est lui-même un point de faillite unique. `keepalived` partage une **IP virtuelle** entre deux load balancers via le protocole VRRP : si le MASTER tombe, le BACKUP prend l'IP instantanément.
```
# /etc/keepalived/keepalived.conf (sur le nœud MASTER)
vrrp_instance VI_1 {
    state MASTER
    interface eth0
    virtual_router_id 51
    priority 150
    virtual_ipaddress {
        192.168.1.100
    }
}
```
Sur le nœud BACKUP : `state BACKUP` et une `priority` plus basse (ex : 100) — le nœud avec la priorité la plus élevée devient MASTER.

### Ce que l'exemple minimal ne fait pas (et qui compte en production)
**Un contrôle de santé plus fin.** `check` seul vérifie que le port répond. Un serveur web dont l'application ne joint plus sa base répond très bien sur le port 80… et sert des erreurs. On demande une page qui **traverse** la chaîne :
```
backend serveurs
    balance roundrobin
    option httpchk GET /sante          # /sante : une route qui interroge vraiment la base
    http-check expect status 200
    default-server inter 2s fall 2 rise 2
    retries 2
    option redispatch                  # réessayer une requête sur un AUTRE serveur si le sien tombe
    server web1 192.168.1.10:80 check
    server web2 192.168.1.11:80 check
```
**Terminer TLS sur le répartiteur**, avec redirection et en-têtes :
```
frontend http
    bind *:80
    http-request redirect scheme https code 301
frontend https
    bind *:443 ssl crt /etc/haproxy/certs/site.pem alpn h2,http/1.1   # certificat + clé dans UN .pem
    http-response set-header Strict-Transport-Security "max-age=31536000"
    http-request deny if { path_beg /admin }
    default_backend serveurs
```
```bash
sudo haproxy -c -f /etc/haproxy/haproxy.cfg     # valider AVANT de recharger (même réflexe que nginx -t)
sudo systemctl reload haproxy                    # reload : sans couper les connexions en cours
echo "show stat" | sudo socat stdio /run/haproxy/admin.sock | cut -d, -f1,2,18   # proxy, serveur, UP/DOWN
echo "disable server serveurs/web2" | sudo socat stdio /run/haproxy/admin.sock   # maintenance (MAINT)
```
🪤 `bind 192.168.1.100:443` (l'IP virtuelle) échoue sur le répartiteur qui ne la porte pas : `cannot bind socket`. Deux solutions : `bind *:443` (toutes les adresses), ou `net.ipv4.ip_nonlocal_bind=1`.

**keepalived qui suit HAProxy.** Sans `track_script`, keepalived garde l'IP virtuelle sur une machine dont HAProxy est mort : la redondance ne sert à rien. Version complète :
```
global_defs {
    script_user keepalived_script        # un compte dédié, pas root
    enable_script_security
}
vrrp_script haproxy_vivant {
    script "/usr/bin/curl -sf -o /dev/null -m 1 http://127.0.0.1:8404/"   # la page de stats répond ?
    interval 1                            # vérifié : 1 à 2 requêtes perdues sur 60 à la bascule
    fall 1                                # (interval 2 + fall 2 : 13 perdues)
    rise 2
}
vrrp_instance VI_1 {
    state BACKUP                          # les deux en BACKUP : la priorité seule décide
    interface eth0
    virtual_router_id 51
    priority 150                          # 100 sur l'autre
    advert_int 1
    unicast_src_ip 192.168.1.11           # UNICAST : beaucoup d'hébergeurs filtrent le multicast VRRP
    unicast_peer {
        192.168.1.12
    }
    authentication {
        auth_type PASS
        auth_pass Xk9p2mQa                # 8 caractères au plus : au-delà, silencieusement tronqué
    }
    virtual_ipaddress {
        192.168.1.100/24 dev eth0
    }
    track_script {
        haproxy_vivant
    }
}
```
🪤 **Vérifié sur Ubuntu 24.04** : le classique `script "/usr/bin/pidof haproxy"` ne marche **jamais** avec `enable_script_security`. `/usr/bin/pidof` y est un lien vers `killall5`, et keepalived exécute la cible du lien : `killall5` sans signal répond par son aide et le code 1. Les deux répartiteurs passent en `FAULT` et **personne** ne porte l'IP virtuelle (`journalctl -u keepalived` : `usage: killall5 -signum`). Interroger HAProxy (sa page de stats sur 127.0.0.1) est de toute façon meilleur : un processus vivant mais bloqué doit aussi céder l'IP.
**Le split-brain version VRRP.** Si les annonces VRRP ne passent plus (un pare-feu qui les bloque, un lien coupé), chaque répartiteur se croit seul et **les deux** portent l'IP virtuelle : les clients sont servis au hasard, les connexions cassent. Le pare-feu doit laisser passer VRRP (protocole IP 112, pas un port) entre les deux : `ip protocol vrrp ip saddr <l'autre> accept`. Et la surveillance doit vérifier que l'IP virtuelle est portée par **exactement un** répartiteur : zéro est une panne visible, deux est une panne sournoise.
```bash
ip -4 addr show | grep 192.168.1.100      # sur chaque répartiteur : un seul doit répondre
journalctl -u keepalived | grep -E 'Entering (MASTER|BACKUP)'    # l'historique des bascules
```

## Module 9 — Réseau avancé : bridges, VLANs, bonding, network namespaces

### Bridges — relier des interfaces au niveau 2
```bash
sudo ip link add br0 type bridge         # crée un bridge logiciel
sudo ip link set eth0 master br0         # attache une interface physique au bridge
sudo ip link set br0 up
bridge link show                          # ports rattachés au bridge et leur état
```
Base de la mise en réseau des machines virtuelles et conteneurs : le bridge se comporte comme un switch virtuel.

> ⚠️ **Attacher `eth0` à un bridge te déconnecte immédiatement si tu travailles en SSH.** Une interface esclave d'un bridge **perd son adresse IP** : c'est désormais `br0` qui doit la porter. Entre les deux commandes, la machine n'a plus de connectivité — et tu n'as plus la main pour finir la configuration.
>
> Deux façons de s'en sortir :
> ```bash
> # 1. Enchaîner l'opération en une seule commande, pour qu'il n'y ait pas de fenêtre d'interruption
> sudo ip -b - << 'EOF'
> link add br0 type bridge
> link set eth0 master br0
> addr flush dev eth0
> addr add 192.168.1.50/24 dev br0
> link set br0 up
> route add default via 192.168.1.1
> EOF
> ```
> ```bash
> # 2. Ou, plus sûr : programmer un filet de sécurité avant de commencer
> sudo sh -c 'sleep 300 && reboot' &      # si tu perds la main, la machine revient à son état de départ
> ```
> Sur une machine distante, ce genre de manipulation se fait **depuis une console hors bande** (hyperviseur, IPMI), ou via une configuration déclarative appliquée au redémarrage (netplan, `systemd-networkd`) — jamais en commandes `ip` successives sur le lien qui te porte.

> 💡 Les commandes `ip` ne survivent pas au redémarrage. Pour un bridge permanent, la configuration se déclare dans `/etc/netplan/*.yaml` (Ubuntu), `/etc/systemd/network/*.netdev` + `*.network` (systemd-networkd), ou via NetworkManager (`nmcli con add type bridge`).

### VLANs — segmenter un réseau physique unique
```bash
sudo ip link add link eth0 name eth0.10 type vlan id 10   # sous-interface pour le VLAN 10
sudo ip addr add 192.168.10.1/24 dev eth0.10
sudo ip link set eth0.10 up
```

### Bonding — agréger plusieurs interfaces physiques
```bash
sudo apt install ifenslave
# /etc/network/interfaces (Debian classique) ou netplan (Ubuntu moderne) :
# bond0 combine eth0 + eth1 pour la redondance (failover) ou le débit cumulé (selon le mode)
```
Modes courants : `active-backup` (redondance simple), `802.3ad`/LACP (agrégation de débit, nécessite un switch compatible).

### Network namespaces — isoler complètement une pile réseau
```bash
sudo ip netns add ns1                     # crée un namespace réseau isolé
sudo ip netns exec ns1 ip a                 # à l'intérieur : aucune interface (sauf lo) — totalement isolé
sudo ip link add veth0 type veth peer name veth1     # crée une paire d'interfaces virtuelles reliées
sudo ip link set veth1 netns ns1               # place une extrémité dans le namespace
sudo ip netns exec ns1 ip link set veth1 up
```

## Module 10 — VPN et tunnels : WireGuard et IPsec

### WireGuard — moderne, simple, rapide à auditer
```bash
sudo apt install wireguard
umask 077                                    # AVANT de générer : sinon la clé privée est lisible par tous
wg genkey | tee privatekey | wg pubkey > publickey
```

> ⚠️ **`umask 077` avant toute génération de clé.** Sans lui, `privatekey` naît en `644` — lisible par n'importe quel utilisateur de la machine, et la clé privée d'un pair VPN suffit à usurper son identité sur le tunnel. `wg-quick` refuse d'ailleurs de démarrer avec un `wg0.conf` trop permissif. Les permissions correctes :
> ```bash
> sudo chmod 600 /etc/wireguard/privatekey /etc/wireguard/wg0.conf
> sudo chmod 700 /etc/wireguard
> ```
```
# /etc/wireguard/wg0.conf
[Interface]
PrivateKey = <clé privée du serveur>
Address = 10.0.0.1/24
ListenPort = 51820

[Peer]
PublicKey = <clé publique du client>
AllowedIPs = 10.0.0.2/32
```
Et la configuration du **client**, que la moitié des tutoriels oublient :
```
# côté client
[Interface]
PrivateKey = <clé privée du client>
Address = 10.0.0.2/24

[Peer]
PublicKey = <clé publique du serveur>
Endpoint = serveur.exemple.com:51820
AllowedIPs = 10.0.0.0/24        # seul le réseau du VPN passe par le tunnel
# AllowedIPs = 0.0.0.0/0        # ... ou TOUT le trafic (mode "full tunnel")
PersistentKeepalive = 25         # indispensable si le client est derrière un NAT
```

```bash
sudo wg-quick up wg0
sudo wg show                          # état des pairs, dernier handshake, octets échangés
sudo systemctl enable --now wg-quick@wg0   # démarrage automatique au boot
sudo wg-quick down wg0
```

> 🪤 **`AllowedIPs` n'est pas une simple règle de filtrage** : c'est aussi la **table de routage** du tunnel. WireGuard n'envoie à un pair que le trafic destiné à ses `AllowedIPs`, et n'accepte de sa part que le trafic en provenance de ces plages (« cryptokey routing »). Deux conséquences qui expliquent la majorité des « le tunnel est monté mais rien ne passe » :
> - un `AllowedIPs` trop restreint côté client fait sortir le trafic hors du tunnel, silencieusement ;
> - deux pairs ne peuvent pas déclarer des `AllowedIPs` qui se recouvrent.

> 🪤 **Un tunnel qui monte sans faire passer le trafic vient presque toujours de l'un de ces trois points**, dans cet ordre de fréquence :
> 1. `net.ipv4.ip_forward=1` absent côté serveur (Module 3) — obligatoire dès que le serveur route pour ses pairs ;
> 2. pas de NAT en sortie : `sudo iptables -t nat -A POSTROUTING -s 10.0.0.0/24 -o eth0 -j MASQUERADE` ;
> 3. le port UDP 51820 n'est pas ouvert dans le pare-feu ou chez l'hébergeur — WireGuard est en **UDP**, un oubli fréquent quand on a l'habitude de n'ouvrir que du TCP.
>
> Le diagnostic tient en une commande : `sudo wg show` affiche `latest handshake`. S'il est vide, le problème est en amont (port, pare-feu, `Endpoint`). S'il est récent mais qu'aucun octet ne circule, c'est le routage (`AllowedIPs`, `ip_forward`, NAT).

> 💡 WireGuard est **silencieux par conception** : il ne répond rien à un paquet dont la clé ne correspond pas. Un scan de port ne révèle donc pas sa présence — mais cela signifie aussi qu'aucun message d'erreur ne t'aidera en cas de mauvaise configuration. `sudo wg show` et `journalctl -u wg-quick@wg0` sont les seules sources d'information.

### IPsec (aperçu) — le standard d'entreprise historique
Plus complexe à configurer (négociation IKE, associations de sécurité) mais largement supporté par le matériel réseau existant (routeurs, pare-feux d'entreprise) — souvent implémenté via `strongSwan` sous Linux. À connaître de nom et pour l'interopérabilité, WireGuard est généralement préféré pour un déploiement neuf entre serveurs que tu contrôles.

# Partie 4 — Conteneurs et virtualisation depuis les fondations

## Module 12 — Construire un conteneur à la main

### Le concept
Docker paraît magique tant qu'on n'a pas vu qu'il combine simplement `chroot` + namespaces (Module 2) + cgroups (Module 2) + un système de fichiers en couches (overlayfs) + une CLI conviviale. Ce module démonte la boîte noire.

### Étape 1 : une racine minimale
Il faut d'abord se procurer un système de fichiers racine. Alpine en publie un, d'environ 5 Mo :
```bash
mkdir -p /tmp/moncontainer
VERSION=3.20.3
curl -fSLO "https://dl-cdn.alpinelinux.org/alpine/v3.20/releases/x86_64/alpine-minirootfs-${VERSION}-x86_64.tar.gz"
sudo tar -xzf "alpine-minirootfs-${VERSION}-x86_64.tar.gz" -C /tmp/moncontainer
ls /tmp/moncontainer      # bin, etc, lib, usr... : une arborescence Linux complète, en 5 Mo
```
(Adapte le numéro de version : les archives anciennes sont retirées du miroir. Alternative sans téléchargement, si Docker est présent : `docker export $(docker create alpine) | sudo tar -x -C /tmp/moncontainer`.)

> 💡 Ces 5 Mo sont exactement ce qu'est une « image » de conteneur, dépouillée de toute magie : une arborescence de fichiers dans une archive. Ce que Docker y ajoute — les couches, le registre, les métadonnées — est de l'outillage autour de ce tas de fichiers, pas un mécanisme d'isolation.

### Étape 2 : isoler avec chroot + namespaces
```bash
sudo unshare --mount --uts --ipc --net --pid --fork --root=/tmp/moncontainer --mount-proc /bin/sh
```
🪤 **`--root`, pas `… --mount-proc chroot /tmp/moncontainer /bin/sh`** (la forme qu'on lit souvent) : dans cette forme, `/proc` est monté **avant** le changement de racine, donc à l'extérieur ; dans le conteneur, `/proc` est vide et `ps aux` n'affiche rien (vérifié, util-linux 2.39). Avec `--root`, unshare change de racine **puis** monte `/proc` dedans.

À l'intérieur :
```sh
ps aux     # ne montre QUE ce shell, en PID 1
ip a        # aucune interface réseau (namespace réseau vide — il faudrait lui donner un veth, cf. Module 9)
hostname     # peut être changé sans affecter l'hôte (namespace UTS)
```

### Étape 3 : limiter les ressources
Le conteneur doit **naître dans** le cgroup (ses enfants en héritent) : un shell root y entre, puis se **remplace** (`exec`) par le conteneur de l'étape 2.
```bash
sudo mkdir /sys/fs/cgroup/moncontainer
echo "50000 100000" | sudo tee /sys/fs/cgroup/moncontainer/cpu.max      # 50 % d'un cœur
sudo sh -c 'echo $$ > /sys/fs/cgroup/moncontainer/cgroup.procs
            exec unshare --mount --uts --ipc --net --pid --fork --root=/tmp/moncontainer --mount-proc /bin/sh'
cat /proc/self/cgroup        # DANS le conteneur : 0::/moncontainer
```
🪤 `echo $$ | sudo tee …/cgroup.procs`, vu partout, place **ton propre shell** (celui de l'hôte) dans le cgroup, pas le conteneur déjà lancé : tout ce que tu tapes ensuite est bridé, et le conteneur, lui, ne l'est pas. Depuis l'hôte, `cat /sys/fs/cgroup/moncontainer/cgroup.procs` dit qui est vraiment dedans.

> 💡 **C'est littéralement ce que Docker fait en interne**, avec en plus une gestion d'images en couches (overlayfs, pour ne pas dupliquer les fichiers communs entre images) et l'automatisation complète de la mise en réseau (bridge `docker0`, NAT, port mapping).

### Ce qu'il manque encore — et pourquoi c'est la partie intéressante
Le conteneur ci-dessus tourne, mais il n'est ni utilisable ni sûr. L'inventaire de ce qui manque est la meilleure description possible de ce qu'un runtime de conteneurs apporte réellement :

| Manque | Conséquence | Ce que fait Docker |
|---|---|---|
| Aucun réseau (`--net` crée un namespace **vide**) | pas même de résolution DNS | paire `veth` + bridge `docker0` + NAT (Module 9) |
| Pas de `user namespace` | root dans le conteneur = **root sur l'hôte** en cas d'évasion | `userns-remap`, ou rootless |
| `/dev` incomplet | de nombreux programmes échouent sans `/dev/null`, `/dev/urandom` | monte un `/dev` minimal |
| Pas de couches | chaque conteneur duplique tout son rootfs | overlayfs |
| Aucune restriction d'appels système | toute la surface du noyau est atteignable | profils **seccomp** et suppression de **capabilities** |
| `chroot` seul | contournable par un processus root (`chroot` n'est pas une frontière de sécurité) | `pivot_root` |

> ⚠️ **`chroot` n'a jamais été un mécanisme de sécurité**, et le savoir est la conclusion la plus importante de ce module. Un processus root dans un `chroot` s'en échappe en quelques lignes de C (ouvrir un descripteur sur un répertoire extérieur, puis `chroot` à nouveau). C'est pourquoi les vrais runtimes utilisent `pivot_root`, combiné aux namespaces, aux capabilities et à seccomp. Un conteneur n'est sécurisé que par l'**empilement** de ces mécanismes — jamais par un seul.

> 💡 Le corollaire pratique, qui vaut pour tout l'écosystème : **root dans un conteneur reste root sur l'hôte** si le user namespace n'est pas utilisé. C'est la raison d'être du mode rootless (Podman, Docker rootless) et des `securityContext` de Kubernetes, et cela explique pourquoi « ça tourne dans un conteneur » n'est pas une réponse à une question de sécurité.

### Exercice 12.1

```

</details>

### Exercice 12.2

<details><summary>💡 Solution</summary>

### Exercice 12.3 (optionnel, labo)
Ajoute une limite mémoire cgroup à ton conteneur manuel et vérifie qu'elle est bien appliquée.

<details><summary>💡 Solution</summary>

```

## Module 13 — `systemd-nspawn`

### Le concept
Un runtime de conteneur natif à systemd, plus proche d'une "petite VM légère" que Docker : il démarre un vrai `init` (systemd) à l'intérieur, ce qui le rend adapté à faire tourner un système Linux complet plutôt qu'un unique processus applicatif.

```bash
sudo apt install systemd-container debootstrap
sudo debootstrap stable /var/lib/machines/monconteneur    # crée un rootfs Debian minimal
sudo systemd-nspawn -D /var/lib/machines/monconteneur       # démarre un shell dedans, immédiatement
```

### Le gérer comme une "machine" systemd
```bash
sudo machinectl start monconteneur      # démarre en tant que service géré par systemd
machinectl list                            # liste les machines actives
machinectl shell monconteneur                # ouvre un shell dedans
machinectl stop monconteneur                  # l'arrête proprement
```

## Module 14 — Virtualisation avec KVM/QEMU et libvirt

### Conteneurs vs machines virtuelles
Les conteneurs (Modules 12-13) **partagent le noyau de l'hôte** — légers, rapides à démarrer, isolation au niveau processus. Les VM **émulent du matériel complet** et démarrent leur **propre noyau** — isolation bien plus forte (utile en multi-tenant non fiable), mais overhead mémoire/CPU nettement supérieur.

### Installer et créer une VM
```bash
sudo apt install qemu-kvm libvirt-daemon-system virtinst virt-manager
sudo virt-install --name vm1 --memory 2048 --vcpus 2 --disk size=20 --cdrom debian.iso
```

### Gérer les VM avec `virsh`
```bash
virsh list --all           # liste toutes les VM connues, avec leur état
virsh start vm1
virsh shutdown vm1            # arrêt propre (ACPI)
virsh destroy vm1               # arrêt forcé (équivalent débrancher la prise)
virsh console vm1                 # accès console texte
```

Vérifier d'abord que la machine **peut** virtualiser : `ls -l /dev/kvm` (absent : pas d'accélération matérielle — BIOS, ou VPS sans virtualisation imbriquée) et `sudo kvm-ok` (paquet `cpu-checker`).

### LXD / Incus : conteneurs système et VM, avec une seule commande
Entre le conteneur applicatif (Docker : **un** processus) et la VM complète, il y a le **conteneur système** : un vrai système (systemd, SSH, cron, services) qui partage le noyau de l'hôte. LXD (Canonical, en snap) et son dérivé communautaire **Incus** les gèrent — et gèrent **aussi** des VM KVM, avec les mêmes commandes. C'est l'outil idéal pour un labo à plusieurs machines sur un seul serveur (c'est celui du projet fil rouge).
```bash
sudo snap install lxd && sudo usermod -aG lxd "$USER"     # puis se reconnecter
lxd init --auto                                           # stockage + bridge par défaut
lxc launch ubuntu:24.04 web1                              # conteneur système, prêt en quelques secondes
lxc launch ubuntu:24.04 vm1 --vm                          # la même chose… en VM KVM
lxc list                                                  # nom, état, IP, type
lxc exec web1 -- bash                                     # shell root, SANS SSH (console de secours)
lxc file push fichier web1/root/                          # copier dedans
lxc snapshot web1 avant-maj && lxc restore web1 avant-maj # instantané / retour arrière
lxc delete --force web1
```
Réseau privé et adresses fixes, pour un labo reproductible :
```bash
lxc network create labnet ipv4.address=10.10.10.1/24 ipv4.nat=true ipv6.address=none
lxc profile create lab && lxc profile device add lab eth0 nic network=labnet name=eth0
lxc profile set lab limits.memory=1GiB limits.cpu=1
lxc init ubuntu:24.04 db1 -p default -p lab
lxc config device override db1 eth0 ipv4.address=10.10.10.31 && lxc start db1
```
| Besoin | Conteneur système | VM (`--vm`) |
| --- | --- | --- |
| systemd, services, nginx, PostgreSQL, nftables, HAProxy, keepalived | ✅ | ✅ |
| WireGuard | ✅ si le module est chargé sur l'**hôte** | ✅ |
| Disque bloc, LVM, RAID, `auditd`, modules noyau, eBPF | ❌ (noyau partagé) | ✅ |
| Densité (dizaines de machines sur un petit serveur) | ✅ | ❌ |

🪤 Sur un hôte avec **ufw** actif, le bridge LXD peut se retrouver sans DHCP ni NAT : les conteneurs n'ont pas d'IP ou pas d'Internet. Il faut autoriser le trafic du bridge (`ufw allow in on labnet`, `ufw route allow in on labnet`, `ufw route allow out on labnet`) — et **Docker** installé sur le même hôte peut aussi bloquer le transfert (`iptables -P FORWARD DROP`). Diagnostic : `lxc list` (IP ?), puis `lxc exec x -- ping -c1 1.1.1.1`.

## Module 15 — Ansible en profondeur

### Le concept
Ansible décrit l'état désiré d'un système dans un fichier lisible (YAML) et se connecte en SSH pour l'appliquer — **sans agent à installer** sur les machines cibles, contrairement à Puppet/Chef.

### Un premier playbook
```yaml
---
# playbook.yml
- name: Déployer nginx
  hosts: serveurs_web
  become: true
  tasks:
    - name: Installer nginx
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true

    - name: Démarrer et activer nginx
      ansible.builtin.systemd_service:
        name: nginx
        state: started
        enabled: true
```

> 💡 **Écris les modules en nom complet (FQCN) :** `ansible.builtin.apt` plutôt que `apt`. C'est la forme recommandée depuis Ansible 2.10 et la séparation en collections : les noms courts restent acceptés, mais deviennent ambigus dès qu'une collection tierce définit un module homonyme. `ansible-lint` le signale, et tu croiseras les deux formes dans la documentation en ligne.
```bash
ansible-playbook -i inventaire.ini playbook.yml
ansible serveurs_web -i inventaire.ini -m ping     # test de connectivité ad-hoc, sans playbook
ansible-playbook playbook.yml --check                # dry-run : montre ce qui changerait, sans rien appliquer
```

### L'idempotence — le principe fondateur
Exécuter le **même** playbook 10 fois doit produire le **même résultat** que l'exécuter une fois — Ansible vérifie l'état actuel avant d'agir (nginx déjà installé ? il ne réinstalle rien). C'est ce qui distingue un playbook Ansible d'un script bash classique, qui rejoue bêtement toutes ses actions à chaque exécution.

> 🪤 **L'idempotence n'est pas automatique : elle vient des modules.** Les modules déclaratifs (`apt`, `copy`, `lineinfile`, `user`...) comparent l'état avant d'agir. Mais `command` et `shell` sont exécutés **à chaque fois** et rapportent toujours `changed` — un playbook truffé de `shell:` est un script bash déguisé, avec la lenteur d'Ansible en supplément.
>
> Quand `command`/`shell` est inévitable, rends-le idempotent explicitement :
> ```yaml
> - name: Initialiser la base (une seule fois)
>   ansible.builtin.command: /opt/app/init-db.sh
>   args:
>     creates: /var/lib/app/.initialisé      # ne s'exécute pas si ce fichier existe déjà
>
> - name: Vérifier une valeur sans jamais rien modifier
>   ansible.builtin.command: /usr/bin/monoutil --status
>   register: resultat
>   changed_when: false                       # une lecture n'est pas un changement
>   failed_when: "'ERREUR' in resultat.stdout"
> ```
> `creates:`/`removes:`, `changed_when:` et `failed_when:` sont les trois directives qui ramènent une commande brute dans le modèle déclaratif.

> 🪤 **`--check` n'est pas fiable sur tous les playbooks.** En mode simulation, une tâche `command`/`shell` est sautée par défaut : les tâches suivantes qui dépendent de son résultat (`register`) échouent ou rapportent n'importe quoi. Un playbook réellement « dry-run-able » se construit, avec `check_mode: false` sur les tâches de lecture pure. Un `--check` qui passe est un bon signe ; un `--check` qui échoue ne prouve pas que le playbook est mauvais.

> 💡 **Les handlers** évitent le redémarrage systématique : ils ne s'exécutent qu'une fois, en fin de play, et seulement si une tâche a réellement changé quelque chose.
> ```yaml
>   tasks:
>     - name: Déployer la configuration
>       ansible.builtin.template:
>         src: nginx.conf.j2
>         dest: /etc/nginx/nginx.conf
>         validate: 'nginx -t -c %s'      # refuse d'écrire une config invalide
>       notify: Recharger nginx
>   handlers:
>     - name: Recharger nginx
>       ansible.builtin.systemd_service:
>         name: nginx
>         state: reloaded
> ```
> `validate:` est le réflexe à retenir de tout ce module : il applique au déploiement automatisé la même discipline que `sshd -t` à la main (étape 2, M14) — ne jamais écrire une configuration qu'on n'a pas validée.

### Organiser en rôles (pour des projets plus gros)
```
roles/
  nginx/
    tasks/main.yml
    handlers/main.yml
    templates/nginx.conf.j2
    vars/main.yml
```
```yaml
# playbook.yml devient alors :
- hosts: serveurs_web
  roles:
    - nginx
```

### Variables : où les mettre
```
inventaire.ini                 web1 ansible_host=10.10.10.21 marche_loadgen=true   ← propre à une machine
group_vars/all/main.yml        fuseau: Africa/Lome                                  ← toutes les machines
group_vars/all/vault.yml       vault_db_mdp: …   (CHIFFRÉ)                          ← les secrets
group_vars/web.yml             nginx_workers: 4                                     ← un groupe
host_vars/lb1.yml              keepalived_priorite: 150                             ← une machine
roles/x/defaults/main.yml      valeurs par défaut du rôle, les plus faciles à surcharger
```
Les faits collectés (`ansible_default_ipv4.interface`, `ansible_distribution_version`…) et les variables des **autres** machines (`hostvars['db1']['ansible_host']`, `groups['web']`) permettent d'écrire des gabarits qui s'adaptent à l'inventaire au lieu d'y coder des adresses.

### Gabarits Jinja2
```jinja
{# roles/haproxy/templates/haproxy.cfg.j2 #}
backend marche_web
    option httpchk GET /sante
{% for h in groups['web'] %}
    server {{ h }} {{ hostvars[h]['ansible_host'] }}:80 check
{% endfor %}
```
Ajouter `web3` à l'inventaire, relancer : la configuration suit. C'est tout l'intérêt.

### Les secrets : `ansible-vault`
```bash
ansible-vault create group_vars/all/vault.yml      # ou : encrypt un fichier existant
ansible-vault edit group_vars/all/vault.yml
ansible-vault view group_vars/all/vault.yml
ansible-playbook site.yml --ask-vault-pass         # ou vault_password_file dans ansible.cfg (fichier HORS du dépôt)
```
Convention : dans le coffre, des variables préfixées `vault_` ; ailleurs, en clair, `db_mdp: "{{ vault_db_mdp }}"`. On voit ainsi quelles variables existent sans ouvrir le coffre. Et `no_log: true` sur les tâches qui manipulent un secret, sinon il s'affiche en cas d'erreur ou en `-v`.

🪤 **`password_hash` sans sel fixe casse l'idempotence** : `password: "{{ mdp | password_hash('sha512') }}"` tire un sel aléatoire à chaque exécution, donc un hachage différent, et la tâche `user` rapporte `changed` à chaque fois. Sel fixe, lui aussi dans le coffre : `password_hash('sha512', vault_sel)`.

### Contrôler l'exécution
```bash
ansible-playbook site.yml --limit web2              # une seule machine (ou un groupe)
ansible-playbook site.yml --check --diff            # ce qui changerait, ligne par ligne : la DÉRIVE de configuration
ansible-playbook site.yml --tags nginx              # seulement les tâches étiquetées
ansible-playbook site.yml --start-at-task "Déployer la version"
ansible web -m ansible.builtin.command -a "readlink -f /opt/marche/current"   # ad hoc : lire l'état de tout un groupe
```
```yaml
- hosts: web
  serial: 1               # une machine à la fois : l'autre continue de servir pendant le déploiement
  roles: [marche]

# Agir sur une AUTRE machine depuis une tâche (ici : autoriser la clé de db1 sur bak1)
- ansible.posix.authorized_key:
    user: sauvegarde
    key: "{{ cle.content | b64decode }}"
  delegate_to: bak1

# Forcer les handlers MAINTENANT (la suite en a besoin), pas en fin de play
- ansible.builtin.meta: flush_handlers
```
🪤 **`--limit` et les rôles qui lisent d'autres machines.** Un gabarit qui utilise `hostvars['bak1']['wg_cle_publique']` (un fait calculé pendant le play) échoue si `bak1` n'est pas dans le `--limit` : le fait n'existe pas. Pire, en reconstruisant db1 seule, bak1 ne reçoit pas sa **nouvelle** clé. Limite aux deux extrémités, ou relance tout.

🪤 **`ansible.cfg` ignoré dans un dossier accessible en écriture à tous** (un partage Windows monté dans une VM, un `/tmp`…) : Ansible l'annonce en un avertissement et continue avec les valeurs par défaut — mauvais inventaire, mauvais utilisateur, erreurs incompréhensibles. `ANSIBLE_CONFIG=$PWD/ansible.cfg`, ou un dossier normal.

### Qualité : `ansible-lint`
```bash

```
Chaque avertissement désigne un vrai défaut ou une décision à justifier (`# noqa: <règle>` avec un commentaire).

### CIS Benchmarks
Standard reconnu de configurations de sécurité recommandées, publié par le **Center for Internet Security**, décliné par système (Ubuntu CIS Benchmark, RHEL CIS Benchmark...). ### OpenSCAP — audit conforme à un standard officiel
OpenSCAP a deux morceaux : le **scanner** (`oscap`) et le **contenu** (les règles, publiées par le projet ComplianceAsCode sous forme de *datastreams* `ssg-<système>-ds.xml`).

🪤 **Sur Ubuntu 24.04, le paquet `scap-security-guide` n'existe plus** (vérifié : seul `openscap-scanner` est dans les dépôts). Sur 22.04, `sudo apt install scap-security-guide` fournit encore `/usr/share/xml/scap/ssg/content/ssg-ubuntu2204-ds.xml`. Sur 24.04 : télécharger l'archive `scap-security-guide-<version>.zip` publiée sur la page *Releases* de ComplianceAsCode/content et y prendre le datastream de ta version — ou, avec Ubuntu Pro, l'outil de Canonical `usg` (`sudo usg audit cis_level1_server`).
```bash

DS=./ssg-ubuntu2404-ds.xml                         # le datastream de TA version (vérifie le nom dans l'archive)
oscap info "$DS" | grep -A20 'Profiles:'          # les identifiants de profils RÉELS : ne pas les deviner

    --profile xccdf_org.ssgproject.content_profile_cis_level1_server \
    --results resultats.xml --report rapport.html \
    "$DS"
```
Génère un rapport détaillé, point par point, conforme (ou non) au profil choisi — utile pour une certification ou un audit de conformité formel. `rapport.html` se lit dans un navigateur, règle par règle, avec la correction proposée.

🪤 Les identifiants de profil changent d'un système à l'autre (`…_profile_cis` n'existe pas pour Ubuntu, où l'on trouve `cis_level1_server`, `cis_level2_server`, `stig`…) : `oscap info` d'abord, toujours.

## Module 17 — LDAP et Kerberos : authentification centralisée

### Le concept
Au-delà d'une poignée de serveurs, créer un compte utilisateur sur chaque machine individuellement ne passe pas à l'échelle. **LDAP** centralise l'annuaire des utilisateurs/groupes dans un seul endroit interrogeable par toutes les machines (rejoint le Module 1 : c'est une des sources possibles dans `/etc/nsswitch.conf`). **Kerberos** centralise l'**authentification** elle-même par un système de tickets, sans jamais transmettre le mot de passe sur le réseau.

### LDAP
```bash
sudo apt install slapd ldap-utils
ldapsearch -x -b "dc=exemple,dc=com"                        # interroge tout l'annuaire
ldapsearch -x -b "ou=people,dc=exemple,dc=com" "(uid=juvanio)"   # cherche un utilisateur précis
```
Pour que le système utilise réellement cet annuaire pour la connexion (`login`, `ssh`...), il faut ajouter `ldap` dans `/etc/nsswitch.conf` (Module 1) et configurer PAM en conséquence (`pam_ldap` ou `sssd`, plus moderne).

### Kerberos
```bash
kinit utilisateur@REALM.COM      # obtient un ticket après authentification (une seule fois)
klist                               # liste les tickets actuellement valides
kdestroy                             # détruit tous les tickets (équivalent d'une déconnexion)
```
Principe : une fois authentifié, l'utilisateur présente son **ticket** (pas son mot de passe) à chaque service qui le demande — SSH, partages de fichiers, bases de données compatibles — pendant toute la durée de validité du ticket.

### Exercice 17.1
Interroge un annuaire LDAP pour lister tous les utilisateurs d'une unité organisationnelle donnée.

<details><summary>💡 Solution</summary>

```bash

```
</details>

### Exercice 17.2
Explique en un paragraphe pourquoi le principe "ne jamais transmettre le mot de passe sur le réseau" de Kerberos est plus sûr que ré-envoyer un mot de passe à chaque authentification.

<details><summary>💡 Solution</summary>

Avec une authentification classique répétée, le mot de passe (ou son hash) transite potentiellement à chaque connexion vers chaque service, multipliant les occasions d'interception ou de compromission d'un service intermédiaire. Avec Kerberos, le mot de passe n'est utilisé qu'une seule fois, localement, pour obtenir un ticket auprès du centre de distribution de clés (KDC) ; ensuite, seuls des tickets à durée de vie limitée circulent sur le réseau — leur interception a un impact bien plus restreint et temporaire.
</details>

# Partie 6 — Observabilité moderne

## Module 18 — eBPF et bpftrace

### Le concept
**eBPF** permet d'exécuter des programmes légers **directement dans le noyau**, déclenchés par des événements (appel système, connexion réseau...), sans recompiler ni modifier le noyau, et avec des garanties de sécurité vérifiées avant chargement (impossible de planter le noyau ou de boucler infiniment). C'est la technologie derrière des outils modernes comme Cilium (réseau Kubernetes) ou Falco (sécurité runtime).

### `bpftrace` — un langage de script simple par-dessus eBPF
```bash
sudo apt install bpftrace
sudo bpftrace -l 'tracepoint:syscalls:sys_enter_*' | head    # points de trace disponibles
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%-16s %s\n", comm, str(args->filename)); }'
sudo bpftrace -e 'kprobe:tcp_connect { printf("%s initie une connexion TCP\n", comm); }'
```

> 🪤 **Tracer `sys_enter_open` ne montre presque rien — utilise `openat`.** C'est le piège numéro un de tout débutant en eBPF : la glibc moderne implémente `open()` via l'appel système `openat()`. Un traceur branché sur `sys_enter_open` reste donc quasi muet, et on conclut à tort que l'outil ne fonctionne pas. Pour être exhaustif, couvre les deux (et `openat2` sur les noyaux récents) :
> ```bash
> sudo bpftrace -e 'tracepoint:syscalls:sys_enter_open,tracepoint:syscalls:sys_enter_openat {
>     printf("%-16s %s\n", comm, str(args->filename)); }'
> ```
> Le principe général : avant de conclure qu'un traceur ne remonte rien, vérifie que l'appel système que tu traces est bien celui que la libc utilise réellement. `strace -c ta_commande` (étape 2, M5) te le dit en une seconde.

**Quelques recettes qui répondent à de vraies questions :**
```bash
# Latence des écritures disque, en histogramme — la forme de la distribution révèle ce qu'une moyenne cache
sudo bpftrace -e 'tracepoint:block:block_rq_issue { @debut[args->dev, args->sector] = nsecs; }
  tracepoint:block:block_rq_complete /@debut[args->dev, args->sector]/ {
    @latence_us = hist((nsecs - @debut[args->dev, args->sector]) / 1000);
    delete(@debut[args->dev, args->sector]); }'

# Quel processus tue qui, et avec quel signal
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_kill {
    printf("%s (%d) -> PID %d signal %d\n", comm, pid, args->pid, args->sig); }'

# Compter les appels système par processus, pendant 10 secondes
sudo bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); } interval:s:10 { exit(); }'
```

> 💡 L'histogramme (`hist()`) est ce qui rend eBPF supérieur à un échantillonnage classique : une latence disque « moyenne de 5 ms » peut cacher 99 % d'accès à 0,1 ms et 1 % à 2 secondes. C'est ce 1 % que les utilisateurs ressentent, et seule la distribution le montre.

> 🪤 eBPF exige un noyau récent (4.9 minimum, 5.x en pratique) compilé avec `CONFIG_BPF_SYSCALL`, ainsi que `CONFIG_DEBUG_INFO_BTF` pour les fonctionnalités modernes. Dans un conteneur non privilégié, `bpftrace` ne fonctionne pas : le traçage se fait depuis l'hôte, où l'on voit de toute façon les processus de tous les conteneurs.

### Outils prêts à l'emploi (paquet `bpfcc-tools`)
```bash
sudo opensnoop-bpfcc         # observe en temps réel TOUS les fichiers ouverts sur le système, par quel processus
sudo tcplife-bpfcc              # observe la durée de vie de chaque connexion TCP (ouverture → fermeture)
sudo execsnoop-bpfcc              # observe chaque nouveau processus lancé sur le système
```

### Alerter : deux composants, deux rôles distincts
> 🪤 **Les règles d'alerte ne vivent pas dans Alertmanager.** C'est la confusion la plus répandue de l'écosystème Prometheus, et elle fait chercher au mauvais endroit pendant des heures :
> - **Prometheus** évalue les **règles d'alerte** (`alerting_rules.yml`, déclarées via `rule_files:`). C'est lui qui décide qu'une alerte passe en `firing`.
> - **Alertmanager** reçoit les alertes déjà déclenchées et gère leur **acheminement** : regroupement, déduplication, mise en sourdine, temporisation, et envoi vers Slack, e-mail ou PagerDuty (`alertmanager.yml`, avec ses sections `route:` et `receivers:`).
>
> Une règle d'alerte écrite dans `alertmanager.yml` n'a donc aucun effet, et inversement.

**La règle, côté Prometheus** (`/etc/prometheus/alerting_rules.yml`) :
```yaml
groups:
  - name: exemple
    rules:
      - alert: DisqueBientotPlein
        expr: node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"} / node_filesystem_size_bytes < 0.1
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "Moins de 10 % d'espace disque disponible sur {{ $labels.instance }}"
          description: "{{ $labels.mountpoint }} : {{ $value | humanizePercentage }} restant"
```
Puis, dans `prometheus.yml`, il faut **déclarer le fichier et l'adresse d'Alertmanager** — sans quoi la règle est évaluée mais ne part nulle part :
```yaml
rule_files:
  - /etc/prometheus/alerting_rules.yml

alerting:
  alertmanagers:
    - static_configs:
        - targets: ['localhost:9093']
```

**L'acheminement, côté Alertmanager** (`alertmanager.yml`) :
```yaml
route:
  group_by: ['alertname', 'instance']
  group_wait: 30s          # attendre pour regrouper les alertes voisines dans une seule notification
  repeat_interval: 4h      # ne pas répéter une alerte encore active avant 4 h
  receiver: equipe-ops
receivers:
  - name: equipe-ops
    slack_configs:
      - channel: '#alertes'
        api_url: 'https://hooks.slack.com/services/...'
```

> 💡 `for: 10m` est ce qui sépare une alerte utile d'une alerte qu'on finit par ignorer : la condition doit rester vraie 10 minutes d'affilée avant de déclencher, ce qui élimine les pics transitoires. Une alerte sans `for:` sur une métrique bruitée est la recette d'une astreinte épuisée — et une équipe qui ignore ses alertes est moins bien protégée qu'une équipe qui n'en a pas.

> 💡 Filtre `fstype` dans les expressions sur les systèmes de fichiers : sans cela, chaque `tmpfs` et chaque couche de conteneur génère sa propre alerte, pour des volumes dont le remplissage n'a aucune signification.

**Vérifier une chaîne d'alerte avant d'en dépendre :**
```bash
promtool check rules /etc/prometheus/alerting_rules.yml    # valide la syntaxe
promtool check config /etc/prometheus/prometheus.yml
amtool alert query                                          # alertes actuellement reçues par Alertmanager
amtool config routes test --config.file=alertmanager.yml severity=warning   # simule l'acheminement
```

### Tracing distribué (aperçu conceptuel)
Dans une architecture microservices, une requête utilisateur traverse plusieurs services. Les logs de chaque service pris isolément ne montrent jamais **où le temps est réellement passé** sur toute la chaîne. Le tracing distribué (standard OpenTelemetry, visualisé avec Jaeger ou Grafana Tempo) attribue un **trace ID unique** à chaque requête, propagé de service en service, permettant de reconstituer visuellement la chaîne d'appels complète et d'identifier précisément le service ou l'appel responsable d'une lenteur.

### Exercice 19.2
Écris la règle qui se déclenche quand l'usage disque dépasse 90 % pendant plus de 10 minutes. Précise **dans quel fichier et pour quel composant** elle doit être déclarée.

<details><summary>💡 Solution</summary>

C'est une **règle d'alerte Prometheus**, pas une configuration Alertmanager : elle va dans un fichier référencé par `rule_files:` de `prometheus.yml` (Alertmanager, lui, ne fait que router les alertes déjà déclenchées).

```yaml
# /etc/prometheus/alerting_rules.yml
groups:
  - name: stockage
    rules:
      - alert: DisqueCritique
        expr: node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"} / node_filesystem_size_bytes < 0.1
        for: 10m
        labels:
          severity: critical
        annotations:
          summary: "Espace disque critique sur {{ $labels.instance }} ({{ $labels.mountpoint }})"
```
```bash
promtool check rules /etc/prometheus/alerting_rules.yml
sudo systemctl reload prometheus
```
Le filtre `fstype!~"tmpfs|overlay"` évite une alerte par système de fichiers temporaire et par couche de conteneur, dont le taux de remplissage ne veut rien dire.

> 💡 Une alerte sur le seuil est moins utile qu'une alerte sur la **tendance** : `predict_linear` prévient avant la saturation, ce qui laisse le temps d'agir.
> ```
> predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[6h], 4*3600) < 0
> ```
> « Au rythme des 6 dernières heures, ce volume sera plein dans moins de 4 heures. »
</details>

### Exercice 19.3
Explique avec tes propres mots pourquoi le tracing distribué devient nécessaire dès qu'une architecture passe d'un monolithe à plusieurs microservices.

<details><summary>💡 Solution</summary>

Dans un monolithe, un seul fichier de log par processus suffit généralement à reconstituer le déroulé d'une requête. Dès que la requête traverse plusieurs services indépendants (chacun avec ses propres logs, potentiellement sur des machines différentes), retracer manuellement le chemin complet et identifier où le temps a été perdu devient impraticable sans un identifiant de trace commun propagé de bout en bout.
</details>

# Partie 7 — Synthèse

## Module 20 — Projet de synthèse : infrastructure haute disponibilité observée

### Le brief
Sur 2 VM de test (ou plus), réalise ce scénario complet :

1. Configure un cluster **Pacemaker/Corosync** entre les 2 nœuds, gérant une IP flottante.
2. Déploie **HAProxy** sur chaque nœud, répartissant le trafic vers deux serveurs web backend, avec **keepalived** pour la redondance des load balancers eux-mêmes.
3. Durcis les deux nœuds : PAM avec verrouillage après échecs (Module 1), paramètres `sysctl` réseau (Module 3), audit **Lynis** (Module 16).
4. Relie les deux nœuds par un tunnel **WireGuard** pour toute communication interne chiffrée.
5. Déploie `node_exporter` sur chaque nœud, scrapé par **Prometheus**, avec un tableau de bord **Grafana** et une alerte sur l'espace disque.
6. Automatise **l'intégralité** de ce qui précède dans un playbook **Ansible** unique et idempotent, organisé en rôles.

### Pourquoi ce projet
Il recombine volontairement : durcissement PAM/sysctl (M1, M3), clustering (M7), répartition de charge (M8), VPN (M10), observabilité (M19), et automatisation (M15) — l'éventail complet du niveau expert. Si tu peux relancer ce playbook sur des machines vierges et obtenir une infrastructure fonctionnelle en une commande, tu as le niveau.

### L'ordre de travail qui évite de s'enliser
Ne construis pas dans l'ordre du brief. Cette infrastructure a des dépendances, et certaines étapes rendent le débogage des suivantes très difficile :

1. **Le réseau d'abord**, à la main : les deux VM, `/etc/hosts` renseigné, connectivité vérifiée dans les deux sens.
2. **WireGuard ensuite** — le cluster et les métriques passeront dedans. Monter le tunnel avant le cluster évite de déboguer simultanément le chiffrement et le quorum.
3. **L'observabilité en troisième**, avant le cluster. C'est contre-intuitif mais décisif : `node_exporter` et Grafana en place, tu **vois** ce qui se passe pendant un basculement au lieu de le deviner.
4. **HAProxy + keepalived**, testables indépendamment du cluster.
5. **Pacemaker en dernier** — la partie la plus délicate, à aborder avec tous les outils de diagnostic déjà en place.
6. **Le durcissement PAM tout à la fin.** Une pile PAM cassée t'interdit de te reconnecter pour réparer le reste ; c'est la dernière chose à poser, avec une console de secours ouverte (Module 1).
7. **L'Ansible en parallèle, pas après.** Écris le rôle juste après avoir fait l'étape à la main : la traduction est immédiate tant que c'est frais, et pénible un mois plus tard.

### Critères de réussite — vérifie-les un par un
- [ ] `sudo wg show` affiche un `latest handshake` récent **et** des octets échangés dans les deux sens sur les deux nœuds.
- [ ] `sudo pcs status` montre les deux nœuds `Online` et toutes les ressources `Started`.
- [ ] `sudo pcs quorum status` est cohérent, et le fencing est configuré (ou sa désactivation est consciemment documentée comme dette).
- [ ] `ip a | grep <IP_virtuelle>` la trouve sur **exactement un** nœud — jamais zéro, jamais deux.
- [ ] Arrêter brutalement le nœud actif (`virsh destroy`, pas un `shutdown` propre) : l'IP virtuelle migre, et un `curl` en boucle perd au plus quelques requêtes.
- [ ] Pendant ce basculement, Grafana montre la bascule — tu disposes de la preuve, pas d'une impression.
- [ ] Arrêter un seul backend web : HAProxy le retire de la rotation (`show stat`) et le service reste disponible.
- [ ] Remplir un système de fichiers de test au-delà de 90 % déclenche réellement l'alerte, et la notification **arrive** jusqu'à sa destination.
- [ ] 5 échecs d'authentification verrouillent le compte, et `faillock --user <nom> --reset` le débloque.
- [ ] `ansible-playbook site.yml` relancé sur l'infrastructure déjà en place affiche `changed=0` — l'idempotence réelle, pas supposée.
- [ ] **Le test qui valide tout le reste :** détruis les deux VM, recrée-les vierges, et relance `ansible-playbook site.yml`. L'infrastructure doit se reconstruire entièrement, sans intervention manuelle.

> 💡 Le dernier point est le seul qui compte vraiment. Tant qu'une étape reste manuelle — une clé copiée à la main, un mot de passe saisi une fois — l'infrastructure n'est pas reproductible, et la documentation dérive dès la première modification. C'est exactement la frontière entre « j'ai réussi à le faire » et « je peux le refaire ».

### Et maintenant : le projet fil rouge, Palier 3
Ce projet de synthèse se construit sur deux VM. Le **[Palier 3 du projet fil rouge](projet-fil-rouge/palier-3.md)** en est la version exigeante, sur sept machines, avec un correcteur (`verifier-infra.sh`) qui **provoque** lui-même les pannes qu'il vérifie : il coupe HAProxy sur le répartiteur actif et mesure les requêtes perdues pendant la bascule de l'IP virtuelle, arrête un serveur web, tente les connexions que le pare-feu doit refuser, restaure une sauvegarde, rejoue le playbook et exige `changed=0`. ## Glossaire (nouveaux termes de ce niveau)

| Terme | Définition |
|---|---|
| **PAM** | Pluggable Authentication Modules — pile configurable interceptant toute authentification système |
| **NSS** | Name Service Switch — détermine où le système résout utilisateurs/groupes/noms d'hôtes |
| **Namespace (noyau)** | mécanisme isolant ce qu'un processus peut *voir* (PID, réseau, montages...) |
| **Cgroup** | mécanisme limitant ce qu'un processus peut *consommer* (CPU, RAM, I/O) |
| **STONITH / fencing** | extinction forcée d'un nœud suspect dans un cluster, pour éviter un split-brain |
| **Split-brain** | scénario où plusieurs nœuds d'un cluster s'activent simultanément par erreur de coordination |
| **VRRP** | protocole permettant à une IP virtuelle de basculer automatiquement entre plusieurs machines |
| **eBPF** | technologie exécutant des programmes vérifiés et sandboxés directement dans le noyau |
| **Idempotence** | propriété d'une opération produisant le même résultat, qu'elle soit exécutée une ou plusieurs fois |
| **KDC** | Key Distribution Center — serveur central de Kerberos qui délivre les tickets d'authentification |
| **Overlayfs** | système de fichiers en couches utilisé par Docker pour partager les couches communes entre images |
| **Trace ID** | identifiant unique propagé entre services dans le tracing distribué, reliant tous les appels d'une même requête |
| **Quorum** | majorité de nœuds nécessaire pour qu'un cluster s'autorise à agir ; impossible à atteindre avec 2 nœuds, d'où `two_node: 1` |
| **Cryptokey routing** | principe de WireGuard : `AllowedIPs` sert à la fois de filtre et de table de routage pour un pair |
| **seccomp** | filtre restreignant les appels système qu'un processus peut invoquer ; l'une des couches de sécurité d'un conteneur |
| **Capability** | privilège root découpé en droits unitaires (`CAP_NET_BIND_SERVICE`, `CAP_SYS_ADMIN`...), attribuable finement |
| **pivot_root** | remplacement sûr de `chroot` pour changer de racine ; `chroot` n'est pas une frontière de sécurité |
| **Tracepoint / kprobe** | points d'accroche eBPF : stables et documentés (tracepoint) ou sur n'importe quelle fonction noyau (kprobe) |
| **VRRP / IP virtuelle** | protocole par lequel plusieurs machines se partagent une adresse IP ; celle de plus haute priorité en vie la porte |
| **Split-brain** | deux nœuds qui se croient chacun seul survivant et prennent la même ressource (IP, disque) en même temps |
| **Contrôle de santé (health check)** | requête périodique du répartiteur vers chaque serveur ; un échec le retire de la rotation |
| **Coffre (ansible-vault)** | fichier de variables chiffré, déchiffré à l'exécution avec un mot de passe tenu hors du dépôt |
| **Dérive de configuration** | écart entre l'état décrit (Ansible) et l'état réel, souvent dû à une modification manuelle ; `--check --diff` la révèle |
| **Déduplication** | stockage unique des blocs identiques entre sauvegardes (restic, Borg) : chaque sauvegarde semble complète, n'occupe que ses différences |
| **Datastream SCAP** | fichier de règles de conformité (XCCDF, OVAL…) évalué par `oscap` ; publié par ComplianceAsCode |
| **Conteneur système** | conteneur qui fait tourner un système complet (systemd, services) plutôt qu'un seul processus : LXD, Incus, systemd-nspawn |

## Et après ?

Ce cours ferme la boucle sur **l'expertise système Linux pure**. Tu comprends désormais ce qui se passe sous les outils : ce qu'est un conteneur avant d'être une image Docker, comment un cluster décide qui détient une ressource, comment observer un noyau sans le modifier.

**Ce que ce socle rend possible.** Tout l'écosystème Cloud Native — le fameux *CNCF Landscape* et ses centaines de projets — repose intégralement sur les primitives de ce cours. Kubernetes n'est pas une technologie nouvelle posée à côté de Linux : c'est un ordonnanceur qui orchestre les namespaces et cgroups du Module 2, avec le réseau du Module 9 et l'observabilité du Module 19. Un `CrashLoopBackOff`, une `OOMKilled`, un `NetworkPolicy` qui ne filtre pas — ces problèmes se diagnostiquent avec ce que tu viens d'apprendre, et restent opaques sans lui. C'est pourquoi cette étape vient **avant** Kubernetes, et non après.

**Les directions naturelles, par ordre de rentabilité :**

| Direction | Pourquoi maintenant | Point d'ancrage dans ce cours |
|---|---|---|
| **Conteneurs et Kubernetes** | tu sais déjà ce qu'ils automatisent | M2, M12, M9 |
| **Infrastructure as Code** (Terraform, OpenTofu) | prolonge l'idempotence d'Ansible à l'approvisionnement | M15 |
| **GitOps / CI-CD** (Argo CD, Flux) | l'aboutissement du « relançable sur machine vierge » du projet final | M20 |
| **Observabilité avancée** (OpenTelemetry, eBPF avec Cilium, Falco) | eBPF est la base technique des outils actuels | M18, M19 |
| **SRE** (SLO, budgets d'erreur, post-mortem) | la culture qui donne un sens aux alertes du M19 | M19 |

**Si une validation formelle t'intéresse :** **LFCS** est couvert par les étapes 1-2, **RHCSA** par les étapes 2-3 (en révisant la syntaxe RHEL : `dnf`, `firewalld`, SELinux du M15 de l'étape 2), **LFCE/RHCE** correspond à ce cours, et **CKA** est la suite logique côté Kubernetes.

**Le conseil qui compte le plus, pour finir.** L'expertise système ne se prouve pas en connaissant des commandes, mais en diagnostiquant sous pression ce qu'on n'a jamais vu. Deux pratiques y mènent :
1. **Casse volontairement tes propres systèmes**, puis répare-les sans tutoriel — remplis un disque, sature les descripteurs de fichiers, corromps un RAID, débranche un nœud de cluster. Un instantané de VM rend l'exercice gratuit, et c'est le seul entraînement qui transfère réellement vers l'incident réel.
2. **Écris ce que tu trouves.** Un post-mortem court après chaque panne — symptôme, fausses pistes, cause réelle, correction — vaut plus que n'importe quel cours, y compris celui-ci. C'est aussi ce qui distingue, en entretien comme en astreinte, quelqu'un qui a lu d'un ingénieur qui a fait.
