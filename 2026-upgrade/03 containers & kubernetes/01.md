# Partie 1 — Comprendre les conteneurs

## Module 1 — Pourquoi les conteneurs ?

### Le problème historique
« Ça marche sur ma machine. » Une application dépend de bien plus que son code : la version exacte du runtime (Python 3.12 ou 3.9 ?), les bibliothèques système, les variables d'environnement, la configuration. Déployer « à l'ancienne » revient à reproduire cet environnement à la main sur chaque serveur, avec deux risques permanents :
- des **différences subtiles entre environnements** (dev ≠ staging ≠ prod) ;
- des **conflits entre applications** qui se partagent un serveur (l'appli A exige OpenSSL 1.1, l'appli B exige OpenSSL 3).

### La solution : empaqueter l'application avec son environnement
Un conteneur regroupe l'application **et** ses dépendances (tout sauf le noyau) dans une **image** immuable, puis l'exécute de façon isolée. La même image tourne à l'identique sur un laptop, un serveur de CI et un cluster de production.

### Conteneur vs VM (rappel *Linux Expert*, Module 14)
| Critère | Machine virtuelle | Conteneur |
|---|---|---|
| Isolation | noyau propre, matériel émulé | noyau de l'hôte partagé, isolation par namespaces et cgroups |
| Démarrage | dizaines de secondes à minutes | une seconde ou moins |
| Taille typique | Go | Mo à quelques centaines de Mo |
| Densité par serveur | dizaines | centaines |
| Force de l'isolation | très forte | plus faible (noyau partagé) |

### Ce n'est pas de la magie (rappel *Linux Expert*, Modules 2 et 12)
Un conteneur, c'est un processus Linux **isolé par des namespaces** (il ne voit que son propre PID 1, son réseau, ses montages), **limité par des cgroups** (CPU, mémoire), et dont le système de fichiers est assemblé à partir de **couches d'image**. Docker automatise ce que tu as fait à la main avec `unshare` et `chroot`.

### Ce que les conteneurs ne sont pas
- **Pas une VM** : un conteneur Linux a besoin d'un noyau Linux (Docker Desktop lance une petite VM Linux sous Windows et macOS).
- **Pas persistants par défaut** : ce qui est écrit dans un conteneur disparaît avec lui (Module 9).
- **Pas sécurisés automatiquement** : un conteneur lancé en root avec trop de privilèges reste dangereux (Module 8).

### Exercice 1.1
Explique avec tes mots pourquoi « ça marche sur ma machine » est un problème de déploiement, et comment une image de conteneur le résout.

<details><summary>💡 Solution</summary>

Le code dépend d'un environnement (versions de runtime, bibliothèques, configuration) que chaque machine peut avoir légèrement différent. Une image fige le code **et** son environnement dans un artefact immuable : ce qui a été testé est exactement ce qui est déployé, puisque c'est le même paquet qui voyage d'un environnement à l'autre.
</details>

### Exercice 1.2
Compare une VM et un conteneur sur trois critères de ton choix.

<details><summary>💡 Solution</summary>

Par exemple : (1) démarrage — un conteneur démarre en une seconde, une VM en dizaines de secondes ; (2) taille — un conteneur pèse des Mo, une VM des Go car elle embarque un système complet ; (3) isolation — une VM a son propre noyau (isolation plus forte), un conteneur partage le noyau de l'hôte.
</details>

### Exercice 1.3
Pourquoi un conteneur Linux ne peut-il pas tourner directement sur un noyau Windows ou macOS ? Que fait Docker Desktop pour contourner ce problème ?

<details><summary>💡 Solution</summary>

Un conteneur n'embarque pas de noyau : il utilise celui de l'hôte via des mécanismes propres à Linux (namespaces, cgroups). Windows et macOS n'ont pas ces primitives sous cette forme. Docker Desktop lance donc en arrière-plan une petite machine virtuelle Linux, dans laquelle tournent réellement les conteneurs.
</details>

## Module 2 — Vocabulaire : image, conteneur, registre, OCI

### Les termes à ne jamais confondre
| Terme | Définition |
|---|---|
| **Image** | modèle en **lecture seule** : couches empilées + métadonnées (commande de démarrage, variables d'environnement...) |
| **Conteneur** | **instance en exécution** d'une image, avec une fine couche d'écriture éphémère par-dessus |
| **Dockerfile** | la « recette » textuelle qui décrit comment construire une image |
| **Registre** | service qui stocke et distribue des images (Docker Hub, GHCR, ECR...) |
| **Tag** | étiquette lisible et **mutable** pointant vers une image (`nginx:1.27`) |
| **Digest** | identifiant **immuable** d'une image, basé sur son contenu (`sha256:9f2c…`) |

Analogie utile : l'image est à un conteneur ce qu'une classe est à un objet — un modèle, dont on peut lancer autant d'instances qu'on veut.

### Le standard OCI
L'**Open Container Initiative** définit trois spécifications : le format d'**image**, le comportement du **runtime**, et la **distribution** via les registres. Grâce à OCI, une image construite avec Docker peut être exécutée par Podman, containerd ou CRI-O, et stockée dans n'importe quel registre compatible — aucun verrouillage sur un outil unique.

### La pile d'exécution, de la commande au processus
```
docker (CLI) → dockerd (démon) → containerd → runc → processus Linux isolé (namespaces + cgroups)
```
- **runc** crée réellement le conteneur en appelant les primitives du noyau (implémentation de référence de la spec runtime OCI).
- **containerd** gère le cycle de vie des conteneurs, le stockage et le transfert des images.
- **Kubernetes parle directement à containerd (ou CRI-O)** via l'interface CRI, sans passer par `dockerd` — ce qui compte pour le Module 14.

### Exercice 2.1
Explique la différence entre une image et un conteneur, avec une analogie.

<details><summary>💡 Solution</summary>

Une image est un modèle en lecture seule (comme une classe, ou une image ISO). Un conteneur est une instance en cours d'exécution de cette image (comme un objet, ou une machine démarrée depuis l'ISO), avec sa propre couche d'écriture éphémère. Une même image peut donner naissance à autant de conteneurs qu'on veut.
</details>

### Exercice 2.2
Pourquoi le standard OCI est-il important pour l'écosystème ?

<details><summary>💡 Solution</summary>

Il garantit l'interopérabilité : une image respectant la spec OCI se construit, se stocke et s'exécute avec n'importe quel outil compatible (Docker, Podman, containerd, CRI-O, tout registre conforme). Cela évite qu'un fournisseur ou un outil unique verrouille l'écosystème.
</details>

### Exercice 2.3
Range dans l'ordre, du plus haut niveau au plus bas : `runc`, CLI `docker`, `containerd`, `dockerd`. Lequel crée réellement le conteneur ?

<details><summary>💡 Solution</summary>

Ordre : CLI `docker` → `dockerd` → `containerd` → `runc`. C'est **`runc`** qui crée réellement le conteneur, en appelant les primitives du noyau (namespaces, cgroups) ; les niveaux supérieurs gèrent l'interface, les images et le cycle de vie.
</details>

## Module 3 — Premiers pas avec Docker

### Vérifier l'installation et lancer un premier conteneur
```bash
docker version                 # versions du client et du démon
docker run hello-world          # télécharge l'image si absente, crée et lance un conteneur
```
`docker run` enchaîne trois actions : **pull** (si l'image est absente en local), **create**, **start**.

### Lancer un service et l'observer
```bash
docker run -d --name web -p 8080:80 nginx:1.27     # nginx en arrière-plan, port 8080 de l'hôte → port 80 du conteneur
docker ps                                            # conteneurs en cours d'exécution
docker ps -a                                          # tous les conteneurs, y compris arrêtés
docker logs web                                        # sortie du conteneur
docker logs -f web                                      # suivi en continu (comme tail -f)
docker exec -it web sh                                   # ouvre un shell dans le conteneur en cours
docker inspect web                                        # toute la configuration au format JSON
docker stop web
docker rm web
```

### Les options à connaître
| Option | Effet |
|---|---|
| `-d` | détaché : le conteneur tourne en arrière-plan |
| `--name` | nom lisible (sinon Docker en génère un aléatoire) |
| `-p hôte:conteneur` | publie un port du conteneur sur l'hôte |
| `-it` | interactif + terminal, pour un shell |
| `--rm` | supprime automatiquement le conteneur à son arrêt |
| `-e CLE=valeur` | définit une variable d'environnement |
| `-v source:cible` | monte un volume ou un dossier (Module 9) |

### Gérer les images
```bash
docker images                   # images présentes en local
docker pull alpine:3.20          # télécharge une image sans la lancer
docker run --rm -it alpine:3.20 sh    # conteneur jetable interactif
docker rmi nginx:1.27             # supprime une image locale
```

### Exercice 3.1
Lance nginx sur le port 8080 de ton hôte et vérifie qu'il répond.

<details><summary>💡 Solution</summary>

```bash
docker run -d --name web -p 8080:80 nginx:1.27
curl -I http://localhost:8080
```
Une réponse `HTTP/1.1 200 OK` confirme que le port publié fonctionne.
</details>

### Exercice 3.2
Ouvre un shell dans le conteneur en cours, liste le contenu de `/usr/share/nginx/html`, puis quitte sans arrêter le conteneur.

<details><summary>💡 Solution</summary>

```bash
docker exec -it web sh
ls /usr/share/nginx/html
exit
docker ps      # le conteneur tourne toujours
```
</details>

### Exercice 3.3
Lance un conteneur `alpine` jetable qui affiche « hello » puis se supprime tout seul.

<details><summary>💡 Solution</summary>

```bash
docker run --rm alpine:3.20 echo hello
docker ps -a     # aucune trace du conteneur grâce à --rm
```
</details>

## Module 4 — Cycle de vie, limites de ressources et redémarrage

### Les états d'un conteneur
`created` → `running` → `exited` (ou `paused`, `restarting`). Les commandes associées :
```bash
docker create --name c1 nginx:1.27     # crée sans démarrer
docker start c1
docker pause c1 / docker unpause c1    # gèle / dégèle les processus
docker restart c1
docker stop c1                          # arrêt propre
docker kill c1                           # arrêt brutal
```

### `stop` vs `kill` : une histoire de signaux (rappel *Linux Intermédiaire*, Module 5)
- `docker stop` envoie **SIGTERM**, laisse un délai de grâce (10 s par défaut), puis envoie **SIGKILL** si le processus n'a pas terminé.
- `docker kill` envoie **SIGKILL** immédiatement : pas de nettoyage possible.

Une application doit donc **intercepter SIGTERM** pour s'arrêter proprement. Attention : le processus lancé par le conteneur est le **PID 1**, que le noyau traite différemment (il ne reçoit pas les signaux par défaut s'il ne les gère pas explicitement). L'option `--init` ajoute un mini-init (`tini`) qui règle ce problème.

### Politiques de redémarrage
```bash
docker run -d --restart unless-stopped nginx:1.27
```
| Politique | Comportement |
|---|---|
| `no` (défaut) | jamais redémarré automatiquement |
| `on-failure[:N]` | redémarré seulement si code de sortie ≠ 0, N fois maximum |
| `always` | toujours redémarré, y compris au démarrage du démon Docker |
| `unless-stopped` | comme `always`, sauf si tu l'as arrêté toi-même |

### Limiter les ressources (cgroups, rappel *Linux Expert*, Module 2)
```bash
docker run -d --name limited --memory 128m --cpus 0.5 --pids-limit 100 nginx:1.27
docker stats --no-stream            # consommation instantanée par conteneur
docker inspect -f '{{.State.OOMKilled}}' limited     # true si tué par manque de mémoire
```
Sans limite, un conteneur peut consommer toute la mémoire de l'hôte et déclencher l'OOM killer sur **d'autres** processus.

### Exercice 4.1
Lance un conteneur nginx limité à 64 Mo de mémoire et vérifie que la limite est bien appliquée.

<details><summary>💡 Solution</summary>

```bash
docker run -d --name limited --memory 64m nginx:1.27
docker inspect -f '{{.HostConfig.Memory}}' limited     # 67108864 (octets)
docker stats --no-stream limited                        # la colonne LIMIT affiche 64MiB
```
</details>

### Exercice 4.2
Explique la différence entre `docker stop` et `docker kill`, en termes de signaux.

<details><summary>💡 Solution</summary>

`docker stop` envoie SIGTERM (que l'application peut intercepter pour se fermer proprement), attend le délai de grâce, puis envoie SIGKILL en dernier recours. `docker kill` envoie SIGKILL tout de suite : ce signal ne peut pas être intercepté, donc aucune fermeture propre (connexions, fichiers, transactions) n'est possible.
</details>

### Exercice 4.3
Choisis une politique de redémarrage pour chaque cas : (a) un job de migration de base de données exécuté une seule fois, (b) un service web qui doit survivre à un redémarrage du serveur, (c) un service instable en développement pour lequel tu veux éviter les boucles infinies.

<details><summary>💡 Solution</summary>

(a) `no`, ou `on-failure:3` si tu acceptes quelques nouvelles tentatives — un job ponctuel ne doit pas se relancer indéfiniment. (b) `unless-stopped` (ou `always`) : il redémarre avec le serveur, sauf arrêt volontaire. (c) `on-failure:5` : quelques essais, puis abandon, ce qui évite la boucle de redémarrage infinie qui masquerait le bug.
</details>

# Partie 2 — Construire et distribuer des images

## Module 5 — Le Dockerfile : instructions essentielles

### Un premier Dockerfile
```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["gunicorn", "--bind", "0.0.0.0:8000", "app:app"]
```
```bash
docker build -t monapp:1.0 .          # construit l'image à partir du Dockerfile du dossier courant
docker run -d --name monapp -p 8000:8000 monapp:1.0
```

### Les instructions à maîtriser
| Instruction | Rôle |
|---|---|
| `FROM` | image de base sur laquelle on construit (toujours la première instruction) |
| `WORKDIR` | répertoire de travail pour les instructions suivantes (le crée si besoin) |
| `COPY` | copie des fichiers de l'hôte vers l'image |
| `ADD` | comme `COPY`, avec extraction d'archives et URL — à éviter sauf besoin précis |
| `RUN` | exécute une commande **pendant la construction** (installer des paquets...) |
| `ENV` | variable d'environnement, présente dans l'image **et** à l'exécution |
| `ARG` | variable disponible **uniquement pendant la construction** |
| `EXPOSE` | documente le port écouté — **ne publie rien** (c'est `-p` qui publie) |
| `USER` | utilisateur sous lequel tourneront les instructions suivantes et le conteneur |
| `CMD` | commande par défaut au démarrage du conteneur |
| `ENTRYPOINT` | exécutable fixe du conteneur, auquel `CMD` fournit des arguments par défaut |
| `HEALTHCHECK` | commande vérifiant périodiquement que l'application est saine |

### `CMD` vs `ENTRYPOINT`
```dockerfile
ENTRYPOINT ["python", "manage.py"]
CMD ["runserver", "0.0.0.0:8000"]
```
```bash
docker run monapp                # exécute : python manage.py runserver 0.0.0.0:8000
docker run monapp migrate         # exécute : python manage.py migrate  (CMD remplacé, ENTRYPOINT conservé)
```
`CMD` se remplace facilement en ligne de commande ; `ENTRYPOINT` fixe ce que le conteneur **est**.

### Forme exec vs forme shell
```dockerfile
CMD ["python", "app.py"]      # forme exec (JSON) : le processus est directement le PID 1
CMD python app.py              # forme shell : lancé via /bin/sh -c, le shell devient PID 1
```
Avec la forme shell, `sh` est le PID 1 et **ne transmet pas les signaux** (SIGTERM d'un `docker stop`) à ton application : elle sera tuée brutalement après le délai de grâce au lieu de s'arrêter proprement.

### `ARG` vs `ENV`
```dockerfile
ARG APP_VERSION=dev          # docker build --build-arg APP_VERSION=1.2.3 .
ENV APP_ENV=production        # persiste dans l'image et dans le conteneur
```

### Exercice 5.1
Écris un Dockerfile pour une application Node.js (fichiers `package.json` et `server.js`, écoute sur le port 3000).

<details><summary>💡 Solution</summary>

```dockerfile
FROM node:20-slim
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]
```
Les fichiers de dépendances sont copiés avant le reste du code : on verra au Module 6 pourquoi cet ordre compte.
</details>

### Exercice 5.2
Explique la différence entre `CMD` et `ENTRYPOINT`.

<details><summary>💡 Solution</summary>

`ENTRYPOINT` définit l'exécutable fixe du conteneur ; `CMD` fournit des arguments par défaut, facilement remplaçables par ce qu'on tape après le nom de l'image dans `docker run`. Combinés, `ENTRYPOINT` dit *quoi exécuter* et `CMD` dit *avec quels arguments par défaut*.
</details>

### Exercice 5.3
Pourquoi préférer la forme exec (JSON) à la forme shell pour `CMD` ?

<details><summary>💡 Solution</summary>

En forme shell, `/bin/sh -c` devient le PID 1 et ne relaie pas les signaux à l'application : un `docker stop` n'arrive jamais jusqu'à elle, qui est tuée brutalement par SIGKILL après le délai de grâce. En forme exec, l'application est directement le PID 1 et peut intercepter SIGTERM pour s'arrêter proprement.
</details>

## Module 6 — Couches, cache de build et multi-stage builds

### Chaque instruction crée une couche
Les instructions `RUN`, `COPY` et `ADD` produisent chacune une **couche** immuable. Docker met ces couches en **cache** : si une instruction et tout ce qui la précède sont inchangés, la couche est réutilisée telle quelle. Dès qu'une instruction change, **elle et toutes les suivantes** sont reconstruites.

### La règle d'or : du moins changeant au plus changeant
```dockerfile
# ❌ Mauvais ordre : la moindre modif du code invalide aussi l'installation des dépendances
COPY . .
RUN pip install -r requirements.txt

# ✅ Bon ordre : les dépendances (rarement modifiées) sont mises en cache
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
```

### `.dockerignore` — ne pas envoyer n'importe quoi au build
```
.git
__pycache__/
*.pyc
node_modules/
.env
*.log
```
Cela accélère le build **et** évite d'embarquer par erreur un `.env` avec des secrets dans l'image.

### Nettoyer dans la même couche
```dockerfile
RUN apt-get update \
    && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*
```
Une couche n'est jamais modifiée après sa création : supprimer des fichiers dans une couche **ultérieure** ne fait que les masquer, ils occupent toujours la place dans la couche d'origine.

### Multi-stage builds — construire gros, livrer petit
```dockerfile
# Étape 1 : image de build, avec compilateur et outils
FROM golang:1.23 AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/app ./cmd/app

# Étape 2 : image finale minimale, sans compilateur ni outils
FROM gcr.io/distroless/static-debian12
COPY --from=builder /out/app /app
USER nonroot:nonroot
ENTRYPOINT ["/app"]
```
L'image finale ne contient que le binaire : quelques Mo au lieu de plusieurs centaines, et **presque aucune surface d'attaque** (ni shell, ni gestionnaire de paquets, ni compilateur).

### Inspecter les couches
```bash
docker history monapp:1.0        # chaque couche, sa commande et sa taille
docker image ls monapp            # taille totale
```

### Exercice 6.1
Réordonne ce Dockerfile pour tirer parti du cache de build :
```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
CMD ["python", "main.py"]
```

<details><summary>💡 Solution</summary>

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "main.py"]
```
Tant que `requirements.txt` ne change pas, l'installation des dépendances est réutilisée depuis le cache, même si le code source change à chaque build.
</details>

### Exercice 6.2
Pourquoi un `RUN rm -rf /tmp/cache` placé dans une couche **ultérieure** ne réduit-il pas la taille de l'image ?

<details><summary>💡 Solution</summary>

Les couches sont immuables et empilées : les fichiers créés dans une couche antérieure restent stockés dans cette couche. Une suppression ultérieure ne fait que les « masquer » dans la vue finale du système de fichiers, sans libérer l'espace. Le nettoyage doit se faire dans **la même instruction `RUN`** que celle qui a créé les fichiers.
</details>

### Exercice 6.3
Quels bénéfices apporte un multi-stage build, en taille et en sécurité ?

<details><summary>💡 Solution</summary>

L'image finale ne contient que ce qui est nécessaire à l'exécution (le binaire ou l'application construite), sans compilateur, sans outils de build, sans code source. Elle est beaucoup plus petite (transfert et démarrage plus rapides) et expose beaucoup moins de composants susceptibles de porter des vulnérabilités.
</details>

## Module 7 — Registres : tags, digests, push et pull

### Où stocker ses images
| Registre | Type |
|---|---|
| Docker Hub | public (et privé), registre par défaut |
| GHCR (GitHub Container Registry) | intégré à GitHub |
| ECR / Artifact Registry / ACR | registres privés managés d'AWS / GCP / Azure |
| Harbor | registre auto-hébergé open source (projet CNCF) avec scan et signature |

### Anatomie d'un nom d'image
```
ghcr.io/mon-org/api:2.4.1
└──┬──┘ └───┬───┘ └┬┘ └──┬─┘
registre  espace  dépôt  tag
```
Un nom sans registre (`nginx`) est complété en `docker.io/library/nginx:latest` : registre Docker Hub, espace « library », tag `latest`.

### Tags mutables, digests immuables
Un **tag** est un simple pointeur qui peut être déplacé vers une autre image (`latest` change à chaque publication). Un **digest** (`sha256:…`) identifie un contenu précis et ne peut jamais désigner autre chose.
```bash
docker images --digests                                   # affiche les digests
docker inspect --format '{{index .RepoDigests 0}}' localhost:5000/monapp:1.0
```
Épingler par digest garantit la reproductibilité : `FROM python:3.12-slim@sha256:…`.

### Stratégie de tags recommandée
- des tags de version **précis** (`2.4.1`), complétés au besoin par `2.4` ;
- en CI, le **SHA du commit** (`monapp:git-3f9c2ab`) pour relier une image à son code source exact ;
- **jamais `latest` en production** : on ne sait pas quelle version tourne, deux déploiements successifs peuvent donner des images différentes, et un rollback devient ambigu.

### Pousser et tirer
```bash
docker tag monapp:1.0 ghcr.io/mon-org/monapp:1.0     # donne un second nom à la même image
docker login ghcr.io
docker push ghcr.io/mon-org/monapp:1.0
docker pull ghcr.io/mon-org/monapp:1.0
```

### Un registre local pour s'entraîner
```bash
docker run -d -p 5000:5000 --name registry registry:2
docker tag monapp:1.0 localhost:5000/monapp:1.0
docker push localhost:5000/monapp:1.0
curl http://localhost:5000/v2/_catalog        # {"repositories":["monapp"]}
```

### Exercice 7.1
Démarre un registre local, pousses-y une image, supprime-la de ta machine, puis récupère-la depuis le registre.

<details><summary>💡 Solution</summary>

```bash

docker pull alpine:3.20
docker tag alpine:3.20 localhost:5000/alpine:3.20
docker push localhost:5000/alpine:3.20
docker rmi alpine:3.20 localhost:5000/alpine:3.20
docker pull localhost:5000/alpine:3.20
docker images | grep alpine
```
</details>

### Exercice 7.2
Pourquoi utiliser `:latest` en production est-il une mauvaise pratique, et que faut-il utiliser à la place ?

<details><summary>💡 Solution</summary>

`latest` est un tag mutable : il désigne une image différente selon le moment où on le résout, donc deux déploiements du « même » manifeste peuvent faire tourner des versions différentes, et on ne peut pas dire précisément ce qui est en production ni revenir de façon fiable à la version précédente. Il faut utiliser un tag de version précis (`2.4.1`), un tag basé sur le SHA du commit, ou mieux, un digest.
</details>

### Exercice 7.3
Décompose le nom `ghcr.io/mon-org/api:2.4.1`, puis explique ce que désigne exactement le nom `nginx`.

<details><summary>💡 Solution</summary>

Registre : `ghcr.io` ; espace (organisation) : `mon-org` ; dépôt : `api` ; tag : `2.4.1`. Le nom `nginx` seul est complété par défaut en `docker.io/library/nginx:latest`.
</details>

## Module 8 — Images sécurisées : non-root, images minimales, scan de vulnérabilités

### Ne pas tourner en root
Par défaut, un conteneur s'exécute en **root** (à l'intérieur de son namespace). Si l'application est compromise, l'attaquant a des droits maximaux dans le conteneur, ce qui facilite une évasion vers l'hôte.
```dockerfile
FROM python:3.12-slim
RUN useradd --system --uid 10001 --no-create-home appuser
WORKDIR /app
COPY --chown=appuser:appuser . .
USER appuser
CMD ["python", "main.py"]
```

### Images minimales
Moins de paquets = moins de vulnérabilités potentielles. Ordre de préférence : `distroless` ou `scratch` (pas de shell), puis `-slim`, puis `alpine` (petit, mais bibliothèque `musl` parfois incompatible), en évitant les images « complètes » quand c'est possible.

### Scanner les vulnérabilités
```bash
trivy image monapp:1.0                                # rapport complet
trivy image --severity HIGH,CRITICAL monapp:1.0        # ne garde que le grave
trivy image --exit-code 1 --severity CRITICAL monapp:1.0   # échoue (code 1) : utilisable dans une CI
```
Trivy, Grype et Docker Scout comparent les paquets de l'image à des bases de CVE connues. Un scan n'a de valeur que **répété** : de nouvelles vulnérabilités sont publiées chaque jour sur des paquets déjà déployés.

### Pas de secrets dans l'image
Les valeurs passées par `ARG` ou `ENV` restent visibles pour quiconque a accès à l'image :
```bash
docker history --no-trunc monapp:1.0
docker inspect monapp:1.0
```
Pour un secret nécessaire **au build** (jeton d'un registre privé, par exemple), BuildKit propose un montage éphémère qui ne laisse aucune trace dans les couches :
```dockerfile
# syntax=docker/dockerfile:1
RUN --mount=type=secret,id=npm_token \
    NPM_TOKEN=$(cat /run/secrets/npm_token) npm ci
```
```bash
docker build --secret id=npm_token,src=./npm_token.txt -t monapp:1.0 .
```

### Durcir à l'exécution
```bash
docker run -d --name hardened \
  --read-only --tmpfs /tmp \
  --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --user 10001:10001 \
  -p 8080:8080 monapp:1.0
```
- `--read-only` : système de fichiers racine en lecture seule (l'application n'écrit que dans `/tmp` ou des volumes) ;
- `--cap-drop ALL` : retire toutes les *capabilities* Linux, à ne réajouter qu'au cas par cas ;
- `no-new-privileges` : empêche un processus d'obtenir plus de privilèges (via `setuid`, par exemple).

### Le socket Docker n'est pas un fichier anodin
Monter `/var/run/docker.sock` dans un conteneur lui donne le contrôle complet du démon Docker de l'hôte. Il peut alors lancer un conteneur privilégié qui monte `/` : c'est équivalent à **donner root sur l'hôte**.

### Exercice 8.1
Modifie ce Dockerfile pour que l'application ne tourne plus en root :
```dockerfile
FROM node:20-slim
WORKDIR /app
COPY . .
RUN npm ci --omit=dev
CMD ["node", "server.js"]
```

<details><summary>💡 Solution</summary>

```dockerfile
FROM node:20-slim
WORKDIR /app
COPY --chown=node:node . .
RUN npm ci --omit=dev
USER node
CMD ["node", "server.js"]
```
Les images officielles Node fournissent déjà un utilisateur non privilégié `node` ; il suffit de lui donner les fichiers et de basculer dessus avec `USER`.
</details>

### Exercice 8.2
Pourquoi passer un mot de passe via `ARG` ou `ENV` dans un Dockerfile est-il dangereux ?

<details><summary>💡 Solution</summary>

La valeur est enregistrée dans les métadonnées et l'historique de l'image : `docker history --no-trunc` et `docker inspect` la révèlent à quiconque peut récupérer l'image. Or une image est ensuite copiée, poussée dans des registres, partagée : le secret circule avec elle et ne peut plus être retiré.
</details>

### Exercice 8.3
Pourquoi monter le socket Docker dans un conteneur revient-il à donner root sur l'hôte ?

<details><summary>💡 Solution</summary>

Le socket permet de piloter le démon Docker, qui tourne en root sur l'hôte. Depuis le conteneur, on peut demander au démon de lancer un nouveau conteneur privilégié avec le système de fichiers de l'hôte monté : on obtient ainsi un accès root complet à l'hôte, en contournant toute l'isolation du conteneur d'origine.
</details>

# Partie 3 — Données, réseau et applications multi-conteneurs

## Module 9 — Volumes et persistance des données

### Le problème
Un conteneur écrit dans une fine couche d'écriture **éphémère** : quand il est supprimé, ses données disparaissent. Pour une base de données, des uploads ou des logs à conserver, il faut sortir les données du cycle de vie du conteneur.

### Trois mécanismes
| Mécanisme | Où sont les données | Usage typique |
|---|---|---|
| **Volume nommé** | géré par Docker (`/var/lib/docker/volumes`) | données applicatives persistantes (base de données) |
| **Bind mount** | un dossier précis de l'hôte | développement : monter son code source pour un rechargement à chaud |
| **tmpfs** | en mémoire vive uniquement | données temporaires ou sensibles qui ne doivent jamais toucher le disque |

```bash
docker volume create data
docker run -d --name db -v data:/var/lib/postgresql/data -e POSTGRES_PASSWORD=secret postgres:16
docker volume ls
docker volume inspect data
docker run --rm -v "$(pwd)":/work -w /work alpine ls          # bind mount du dossier courant
docker run --rm --tmpfs /tmp:rw,size=64m alpine df -h /tmp     # tmpfs limité à 64 Mo
```

### Sauvegarder un volume
```bash
docker run --rm -v data:/data -v "$(pwd)":/backup alpine \
  tar czf /backup/data.tgz -C /data .
```

### Piège fréquent : les permissions
Avec un bind mount, les fichiers gardent les **UID/GID de l'hôte**. Si le conteneur tourne avec un autre UID (bonne pratique du Module 8), il peut ne pas avoir le droit d'écrire dans le dossier monté.

### Exercice 9.1
Prouve la persistance : écris un fichier dans un volume, supprime le conteneur, puis retrouve le fichier avec un nouveau conteneur.

<details><summary>💡 Solution</summary>

```bash
docker volume create demo
docker run --rm -v demo:/data alpine sh -c 'echo persistant > /data/fichier.txt'
docker run --rm -v demo:/data alpine cat /data/fichier.txt      # affiche : persistant
```
Le premier conteneur a disparu (`--rm`), le volume et son contenu restent.
</details>

### Exercice 9.2
Choisis volume nommé, bind mount ou tmpfs pour : (a) une base de données en production, (b) ton code source pendant le développement, (c) des fichiers temporaires sensibles qui ne doivent jamais être écrits sur disque.

<details><summary>💡 Solution</summary>

(a) Volume nommé : géré par Docker, indépendant de l'arborescence de l'hôte. (b) Bind mount : les modifications de code sont visibles immédiatement dans le conteneur. (c) tmpfs : les données ne vivent qu'en mémoire et disparaissent à l'arrêt.
</details>

### Exercice 9.3
Sauvegarde un volume nommé dans une archive `tar.gz` du dossier courant.

<details><summary>💡 Solution</summary>

```bash
docker run --rm -v demo:/data -v "$(pwd)":/backup alpine \
  tar czf /backup/demo-backup.tgz -C /data .
ls -lh demo-backup.tgz
```
</details>

## Module 10 — Réseau Docker : bridge, réseaux personnalisés, ports publiés

### Les pilotes réseau
| Pilote | Comportement |
|---|---|
| `bridge` (défaut) | réseau privé virtuel sur l'hôte, avec NAT vers l'extérieur |
| `host` | le conteneur partage directement la pile réseau de l'hôte (pas d'isolation réseau) |
| `none` | aucune connectivité |
| `overlay` | réseau multi-hôtes (Swarm) — hors du périmètre de ce cours |

### Réseau par défaut vs réseau personnalisé
Le bridge par défaut (`docker0`, souvent `172.17.0.0/16`) **ne fournit pas de résolution DNS par nom** de conteneur. Un réseau **défini par l'utilisateur** l'offre : les conteneurs s'y joignent par leur nom, et sont isolés des autres réseaux.
```bash
docker network create backend
docker run -d --name db --network backend -e POSTGRES_PASSWORD=secret postgres:16
docker run -d --name api --network backend -e DB_HOST=db monapp:1.0
docker exec api getent hosts db        # résolution DNS interne : nom → IP du conteneur db
docker network inspect backend
```

### Publier un port = une règle DNAT
```bash
docker run -d -p 8080:80 nginx:1.27                  # écoute sur TOUTES les interfaces de l'hôte
docker run -d -p 127.0.0.1:8080:80 nginx:1.27         # écoute uniquement en local
sudo iptables -t nat -L DOCKER -n                      # les règles DNAT créées par Docker
```
C'est le **DNAT** vu dans *Networking and Cloud Fundamentals* (Module 10). Et `EXPOSE` dans un Dockerfile **ne publie rien**.

> ⚠️ Docker écrit directement dans iptables : un port publié peut **contourner les règles d'un pare-feu comme `ufw`**. Pour limiter l'exposition, publie sur `127.0.0.1` ou sur une interface précise.

### Segmenter avec plusieurs réseaux
Un conteneur peut appartenir à plusieurs réseaux : c'est la version Docker de la DMZ et de la micro-segmentation (*Networking and Cloud*, Modules 10 et 5).

### Exercice 10.1
Crée un réseau, lance-y deux conteneurs et vérifie qu'ils se joignent par leur nom.

<details><summary>💡 Solution</summary>

```bash
docker network create lab
docker run -d --name a --network lab alpine sleep 3600
docker run -d --name b --network lab alpine sleep 3600
docker exec a ping -c 2 b
```
</details>

### Exercice 10.2
Quelle différence entre `-p 8080:80` et `-p 127.0.0.1:8080:80` ? Quel mécanisme réseau est utilisé ?

<details><summary>💡 Solution</summary>

La première forme rend le service joignable depuis toutes les interfaces de l'hôte, donc depuis le réseau ; la seconde le limite à la machine locale. Dans les deux cas, Docker installe une règle **DNAT** (table `nat`, chaîne `DOCKER` d'iptables) qui redirige le trafic entrant vers l'IP du conteneur.
</details>

### Exercice 10.3
Conçois un schéma proxy / API / base de données avec deux réseaux, tel que la base ne soit pas joignable depuis le proxy.

<details><summary>💡 Solution</summary>

Réseaux `frontend` et `backend`. Le proxy est **seulement** sur `frontend`, la base **seulement** sur `backend`, et l'API sur **les deux**. Le proxy ne peut atteindre que l'API ; seule l'API atteint la base — un compromis du proxy n'ouvre pas directement l'accès à la base.
</details>

## Module 11 — Docker Compose : applications multi-conteneurs

### Le principe
Compose décrit une application entière (services, réseaux, volumes) dans un fichier `compose.yaml` versionnable, et la pilote en une commande.
```bash
docker compose up -d          # crée et démarre tout
docker compose ps
docker compose logs -f web
docker compose exec db psql -U app
docker compose build           # reconstruit les images
docker compose config           # affiche le fichier final, variables résolues
docker compose down             # arrête et supprime conteneurs et réseaux
docker compose down -v           # supprime AUSSI les volumes (données perdues)
```

### Un exemple complet
```yaml
services:
  web:
    build: .
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgres://app:${DB_PASSWORD}@db:5432/app
      REDIS_HOST: cache
    depends_on:
      db:
        condition: service_healthy
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: app
    volumes:
      - dbdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      timeout: 3s
      retries: 10
  cache:
    image: redis:7
volumes:
  dbdata:
```
Le fichier `.env` voisin fournit `DB_PASSWORD=...` — **à ne jamais commiter** (ajoute-le au `.gitignore`).

### Ce que Compose fait pour toi
- crée un **réseau par défaut** où chaque service est joignable par son **nom** (`db`, `cache`) ;
- nomme les conteneurs et volumes avec un préfixe de projet ;
- `depends_on` **ordonne le démarrage**, mais sans `condition: service_healthy` il n'attend pas que la base soit *prête*.

### La limite : un seul hôte
Compose gère une seule machine. Pas de reprise automatique sur un autre serveur, pas de mise à l'échelle multi-nœuds : c'est précisément le problème que Kubernetes résout (Module 13).

### Exercice 11.1
Écris un `compose.yaml` pour une application (construite depuis le dossier courant) qui utilise Redis.

<details><summary>💡 Solution</summary>

```yaml
services:
  app:
    build: .
    ports:
      - "8000:8000"
    environment:
      REDIS_HOST: cache
    depends_on:
      - cache
  cache:
    image: redis:7
```
</details>

### Exercice 11.2
Pourquoi `depends_on` seul ne garantit-il pas que la base de données est prête à recevoir des connexions ?

<details><summary>💡 Solution</summary>

`depends_on` ne contrôle que l'**ordre de démarrage** des conteneurs : le conteneur de la base est *démarré*, pas forcément *prêt* (initialisation, recovery). Pour attendre la disponibilité réelle, il faut un `healthcheck` sur la base et `condition: service_healthy`, ou une logique de nouvelles tentatives côté application.
</details>

### Exercice 11.3
Que se passe-t-il pour tes données avec `docker compose down`, puis avec `docker compose down -v` ?

<details><summary>💡 Solution</summary>

`down` supprime conteneurs et réseaux mais **conserve les volumes nommés** : les données survivent. `down -v` supprime aussi les volumes : les données sont définitivement perdues.
</details>

## Module 12 — Configuration et secrets : les principes 12-factor

### Les principes qui comptent pour les conteneurs
La méthode **12-factor app** résume les bonnes pratiques d'une application cloud native. Les plus concrets :
- **Config dans l'environnement**, jamais dans l'image : la même image sert en dev, staging et prod ;
- **Processus sans état** : tout ce qui doit survivre va dans un service externe ou un volume ;
- **Logs sur `stdout`/`stderr`** : le runtime les collecte, la plateforme les achemine ;
- **Jetables** : démarrage rapide, arrêt propre sur SIGTERM ;
- **Parité dev/prod** : mêmes images, mêmes dépendances.

### Injecter de la configuration
```bash
docker run -e LOG_LEVEL=debug monapp:1.0
docker run --env-file app.env monapp:1.0
```
```yaml
services:
  web:
    env_file: app.env
    environment:
      LOG_LEVEL: info
```

### Les logs : stdout, pas de fichiers
```bash
docker logs -f web
docker run --log-opt max-size=10m --log-opt max-file=3 monapp:1.0     # rotation
```
Écrire dans un fichier *dans* le conteneur le perd à la suppression, empêche le mode `--read-only` et complique l'agrégation.

### Secrets : les variables d'environnement ont des limites
Une variable d'environnement est visible via `docker inspect` et `/proc/<pid>/environ` : acceptable en développement, insuffisant en production. Préfère des **secrets montés comme fichiers** (Compose `secrets:`, Secrets Kubernetes au Module 19) ou un gestionnaire externe comme Vault ou Secrets Manager (*Networking and Cloud Intermédiaire*, Module 11).
```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
secrets:
  db_password:
    file: ./db_password.txt
```
Le secret apparaît dans le conteneur sous `/run/secrets/db_password`.

### Exercice 12.1
Lance un conteneur avec `--env-file` et vérifie que les variables sont bien présentes.

<details><summary>💡 Solution</summary>

```bash
printf 'APP_ENV=dev\nLOG_LEVEL=debug\n' > app.env
docker run --rm --env-file app.env alpine env | grep -E 'APP_ENV|LOG_LEVEL'
```
</details>

### Exercice 12.2
Pourquoi une application conteneurisée doit-elle écrire ses logs sur `stdout` plutôt que dans un fichier local ?

<details><summary>💡 Solution</summary>

Le runtime capture `stdout`/`stderr` et les met à disposition (`docker logs`, pilotes de logs, agrégateurs) sans que l'application ne connaisse l'infrastructure. Un fichier interne disparaît avec le conteneur, grossit sans rotation, empêche un système de fichiers en lecture seule et rend la collecte centralisée bien plus difficile.
</details>

### Exercice 12.3
Fournis le mot de passe de PostgreSQL via un secret Compose plutôt qu'une variable en clair.

<details><summary>💡 Solution</summary>

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
secrets:
  db_password:
    file: ./db_password.txt
```
L'image officielle PostgreSQL lit la valeur depuis le fichier indiqué par `POSTGRES_PASSWORD_FILE`.
</details>

# Partie 4 — Premiers pas avec Kubernetes

## Module 13 — Pourquoi Kubernetes ?

### Les limites de Docker et Compose seuls
Compose pilote **une machine**. Dès qu'on vise la production, les manques apparaissent :
- si l'hôte tombe, **tout** tombe ; rien ne relance le service ailleurs ;
- pas de placement automatique des conteneurs sur plusieurs serveurs ;
- mise à l'échelle manuelle, mises à jour sans interruption à bricoler soi-même ;
- pas d'API unifiée décrivant l'état voulu de tout un parc.

### Ce que Kubernetes apporte
| Capacité | Ce que ça signifie |
|---|---|
| **Modèle déclaratif** | tu décris l'état **désiré** (« 3 réplicas de cette image »), Kubernetes fait converger la réalité vers lui |
| **Scheduling** | placement des Pods sur les nœuds selon les ressources disponibles |
| **Auto-réparation** | un Pod ou un nœud défaillant est remplacé automatiquement |
| **Mise à l'échelle** | changer le nombre de réplicas (manuellement, ou automatiquement — palier 2) |
| **Mises à jour progressives** | rolling update et retour arrière intégrés |
| **Découverte de services** | nom DNS stable et répartition de charge interne |
| **Config et secrets** | injection propre sans modifier l'image |

### Le cœur du modèle : la boucle de réconciliation
Des **controllers** comparent en permanence l'**état désiré** (ce que tu as déclaré) à l'**état observé** (ce qui tourne) et agissent pour réduire l'écart. Exemple : tu déclares 3 réplicas ; un Pod meurt, il n'en reste que 2 ; le controller le constate et en crée un nouveau, sans qu'aucun humain n'intervienne.

### Quand Kubernetes n'est PAS le bon choix
Une petite application, une équipe réduite, une seule VM suffisante : Compose (ou un service de conteneurs managé comme Cloud Run ou ECS) est bien plus simple. Kubernetes a un **coût opérationnel réel** ; il se justifie quand la complexité qu'il résout existe vraiment. Alternatives : Nomad, ECS, services serverless de conteneurs.

### Exercice 13.1
Cite trois limites de Compose sur un seul serveur que Kubernetes résout.

<details><summary>💡 Solution</summary>

Par exemple : (1) une panne de l'hôte arrête tout, alors que Kubernetes replanifie les Pods sur d'autres nœuds ; (2) la mise à l'échelle et le placement sur plusieurs machines sont manuels ; (3) les mises à jour progressives sans interruption ne sont pas intégrées.
</details>

### Exercice 13.2
Explique « état désiré vs état observé » avec un exemple concret.

<details><summary>💡 Solution</summary>

L'état désiré est ce que tu as déclaré : 3 réplicas d'une application. L'état observé est ce qui tourne réellement. Si un Pod plante, l'état observé passe à 2 réplicas ; le controller du Deployment détecte l'écart et crée un Pod de remplacement. Cette boucle tourne en continu.
</details>

### Exercice 13.3
Donne un cas où Kubernetes est un mauvais choix, et une alternative.

<details><summary>💡 Solution</summary>

Une application interne à un seul conteneur, sur une seule VM, gérée par une personne : Kubernetes ajouterait une complexité et un coût d'exploitation disproportionnés. Docker Compose, ou un service managé de conteneurs (Cloud Run, ECS), suffit.
</details>

## Module 14 — Architecture de Kubernetes

### Un cluster = un plan de contrôle + des nœuds
```
┌──────────────── PLAN DE CONTRÔLE ────────────────┐      ┌────────── NŒUD WORKER ──────────┐
│  kube-apiserver  ←→  etcd                         │      │  kubelet                        │
│  kube-scheduler                                   │ ───► │  kube-proxy                     │
│  kube-controller-manager                          │      │  runtime (containerd / CRI-O)   │
│  cloud-controller-manager (si cloud)              │      │  [Pod] [Pod] [Pod]              │
└───────────────────────────────────────────────────┘      └─────────────────────────────────┘
```

### Le plan de contrôle
| Composant | Rôle |
|---|---|
| **kube-apiserver** | point d'entrée REST du cluster ; authentifie, valide, et est le **seul** à parler à etcd |
| **etcd** | base clé-valeur cohérente (consensus Raft) qui stocke tout l'état du cluster |
| **kube-scheduler** | choisit sur quel nœud lancer chaque Pod non encore placé |
| **kube-controller-manager** | héberge les boucles de réconciliation (Deployments, nœuds, endpoints...) |
| **cloud-controller-manager** | intégration avec le cloud : load balancers, volumes, nœuds |

### Sur chaque nœud
| Composant | Rôle |
|---|---|
| **kubelet** | agent du nœud : s'assure que les conteneurs des Pods assignés tournent et sont sains |
| **kube-proxy** | programme les règles réseau (iptables ou IPVS) qui implémentent les Services |
| **Container runtime** | lance réellement les conteneurs (containerd, CRI-O) via l'interface CRI |

### Le trajet d'un `kubectl apply` de Deployment
```
1. kubectl → API server : authentification, validation, écriture dans etcd
2. Le controller du Deployment crée un ReplicaSet
3. Le controller du ReplicaSet crée les objets Pod
4. Le scheduler assigne chaque Pod à un nœud
5. Le kubelet du nœud demande au runtime de démarrer les conteneurs
6. Le kubelet remonte l'état à l'API server
```

### Tout est un objet déclaratif
Chaque ressource s'écrit en YAML avec la même ossature :
```yaml
apiVersion: apps/v1     # famille et version de l'API
kind: Deployment         # type d'objet
metadata:                # nom, labels, namespace
  name: web
spec:                    # l'état DÉSIRÉ, écrit par toi
  replicas: 3
# status:                # l'état OBSERVÉ, écrit par le cluster
```

### Exercice 14.1
Associe chaque composant à son rôle : `kubelet`, `etcd`, `kube-scheduler`, `kube-proxy`, `kube-apiserver`.

<details><summary>💡 Solution</summary>

`kube-apiserver` : point d'entrée et gardien de l'état. `etcd` : stockage de l'état du cluster. `kube-scheduler` : choix du nœud pour chaque Pod. `kubelet` : agent qui fait tourner les Pods sur un nœud. `kube-proxy` : règles réseau des Services sur chaque nœud.
</details>

### Exercice 14.2
Décris le trajet d'un `kubectl apply` de Deployment jusqu'au démarrage des conteneurs.

<details><summary>💡 Solution</summary>

`kubectl` envoie le manifeste à l'API server, qui l'authentifie, le valide et le stocke dans etcd. Le controller du Deployment crée un ReplicaSet, dont le controller crée les Pods. Le scheduler assigne chaque Pod à un nœud, le kubelet de ce nœud demande au runtime de démarrer les conteneurs et remonte l'état à l'API server.
</details>

### Exercice 14.3
Pourquoi seul l'API server parle-t-il à etcd, et que se passe-t-il si etcd est perdu sans sauvegarde ?

<details><summary>💡 Solution</summary>

</details>

## Module 16 — Pods

### L'unité de base
Un **Pod** est la plus petite unité déployable : un ou plusieurs conteneurs qui partagent **la même IP**, le même réseau (ils se parlent via `localhost`) et éventuellement des volumes. Un Pod est **éphémère** : s'il est supprimé, il n'est pas ressuscité tout seul, et son remplaçant aura une autre IP.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
  labels:
    app: web
spec:
  containers:
    - name: nginx
      image: nginx:1.27
      ports:
        - containerPort: 80
      resources:
        requests:
          cpu: "100m"
          memory: "64Mi"
        limits:
          memory: "128Mi"
      readinessProbe:
        httpGet:
          path: /
          port: 80
        initialDelaySeconds: 3
        periodSeconds: 5
```
```bash
kubectl apply -f pod.yaml
kubectl get pod web -o wide
kubectl describe pod web
```

### `requests` vs `limits`
- **`requests`** : ce que le scheduler **réserve** pour placer le Pod sur un nœud.
- **`limits`** : plafond appliqué par les cgroups (rappel *Linux Expert*, Module 2) ; dépasser la mémoire déclenche un `OOMKilled`.
Le palier 2 y revient en détail.

### Les probes en un coup d'œil
- **`readinessProbe`** : le Pod est-il *prêt à recevoir du trafic* ? Sinon, il est retiré des Services.
- **`livenessProbe`** : le conteneur est-il *encore vivant* ? Sinon, il est redémarré.

### Labels et selectors
Les **labels** (`app: web`) sont des étiquettes clé-valeur ; les **selectors** s'en servent pour désigner des ensembles d'objets. C'est ainsi qu'un Service retrouve ses Pods.

### Conteneurs multiples
Un Pod peut contenir un conteneur principal et des **sidecars** (collecte de logs, proxy), ou des **`initContainers`** qui s'exécutent et se terminent *avant* le démarrage de l'application (attendre une dépendance, préparer des fichiers).

### États et erreurs courantes
| État | Signification |
|---|---|
| `Pending` | accepté mais pas encore placé ou pas encore démarré |
| `Running` | au moins un conteneur tourne |
| `CrashLoopBackOff` | le conteneur plante en boucle, Kubernetes espace les redémarrages |
| `ImagePullBackOff` | l'image est introuvable ou inaccessible |
| `OOMKilled` | tué pour dépassement de la limite mémoire |

### Diagnostic
```bash
kubectl describe pod web            # section Events : la cause est presque toujours là
kubectl logs web
kubectl logs web --previous          # logs du conteneur AVANT son dernier crash
kubectl get events --sort-by=.lastTimestamp
```

### Exercice 16.1
Écris un manifeste de Pod nginx avec un label, des requests et une limite mémoire, applique-le, puis supprime-le.

<details><summary>💡 Solution</summary>

Utilise le manifeste ci-dessus, puis :
```bash
kubectl apply -f pod.yaml
kubectl get pod web -o wide
kubectl delete pod web
kubectl get pods      # rien ne le recrée : un Pod « nu » n'est pas auto-réparé
```
</details>

### Exercice 16.2
Un Pod est en `ImagePullBackOff`. Comment diagnostiques-tu ?

<details><summary>💡 Solution</summary>

`kubectl describe pod <nom>` et lecture de la section **Events** : elle indique l'erreur exacte. Causes usuelles : faute de frappe dans le nom ou le tag de l'image, image inexistante, registre privé sans identifiants (`imagePullSecrets`), ou registre injoignable depuis le nœud.
</details>

### Exercice 16.3
Pourquoi deux conteneurs d'un même Pod peuvent-ils communiquer via `localhost` ?

<details><summary>💡 Solution</summary>

Les conteneurs d'un Pod partagent le même **namespace réseau** : ils ont la même adresse IP et la même pile réseau, donc un port ouvert par l'un est accessible par l'autre sur `localhost`.

## Module 17 — Deployments et ReplicaSets

### La hiérarchie
```
Deployment  →  ReplicaSet  →  Pods
(stratégie de mise à jour)   (maintient N réplicas)   (les conteneurs)
```
Tu ne crées presque jamais de Pod « nu » : tu déclares un **Deployment**, qui gère un **ReplicaSet**, qui maintient le bon nombre de Pods et les recrée quand l'un disparaît.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 5
```
> Le `selector` doit correspondre aux labels du `template` — sinon le Deployment est rejeté. Le selector est ensuite **immuable**.

### Piloter un Deployment
```bash
kubectl apply -f deployment.yaml
kubectl get deploy,rs,pods
kubectl scale deployment web --replicas=5
kubectl set image deployment/web nginx=nginx:1.27-alpine      # déclenche une mise à jour progressive
kubectl rollout status deployment/web
kubectl rollout history deployment/web
kubectl rollout undo deployment/web                             # retour à la version précédente
```

### Comment fonctionne un rolling update
Un **nouveau ReplicaSet** est créé pour la nouvelle version ; ses Pods montent progressivement pendant que ceux de l'ancien ReplicaSet descendent. La `readinessProbe` décide quand un nouveau Pod est *prêt* : sans elle, Kubernetes croit le Pod prêt dès qu'il démarre et peut basculer le trafic trop tôt.
- **`maxSurge`** : combien de Pods **au-dessus** du nombre désiré pendant la transition ;
- **`maxUnavailable`** : combien de Pods **en dessous** peuvent être indisponibles.

Le rolling update est la stratégie par défaut. Le blue-green et le canary (*Networking and Cloud Intermédiaire*, Module 18) demandent des mécanismes supplémentaires vus aux paliers 2 et 3.

### Exercice 17.1
Crée un Deployment de 3 réplicas nginx, supprime un Pod et observe ce qui se passe.

<details><summary>💡 Solution</summary>

```bash
kubectl apply -f deployment.yaml
kubectl get pods -l app=web
kubectl delete pod <nom-d-un-pod>
kubectl get pods -l app=web -w     # un nouveau Pod apparaît presque immédiatement
```
C'est l'auto-réparation : le ReplicaSet constate 2 Pods au lieu de 3 et en crée un.
</details>

### Exercice 17.2
Mets à jour l'image, observe le rollout, puis fais un retour arrière.

<details><summary>💡 Solution</summary>

```bash
kubectl set image deployment/web nginx=nginx:1.27-alpine
kubectl rollout status deployment/web
kubectl rollout history deployment/web
kubectl rollout undo deployment/web
kubectl get rs      # l'ancien ReplicaSet est de nouveau actif
```
</details>

### Exercice 17.3
Explique `maxSurge: 1` et `maxUnavailable: 0` pour un Deployment de 3 réplicas.

<details><summary>💡 Solution</summary>

Il y aura **au plus 4 Pods** à un instant donné (3 + 1 de surplus) et **au moins 3 Pods disponibles** en permanence. Kubernetes crée 1 nouveau Pod, attend qu'il soit prêt, supprime alors 1 ancien Pod, et répète : aucune perte de capacité pendant la mise à jour.
</details>

## Module 18 — Services et découverte de services

### Le problème
L'IP d'un Pod est **éphémère** : elle change à chaque recréation. Un **Service** fournit une **IP virtuelle stable**, un **nom DNS** et une **répartition de charge** vers les Pods choisis par leurs labels.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
  type: ClusterIP
```

### Les types de Service
| Type | Accessibilité | Usage |
|---|---|---|
| **ClusterIP** (défaut) | interne au cluster seulement | communication entre services |
| **NodePort** | un port (30000-32767) ouvert sur **chaque nœud** | tests, exposition basique |
| **LoadBalancer** | crée un load balancer du cloud (*Networking and Cloud*, VPC et load balancing) | exposition publique sur un cloud |
| **ExternalName** | alias DNS (CNAME) vers un nom externe | pointer vers un service hors cluster |

Sur `kind`, `LoadBalancer` n'obtient pas d'IP externe sans composant additionnel (MetalLB) : utilise `port-forward` ou `NodePort` pour tes tests.

### DNS interne
Chaque Service reçoit un nom géré par **CoreDNS** :
```
web                            # depuis le même namespace
web.prod                        # depuis un autre namespace
web.prod.svc.cluster.local       # nom complet
```

### Endpoints : seuls les Pods *prêts* reçoivent du trafic
Le Service tient à jour la liste des Pods qui correspondent au selector **et** sont `Ready`. Un Pod dont la `readinessProbe` échoue est retiré de cette liste : il ne reçoit plus de requêtes.
```bash
kubectl get endpoints web
kubectl get endpointslices
```

### Sous le capot : `kube-proxy` et le NAT
`kube-proxy` programme sur chaque nœud des règles iptables (ou IPVS) qui traduisent l'IP virtuelle du Service vers l'IP d'un Pod : c'est du **DNAT** (*Networking and Cloud Fundamentals*, Module 10), avec répartition entre les Pods.

### Tester
```bash
kubectl port-forward svc/web 8080:80         # accès depuis ton poste
kubectl run tmp --rm -it --image=busybox:1.36 --restart=Never -- wget -qO- http://web
```

### Exercice 18.1
Expose ton Deployment `web` avec un Service ClusterIP et teste-le depuis un Pod temporaire.

<details><summary>💡 Solution</summary>

```bash
kubectl expose deployment web --port=80 --target-port=80
kubectl run tmp --rm -it --image=busybox:1.36 --restart=Never -- wget -qO- http://web
```
La page d'accueil de nginx s'affiche : le nom `web` est résolu par CoreDNS et la requête est répartie vers un des Pods.
</details>

### Exercice 18.2
Pourquoi un Pod dont la readiness échoue n'apparaît-il pas dans les endpoints, et quel est l'effet sur le trafic ?

<details><summary>💡 Solution</summary>

Le Service ne liste comme endpoints que les Pods `Ready`. Un Pod non prêt (encore en démarrage, ou défaillant) est retiré : il ne reçoit plus de trafic, et les utilisateurs ne sont pas dirigés vers une instance qui ne peut pas répondre.
</details>

### Exercice 18.3
Compare ClusterIP, NodePort et LoadBalancer, avec un cas d'usage de chacun.

<details><summary>💡 Solution</summary>

ClusterIP : appels entre services internes (une API qui parle à sa base). NodePort : exposition simple pour tester un service depuis l'extérieur, sans load balancer. LoadBalancer : exposer un service au public en s'appuyant sur le load balancer managé du cloud.
</details>

## Module 19 — ConfigMaps, Secrets et Namespaces

### ConfigMap : la configuration non sensible
```bash
kubectl create configmap app-config \
  --from-literal=LOG_LEVEL=info \
  --from-literal=FEATURE_X=true
```
Elle se consomme en variables d'environnement ou en fichiers montés :
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app
spec:
  containers:
    - name: app
      image: monapp:1.0
      envFrom:
        - configMapRef:
            name: app-config
      env:
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-secret
              key: password
      volumeMounts:
        - name: conf
          mountPath: /etc/app
  volumes:
    - name: conf
      configMap:
        name: app-config
```
Un ConfigMap monté en **volume** se met à jour (avec un léger délai) ; les variables d'environnement, elles, ne changent qu'au **redémarrage** du Pod.

### Secret : sensible… mais pas magiquement protégé
```bash
kubectl create secret generic db-secret --from-literal=password='S3cr3t!'
kubectl get secret db-secret -o jsonpath='{.data.password}' | base64 -d
```
> ⚠️ Un Secret est **encodé en base64**, **pas chiffré**. N'importe qui ayant le droit de le lire (ou d'accéder à etcd) le décode en une commande. La vraie protection passe par le **chiffrement au repos d'etcd**, un **RBAC strict** et, idéalement, un gestionnaire externe (*Networking and Cloud Intermédiaire*, Module 11) — approfondis au palier 2.

Et ne commite **jamais** un Secret en clair dans Git : des outils comme SOPS ou Sealed Secrets existent pour cela (palier 3, GitOps).

### Namespaces : découper le cluster
Un **namespace** isole logiquement des ressources : espace de noms distinct, base de quotas, de permissions RBAC et de politiques réseau (palier 2).
| Namespace | Rôle |
|---|---|
| `default` | là où atterrit tout ce qui n'a pas de namespace |
| `kube-system` | composants système de Kubernetes |
| `kube-public`, `kube-node-lease` | usages internes |
```bash
kubectl create namespace dev
kubectl get pods -n dev
kubectl get pods -A
```
Certains objets sont **globaux** (nœuds, namespaces eux-mêmes) et n'appartiennent à aucun namespace.

### Exercice 19.1
Crée un ConfigMap et injecte-le en variables d'environnement dans un Pod, puis vérifie depuis le conteneur.

<details><summary>💡 Solution</summary>

```bash
kubectl create configmap app-config --from-literal=LOG_LEVEL=debug
```
Pod avec `envFrom: - configMapRef: { name: app-config }`, puis :
```bash
kubectl exec app -- env | grep LOG_LEVEL      # LOG_LEVEL=debug
```
</details>

### Exercice 19.2
Décode un Secret et explique pourquoi base64 n'est pas du chiffrement.

<details><summary>💡 Solution</summary>

```bash
kubectl get secret db-secret -o jsonpath='{.data.password}' | base64 -d
```
Base64 est un **encodage réversible** sans clé : il rend des octets affichables, il ne protège rien. Quiconque peut lire le Secret ou accéder à etcd retrouve la valeur immédiatement.
</details>

### Exercice 19.3
Crée deux namespaces `dev` et `prod`, déploie la même application dans chacun, et explique comment la joindre depuis l'autre namespace.

<details><summary>💡 Solution</summary>


</details>

# Partie 5 — Synthèse

## Module 20 — Projet de synthèse : du Dockerfile au cluster

### Le brief
Conteneurise et déploie une application trois tiers (une API, PostgreSQL, Redis) : d'abord avec Compose, puis sur Kubernetes (`kind`).

1. Écris un **Dockerfile multi-stage** pour l'API : utilisateur non-root, `HEALTHCHECK`, ordre de couches optimisé pour le cache.
2. Écris un **`compose.yaml`** : API + PostgreSQL + Redis, volume nommé pour la base, mot de passe fourni par **secret fichier**, `healthcheck` + `depends_on: service_healthy`.
3. **Scanne** l'image avec Trivy ; corrige les vulnérabilités HIGH/CRITICAL corrigibles (image de base plus récente ou plus minimale).
4. **Pousse** l'image dans un registre (local `localhost:5000`, ou GHCR) avec un tag de version précis, et relève son **digest**.
5. Sur Kubernetes : un namespace `demo`, un **ConfigMap**, un **Secret**, un **Deployment** de l'API (3 réplicas, `readinessProbe`, `requests`/`limits`, `RollingUpdate` avec `maxUnavailable: 0`) et un **Service ClusterIP**. Redis et PostgreSQL en Deployments simples, **sans persistance** (le stockage durable — PV, PVC, StatefulSet — arrive au palier 2).
6. **Démontre** : l'auto-réparation (supprime un Pod), un rolling update puis un `rollout undo`, l'accès à l'API par `port-forward`, et la résolution DNS interne depuis un Pod temporaire.

### Pourquoi ce projet
Il recombine tout le palier : images (M5-M8), données et réseau (M9-M10), Compose (M11), configuration (M12), puis les objets Kubernetes de base (M16-M19). Si tu le réalises sans rouvrir les modules, tu as le niveau du palier 1.

```yaml
                secretKeyRef: { name: db-secret, key: password }
          readinessProbe:
            httpGet: { path: /health, port: 8000 }
            periodSeconds: 5
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits: { memory: 256Mi }
```

## Cheat-sheet — Docker

| Catégorie | Commandes clés |
|---|---|
| Exécuter | `docker run -d --name X -p 8080:80 IMG`, `--rm`, `-it`, `-e`, `--restart unless-stopped` |

| Construire | `docker build -t nom:tag .`, `docker history`, multi-stage (`AS builder`, `COPY --from=`) |

| Sécuriser | `USER` non-root, `--read-only`, `--cap-drop ALL`, `trivy image`, pas de secret dans `ARG`/`ENV` |
| Données | volumes nommés, bind mounts (dev), `--tmpfs` |
| Réseau | réseaux personnalisés (DNS par nom), `-p 127.0.0.1:...`, DNAT via iptables |
| Compose | `docker compose up -d`, `down`, `down -v`, `healthcheck` + `service_healthy` |

## Glossaire

| Terme | Définition |
|---|---|
| **Image / Conteneur** | modèle en lecture seule / instance en exécution de ce modèle |
| **OCI** | standards ouverts d'image, de runtime et de distribution |
| **runc / containerd** | création réelle du conteneur / gestion de son cycle de vie et des images |
| **Couche (layer)** | fragment immuable d'image ; le cache de build repose dessus |
| **Multi-stage build** | construction en plusieurs étapes pour ne livrer que l'essentiel |
| **Digest** | identifiant immuable d'une image, basé sur son contenu |
| **Volume / bind mount / tmpfs** | stockage persistant géré / dossier de l'hôte / mémoire volatile |
| **Pod** | plus petite unité déployable, conteneurs partageant IP et réseau |
| **ReplicaSet / Deployment** | maintient N Pods / ajoute mises à jour progressives et rollback |
| **Service** | IP virtuelle stable, nom DNS et répartition de charge vers des Pods |
| **Boucle de réconciliation** | comparaison continue de l'état désiré à l'état observé |
| **Namespace** | découpage logique d'un cluster (noms, quotas, permissions) |
| **kubelet / kube-proxy** | agent du nœud / règles réseau des Services |

## Et après ? Le palier 2

Tu sais maintenant construire, sécuriser et distribuer des images, puis faire tourner une application sur Kubernetes. Il manque tout ce qui sépare un exercice d'une **production** : des applications qui **gardent leurs données** (PV, PVC, StatefulSets), qui sont **exposées proprement** (Ingress, TLS), qui **encaissent la charge** (probes, ressources, HPA), qui sont **cloisonnées et sécurisées** (RBAC, NetworkPolicy, quotas), et qu'on sait **empaqueter, observer et dépanner** (Helm, Kustomize, Prometheus, méthodologie de diagnostic). C'est le **palier 2 — Intermédiaire**.
