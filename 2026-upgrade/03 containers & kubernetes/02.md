# Partie 1 — Fiabilité des workloads

## Module 1 — Probes : readiness, liveness, startup

### Trois questions différentes
| Probe | Question posée | Si elle échoue |
|---|---|---|
| **readiness** | « Puis-je recevoir du trafic ? » | le Pod est **retiré des endpoints** du Service, sans être redémarré |
| **liveness** | « Suis-je encore vivant, ou bloqué ? » | le conteneur est **redémarré** |
| **startup** | « Ai-je fini de démarrer ? » | tant qu'elle n'a pas réussi, liveness et readiness sont suspendues |

Les confondre est l'erreur classique : une liveness trop agressive **redémarre** une application simplement lente, ce qui aggrave la surcharge au lieu de la résoudre.

### Types de vérification
```yaml
containers:
  - name: api
    image: monapp:1.0.0
    startupProbe:
      httpGet: { path: /health, port: 8000 }
      failureThreshold: 30          # jusqu'à 30 × 5 s = 150 s pour démarrer
      periodSeconds: 5
    readinessProbe:
      httpGet: { path: /ready, port: 8000 }
      periodSeconds: 5
      failureThreshold: 3
    livenessProbe:
      httpGet: { path: /health, port: 8000 }
      periodSeconds: 10
      timeoutSeconds: 2
      failureThreshold: 3
```
Autres mécanismes : `tcpSocket` (le port accepte-t-il une connexion ?), `exec` (une commande retourne-t-elle 0 ?), `grpc`.

### Bonnes pratiques
- La **liveness** ne doit vérifier que l'état **interne** du processus, **jamais** une dépendance externe (base de données) : si la base tombe, redémarrer toute la flotte d'API n'arrange rien.
- La **readiness** peut refléter les dépendances nécessaires pour servir correctement.
- Un endpoint `/health` (vivant) distinct de `/ready` (prêt à servir).
- Une **startupProbe** pour les applications lentes à démarrer, plutôt qu'un `initialDelaySeconds` énorme sur la liveness.

### Exercice 1.1
Écris les probes d'une application HTTP sur le port 8080 : `/healthz` pour la liveness, `/ready` pour la readiness.

<details><summary>💡 Solution</summary>

```yaml
readinessProbe:
  httpGet: { path: /ready, port: 8080 }
  periodSeconds: 5
livenessProbe:
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3
```
</details>

### Exercice 1.2
Pourquoi une liveness qui interroge la base de données est-elle dangereuse ?

<details><summary>💡 Solution</summary>

Si la base tombe, **toutes** les instances échouent leur liveness et sont redémarrées en boucle, alors que le redémarrage ne règle rien : l'application ne peut plus se reconnecter tant que la base est absente. On ajoute de l'instabilité à une panne existante. La dépendance externe relève de la readiness (retirer du trafic), pas de la liveness (redémarrer).
</details>

### Exercice 1.3
Une application met 2 minutes à démarrer. Quelle probe utiliser, et pourquoi pas un gros `initialDelaySeconds` ?

<details><summary>💡 Solution</summary>

Une **startupProbe** avec un `failureThreshold` et une `periodSeconds` couvrant ces 2 minutes (ex : 30 × 5 s). Un grand `initialDelaySeconds` sur la liveness retarde aussi la détection d'un blocage **après** le démarrage ; la startupProbe laisse le temps de démarrer tout en gardant une liveness réactive ensuite.
</details>

## Module 2 — Requests, limits et classes de QoS

### Deux rôles distincts
- **`requests`** : ce que le scheduler **réserve** sur un nœud. Un Pod n'est placé que là où la somme des requests tient.
- **`limits`** : le **plafond** appliqué à l'exécution par les cgroups (rappel *Linux Expert*, Module 2).

```yaml
resources:
  requests: { cpu: 250m, memory: 256Mi }
  limits:   { cpu: 500m, memory: 512Mi }
```
`250m` = 250 millicores = un quart de cœur.

### CPU et mémoire ne se comportent pas pareil
| Ressource | Dépassement de la limite |
|---|---|
| **CPU** (compressible) | le conteneur est **ralenti** (*throttling*), jamais tué |
| **Mémoire** (non compressible) | le conteneur est **tué** (`OOMKilled`, code 137) |

Le throttling CPU peut dégrader fortement la latence même quand le nœud a du CPU libre : beaucoup d'équipes ne posent pas de limite CPU (seulement une request) et gardent une limite mémoire.

### Les classes de QoS
Kubernetes en déduit une classe, qui décide **qui est évincé en premier** quand un nœud manque de mémoire :
| Classe | Condition | Priorité d'éviction |
|---|---|---|
| **Guaranteed** | requests = limits, pour CPU **et** mémoire, sur tous les conteneurs | évincé en dernier |
| **Burstable** | au moins une request, sans être Guaranteed | intermédiaire |
| **BestEffort** | aucune request ni limit | évincé en premier |
```bash
kubectl get pod web -o jsonpath='{.status.qosClass}'
kubectl describe pod web | grep -A3 "Last State"       # Reason: OOMKilled, Exit Code: 137
kubectl top pod                                          # nécessite metrics-server (Module 18)
```

### Dimensionner : partir de la mesure
Des requests trop basses entassent trop de Pods sur un nœud (instabilité) ; trop hautes, elles gaspillent (FinOps, *Networking and Cloud*). On mesure la consommation réelle (`kubectl top`, Prometheus) puis on ajuste.

### Exercice 2.1
Quelle classe de QoS pour un Pod dont le conteneur a `requests: {cpu: 500m, memory: 512Mi}` et `limits: {cpu: 500m, memory: 512Mi}` ?

<details><summary>💡 Solution</summary>

**Guaranteed** : requests égales aux limits pour le CPU et la mémoire. C'est la classe la mieux protégée en cas de pression mémoire sur le nœud.
</details>

### Exercice 2.2
Pourquoi dépasser la limite mémoire tue-t-il le conteneur alors que dépasser la limite CPU le ralentit seulement ?

<details><summary>💡 Solution</summary>

Le CPU est **compressible** : on peut donner moins de temps de calcul à un processus sans le casser, d'où le throttling. La mémoire ne l'est pas : on ne peut pas reprendre de la RAM déjà utilisée sans perdre des données ; le noyau déclenche donc l'OOM killer et le conteneur est tué (`OOMKilled`, code 137).
</details>

### Exercice 2.3
Un Pod est régulièrement redémarré avec `Reason: OOMKilled`. Comment le confirmes-tu, et que fais-tu ?

<details><summary>💡 Solution</summary>

`kubectl describe pod` (section *Last State* : `OOMKilled`, exit code 137) et `kubectl top pod` ou Prometheus pour voir la consommation réelle. Selon le cas : augmenter la limite mémoire si le besoin est légitime, ou corriger la fuite mémoire de l'application. Augmenter sans comprendre ne fait que repousser le crash.
</details>

## Module 3 — Scheduling : affinités, taints et tolerations

### Le scheduler en deux temps
Le scheduler **filtre** les nœuds qui conviennent (ressources, contraintes), puis **classe** ceux qui restent. Ces outils orientent ses choix.

### `nodeSelector` : la contrainte simple
```bash
kubectl label node lab-worker disktype=ssd
```
```yaml
spec:
  nodeSelector:
    disktype: ssd
```

### Affinités : des règles plus fines
```yaml
spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels: { app: web }
          topologyKey: kubernetes.io/hostname
```
Cette anti-affinité interdit à deux Pods `app=web` de partager un **nœud** : une panne de nœud n'emporte plus tous les réplicas. Avec `preferredDuringScheduling...` la règle devient une préférence plutôt qu'une obligation.

### Répartir uniformément : `topologySpreadConstraints`
```yaml
spec:
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: DoNotSchedule
      labelSelector:
        matchLabels: { app: web }
```
Les Pods sont répartis entre zones (AZ, *Networking and Cloud*, Module 16) avec un écart maximal de 1 : c'est la traduction Kubernetes de « plusieurs zones de disponibilité ».

### Taints et tolerations : repousser par défaut
Un **taint** sur un nœud **repousse** tous les Pods qui n'ont pas la **toleration** correspondante.
```bash
kubectl taint nodes lab-worker2 dedie=gpu:NoSchedule
```
```yaml
spec:
  tolerations:
    - key: dedie
      operator: Equal
      value: gpu
      effect: NoSchedule
```
Usage : réserver des nœuds (GPU, charges critiques). Le plan de contrôle est lui-même « tainté » pour ne pas héberger de charges applicatives.
> Une toleration **autorise** un Pod à aller sur un nœud tainté, elle ne l'y **force** pas : pour l'y attirer, combine-la avec un `nodeSelector` ou une affinité.

### Exercice 3.1
Empêche deux Pods d'une même application de se retrouver sur le même nœud.

<details><summary>💡 Solution</summary>

Une `podAntiAffinity` `requiredDuringSchedulingIgnoredDuringExecution` avec `labelSelector` sur le label de l'application et `topologyKey: kubernetes.io/hostname` (voir ci-dessus). Tu peux la passer en `preferred` si tu as moins de nœuds que de réplicas.
</details>

### Exercice 3.2
Réserve un nœud à des Pods précis.

<details><summary>💡 Solution</summary>

```bash
kubectl taint nodes lab-worker2 dedie=batch:NoSchedule
kubectl label node lab-worker2 role=batch
```
Puis, dans les Pods concernés : une `toleration` sur `dedie=batch` **et** un `nodeSelector: {role: batch}`. Le taint repousse les autres Pods ; le nodeSelector attire les Pods voulus.
</details>

### Exercice 3.3
Pourquoi une toleration seule ne garantit-elle pas qu'un Pod atterrit sur le nœud tainté ?

<details><summary>💡 Solution</summary>

Une toleration lève seulement l'interdiction : le Pod **peut** aller sur ce nœud, mais le scheduler reste libre de le placer ailleurs. Pour l'y diriger, il faut en plus un `nodeSelector` ou une affinité de nœud.
</details>

## Module 4 — Autoscaling : HPA

### Le Horizontal Pod Autoscaler
Il ajuste automatiquement le **nombre de réplicas** d'un Deployment selon une métrique (CPU, mémoire, métrique personnalisée). Il nécessite **metrics-server** (Module 18).
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
```
```bash
kubectl autoscale deployment web --cpu-percent=60 --min=2 --max=10
kubectl get hpa -w
```

### Comment il décide
`Utilization` se mesure **par rapport aux `requests`** : sans request CPU sur le conteneur, le HPA ne peut pas calculer un pourcentage. Formule simplifiée :
```
réplicas désirés = ceil( réplicas actuels × métrique actuelle / cible )
```
Exemple : 4 réplicas à 90 % de CPU pour une cible de 60 % → ceil(4 × 90 / 60) = 6.

### Stabilisation : éviter le yo-yo
Monter vite, descendre lentement : le HPA applique une fenêtre de stabilisation avant de réduire (5 minutes par défaut), réglable avec `behavior`.

### Les autres niveaux d'autoscaling (aperçu)
| Outil | Ajuste |
|---|---|
| **HPA** | le nombre de Pods |
| **VPA** | les requests/limits d'un Pod |
| **Cluster Autoscaler / Karpenter** | le nombre de **nœuds** (Pods `Pending` faute de place → nouveau nœud) |

C'est l'équivalent Kubernetes de l'auto-scaling group vu dans *Networking and Cloud Intermédiaire*, Module 12.

### Exercice 4.1
Crée un HPA pour `web` : 2 à 10 réplicas, cible CPU 60 %.

<details><summary>💡 Solution</summary>

```bash
kubectl autoscale deployment web --cpu-percent=60 --min=2 --max=10
kubectl get hpa
```
Le Deployment doit définir `resources.requests.cpu`, sans quoi la cible en pourcentage est incalculable.
</details>

### Exercice 4.2
4 réplicas tournent à 90 % de CPU moyen (cible 60 %). Combien de réplicas le HPA vise-t-il ?

<details><summary>💡 Solution</summary>

ceil(4 × 90 / 60) = ceil(6) = **6 réplicas**.
</details>

### Exercice 4.3
Pourquoi le HPA affiche-t-il `<unknown>` comme métrique, et comment corriger ?

<details><summary>💡 Solution</summary>

Soit **metrics-server** n'est pas installé (ou ne répond pas), soit le conteneur n'a **pas de `requests.cpu`**, donc aucun pourcentage n'est calculable. On installe/répare metrics-server et on ajoute des requests au Deployment.
</details>

## Module 5 — Jobs et CronJobs

### Job : exécuter jusqu'à la réussite
Un **Job** lance un ou plusieurs Pods **jusqu'à terminaison réussie** (migrations, traitements ponctuels). Contrairement à un Deployment, on n'attend pas qu'il tourne indéfiniment.
```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: migration
spec:
  backoffLimit: 3
  ttlSecondsAfterFinished: 600
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: monapp:1.0.0
          command: ["python", "manage.py", "migrate"]
```
- `restartPolicy` doit être `Never` ou `OnFailure` (jamais `Always`) ;
- `backoffLimit` : nombre de nouvelles tentatives avant échec définitif ;
- `ttlSecondsAfterFinished` : nettoyage automatique après terminaison.
`completions` et `parallelism` permettent de traiter N éléments en parallèle.

### CronJob : planifier
```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: sauvegarde
spec:
  schedule: "0 3 * * *"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: monapp-backup:1.0.0
```
La syntaxe est celle de cron (*Linux Fondamentals*, Module 15). `concurrencyPolicy: Forbid` empêche une exécution de démarrer si la précédente tourne encore.

### Idempotence
Un Job peut être **relancé** (échec, nœud perdu) : son traitement doit être **idempotent**, comme pour les architectures événementielles (*Networking and Cloud Intermédiaire*, Module 14).

```bash
kubectl create job --from=cronjob/sauvegarde test-manuel     # déclencher un CronJob à la demande
kubectl logs job/migration
```

### Exercice 5.1
Écris un Job qui exécute `echo bonjour` puis se supprime tout seul 5 minutes après.

<details><summary>💡 Solution</summary>

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: hello
spec:
  ttlSecondsAfterFinished: 300
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: hello
          image: busybox:1.36
          command: ["echo", "bonjour"]
```
</details>

### Exercice 5.2
Écris l'expression de planification d'un CronJob « chaque jour ouvré à 8h30 » et une politique qui évite les exécutions qui se chevauchent.

<details><summary>💡 Solution</summary>

`schedule: "30 8 * * 1-5"` et `concurrencyPolicy: Forbid`.
</details>

### Exercice 5.3
Pourquoi un Job doit-il avoir `restartPolicy: Never` ou `OnFailure` ?

<details><summary>💡 Solution</summary>

Un Job doit **se terminer** : avec `Always`, le conteneur serait relancé même après une réussite et le Job ne finirait jamais. `Never` crée un nouveau Pod à chaque échec ; `OnFailure` redémarre le conteneur dans le même Pod.
</details>

## Module 6 — PodDisruptionBudget et interruptions volontaires

### Deux familles d'interruptions
- **Involontaires** : panne de nœud, crash matériel — on ne les choisit pas.
- **Volontaires** : `kubectl drain` pour une maintenance, mise à jour du cluster, autoscaler qui retire un nœud.

### Le PodDisruptionBudget (PDB)
Il fixe combien de Pods d'une application peuvent être **volontairement** indisponibles en même temps.
```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web
spec:
  minAvailable: 2
  selector:
    matchLabels: { app: web }
```
`minAvailable: 2` (ou `maxUnavailable: 1`) : un `drain` **attendra** plutôt que de descendre sous ce seuil.
```bash
kubectl drain lab-worker --ignore-daemonsets --delete-emptydir-data
kubectl uncordon lab-worker
kubectl cordon lab-worker      # marque le nœud non planifiable, sans évincer les Pods
```
> Un PDB ne protège **pas** contre les pannes involontaires. Et un PDB trop strict (`minAvailable` = nombre de réplicas) **bloque** les maintenances : le `drain` ne se termine jamais.

### Bien faire : réplicas, anti-affinité, PDB, readiness
Une application réellement disponible pendant une maintenance combine **au moins 2 réplicas**, une **anti-affinité** ou un topology spread, un **PDB**, et une **readiness** correcte (Module 1).

### Exercice 6.1
Crée un PDB garantissant au moins 2 Pods `app=web` disponibles pendant les interruptions volontaires.

<details><summary>💡 Solution</summary>

Voir le manifeste ci-dessus, avec `minAvailable: 2` et le selector `app: web`. Vérification : `kubectl get pdb`.
</details>

### Exercice 6.2
Différence entre `cordon`, `drain` et `uncordon` ?

<details><summary>💡 Solution</summary>

`cordon` marque le nœud non planifiable (aucun nouveau Pod) sans toucher aux Pods existants. `drain` fait un `cordon` puis **évince** les Pods en respectant les PDB. `uncordon` rend le nœud à nouveau planifiable.
</details>

### Exercice 6.3
Pourquoi un PDB avec `minAvailable` égal au nombre de réplicas est-il un problème ?

<details><summary>💡 Solution</summary>

Il n'autorise **aucune** éviction volontaire : un `drain` ne peut plus évacuer les Pods de l'application et reste bloqué, empêchant les mises à jour de nœuds et la maintenance du cluster.
</details>

# Partie 2 — Stockage

## Module 7 — PersistentVolumes, PVC et StorageClass

### Le problème
Le stockage d'un Pod (`emptyDir`, système de fichiers du conteneur) disparaît avec lui. Pour des données durables, Kubernetes sépare **qui fournit le disque** de **qui l'utilise**.

### Les trois objets
| Objet | Rôle | Qui le gère |
|---|---|---|
| **PersistentVolume (PV)** | un morceau de stockage réel (disque cloud, NFS...) | l'administrateur, ou le provisionnement dynamique |
| **PersistentVolumeClaim (PVC)** | une **demande** de stockage (taille, mode d'accès) | le développeur |
| **StorageClass** | le « catalogue » : quel type de stockage, avec quels paramètres | l'administrateur |

Avec le **provisionnement dynamique**, un PVC référençant une StorageClass déclenche la création automatique du PV correspondant (un disque EBS, un Persistent Disk...).

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: donnees
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: standard
  resources:
    requests:
      storage: 5Gi
---
apiVersion: v1
kind: Pod
metadata:
  name: app
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      volumeMounts:
        - name: data
          mountPath: /data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: donnees
```
```bash
kubectl get storageclass
kubectl get pvc,pv
```
Sur `kind`, une StorageClass `standard` (provisionneur local) est fournie par défaut.

### Modes d'accès
| Mode | Signification |
|---|---|
| `ReadWriteOnce` (RWO) | lecture/écriture par **un seul nœud** — typique d'un disque bloc |
| `ReadOnlyMany` (ROX) | lecture seule par plusieurs nœuds |
| `ReadWriteMany` (RWX) | lecture/écriture par **plusieurs nœuds** — stockage fichier (NFS, EFS) |
Ça reprend la distinction bloc / fichier de *Networking and Cloud Fundamentals*, Module 18.

### `reclaimPolicy` : que devient le disque quand on supprime le PVC ?
- **`Delete`** : le PV **et le disque réel** sont supprimés (défaut de nombreuses StorageClass dynamiques).
- **`Retain`** : le disque est conservé pour une récupération manuelle.
> Supprimer un PVC dont le PV est en `Delete` **détruit les données**. Pour des données précieuses, préfère `Retain` et des sauvegardes.

### Extension
Si la StorageClass a `allowVolumeExpansion: true`, on agrandit un PVC en modifiant `spec.resources.requests.storage` (on ne peut **pas** le réduire).

### Exercice 7.1
Crée un PVC de 1 Gi, monte-le dans un Pod, écris un fichier, supprime le Pod, recrée-le et retrouve le fichier.

<details><summary>💡 Solution</summary>

```bash
kubectl apply -f pvc-pod.yaml
kubectl exec app -- sh -c 'echo persistant > /data/f.txt'
kubectl delete pod app
kubectl apply -f pvc-pod.yaml          # recrée le Pod, le PVC existe toujours
kubectl exec app -- cat /data/f.txt     # persistant
```
Note : sur certaines StorageClass, le PVC reste `Pending` tant qu'un Pod ne l'utilise pas (`volumeBindingMode: WaitForFirstConsumer`).
</details>

### Exercice 7.2
Pourquoi un PVC `ReadWriteOnce` peut-il bloquer un Deployment de plusieurs réplicas ?

<details><summary>💡 Solution</summary>

`RWO` limite le volume à **un seul nœud** à la fois. Si le scheduler place des réplicas sur des nœuds différents, ceux qui ne sont pas sur le nœud du volume ne peuvent pas le monter et restent bloqués. Pour partager un volume entre nœuds il faut `RWX` (stockage fichier) ; pour des données propres à chaque réplica, un StatefulSet (Module 8).
</details>

### Exercice 7.3
Que se passe-t-il pour les données si tu supprimes un PVC dont le PV a une `reclaimPolicy: Delete` ? Comment te protéger ?

<details><summary>💡 Solution</summary>

Le PV et le disque sous-jacent sont supprimés : les données sont perdues. Protection : `reclaimPolicy: Retain` pour les données précieuses, des sauvegardes régulières et testées (RPO/RTO, *Networking and Cloud Intermédiaire*, Module 15), et des permissions RBAC limitant qui peut supprimer des PVC.
</details>

## Module 8 — StatefulSets

### Quand un Deployment ne suffit pas
Un Deployment traite ses Pods comme **interchangeables** et anonymes. Une base de données, un broker de messages ou un cluster (Kafka, PostgreSQL répliqué) demandent :
- une **identité stable** (`db-0`, `db-1`, `db-2`) qui survit aux recréations ;
- un **stockage propre** à chaque réplica ;
- un **ordre** de démarrage et d'arrêt.
C'est le rôle du **StatefulSet**.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: db
spec:
  clusterIP: None            # Service « headless »
  selector:
    app: db
  ports:
    - port: 5432
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db
  replicas: 3
  selector:
    matchLabels: { app: db }
  template:
    metadata:
      labels: { app: db }
    spec:
      containers:
        - name: postgres
          image: postgres:16
          env:
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef: { name: db-secret, key: password }
            - name: PGDATA
              value: /var/lib/postgresql/data/pgdata
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 10Gi
```

### Ce que ça garantit
- Pods nommés `db-0`, `db-1`, `db-2`, créés **dans l'ordre** et supprimés dans l'ordre inverse ;
- chaque Pod obtient **son propre PVC** (`data-db-0`, ...) recréé et rattaché au même Pod après une recréation ;
- un **nom DNS stable** par Pod grâce au Service headless : `db-0.db.<namespace>.svc.cluster.local`.
Un Service **headless** (`clusterIP: None`) ne fait pas de répartition de charge : le DNS renvoie directement les IP des Pods.

### Ce que ça ne fait PAS
Un StatefulSet donne de l'identité et du stockage, **pas** la réplication des données ni la haute disponibilité d'une base : c'est l'application (ou un **operator**, palier 3) qui doit configurer la réplication, l'élection d'un primaire, les sauvegardes.

> Pour une base de production, beaucoup d'équipes préfèrent un service managé (RDS, Cloud SQL — *Networking and Cloud Intermédiaire*, Module 13) ou un operator éprouvé, plutôt qu'un StatefulSet écrit à la main.

### Suppression et PVC
Supprimer un StatefulSet **ne supprime pas** ses PVC (sécurité par défaut) : ils restent, et sont rattachés à nouveau si tu recrées le StatefulSet.

### Exercice 8.1
Déploie un StatefulSet de 3 réplicas avec `volumeClaimTemplates` et liste Pods et PVC.

<details><summary>💡 Solution</summary>

```bash
kubectl apply -f statefulset.yaml
kubectl get pods -l app=db        # db-0, db-1, db-2, démarrés dans l'ordre
kubectl get pvc                    # data-db-0, data-db-1, data-db-2
```
</details>

### Exercice 8.2
Supprime le Pod `db-1` : quelle identité et quel stockage le nouveau Pod reçoit-il ?

<details><summary>💡 Solution</summary>

```bash
kubectl delete pod db-1
kubectl get pods -l app=db -w
```
Le nouveau Pod s'appelle à nouveau **`db-1`** et remonte le **même PVC** `data-db-1` : identité et données sont conservées.
</details>

### Exercice 8.3
Un StatefulSet PostgreSQL de 3 réplicas garantit-il que les 3 bases sont synchronisées ? Pourquoi ?

<details><summary>💡 Solution</summary>

Non. Le StatefulSet fournit des identités stables et un stockage par Pod, mais **rien** ne réplique les données entre eux. La réplication doit être configurée dans PostgreSQL (ou gérée par un operator dédié).
</details>

## Module 9 — Ingress et TLS

### Le problème
Un Service de type `LoadBalancer` par application coûte un load balancer cloud chacun. Un **Ingress** permet de **mutualiser** un point d'entrée et de router en **L7** (par nom d'hôte et chemin), comme vu dans *Networking and Cloud Fundamentals*, Module 11.

### Deux éléments à ne pas confondre
- **Ingress** : la *règle* de routage (un objet déclaratif) ;
- **Ingress Controller** : le composant qui **applique** ces règles (NGINX Ingress, Traefik, HAProxy...). Sans controller installé, un Ingress **ne fait rien**.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
spec:
  ingressClassName: nginx
  tls:
    - hosts: [app.exemple.com]
      secretName: app-tls
  rules:
    - host: app.exemple.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service: { name: api, port: { number: 80 } }
          - path: /
            pathType: Prefix
            backend:
              service: { name: web, port: { number: 80 } }
```

### Installer un controller sur `kind`
La configuration `kind` doit exposer les ports 80/443 (`extraPortMappings` sur le control-plane avec le label `ingress-ready=true`), puis on installe ingress-nginx avec le manifeste ou le chart Helm officiel.
```bash
kubectl get pods -n ingress-nginx
curl -H "Host: app.exemple.com" http://localhost/api
```
L'en-tête `Host` permet de tester sans DNS réel.

### TLS automatique : cert-manager (aperçu)
**cert-manager** obtient et **renouvelle** automatiquement des certificats (Let's Encrypt, PKI interne) et les stocke dans un Secret référencé par l'Ingress : plus de certificat expiré oublié (*Networking and Cloud Fundamentals*, Module 9).

### Et la Gateway API ?
La **Gateway API** est le successeur, plus expressif et mieux séparé entre rôles (infrastructure / application), de l'Ingress. À connaître, elle s'installe progressivement dans l'écosystème.

### Exercice 9.1
Écris un Ingress qui envoie `/api` vers le Service `api` et `/` vers le Service `web` pour l'hôte `app.exemple.com`.

<details><summary>💡 Solution</summary>

Utilise le manifeste ci-dessus (sans le bloc `tls` si tu n'as pas de certificat). Pour tester : `curl -H "Host: app.exemple.com" http://localhost/api`.
</details>

### Exercice 9.2
Pourquoi ton Ingress ne produit-il aucun effet alors qu'il est créé sans erreur ?

<details><summary>💡 Solution</summary>

Il n'y a probablement **pas d'Ingress Controller** installé (ou `ingressClassName` ne correspond à aucun controller). L'objet Ingress n'est qu'une déclaration ; c'est le controller qui la traduit en configuration de proxy.
</details>

### Exercice 9.3
Quel avantage un Ingress apporte-t-il par rapport à un Service `LoadBalancer` par application ?

<details><summary>💡 Solution</summary>

Un **seul** point d'entrée (donc un seul load balancer cloud, un seul coût) route vers de nombreux services selon l'hôte et le chemin, avec terminaison TLS centralisée — au lieu d'un load balancer distinct par application.
</details>

## Module 10 — DNS et découverte de services en profondeur

### CoreDNS
Le DNS du cluster est assuré par **CoreDNS**, dont la configuration est un ConfigMap (`kubectl -n kube-system get cm coredns`).

### Comment un Pod résout un nom
Le fichier `/etc/resolv.conf` de chaque Pod contient un **serveur DNS** (CoreDNS) et des **domaines de recherche** :
```
search demo.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5
```
Ainsi `web` est complété en `web.demo.svc.cluster.local`, puis `web.svc.cluster.local`, etc.

### Le piège `ndots:5`
Avec `ndots:5`, tout nom contenant **moins de 5 points** est d'abord essayé avec chaque domaine de recherche **avant** d'être résolu tel quel : `api.exemple.com` (2 points) génère plusieurs requêtes DNS inutiles avant la bonne. Sur des applications très bavardes, cela peut charger CoreDNS et allonger la latence. Remèdes : nom complet avec point final (`api.exemple.com.`), ou réglage `dnsConfig` du Pod.

### Types d'enregistrements créés
| Cible | Nom | Résultat |
|---|---|---|
| Service ClusterIP | `svc.ns.svc.cluster.local` | l'IP virtuelle du Service |
| Service headless | `svc.ns.svc.cluster.local` | les IP de **tous** les Pods |
| Pod d'un StatefulSet | `pod-0.svc.ns.svc.cluster.local` | l'IP de ce Pod précis |

### Diagnostiquer
```bash
kubectl run dbg --rm -it --image=busybox:1.36 --restart=Never -- nslookup web.demo.svc.cluster.local
kubectl exec pod-x -- cat /etc/resolv.conf
kubectl -n kube-system logs -l k8s-app=kube-dns
```

### Exercice 10.1
Résous depuis un Pod temporaire le nom complet d'un Service de ton cluster.

<details><summary>💡 Solution</summary>

```bash
kubectl run dbg --rm -it --image=busybox:1.36 --restart=Never -- nslookup web.default.svc.cluster.local
```
</details>

### Exercice 10.2
Que signifie `ndots:5` et quel effet a-t-il sur la résolution de `api.exemple.com` ?

<details><summary>💡 Solution</summary>

Tout nom ayant **moins de 5 points** est d'abord essayé en lui ajoutant chaque domaine de recherche du cluster, avant d'être tenté tel quel. `api.exemple.com` (2 points) provoque donc plusieurs requêtes DNS qui échouent avant la résolution correcte, d'où une latence et une charge inutiles.
</details>

### Exercice 10.3
Quelle différence entre le DNS d'un Service ClusterIP et celui d'un Service headless ?

<details><summary>💡 Solution</summary>

Un Service ClusterIP renvoie **une IP virtuelle** unique, derrière laquelle kube-proxy répartit la charge. Un Service headless (`clusterIP: None`) renvoie directement **les IP des Pods** : pas de répartition côté Kubernetes, ce qui permet aux clients (ou aux membres d'un cluster) de choisir leurs pairs.
</details>

## Module 11 — NetworkPolicies

### Le point de départ : tout est ouvert
Par défaut, **tout Pod peut parler à tout autre Pod**, quel que soit le namespace. Un Pod compromis peut donc joindre n'importe quoi : c'est le mouvement latéral vu dans *Networking and Cloud Expert*, Module 5. Les **NetworkPolicies** apportent la micro-segmentation.

> ⚠️ Elles ne sont appliquées que si le **plugin réseau (CNI)** les supporte (Calico, Cilium...). Le CNI par défaut de `kind` ne les applique pas : l'objet est créé sans erreur mais **n'a aucun effet**.

### Le principe
Une NetworkPolicy sélectionne des Pods (`podSelector`) ; dès qu'un Pod est sélectionné par une policy, le trafic qu'elle ne mentionne pas explicitement est **refusé** pour ce sens (`Ingress`, `Egress`).

### Étape 1 : tout refuser dans un namespace
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: demo
spec:
  podSelector: {}
  policyTypes: ["Ingress", "Egress"]
```

### Étape 2 : autoriser le strict nécessaire
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-vers-db
  namespace: demo
spec:
  podSelector:
    matchLabels: { app: db }
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: api }
      ports:
        - protocol: TCP
          port: 5432
```
Seuls les Pods `app=api` peuvent joindre la base sur le port 5432.

### N'oublie pas le DNS
Avec un `default-deny` sur l'`Egress`, les Pods ne peuvent plus résoudre de noms : il faut **autoriser explicitement** la sortie vers CoreDNS (UDP/TCP 53 vers le namespace `kube-system`).

### Les policies sont additives
Il n'existe pas de règle « deny » explicite : on part d'un refus (default-deny) et on **additionne** des autorisations.

### Exercice 11.1
Écris une policy interdisant tout trafic entrant vers les Pods d'un namespace.

<details><summary>💡 Solution</summary>

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-ingress
  namespace: demo
spec:
  podSelector: {}
  policyTypes: ["Ingress"]
```
Un `podSelector` vide sélectionne tous les Pods ; sans règle `ingress`, rien n'est autorisé.
</details>

### Exercice 11.2
Autorise seulement les Pods `app=api` à joindre les Pods `app=db` sur le port 5432.

<details><summary>💡 Solution</summary>

Voir la policy `api-vers-db` ci-dessus. À combiner avec un `default-deny` pour que la règle ait un sens.
</details>

### Exercice 11.3
Ta NetworkPolicy est créée mais ne bloque rien. Pourquoi ?

<details><summary>💡 Solution</summary>

Le **CNI** du cluster ne supporte probablement pas les NetworkPolicies (c'est le cas du CNI par défaut de `kind`). Kubernetes accepte l'objet mais aucun composant ne l'applique. Il faut un CNI compatible (Calico, Cilium).
</details>

## Module 12 — RBAC

### Le principe
Le **RBAC** (Role-Based Access Control) décide **qui** peut faire **quoi** sur **quelles ressources** via l'API Kubernetes. Il s'appuie sur le moindre privilège, comme l'IAM cloud (*Networking and Cloud Fundamentals*, Module 20).

### Quatre objets
| Objet | Portée | Rôle |
|---|---|---|
| **Role** | un namespace | liste de permissions (verbes sur des ressources) |
| **ClusterRole** | tout le cluster | idem, y compris ressources globales (nœuds) |
| **RoleBinding** | un namespace | accorde un Role/ClusterRole à des sujets **dans ce namespace** |
| **ClusterRoleBinding** | tout le cluster | accorde un ClusterRole **partout** |

Les **sujets** sont des utilisateurs, des groupes ou des **ServiceAccounts** (identités des Pods, équivalent des rôles IAM pour les machines).

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: lecteur-pods
  namespace: demo
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: lecteur-pods-alice
  namespace: demo
subjects:
  - kind: User
    name: alice
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: lecteur-pods
  apiGroup: rbac.authorization.k8s.io
```

### ServiceAccounts : l'identité des Pods
```bash
kubectl create serviceaccount app-sa -n demo
```
```yaml
spec:
  serviceAccountName: app-sa
  automountServiceAccountToken: false     # ne monte pas de jeton si l'appli n'appelle pas l'API
```
Par défaut, un Pod reçoit un jeton lui permettant d'appeler l'API Kubernetes : si l'application n'en a pas besoin, **désactive-le** — un Pod compromis n'aura pas d'identité à abuser.

### Tester les permissions
```bash
kubectl auth can-i list pods -n demo --as alice          # yes / no
kubectl auth can-i delete deployments -n demo --as alice
kubectl auth can-i --list -n demo --as alice
```

### Pièges classiques
- **`cluster-admin` distribué à la légère** : `ClusterRoleBinding` vers `cluster-admin` donne tout, partout ;
- verbes ou ressources en `"*"` ;
- accès en lecture aux **Secrets** : `get`/`list` sur `secrets` équivaut à voir tous les mots de passe du namespace.

### Exercice 12.1
Donne à un ServiceAccount `ci` le droit de lire les Deployments (pas de les modifier) dans le namespace `demo`.

<details><summary>💡 Solution</summary>

```bash
kubectl create serviceaccount ci -n demo
kubectl create role lecteur-deploy -n demo --verb=get,list,watch --resource=deployments
kubectl create rolebinding ci-lecteur -n demo --role=lecteur-deploy --serviceaccount=demo:ci
kubectl auth can-i delete deployments -n demo --as system:serviceaccount:demo:ci   # no
```
</details>

### Exercice 12.2
Différence entre un Role + RoleBinding et un ClusterRole + ClusterRoleBinding ?

<details><summary>💡 Solution</summary>

Un Role/RoleBinding s'applique à **un namespace** précis. Un ClusterRole/ClusterRoleBinding s'applique à **tout le cluster** et couvre aussi les ressources globales (nœuds, namespaces). On peut aussi lier un ClusterRole avec un RoleBinding pour réutiliser une définition tout en limitant la portée à un namespace.
</details>

### Exercice 12.3
Pourquoi donner un droit `list` sur les `secrets` est-il sensible ?

<details><summary>💡 Solution</summary>

`list` (et `get`) sur `secrets` permet de lire **le contenu** de tous les Secrets du périmètre — mots de passe, jetons, certificats, simplement décodés depuis base64. C'est en pratique un accès à tous les identifiants du namespace : à réserver au strict nécessaire.
</details>

## Module 13 — securityContext et Pod Security Standards

### Durcir chaque Pod
Le `securityContext` applique au niveau du Pod ou du conteneur les protections vues dans le palier 1, Module 8.
```yaml
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    fsGroup: 10001
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      image: monapp:1.0.0
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
```
| Champ | Effet |
|---|---|
| `runAsNonRoot` | refuse de démarrer si l'image tourne en root |
| `allowPrivilegeEscalation: false` | empêche de gagner des privilèges (équivalent `no-new-privileges`) |
| `readOnlyRootFilesystem` | système de fichiers racine en lecture seule |
| `capabilities.drop: ALL` | retire toutes les capabilities Linux |
| `seccompProfile: RuntimeDefault` | filtre les appels système dangereux |
Avec `readOnlyRootFilesystem`, fournis des volumes `emptyDir` pour les dossiers où l'application doit écrire (`/tmp`).

### Pod Security Standards (PSS) et Pod Security Admission
Trois niveaux **cumulatifs** :
| Niveau | Intention |
|---|---|
| **privileged** | aucune restriction |
| **baseline** | interdit les escalades connues (hostNetwork, conteneurs privilégiés...) |
| **restricted** | pratiques de durcissement complètes (non-root, capabilities retirées, seccomp...) |

Ils s'appliquent par **namespace**, via des labels :
```bash
kubectl label namespace demo \
  pod-security.kubernetes.io/enforce=baseline \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/audit=restricted
```
- **`enforce`** : **rejette** les Pods non conformes ;
- **`warn`** : accepte mais affiche un avertissement ;
- **`audit`** : accepte et consigne dans le journal d'audit.
Une bonne méthode de migration : `warn`/`audit` en `restricted` pour mesurer l'écart, puis `enforce` une fois les charges corrigées.

### Exercice 13.1
Écris un `securityContext` qui empêche de tourner en root, interdit l'escalade de privilèges et retire toutes les capabilities.

<details><summary>💡 Solution</summary>

```yaml
securityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  capabilities:
    drop: ["ALL"]
```
(le premier champ peut aussi se placer au niveau du Pod)
</details>

### Exercice 13.2
Applique le niveau `restricted` en mode `enforce` à un namespace et observe le rejet d'un Pod qui tourne en root.

<details><summary>💡 Solution</summary>

```bash
kubectl create namespace strict
kubectl label namespace strict pod-security.kubernetes.io/enforce=restricted
kubectl run test -n strict --image=nginx:1.27
```
La création est **refusée** avec la liste des violations (par exemple `runAsNonRoot`, `allowPrivilegeEscalation`, `capabilities`).
</details>

### Exercice 13.3
Différence entre les modes `enforce`, `warn` et `audit` ?

<details><summary>💡 Solution</summary>

`enforce` bloque les Pods non conformes ; `warn` les accepte en affichant un avertissement à l'utilisateur ; `audit` les accepte et enregistre la violation dans le journal d'audit. On les combine pour migrer progressivement sans casser les charges existantes.
</details>

## Module 14 — Quotas et LimitRange

### Le problème : un voisin bruyant
Sur un cluster partagé, un namespace qui demande trop de ressources (ou une boucle qui crée des Pods sans fin) prive les autres. Deux mécanismes posent des garde-fous **par namespace**.

### ResourceQuota : plafonner le total
```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: quota-equipe
  namespace: demo
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.memory: 16Gi
    pods: "30"
    persistentvolumeclaims: "10"
    services.loadbalancers: "1"
```
```bash
kubectl describe quota -n demo        # consommé vs plafond
```
Le quota limite aussi le **nombre d'objets** (Pods, PVC, LoadBalancers) : le dernier évite qu'une équipe crée dix load balancers cloud facturés. Une fois un quota `requests`/`limits` posé, chaque Pod **doit** déclarer ces valeurs, sinon il est refusé.

### LimitRange : des valeurs par défaut et des bornes
```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: defauts
  namespace: demo
spec:
  limits:
    - type: Container
      default:
        memory: 256Mi
      defaultRequest:
        cpu: 100m
        memory: 128Mi
      max:
        memory: 1Gi
```
Il injecte des requests/limits **par défaut** aux conteneurs qui n'en déclarent pas (évitant le rejet dû au quota, et la classe BestEffort), et refuse ceux qui dépassent le maximum.

### Le lien avec le FinOps
Quotas et labels par équipe sont le socle de l'allocation des coûts d'un cluster partagé (*Networking and Cloud Expert*, Module 18).

### Exercice 14.1
Limite un namespace à 10 Pods et 2 CPU de requests au total.

<details><summary>💡 Solution</summary>

```bash
kubectl create quota petit -n demo --hard=pods=10,requests.cpu=2
kubectl describe quota petit -n demo
```
</details>

### Exercice 14.2
Après avoir posé un quota mémoire, tes Pods sans `resources` sont rejetés. Pourquoi, et comment y remédier ?

<details><summary>💡 Solution</summary>

Quand un quota porte sur `requests`/`limits`, chaque Pod doit les déclarer pour que le quota puisse être décompté ; sans elles l'API refuse le Pod. On ajoute les `resources` dans les manifestes, ou on pose un **LimitRange** qui injecte des valeurs par défaut.
</details>

### Exercice 14.3
Pourquoi limiter aussi le nombre de Services `LoadBalancer` avec un quota ?

<details><summary>💡 Solution</summary>

Chaque Service `LoadBalancer` crée un load balancer chez le fournisseur cloud, avec un coût récurrent. Sans plafond, une erreur ou un manque de discipline peut en créer de nombreux et faire exploser la facture.
</details>

## Module 15 — Secrets en pratique

### Rappel : base64 n'est pas du chiffrement
Un Secret Kubernetes est stocké **en clair (base64) dans etcd** par défaut. Trois couches de protection :

### 1. Chiffrement au repos d'etcd
Le fichier `EncryptionConfiguration` de l'API server chiffre les Secrets **avant** écriture dans etcd (AES-CBC/GCM, ou un KMS externe : AWS KMS, GCP KMS, Vault). Sur les clusters managés (EKS, GKE, AKS), l'option se coche à la création.

### 2. RBAC strict
Limite `get`/`list`/`watch` sur `secrets` (Module 12) et évite les jetons de ServiceAccount montés inutilement.

### 3. Le Secret n'est pas la source de vérité : un gestionnaire externe
Un dépôt Git ne doit **jamais** contenir de Secret en clair. Trois approches :
| Approche | Principe |
|---|---|
| **External Secrets Operator** | synchronise dans le cluster des secrets stockés dans Vault / AWS Secrets Manager / GCP Secret Manager (*Networking and Cloud Intermédiaire*, Module 11) |
| **Sealed Secrets** | on commite un secret **chiffré** que seul le cluster sait déchiffrer |
| **SOPS** | chiffre les valeurs d'un fichier YAML avec une clé KMS/age, déchiffré au déploiement |

### Consommer un Secret : fichier plutôt que variable
```yaml
volumes:
  - name: creds
    secret:
      secretName: db-secret
containers:
  - name: app
    volumeMounts:
      - name: creds
        mountPath: /etc/secrets
        readOnly: true
```
Un Secret monté en **fichier** est mis à jour sans redémarrer le Pod et n'apparaît pas dans l'environnement (`env`, `docker inspect`, dumps de crash). Les variables d'environnement, elles, sont figées au démarrage.

### Rotation
Un secret qui ne change jamais reste une cible permanente. Avec un gestionnaire externe, la rotation est automatisée et se propage au cluster (*Networking and Cloud Intermédiaire*, Module 11).

### Exercice 15.1
Monte un Secret en fichier en lecture seule dans un conteneur et lis-le depuis le Pod.

<details><summary>💡 Solution</summary>

```bash
kubectl create secret generic db-secret --from-literal=password='S3cr3t!'
# Pod avec le volume secret monté sur /etc/secrets (voir ci-dessus)
kubectl exec app -- cat /etc/secrets/password
```
</details>

### Exercice 15.2
Pourquoi préférer un Secret monté en fichier à une variable d'environnement ?

<details><summary>💡 Solution</summary>

Une variable d'environnement est figée au démarrage, visible dans les dumps de processus/de crash et l'inspection du conteneur, et facilement héritée par les processus enfants. Un fichier peut être mis à jour sans redémarrage, avec des permissions précises, et fuit moins facilement.
</details>

### Exercice 15.3
Comment stocker les manifestes d'une application dans Git sans y mettre de secret en clair ?

<details><summary>💡 Solution</summary>

En commitant seulement des **références ou des secrets chiffrés** : External Secrets Operator (le dépôt contient une référence vers Vault/Secrets Manager), Sealed Secrets (secret chiffré déchiffrable uniquement par le cluster) ou SOPS (valeurs chiffrées dans le YAML). Le secret en clair n'entre jamais dans Git.
</details>

# Partie 5 — Packaging, observabilité, dépannage

## Module 16 — Helm

### Le problème
Une application réelle, ce sont des dizaines de manifestes qui varient d'un environnement à l'autre (dev, staging, prod). Copier-coller du YAML ne passe pas à l'échelle. **Helm** est le gestionnaire de paquets de Kubernetes : un **chart** est un paquet de manifestes **templatés**, une **release** est une installation de ce chart dans un cluster.

### Utiliser un chart existant
```bash
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
helm search repo redis
helm show values bitnami/redis > values-defaut.yaml       # tous les réglages possibles
helm install cache bitnami/redis -n demo --create-namespace -f mes-valeurs.yaml
helm list -n demo
helm upgrade cache bitnami/redis -n demo -f mes-valeurs.yaml
helm rollback cache 1 -n demo                              # retour à la révision 1
helm uninstall cache -n demo
```
`-f mes-valeurs.yaml` (ou `--set clé=valeur`) surcharge les valeurs par défaut : le **même chart** sert dev et prod avec des fichiers de valeurs différents.

### Anatomie d'un chart
```
monchart/
├── Chart.yaml          # nom, version du chart, version de l'application
├── values.yaml         # valeurs par défaut
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    └── _helpers.tpl     # fragments réutilisables
```
```yaml
# templates/deployment.yaml (extrait)
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```
```bash
helm create monchart                       # génère un squelette
helm lint monchart                          # vérifie
helm template monchart -f values-prod.yaml   # affiche le YAML final SANS installer
helm install --dry-run --debug demo ./monchart
```

### Bonnes pratiques
- **`helm template` / `--dry-run`** avant toute installation, comme `terraform plan` (*Networking and Cloud Intermédiaire*, Module 9) ;
- **épingle** la version du chart (`--version`) pour la reproductibilité ;
- ne mets pas de secrets en clair dans les `values` versionnés (Module 15) ;
- Helm **suit les révisions** : `helm history` et `helm rollback` fournissent un retour arrière propre.

### Exercice 16.1
Installe un chart depuis un dépôt public dans un namespace dédié, puis liste les releases.

<details><summary>💡 Solution</summary>

```bash
helm repo add bitnami https://charts.bitnami.com/bitnami
helm install cache bitnami/redis -n demo --create-namespace
helm list -n demo
kubectl get pods -n demo
```
</details>

### Exercice 16.2
Visualise le YAML qu'un chart génèrerait avec tes valeurs, sans rien installer.

<details><summary>💡 Solution</summary>

```bash
helm template cache bitnami/redis -f mes-valeurs.yaml
```
ou `helm install --dry-run --debug cache bitnami/redis -f mes-valeurs.yaml`.
</details>

### Exercice 16.3
Une mise à jour Helm casse l'application. Que fais-tu ?

<details><summary>💡 Solution</summary>

```bash
helm history cache -n demo
helm rollback cache <révision-précédente> -n demo
```
Helm conserve chaque révision : le retour arrière restaure la configuration précédente. On analyse ensuite la cause avec `helm template`/`helm diff` avant de retenter.
</details>

## Module 17 — Kustomize

### Une autre philosophie : superposer plutôt que templater
Kustomize (intégré à `kubectl`) ne modifie pas le YAML avec des templates : il part d'une **base** valide et lui applique des **patchs par environnement** (overlays).
```
app/
├── base/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── kustomization.yaml
└── overlays/
    ├── dev/
    │   └── kustomization.yaml
    └── prod/
        ├── kustomization.yaml
        └── patch-replicas.yaml
```
```yaml
# base/kustomization.yaml
resources:
  - deployment.yaml
  - service.yaml
```
```yaml
# overlays/prod/kustomization.yaml
resources:
  - ../../base
namespace: prod
namePrefix: prod-
images:
  - name: monapp
    newTag: 1.4.2
patches:
  - path: patch-replicas.yaml
```
```yaml
# overlays/prod/patch-replicas.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 5
```
```bash
kubectl kustomize overlays/prod        # affiche le résultat final
kubectl apply -k overlays/prod          # l'applique
kubectl diff -k overlays/prod
```

### Helm ou Kustomize ?
| | Helm | Kustomize |
|---|---|---|
| Approche | templates + valeurs | base + patchs |
| Force | distribuer des applications tierces, gestion de versions/rollback | adapter **ses propres** manifestes par environnement |
| Courbe | templates Go à maîtriser | YAML pur, plus simple |
Les deux se combinent, et sont courants dans les pipelines GitOps (palier 3).

### Exercice 17.1
Crée une base (Deployment + Service) et un overlay `prod` qui passe à 5 réplicas.

<details><summary>💡 Solution</summary>

Reprends la structure ci-dessus, avec `patch-replicas.yaml` fixant `replicas: 5`, puis :
```bash
kubectl kustomize overlays/prod | grep replicas
kubectl apply -k overlays/prod
```
</details>

### Exercice 17.2
Change le tag de l'image pour l'overlay `prod` sans toucher à la base.

<details><summary>💡 Solution</summary>

Dans `overlays/prod/kustomization.yaml` :
```yaml
images:
  - name: monapp
    newTag: 1.4.3
```
La base reste inchangée ; seul l'overlay porte la version.
</details>

### Exercice 17.3
Quand préférer Kustomize à Helm ?

<details><summary>💡 Solution</summary>

Pour adapter **ses propres manifestes** à plusieurs environnements avec peu de variations, sans la complexité de templates : la base reste du YAML valide et lisible. Helm est plus adapté à la distribution d'applications tierces et à la gestion de versions/rollback.
</details>

## Module 18 — Observabilité

### Trois piliers, sur Kubernetes
Métriques, logs et traces (*Networking and Cloud Intermédiaire*, Module 17) — ici, avec les outils standards de l'écosystème.

### metrics-server : les métriques de base
Il alimente `kubectl top` et le HPA (Module 4) avec la consommation CPU/mémoire des Pods et nœuds. Ce n'est **pas** un outil de monitoring long terme : il ne garde pas d'historique.
```bash
kubectl top nodes
kubectl top pods -A --sort-by=memory
```
Sur `kind`, metrics-server demande l'option `--kubelet-insecure-tls`.

### Prometheus + Grafana : `kube-prometheus-stack`
Le chart Helm `kube-prometheus-stack` installe Prometheus, Alertmanager, Grafana, des exporters et des tableaux de bord prêts à l'emploi (*Linux Expert*, Module 19).
```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm install monitoring prometheus-community/kube-prometheus-stack -n monitoring --create-namespace
kubectl port-forward -n monitoring svc/monitoring-grafana 3000:80
```
Le **ServiceMonitor** déclare à Prometheus quels Services scraper :
```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: api
  namespace: monitoring
spec:
  selector:
    matchLabels: { app: api }
  namespaceSelector:
    matchNames: [demo]
  endpoints:
    - port: metrics
      interval: 15s
```

### Requêtes PromQL utiles
```
sum(rate(container_cpu_usage_seconds_total{namespace="demo"}[5m])) by (pod)
sum(container_memory_working_set_bytes{namespace="demo"}) by (pod)
sum(kube_pod_container_status_restarts_total) by (pod) > 3
```

### Logs
```bash
kubectl logs deploy/api --all-containers --tail=100
kubectl logs -l app=api --since=10m
kubectl logs pod-x --previous
```
`kubectl logs` ne suffit pas en production : les logs disparaissent avec le Pod. On les collecte via un agent sur chaque nœud (Promtail/Fluent Bit) vers un stockage central (Loki, Elasticsearch, un service cloud).

### Les événements
```bash
kubectl get events -n demo --sort-by=.lastTimestamp
```
Les événements racontent ce que fait le cluster (planification, échec de pull, sondes qui échouent) mais **expirent vite** (environ une heure) : à exporter aussi.

### Alertes : symptômes plutôt que causes
Alerter sur ce que **vit l'utilisateur** (taux d'erreurs, latence, indisponibilité — les SLO, *Networking and Cloud Expert*, Module 15) plutôt que sur chaque pic de CPU.

### Exercice 18.1
Affiche les 5 Pods les plus gourmands en mémoire du cluster.

<details><summary>💡 Solution</summary>

```bash
kubectl top pods -A --sort-by=memory | head -n 6
```
(nécessite metrics-server)
</details>

### Exercice 18.2
Écris une requête PromQL détectant les Pods qui ont redémarré plus de 3 fois.

<details><summary>💡 Solution</summary>

```
sum(kube_pod_container_status_restarts_total) by (namespace, pod) > 3
```
(métrique fournie par kube-state-metrics, inclus dans `kube-prometheus-stack`)
</details>

### Exercice 18.3
Pourquoi `kubectl logs` ne suffit-il pas en production ?

<details><summary>💡 Solution</summary>

Les logs sont liés au Pod : ils disparaissent quand il est supprimé ou évincé, ce qui arrive justement lors d'un incident. Ils sont aussi dispersés sur des dizaines de Pods. Il faut les collecter en continu vers un système central, interrogeable et conservé.
</details>

## Module 19 — Méthodologie de dépannage

### Le réflexe : de l'extérieur vers l'intérieur
```
1. Le Pod tourne-t-il ?            kubectl get pods
2. Que dit Kubernetes ?            kubectl describe pod  → Events
3. Que dit l'application ?         kubectl logs (--previous)
4. Le Service pointe-t-il bien ?    kubectl get endpoints
5. Le réseau/DNS fonctionne-t-il ?  pod de debug, nslookup, wget
```

### Symptôme → cause → vérification
| Symptôme | Causes probables | Où regarder |
|---|---|---|
| `Pending` | ressources insuffisantes, taint/affinité, PVC non lié | `describe pod` → Events (`FailedScheduling`) |
| `ImagePullBackOff` | tag/nom erroné, registre privé sans identifiants | `describe pod` → Events |
| `CrashLoopBackOff` | l'application plante au démarrage, mauvaise config | `logs --previous` |
| `OOMKilled` (code 137) | limite mémoire trop basse ou fuite | `describe pod` → Last State |
| `Running` mais `0/1 Ready` | readiness qui échoue | `describe pod`, logs, endpoint de readiness |
| Service sans réponse | selector faux, aucun Pod Ready, mauvais `targetPort` | `kubectl get endpoints` |
| 503 via Ingress | aucun endpoint sain, mauvais port de backend | endpoints, logs du controller |

### Un Service qui ne répond pas : la démarche
```bash
kubectl get endpoints web                         # vide ? le selector ne trouve aucun Pod Ready
kubectl get pods --show-labels                     # les labels correspondent-ils au selector ?
kubectl describe svc web                            # port, targetPort, selector
kubectl run dbg --rm -it --image=busybox:1.36 --restart=Never -- wget -qO- http://web
```
Un endpoint **vide** est la signature d'un selector qui ne correspond à aucun Pod, ou de Pods non Ready.

### Débugger un Pod qui n'a pas de shell
Les images minimales (distroless) n'ont pas de shell : `kubectl exec` échoue. On attache un conteneur **éphémère** de debug :
```bash
kubectl debug -it pod-x --image=busybox:1.36 --target=app
```

### Corréler
Un incident se lit dans le temps : `kubectl get events --sort-by=.lastTimestamp`, un déploiement récent (`rollout history`), une alerte, un changement de config. Souvent, la cause est **ce qui a changé juste avant**.

### Exercice 19.1
Un Pod est en `Pending`. Décris ta démarche.

<details><summary>💡 Solution</summary>

`kubectl describe pod` et lecture des **Events** : un `FailedScheduling` indique la raison (CPU/mémoire insuffisants, taint sans toleration, affinité impossible, PVC non lié). On corrige selon la cause : ajuster les requests, ajouter un nœud ou une toleration, ou créer/lier le PVC.
</details>

### Exercice 19.2
Un Service ne répond pas. Quelle est ta première vérification ?

<details><summary>💡 Solution</summary>

`kubectl get endpoints <service>` : s'il est **vide**, le selector ne correspond à aucun Pod, ou aucun Pod n'est `Ready`. On compare alors les labels des Pods (`--show-labels`) au selector du Service, et on vérifie la readiness.
</details>

### Exercice 19.3
Comment debugger un conteneur distroless sans shell ?

<details><summary>💡 Solution</summary>

Avec un conteneur éphémère : `kubectl debug -it <pod> --image=busybox:1.36 --target=<conteneur>`. Il partage les namespaces du Pod et fournit un shell et des outils sans modifier l'image de production.
</details>

# Partie 6 — Synthèse

## Module 20 — Projet de synthèse : une application prête pour la production

### Le brief
Sur un cluster `kind` multi-nœuds, prépare une application (API + base PostgreSQL) pour la production :

1. **Namespace** `prod` avec les labels **Pod Security** (`enforce=baseline`, `warn`/`audit` en `restricted`), un **ResourceQuota** et un **LimitRange**.
2. **API** en Deployment : 3 réplicas, `startup`/`readiness`/`liveness` bien séparées, `requests`/`limits`, `securityContext` durci (non-root, lecture seule, capabilities retirées), **topologySpreadConstraints** entre nœuds, **PodDisruptionBudget**, **HPA** (2 à 8 réplicas).
3. **Base** en **StatefulSet** avec `volumeClaimTemplates` et Service headless ; mot de passe monté en **fichier** depuis un Secret.
4. **RBAC** : un ServiceAccount dédié à l'API (sans jeton monté s'il n'appelle pas l'API), et un Role de lecture seule pour un profil « support ».
5. **Réseau** : `default-deny` puis autorisations minimales (Ingress → API, API → base, DNS), **Ingress** avec TLS.
6. **Packaging** : un chart Helm **ou** une base Kustomize avec overlays `dev` et `prod`.
7. **Observabilité** : `kube-prometheus-stack`, un `ServiceMonitor`, une alerte sur le taux d'erreurs.
8. **Épreuves** : vider un nœud (`drain`) sans interruption ; tuer un Pod de la base et retrouver ses données ; provoquer volontairement un `CrashLoopBackOff` et le diagnostiquer avec la méthode du Module 19.

> Rappel : les NetworkPolicies ne s'appliquent que si le CNI les supporte. Sur `kind`, installe Calico ou Cilium, ou valide ces règles sur un cluster managé.

### Pourquoi ce projet
Il recombine tout le palier : fiabilité (M1-M6), stockage (M7-M8), réseau (M9-M11), sécurité et gouvernance (M12-M15), packaging et exploitation (M16-M19). Si tu le réalises et le dépannes sans rouvrir les modules, tu as le niveau intermédiaire.

<details><summary>💡 Solution guidée (structure et points d'attention)</summary>

```
prod-app/
├── base/
│   ├── namespace.yaml           # labels Pod Security
│   ├── quota-limitrange.yaml
│   ├── rbac.yaml                 # ServiceAccount + Role support
│   ├── api-deployment.yaml       # probes, securityContext, topology spread
│   ├── api-service.yaml
│   ├── api-hpa.yaml
│   ├── api-pdb.yaml
│   ├── db-statefulset.yaml       # headless service + volumeClaimTemplates
│   ├── networkpolicies.yaml      # default-deny + autorisations
│   ├── ingress.yaml
│   └── kustomization.yaml
└── overlays/
    ├── dev/kustomization.yaml     # 1 réplica, ressources réduites
    └── prod/kustomization.yaml     # 3+ réplicas, tag d'image épinglé
```

Points d'attention :
- **Ordre de vérification** : sans quota/LimitRange corrects, les Pods sans `resources` sont rejetés ; sans requests CPU, le HPA affiche `<unknown>`.
- **Sécurité** : `readOnlyRootFilesystem: true` impose des `emptyDir` pour `/tmp` ; `runAsNonRoot` exige un UID numérique dans l'image.
- **NetworkPolicy** : n'oublie pas l'Egress DNS vers `kube-system` après un `default-deny`.
- **Épreuve drain** : `kubectl drain <nœud> --ignore-daemonsets --delete-emptydir-data` ; le PDB doit permettre la progression sans jamais descendre sous `minAvailable`.
- **Épreuve StatefulSet** : `kubectl delete pod db-0` ; le Pod revient avec le même nom et le même PVC.
- **Diagnostic** : `describe` → `logs --previous` → `get endpoints`, dans cet ordre.
</details>

## Cheat-sheet

| Catégorie | Repères clés |
|---|---|
| Probes | readiness = trafic, liveness = redémarrage (état **interne** seulement), startup = démarrage lent |
| Ressources | `requests` (scheduling) vs `limits` ; CPU throttlé, mémoire tuée (137) ; QoS Guaranteed / Burstable / BestEffort |
| Placement | `nodeSelector`, `podAntiAffinity`, `topologySpreadConstraints`, taints + tolerations |
| Scaling | HPA (requests CPU obligatoires, metrics-server), VPA, Cluster Autoscaler |
| Batch | Job (`restartPolicy` Never/OnFailure, `backoffLimit`), CronJob (`concurrencyPolicy`) |
| Interruptions | PDB (`minAvailable`), `cordon` / `drain` / `uncordon` |
| Stockage | StorageClass → PVC → PV ; RWO vs RWX ; `reclaimPolicy` Delete vs Retain ; StatefulSet = identité + PVC par Pod |
| Exposition | Ingress (règles) ≠ Ingress Controller (application) ; cert-manager pour TLS |
| DNS | `svc.ns.svc.cluster.local` ; headless = IP des Pods ; piège `ndots:5` |
| Réseau | NetworkPolicy : `default-deny` puis autorisations ; nécessite un CNI compatible |
| Accès | Role/ClusterRole + Binding ; `kubectl auth can-i` ; ServiceAccount sans jeton inutile |
| Durcissement | `runAsNonRoot`, `allowPrivilegeEscalation: false`, `drop ALL`, Pod Security `enforce/warn/audit` |
| Gouvernance | ResourceQuota (totaux, objets) + LimitRange (défauts, bornes) |
| Secrets | chiffrement etcd, RBAC strict, fichier > variable, External Secrets / Sealed Secrets / SOPS |
| Packaging | Helm (`template`, `--dry-run`, `rollback`) · Kustomize (base + overlays, `apply -k`) |
| Exploitation | `kubectl top`, kube-prometheus-stack, logs collectés, événements, `kubectl debug` |
| Dépannage | `get` → `describe` (Events) → `logs --previous` → `get endpoints` → pod de debug |

## Glossaire

| Terme | Définition |
|---|---|
| **Probe** | vérification périodique de l'état d'un conteneur (readiness, liveness, startup) |
| **QoS class** | classe déduite des requests/limits qui décide de l'ordre d'éviction |
| **HPA** | ajuste automatiquement le nombre de réplicas selon une métrique |
| **PDB** | plafond d'indisponibilité volontaire d'une application |
| **PV / PVC / StorageClass** | disque réel / demande de stockage / catalogue de types de stockage |
| **StatefulSet** | workload à identité stable et stockage propre par réplica |
| **Service headless** | Service sans IP virtuelle, dont le DNS renvoie les IP des Pods |
| **Ingress / Ingress Controller** | règle de routage L7 / composant qui l'applique |
| **NetworkPolicy** | règle de filtrage du trafic entre Pods |
| **RBAC** | contrôle d'accès fondé sur des rôles pour l'API Kubernetes |
| **ServiceAccount** | identité d'un Pod pour appeler l'API |
| **Pod Security Standards** | niveaux privileged / baseline / restricted appliqués par namespace |
| **ResourceQuota / LimitRange** | plafond total par namespace / défauts et bornes par conteneur |
| **Chart / Release** | paquet Helm / installation de ce paquet dans un cluster |
| **Overlay (Kustomize)** | ensemble de patchs appliqués à une base pour un environnement |
| **Événement (Event)** | trace éphémère d'une action du cluster (planification, échec de pull...) |
