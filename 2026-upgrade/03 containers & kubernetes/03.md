# Partie 1 — Internals du control plane

## Module 1 — etcd en profondeur

### Le cœur de tout
Tout ce que tu as manipulé depuis le palier 1 — Pods, Deployments, Secrets, CRD — n'est, in fine, qu'une entrée dans **etcd**. C'est la seule source de vérité du cluster.

### Raft : comment plusieurs nœuds etcd restent d'accord
etcd réplique son journal via l'algorithme de consensus **Raft** : un **leader** est élu, toutes les écritures passent par lui et ne sont validées qu'une fois répliquées sur une **majorité** des membres.
| Membres | Pannes tolérées | Majorité requise |
|---|---|---|
| 1 | 0 | 1 |
| 3 | 1 | 2 |
| 4 | 1 | 3 |
| 5 | 2 | 3 |

Un nombre **impair** est systématiquement préférable : 4 membres ne tolèrent pas plus de pannes que 3 (toujours 1), pour un coût de latence et de matériel supérieur — le 4ᵉ nœud n'ajoute aucune résilience, seulement du coût.

### Sauvegarder et restaurer
```bash
etcdctl endpoint health
etcdctl endpoint status --write-out=table
etcdctl snapshot save /backup/etcd-$(date +%F).db
etcdctl snapshot restore /backup/etcd-2026-09-30.db --data-dir=/var/lib/etcd-restore
```
Restaurer un instantané **recrée un cluster etcd** à partir de ce point dans le temps (nouvel identifiant de cluster) : ce n'est pas une simple copie de fichier, c'est une procédure à part entière, à documenter et à **tester** avant d'en avoir besoin en urgence (Module 19).

### Sensibilité à la latence
etcd confirme une écriture seulement après l'avoir **persistée sur disque** sur la majorité des membres : un disque lent (ou partagé avec d'autres charges d'I/O) dégrade directement la latence de **toute** opération d'écriture sur l'API Kubernetes — stocker etcd sur un SSD dédié, séparé des autres charges, est une recommandation de production, pas un détail.

### Exercice 1.1
Pourquoi les clusters etcd utilisent-ils un nombre impair de membres (3 ou 5) plutôt que pair ?

<details><summary>💡 Solution</summary>

La tolérance aux pannes dépend de la capacité à maintenir une **majorité** active. Un cluster à 4 membres ne tolère pas plus de pannes qu'un cluster à 3 (toujours 1, puisqu'il faut 3 nœuds sur 4 pour la majorité) : le 4ᵉ membre ajoute du coût et de la latence de réplication sans gain de résilience. Un nombre impair maximise la tolérance aux pannes pour chaque nœud ajouté.
</details>

### Exercice 1.2
Prends un instantané etcd et décris, dans les grandes lignes, la procédure de restauration.

<details><summary>💡 Solution</summary>

```bash
etcdctl snapshot save backup.db
```
La restauration (`etcdctl snapshot restore`) recrée un **nouveau** répertoire de données etcd à partir de cet instantané, avec un nouvel identifiant de cluster ; il faut ensuite reconfigurer le(s) membre(s) etcd pour utiliser ce nouveau répertoire, et redémarrer le plan de contrôle pointant dessus. Ce n'est jamais un simple redémarrage : c'est une reconstruction.
</details>

### Exercice 1.3
Pourquoi la latence d'etcd affecte-t-elle directement la réactivité de toute l'API Kubernetes ?

<details><summary>💡 Solution</summary>

Chaque écriture à travers l'API server (créer un Pod, mettre à jour un Deployment) n'est confirmée qu'une fois persistée dans etcd sur une majorité de membres. Si le disque d'etcd est lent, chaque opération d'écriture du cluster entier hérite de ce délai — etcd est un goulot d'étranglement partagé par absolument toutes les ressources du cluster.
</details>

## Module 2 — kube-apiserver : admission control et webhooks

### Le trajet complet d'une requête
```
Requête → Authentification (qui es-tu ?) → Autorisation RBAC (as-tu le droit ?)
        → Admission MUTATING (on peut modifier l'objet) → Admission VALIDATING (accepter ou rejeter)
        → persistance dans etcd
```
L'ordre compte : les webhooks **mutating** s'exécutent **avant** les **validating**, précisément pour que la validation finale porte sur l'objet **déjà complété** (valeurs par défaut injectées, labels ajoutés) plutôt que sur sa version brute initiale.

### Les admission controllers déjà rencontrés
Tu as déjà utilisé ce mécanisme sans le nommer : **ResourceQuota** et **Pod Security Admission** (palier 2, Modules 13-14) sont des admission controllers **intégrés**, validants pour la plupart ; **LimitRange** est **mutating** (il injecte des valeurs par défaut) autant que validant (il refuse les dépassements).
```bash
kubectl api-resources | grep -i admission
kube-apiserver --help | grep enable-admission-plugins      # (sur le nœud du control plane)
```

### Exercice 2.1
Pourquoi les webhooks mutating s'exécutent-ils avant les validating, et pas l'inverse ?

<details><summary>💡 Solution</summary>

Les mutating webhooks complètent l'objet (valeurs par défaut, labels injectés). Si la validation passait avant, elle jugerait l'objet sur sa forme brute, incomplète, pouvant le rejeter à tort pour l'absence d'une valeur que la mutation aurait justement fournie. Valider **après** mutation garantit que la décision finale porte sur l'objet tel qu'il sera réellement persisté.
</details>

### Exercice 2.2
Où se situe RBAC dans ce pipeline, par rapport à l'admission control ?

<details><summary>💡 Solution</summary>

RBAC (autorisation) s'exécute **avant** l'admission control : on vérifie d'abord que l'utilisateur ou le ServiceAccount a le droit de faire cette action sur cette ressource, puis seulement ensuite l'objet passe par les étapes de mutation et de validation.
</details>

### Exercice 2.3
Le LimitRange (palier 2, Module 14) est-il un admission controller mutating, validating, ou les deux ?

<details><summary>💡 Solution</summary>

**Les deux** : il est mutating quand il injecte des `requests`/`limits` par défaut à un conteneur qui n'en déclare pas, et validating quand il refuse un conteneur dont les valeurs déclarées dépassent les bornes `max` définies.
</details>

## Module 3 — kube-scheduler : comment il décide

### Le scheduling framework
Une décision de placement traverse une série de **points d'extension**, en deux grandes phases :
```
Filtrage  : élimine les nœuds qui NE conviennent PAS (ressources insuffisantes, taint sans toleration...)
Scoring   : note les nœuds restants et choisit le meilleur score
```
(Rappel palier 2, Module 3 : `nodeSelector`, affinités, taints/tolerations, topology spread sont autant de **signaux** que ce pipeline de filtrage/scoring prend en compte.)

### Plusieurs scheduler dans un même cluster
Kubernetes n'impose pas un scheduler unique :
```yaml
spec:
  schedulerName: mon-scheduler-personnalise
```
Un Pod sans `schedulerName` explicite utilise `default-scheduler`. On peut déployer un second scheduler (avec sa propre logique de scoring) pour des charges aux contraintes spécifiques (placement optimisé pour du calcul GPU, de l'inférence ML...), sans toucher au scheduler par défaut qui continue de traiter tout le reste.

### Exercice 3.1
Pourquoi Kubernetes permet-il de faire tourner plusieurs scheduler simultanément dans un même cluster ?

<details><summary>💡 Solution</summary>

Certaines charges ont des besoins de placement très spécifiques (optimisation GPU, colocalisation précise) que la logique de scoring par défaut ne prend pas en compte. Plutôt que de complexifier le scheduler par défaut pour tous les cas, on peut déployer un scheduler dédié, utilisé seulement par les Pods qui le déclarent via `schedulerName`, sans affecter le reste du cluster.
</details>

### Exercice 3.2
Décris les deux grandes phases par lesquelles passe une décision de scheduling.

<details><summary>💡 Solution</summary>

D'abord le **filtrage** : élimine tous les nœuds qui ne peuvent structurellement pas accueillir le Pod (ressources insuffisantes, taint non toléré, affinité non satisfaite). Ensuite le **scoring** : note les nœuds restants selon divers critères (équilibrage de charge, affinité préférentielle) et choisit celui qui obtient le meilleur score.
</details>

### Exercice 3.3
Donne un scénario justifiant un scheduler personnalisé plutôt que le scheduler par défaut.

<details><summary>💡 Solution</summary>

Une plateforme d'inférence ML qui doit placer ses Pods en tenant compte de la topologie précise des GPU disponibles sur chaque nœud (affinité mémoire GPU, interconnexion NVLink) — un critère de scoring que le scheduler par défaut ne connaît pas nativement, et qu'un scheduler personnalisé peut implémenter spécifiquement pour ces charges.
</details>

## Module 4 — Boucles de contrôle : le pattern controller

### Le pattern générique, formalisé
Tu as déjà rencontré la boucle de réconciliation (palier 1, Module 13 : « état désiré vs état observé »). Voici comment elle s'écrit réellement :
```go
func Reconcile(ctx context.Context, req Request) (Result, error) {
    var obj MonCRD
    if err := client.Get(ctx, req.NamespacedName, &obj); err != nil {
        return Result{}, client.IgnoreNotFound(err)
    }
    // Comparer obj.Spec (désiré) à la réalité observée
    // Agir pour réduire l'écart (créer/modifier/supprimer des ressources enfants)
    return Result{}, nil
}
```

### Informers : regarder, pas interroger en boucle
Un controller ne fait **pas** de `GET` répété sur l'API server (ce qui écraserait l'API server à grande échelle). Il utilise un **informer** : une connexion **watch** persistante vers l'API server, maintenant un **cache local** à jour, qui déclenche la fonction `Reconcile` seulement quand quelque chose change réellement.

### Réconciliation « par niveau », pas « par événement »
Un bon controller réagit à **l'état actuel complet** de l'objet, pas aux détails précis de l'événement qui l'a déclenché. Si trois mises à jour arrivent coup sur coup, `Reconcile` peut n'être appelée qu'une fois, avec l'état **final** : c'est pourquoi la fonction doit être **idempotente** (même principe que les architectures événementielles, *Networking and Cloud Intermédiaire*, Module 14) — un appel répété avec le même état ne doit rien casser.

### Exercice 4.1
Pourquoi un controller utilise-t-il un mécanisme de watch (informer) plutôt que d'interroger l'API server en boucle ?

<details><summary>💡 Solution</summary>

Interroger en boucle (polling) des milliers de controllers sur un gros cluster surchargerait l'API server et introduirait un délai entre un changement réel et sa détection. Le watch pousse les changements au fil de l'eau vers un cache local, réduisant la charge sur l'API server et la latence de réaction du controller.
</details>

### Exercice 4.2
Qu'est-ce que la réconciliation « par niveau » et pourquoi est-elle plus robuste qu'une logique « par événement » ?

<details><summary>💡 Solution</summary>

La réconciliation par niveau réagit à l'**état actuel complet** de l'objet, indépendamment de l'événement précis qui a déclenché l'appel — même logique qu'on ait raté un événement intermédiaire ou qu'on en ait reçu trois d'affilée, le résultat final converge correctement. Une logique « par événement » (qui réagirait différemment selon qu'il s'agit d'une création, modification ou suppression précise) est fragile si un événement est manqué ou arrive en double.
</details>

### Exercice 4.3
Décris, en pseudocode, ce que ferait la fonction `Reconcile` d'une ressource personnalisée `BackupSchedule`.

<details><summary>💡 Solution</summary>

```
Reconcile(BackupSchedule) :
    lire la ressource (schedule désiré, rétention désirée)
    vérifier si un CronJob correspondant existe déjà
    si absent → le créer avec le schedule déclaré
    si présent mais différent (schedule changé) → le mettre à jour
    si la ressource BackupSchedule est supprimée → supprimer le CronJob associé
```
</details>

# Partie 2 — Étendre Kubernetes

## Module 5 — Custom Resource Definitions

### Donner un nouveau type à l'API
Une **CRD** ajoute un type de ressource entièrement nouveau à l'API Kubernetes — tu peux ensuite le manipuler exactement comme un Pod ou un Deployment (`kubectl get`, `kubectl apply`, RBAC, labels).
```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: backupschedules.exemple.io
spec:
  group: exemple.io
  names:
    kind: BackupSchedule
    plural: backupschedules
    singular: backupschedule
    shortNames: ["bs"]
  scope: Namespaced
  versions:
    - name: v1
      served: true
      storage: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                schedule: { type: string }
                retention: { type: integer, minimum: 1 }
              required: ["schedule"]
```
```yaml
apiVersion: exemple.io/v1
kind: BackupSchedule
metadata:
  name: quotidien
spec:
  schedule: "0 3 * * *"
  retention: 7
```
```bash
kubectl apply -f crd.yaml
kubectl apply -f backupschedule.yaml
kubectl get backupschedules
kubectl get bs            # grâce au shortName
```

### Une CRD seule n'est que de la donnée structurée
Sans **controller** qui l'observe et agit, une instance de `BackupSchedule` ne fait **strictement rien** : c'est un objet stocké dans etcd, validé par son schéma, mais totalement passif — exactement comme un ConfigMap. C'est le Module 6 qui lui donne un comportement.

### `served` et `storage`
Plusieurs versions (`v1`, `v1beta1`...) peuvent coexister : `served` indique si l'API expose cette version, `storage` indique laquelle est **réellement persistée** dans etcd (une seule version peut avoir `storage: true`). Un **conversion webhook** traduit entre versions quand nécessaire.

### Exercice 5.1
Crée la CRD `BackupSchedule` ci-dessus et une instance, puis interroge-la avec `kubectl`.

<details><summary>💡 Solution</summary>

```bash
kubectl apply -f crd.yaml
kubectl apply -f backupschedule.yaml
kubectl get backupschedules -o yaml
```
</details>

### Exercice 5.2
Pourquoi une CRD sans controller associé est-elle « juste de la donnée », sans aucun effet réel ?

<details><summary>💡 Solution</summary>

La CRD ne fait que définir et valider la **structure** d'un nouvel objet dans l'API. Rien dans Kubernetes n'observe cet objet pour agir dessus par défaut — il faut un controller qui le surveille (via un informer, Module 4) et traduit son contenu en actions réelles (créer un CronJob, par exemple) pour qu'il ait un effet concret.
</details>

### Exercice 5.3
Que signifient les champs `served` et `storage` quand une CRD a plusieurs versions ?

<details><summary>💡 Solution</summary>

`served: true` indique que cette version de l'API est accessible aux clients (`kubectl`, les controllers). `storage: true` indique que c'est **cette** version précise qui est réellement écrite dans etcd — une seule version peut avoir `storage: true` à la fois ; les autres versions servies sont converties à la volée vers/depuis la version de stockage.
</details>

## Module 6 — Operators : le pattern et controller-runtime

### Encoder le savoir opérationnel
Un **Operator** combine une CRD et un controller qui encode le **savoir-faire d'un humain expert** sur une application précise : comment la déployer correctement, la sauvegarder, gérer un basculement de primaire, l'upgrader sans interruption. Un Deployment simple ne sait **rien** de tout cela — il maintient juste N réplicas d'une image, sans aucune notion de ce qu'est « une base de données saine ».

### `controller-runtime` / Kubebuilder : ne pas réinventer la roue
Écrire un controller à la main (informers, file de travail, leader election entre plusieurs réplicas du controller lui-même) est un travail d'infrastructure répétitif. **Kubebuilder** / **controller-runtime** fournissent ce socle tout fait : tu écris seulement la fonction `Reconcile` (Module 4), le reste (watch, cache, requeue, métriques) est généré.
```bash
kubebuilder init --domain exemple.io
kubebuilder create api --group backup --version v1 --kind BackupSchedule
```

### Ce qu'un bon Operator automatise, au-delà du déploiement initial
« Day 2 operations » : sauvegardes programmées et vérifiées, détection et promotion automatique d'un nouveau primaire en cas de panne (recap StatefulSet, palier 2 Module 8, qui ne fait **pas** ça tout seul), mise à jour de version avec une séquence précise (geler les écritures, migrer le schéma, reprendre), scaling intelligent (pas juste plus de réplicas, mais une reconfiguration du cluster de données).

### Exercice 6.1
Compare ce qu'un Deployment classique et un Operator PostgreSQL savent faire respectivement pour gérer une panne du primaire.

<details><summary>💡 Solution</summary>

Un Deployment remplace un Pod mort par un nouveau, sans aucune notion de « primaire » ou de « réplique » — il recrée simplement un conteneur avec la même image. Un Operator PostgreSQL comprend la topologie de réplication : il détecte la panne du primaire, promeut automatiquement une réplique saine comme nouveau primaire, et reconfigure les autres répliques pour suivre ce nouveau primaire.
</details>

### Exercice 6.2
Qu'apportent Kubebuilder/controller-runtime que tu devrais sinon écrire toi-même ?

<details><summary>💡 Solution</summary>

Le mécanisme d'informer (watch + cache), la file de travail gérant les nouvelles tentatives, la leader election si le controller tourne en plusieurs réplicas (pour qu'un seul agisse à la fois), l'exposition de métriques standard, et le squelette de projet — tout le code d'infrastructure répétitif, pour ne laisser à écrire que la logique métier dans `Reconcile`.
</details>

### Exercice 6.3
Donne un exemple de « Day 2 operation » qu'un bon Operator automatiserait, au-delà du simple déploiement initial.

<details><summary>💡 Solution</summary>

Une sauvegarde programmée et vérifiée automatiquement (pas juste déclenchée, mais testée en la restaurant périodiquement), ou une mise à jour de version majeure orchestrée avec la séquence correcte (geler les écritures, migrer le schéma, basculer, rouvrir) plutôt qu'un simple remplacement d'image qui risquerait de corrompre les données.
</details>

## Module 7 — Admission webhooks personnalisés

### Deux types, deux rôles
Rappel du Module 2 : un webhook **mutating** modifie l'objet, un webhook **validating** l'accepte ou le rejette — tous deux s'exécutent via un service HTTP que **tu héberges toi-même** dans le cluster.
```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: valide-labels
webhooks:
  - name: valide-labels.exemple.io
    clientConfig:
      service:
        name: webhook-service
        namespace: webhook-system
        path: "/validate"
    rules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        resources: ["pods"]
        operations: ["CREATE"]
    failurePolicy: Fail
    admissionReviewVersions: ["v1"]
    sideEffects: None
```

### `failurePolicy` : un choix de disponibilité
- **`Fail`** : si le webhook est injoignable, la requête est **rejetée** — sûr par défaut (fail-closed), mais une panne du service webhook **bloque toute création** d'objet du type concerné dans tout le cluster.
- **`Ignore`** : si le webhook est injoignable, la requête est **acceptée sans vérification** — le cluster continue de fonctionner, mais la politique n'est plus appliquée pendant la panne (fail-open).

### Une nouvelle dépendance critique
Un webhook mal dimensionné, en panne, ou trop lent devient un **point de défaillance unique pour l'API Kubernetes elle-même** : avec `failurePolicy: Fail` sur les Pods, par exemple, plus aucun Pod ne peut être créé dans le cluster tant que le webhook ne répond pas. D'où l'importance de son propre PDB, de ses propres probes, et d'un `timeoutSeconds` raisonnable.

### Exercice 7.1
Différence entre un webhook mutating et validating ?

<details><summary>💡 Solution</summary>

Un webhook mutating peut **modifier** l'objet avant sa persistance (ajouter un label, injecter une valeur par défaut). Un webhook validating ne peut qu'**accepter ou rejeter** l'objet tel quel, sans le modifier.
</details>

### Exercice 7.2
Explique le compromis entre `failurePolicy: Fail` et `failurePolicy: Ignore`.

<details><summary>💡 Solution</summary>

`Fail` est sûr par défaut (fail-closed) : aucun objet non conforme ne peut jamais passer, mais une panne du webhook bloque toute création — un risque de disponibilité. `Ignore` garde le cluster fonctionnel même si le webhook tombe, mais pendant cette panne, **aucune** politique n'est appliquée — un risque de sécurité. Le choix dépend de la criticité de la politique appliquée.
</details>

### Exercice 7.3
Pourquoi un webhook d'admission introduit-il une nouvelle dépendance critique pour l'ensemble du cluster ?

<details><summary>💡 Solution</summary>

Toute requête de création (ou modification) de la ressource concernée doit désormais attendre une réponse de ce webhook avant d'être traitée par l'API server. Si le webhook est lent, en panne, ou surchargé, il ralentit ou bloque (selon `failurePolicy`) des opérations basiques du cluster qui n'avaient auparavant aucune dépendance externe.
</details>

## Module 8 — Policy as code : OPA Gatekeeper et Kyverno

### Déclarer des politiques plutôt qu'écrire des webhooks à la main
Plutôt que de coder soi-même un webhook pour chaque règle (Module 7), les moteurs de politique exposent un **webhook générique**, déjà écrit et éprouvé, qui évalue des **règles déclaratives** que tu écris, toi, en configuration plutôt qu'en code.
| Moteur | Langage de règles |
|---|---|
| **OPA / Gatekeeper** | Rego (langage dédié, plus expressif, courbe d'apprentissage réelle) |
| **Kyverno** | YAML natif Kubernetes (plus simple à démarrer) |

### Un exemple Kyverno
```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: exiger-labels
spec:
  validationFailureAction: Enforce
  rules:
    - name: verifier-label-equipe
      match:
        resources:
          kinds: ["Pod"]
      validate:
        message: "Le label 'equipe' est obligatoire sur chaque Pod"
        pattern:
          metadata:
            labels:
              equipe: "?*"
```
```bash
kubectl apply -f policy.yaml
kubectl run test --image=nginx:1.27      # rejeté : label 'equipe' manquant
kubectl run test --image=nginx:1.27 --labels=equipe=backend    # accepté
```
`validationFailureAction: Audit` (plutôt que `Enforce`) permet de mesurer l'impact d'une nouvelle règle avant de la faire appliquer strictement — même logique de migration progressive que les Pod Security Standards (palier 2, Module 13).

### Le même principe, appliqué un cran plus bas que le cloud
C'est très exactement le rôle du **CSPM** vu dans *Networking and Cloud Expert*, Module 16 — sauf qu'ici, la surveillance et le blocage se font au niveau de **l'API Kubernetes elle-même**, et non au niveau de l'API du fournisseur cloud.

### Exercice 8.1
Comment un moteur comme Kyverno s'intègre-t-il au mécanisme de webhook d'admission du Module 7 ?

<details><summary>💡 Solution</summary>

Kyverno déploie **un seul** webhook générique (déjà écrit), qui charge et évalue dynamiquement tes `ClusterPolicy` au moment de chaque requête d'admission — tu écris des règles déclaratives en YAML plutôt que du code de webhook sur mesure pour chaque politique.
</details>

### Exercice 8.2
Écris (conceptuellement) une politique exigeant que chaque Pod déclare un label `team`.

<details><summary>💡 Solution</summary>

Voir la policy Kyverno ci-dessus, en remplaçant `equipe` par `team` : un `validate.pattern` exigeant que `metadata.labels.team` existe et ne soit pas vide (`"?*"`).
</details>

### Exercice 8.3
En quoi ce mécanisme ressemble-t-il au CSPM vu au niveau cloud (*Networking and Cloud Expert*, Module 16) ?

<details><summary>💡 Solution</summary>

Le principe est identique — surveiller et bloquer automatiquement les configurations non conformes à une politique définie — mais le périmètre diffère : le CSPM agit au niveau des ressources du **fournisseur cloud** (buckets, IAM), tandis que Gatekeeper/Kyverno agissent au niveau des objets de **l'API Kubernetes** (Pods, Deployments, NetworkPolicies).
</details>

# Partie 3 — Réseau avancé et service mesh

## Module 9 — CNI en profondeur

### Ce que fait réellement un plugin CNI
Quand le kubelet crée un Pod, il appelle un **plugin CNI** (Container Network Interface) qui, concrètement, répète ce que tu as fait à la main dans *Linux Expert*, Module 9 :
```
1. créer une paire veth
2. placer une extrémité dans le network namespace du Pod
3. attacher l'autre extrémité au réseau du nœud (souvent un bridge)
4. assigner une adresse IP au Pod (via le composant IPAM)
5. configurer les routes nécessaires
```
```bash
ls /etc/cni/net.d/              # configuration des plugins CNI installés
cat /etc/cni/net.d/10-calico.conflist
ip netns list                     # les namespaces réseau des Pods, sur le nœud
```

### IPAM : qui distribue les adresses
Le composant **IPAM** (IP Address Management) du plugin CNI assigne à chaque Pod une adresse depuis la plage CIDR dédiée du cluster (souvent une sous-plage par nœud) — directement l'application du subnetting/VLSM vus dans *Networking and Cloud Fondamentals/Intermédiaire* à l'échelle d'un cluster.

### Changer de CNI : une opération lourde
Le CNI façonne fondamentalement comment les Pods communiquent (routage, règles, encapsulation éventuelle). Le changer sur un cluster **en production** nécessite généralement de recréer tous les nœuds un par un (ou tout le cluster) : ce n'est jamais un simple remplacement de composant à chaud, contrairement à beaucoup d'autres extensions.

### Exercice 9.1
En t'appuyant sur les network namespaces et paires veth (*Linux Expert*, Module 9), décris ce qu'un plugin CNI fait à la création d'un Pod.

<details><summary>💡 Solution</summary>

Il crée une paire veth, place une extrémité dans le network namespace du Pod (lui donnant sa propre pile réseau isolée) et attache l'autre au réseau du nœud (souvent un bridge), puis assigne une IP via l'IPAM et configure les routes — exactement les étapes manuelles du Module 9 de *Linux Expert*, automatisées.
</details>

### Exercice 9.2
Quel est le rôle du composant IPAM au sein d'un plugin CNI ?

<details><summary>💡 Solution</summary>

Il distribue les adresses IP aux Pods depuis la plage CIDR allouée au cluster (souvent découpée en sous-plages par nœud), en garantissant qu'aucune IP n'est attribuée deux fois — l'équivalent, à l'échelle du cluster, de la gestion de sous-réseaux vue dans les cours réseau.
</details>

### Exercice 9.3
Pourquoi changer de plugin CNI sur un cluster de production est-il risqué et lourd ?

<details><summary>💡 Solution</summary>

Le CNI définit fondamentalement comment les Pods obtiennent leur réseau et communiquent entre eux ; deux CNI différents ne cohabitent généralement pas sur un même nœud. Le changement implique presque toujours de recréer les nœuds (et donc de redéployer les Pods dessus) un par un ou de reconstruire le cluster entier, bien au-delà d'une simple mise à jour de composant.
</details>

## Module 10 — Cilium et eBPF

### Remplacer iptables par eBPF
`kube-proxy` traditionnel programme des règles **iptables** pour chaque Service (palier 1, Module 18) — des règles évaluées **séquentiellement**, dont le nombre croît avec celui des Services et des endpoints. **Cilium** (CNI basé sur eBPF, rappel *Linux Expert*, Module 18) remplace ce mécanisme par des **programmes eBPF** utilisant des tables de hachage : la latence de résolution reste quasi constante, même avec des milliers de Services — un vrai gain à l'échelle.

### Installer et observer
```bash
cilium status
cilium connectivity test
hubble observe --namespace demo                 # flux réseau en direct, Pod par Pod
hubble observe --verdict DROPPED                  # uniquement les paquets bloqués, avec la raison
```
**Hubble** est la brique d'observabilité de Cilium : elle montre, pour chaque flux, **quelle politique** l'a autorisé ou bloqué — un niveau de détail que `kubectl` seul ne donne jamais (rappel palier 2, Module 19 : la méthodologie de dépannage y gagne une étape supplémentaire directement exploitable).

### Au-delà de L3/L4 : des NetworkPolicies conscientes de L7
Une NetworkPolicy standard (palier 2, Module 11) ne filtre que par IP/port. Cilium étend ce modèle au niveau applicatif :
```yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: api-lecture-seule
spec:
  endpointSelector:
    matchLabels: { app: api }
  ingress:
    - fromEndpoints:
        - matchLabels: { app: frontend }
      toPorts:
        - ports: [{ port: "8080", protocol: TCP }]
          rules:
            http:
              - method: "GET"
                path: "/api/.*"
```
Ici, `frontend` ne peut faire que des `GET` sur `/api/...` — même avec une connexion TCP établie sur le bon port, une requête `DELETE` est bloquée. C'est une micro-segmentation Zero Trust **au niveau applicatif** (*Networking and Cloud Expert*, Module 5), impossible avec une NetworkPolicy L3/L4 classique.

### Exercice 10.1
Explique l'avantage de performance d'un réseau basé sur eBPF (Cilium) par rapport à kube-proxy/iptables à grande échelle.

<details><summary>💡 Solution</summary>

iptables évalue ses règles **séquentiellement** : le temps de traitement croît avec le nombre de règles (donc de Services et d'endpoints). eBPF utilise des structures de données en hachage consultées en temps quasi constant, indépendamment du nombre de règles — un cluster à plusieurs milliers de Services garde une latence de résolution stable avec Cilium, là où iptables se dégraderait.
</details>

### Exercice 10.2
Que permet une NetworkPolicy consciente de L7 (Cilium) qu'une NetworkPolicy Kubernetes standard ne permet pas ?

<details><summary>💡 Solution</summary>

Une NetworkPolicy standard n'autorise ou ne bloque qu'au niveau IP/port (L3/L4) : une fois la connexion TCP autorisée, **toute** requête HTTP passe. Une policy L7-aware peut distinguer les méthodes et chemins HTTP eux-mêmes — autoriser seulement les `GET` sur certains chemins, par exemple, même à l'intérieur d'une connexion déjà permise.
</details>

### Exercice 10.3
Qu'apporte Hubble en termes d'observabilité que les commandes `kubectl` classiques n'offrent pas ?

<details><summary>💡 Solution</summary>

Hubble montre les **flux réseau réels** entre Pods, en précisant exactement quelle politique (ou absence de politique) a autorisé ou bloqué chaque paquet — une visibilité directe sur l'effet concret des NetworkPolicies, alors que `kubectl` ne montre que les objets déclarés, jamais leur effet réel sur le trafic.
</details>

## Module 11 — Service mesh : concepts fondamentaux

### Le pattern sidecar
Un service mesh injecte un **proxy** (souvent Envoy) **à côté** de chaque conteneur applicatif, dans le **même Pod** : tout le trafic entrant et sortant de l'application transite d'abord par ce sidecar, **sans aucune modification du code applicatif**.
```
┌──────────── Pod ────────────┐
│  [app]  ←→  [sidecar proxy]  │ ←→ réseau ←→ [sidecar proxy]  ←→  [app]
└──────────────────────────────┘                └──────────────────────┘
```
Un **control plane** central (Istiod pour Istio) configure dynamiquement tous ces sidecars à travers le cluster.

### Ce que le mesh apporte, sans toucher au code
- **mTLS automatique partout** : chaque sidecar négocie un chiffrement et une authentification **mutuelle** avec le sidecar destinataire — le Zero Trust (*Networking and Cloud Expert*, Module 5) appliqué **automatiquement**, sans que chaque équipe applicative ne gère ses propres certificats ;
- **gestion fine du trafic** : retries automatiques, timeouts, *circuit breaking* (cesser d'envoyer du trafic vers un service qui échoue), répartition pondérée pour un canary (*Networking and Cloud Intermédiaire*, Module 18) — appliqué au niveau L7, pas seulement via le DNS ;
- **observabilité uniforme** : chaque sidecar émet des métriques et des traces standardisées pour **chaque appel inter-service**, sans que le développeur n'ait rien instrumenté lui-même.

### Ce n'est pas gratuit
Chaque Pod héberge désormais **un conteneur de plus** (consommation CPU/mémoire supplémentaire, rappel QoS et requests/limits, Module 2 du palier 2) et **un saut réseau de plus** par appel (latence additionnelle, généralement de l'ordre du milliseconde mais non nulle). Un service mesh se justifie à partir d'un nombre de services et d'une exigence de sécurité/observabilité qui rendent ce coût rentable — pas pour trois microservices qui se parlent une fois par minute.

### Exercice 11.1
Explique le pattern sidecar et pourquoi il permet d'obtenir mTLS, retries et métriques sans modifier le code applicatif.

<details><summary>💡 Solution</summary>

Le sidecar intercepte **tout** le trafic réseau entrant et sortant du conteneur applicatif, au niveau du Pod, de façon totalement transparente pour l'application (qui continue de parler en clair sur `localhost` à son propre proxy). C'est le proxy, configuré de l'extérieur par le control plane, qui gère le chiffrement, les tentatives et la collecte de métriques — l'application n'a jamais besoin de savoir que cela existe.
</details>

### Exercice 11.2
Comment un service mesh obtient-il du Zero Trust automatique (mTLS partout) sans configuration manuelle par application ?

<details><summary>💡 Solution</summary>

Le control plane du mesh distribue et renouvelle automatiquement des certificats à chaque sidecar, et configure chaque proxy pour n'accepter que des connexions mutuellement authentifiées venant d'autres sidecars du mesh. Aucune équipe applicative n'a besoin de générer, distribuer ou renouveler le moindre certificat elle-même — le mesh le fait de façon uniforme pour tous les services qu'il couvre.
</details>

### Exercice 11.3
Quel coût un service mesh introduit-il, et pourquoi n'est-il pas justifié pour toute architecture ?

<details><summary>💡 Solution</summary>

Chaque Pod gagne un conteneur sidecar supplémentaire (consommation de ressources additionnelle à multiplier par le nombre de Pods du cluster) et chaque appel inter-service traverse un saut réseau de plus (latence additionnelle). Pour une architecture à faible nombre de services avec des exigences de sécurité/observabilité modestes, ce coût dépasse le bénéfice ; le mesh se justifie surtout à partir d'un nombre significatif de microservices et d'exigences de sécurité strictes.
</details>

## Module 12 — Istio ou Linkerd en pratique

### Installer et activer l'injection
```bash
istioctl install --set profile=demo
kubectl label namespace demo istio-injection=enabled
kubectl rollout restart deployment -n demo          # les Pods EXISTANTS doivent être recréés pour recevoir le sidecar
kubectl get pods -n demo                              # chaque Pod affiche désormais 2/2 conteneurs
```
Le label active l'injection **future** : les Pods déjà en cours d'exécution ne reçoivent le sidecar qu'après avoir été recréés (`rollout restart`).

### Vérifier le mTLS
```bash
istioctl proxy-config listeners pod-x -n demo
istioctl authn tls-check pod-x.demo
```

### Déploiement canary via le mesh (pas seulement le DNS)
```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: api
spec:
  hosts: [api]
  http:
    - route:
        - destination: { host: api, subset: v1 }
          weight: 90
        - destination: { host: api, subset: v2 }
          weight: 10
```
Comparé au DNS pondéré (*Networking and Cloud Intermédiaire*, Module 8), cette répartition se fait **au niveau du proxy L7**, requête par requête — plus précise et réactive qu'une résolution DNS mise en cache côté client.

### Exercice 12.1
Active l'injection de sidecar pour un namespace et vérifie qu'un Pod a bien 2 conteneurs.

<details><summary>💡 Solution</summary>

```bash
kubectl label namespace demo istio-injection=enabled
kubectl rollout restart deployment -n demo
kubectl get pods -n demo       # colonne READY affiche 2/2
```
</details>

### Exercice 12.2
Écris une répartition de trafic envoyant 90% vers `v1` et 10% vers `v2` d'un service (canary).

<details><summary>💡 Solution</summary>

Voir le `VirtualService` ci-dessus — `weight: 90` pour le subset `v1`, `weight: 10` pour le subset `v2`.
</details>

### Exercice 12.3
Pourquoi faut-il redémarrer les Deployments existants après avoir activé l'injection de sidecar sur un namespace ?

<details><summary>💡 Solution</summary>

Le label sur le namespace ne modifie que le comportement **futur** de l'admission (un webhook mutating, Module 7, injecte le sidecar à la création d'un nouveau Pod). Les Pods déjà en cours d'exécution ont été créés **avant** cette activation et ne possèdent pas le sidecar ; seul un redémarrage (qui recrée les Pods) déclenche l'injection pour eux.
</details>

# Partie 4 — Chaîne d'approvisionnement et sécurité runtime

## Module 13 — SBOM et signature d'images

### SBOM : savoir précisément ce qu'il y a dans une image
Un **SBOM** (Software Bill of Materials) est l'inventaire complet des composants et dépendances d'une image — bibliothèques, versions exactes, licences. Sans lui, répondre à « sommes-nous affectés par la faille annoncée aujourd'hui sur telle bibliothèque ? » exige de rescanner **toutes** les images une par une ; avec des SBOM déjà générés et archivés, une simple recherche suffit.
```bash
syft monapp:1.0.0 -o json > sbom.json
syft monapp:1.0.0 -o spdx-json          # format standardisé SPDX
```

### Signer pour prouver la provenance
Un scan de vulnérabilités (palier 1, Module 8) dit *ce qu'il y a* dans l'image. La **signature** dit *d'où elle vient réellement* : qu'elle a bien été construite par ta CI, et qu'elle n'a pas été altérée depuis.
```bash
cosign generate-key-pair
cosign sign --key cosign.key ghcr.io/mon-org/monapp:1.0.0
cosign verify --key cosign.pub ghcr.io/mon-org/monapp:1.0.0
```
**Sigstore/Fulcio** permet même une signature **sans gérer de clé privée soi-même** (certificats de courte durée liés à une identité OIDC, comme celle d'un pipeline CI) — éliminant le risque de fuite d'une clé de signature statique.

### Refuser les images non signées à l'admission
```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: exiger-signature
spec:
  validationFailureAction: Enforce
  rules:
    - name: verifie-signature-cosign
      match:
        resources:
          kinds: ["Pod"]
      verifyImages:
        - imageReferences: ["ghcr.io/mon-org/*"]
          attestors:
            - entries:
                - keys:
                    publicKeys: |-
                      -----BEGIN PUBLIC KEY-----
                      ...
                      -----END PUBLIC KEY-----
```
Ce module boucle directement avec le Module 8 : la **politique** (Kyverno) applique la **preuve cryptographique** (cosign) au moment de l'**admission** (Module 2/7).

### Exercice 13.1
À quoi sert un SBOM, concrètement, quand une vulnérabilité critique est annoncée sur une bibliothèque largement utilisée ?

<details><summary>💡 Solution</summary>

Plutôt que de rescanner chaque image une par une pour savoir si elle embarque la bibliothèque et la version vulnérables, on interroge directement les SBOM déjà générés et archivés : une simple recherche révèle immédiatement toutes les images concernées, accélérant drastiquement la réponse à incident.
</details>

### Exercice 13.2
Qu'est-ce que la signature d'image protège, que le scan de vulnérabilités (palier 1, Module 8) ne protège pas ?

<details><summary>💡 Solution</summary>

Le scan de vulnérabilités vérifie le **contenu** de l'image (quels paquets, quelles failles connues). La signature prouve la **provenance** : que cette image précise a bien été construite par un pipeline de confiance et n'a pas été modifiée ou remplacée (par exemple dans un registre compromis) depuis sa construction — une garantie différente et complémentaire.
</details>

### Exercice 13.3
Comment une politique d'admission peut-elle imposer « seules les images signées par notre CI tournent en production » ?

<details><summary>💡 Solution</summary>

Une policy Kyverno (ou Gatekeeper) avec une règle `verifyImages` vérifie, au moment de l'admission de chaque Pod, que la signature cosign de l'image correspond à la clé publique (ou à l'identité Sigstore) de la CI — toute image non signée, ou signée par une clé non reconnue, est automatiquement rejetée avant même d'être planifiée.
</details>

## Module 14 — Runtime security : Falco et détection d'anomalies

### Prévention vs détection
Les NetworkPolicies (palier 2, Module 11) et les policies d'admission (Module 8) sont de la **prévention** : elles empêchent *a priori* certaines actions. **Falco** (rappel *Linux Expert*, Module 18 : basé sur eBPF) fait de la **détection** : il observe en temps réel ce qui se passe réellement à l'intérieur des conteneurs, et alerte sur des comportements suspects — précieux précisément pour ce que la prévention n'a pas anticipé.

### Une règle Falco adaptée au contexte Kubernetes
```yaml
- rule: Shell lancé dans un conteneur de prod
  desc: Détecte l'exécution d'un shell interactif dans le namespace de production
  condition: >
    spawned_process and container and
    proc.name in (bash, sh, zsh) and
    k8s.ns.name = "prod"
  output: >
    Shell lancé dans %container.name
    (pod=%k8s.pod.name ns=%k8s.ns.name image=%container.image.repository)
  priority: WARNING
```
Falco enrichit nativement ses événements avec le contexte Kubernetes (`k8s.ns.name`, `k8s.pod.name`) — une alerte directement exploitable, sans corrélation manuelle.

### Pourquoi un shell n'est « que » suspect
Lancer un shell dans un conteneur de production n'est **pas intrinsèquement malveillant** (un opérateur en plein incident peut légitimement le faire) — mais c'est un signal **statistiquement rare et à surveiller** : en fonctionnement normal, une application ne lance jamais de shell interactif elle-même. C'est le même principe que les anomalies réseau (*Networking and Cloud Expert*, Module 6, détection par anomalie) : pas une preuve, un signal à qualifier.

### Exercice 14.1
Pourquoi détecter un shell lancé dans un conteneur de production est-il un signal de sécurité utile, même si ce n'est pas en soi la preuve d'une attaque ?

<details><summary>💡 Solution</summary>

En fonctionnement normal, une application ne lance jamais de shell interactif d'elle-même — ce comportement est donc statistiquement rare et mérite d'être examiné, qu'il s'agisse d'un opérateur légitime en intervention d'urgence ou d'un attaquant ayant obtenu une exécution de commande à distance. C'est un signal à qualifier, pas une alerte binaire de compromission certaine.
</details>

### Exercice 14.2
Différence entre ce qu'empêche une NetworkPolicy et ce que détecte Falco ?

<details><summary>💡 Solution</summary>

Une NetworkPolicy **empêche a priori** certaines connexions réseau de se produire (prévention). Falco **observe a posteriori** ce qui se passe réellement (processus lancés, appels système, accès fichiers) et alerte sur un comportement anormal — y compris des actions qu'aucune règle de prévention n'avait anticipées (détection).
</details>

### Exercice 14.3
Pourquoi la sécurité runtime (Falco) complète-t-elle, plutôt que remplace, la sécurité à l'admission (Kyverno/Gatekeeper, Module 8) ?

<details><summary>💡 Solution</summary>

L'admission ne peut bloquer que ce qui est visible et vérifiable **avant** l'exécution (la configuration déclarée d'un Pod). Une fois le conteneur en cours d'exécution, son comportement réel peut diverger de ce que sa configuration laissait prévoir (une vulnérabilité exploitée, une dépendance compromise) — seule une observation en continu comme Falco peut détecter ce qui se passe **après** que l'admission a déjà laissé passer l'objet.
</details>

## Module 15 — Chiffrement avancé et KMS pour etcd

### Au-delà du principe (rappel palier 2, Module 15)
Le chiffrement au repos d'etcd se configure via un fichier `EncryptionConfiguration` sur l'API server, avec un ou plusieurs **providers** :
```yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources: ["secrets"]
    providers:
      - kms:
          name: monkms
          endpoint: unix:///var/run/kmsplugin/socket.sock
      - identity: {}
```

### Pourquoi un KMS externe plutôt qu'une clé locale statique
Une clé de chiffrement stockée en local sur le disque du control plane est elle-même une cible : qui accède au disque accède à la clé **et** aux données chiffrées. Un **KMS externe** (Vault, un KMS cloud — *Networking and Cloud Intermédiaire*, Module 11) garde la clé maîtresse **hors** du cluster, avec sa propre gouvernance d'accès et de rotation — exactement le chiffrement enveloppe déjà vu : etcd chiffre les données avec une clé locale, elle-même chiffrée par la clé maîtresse du KMS.

### L'ordre des providers compte, et une rotation exige une migration
Le **premier** provider de la liste chiffre toutes les **nouvelles** écritures ; les suivants ne servent qu'à **déchiffrer** les anciennes données existantes. Changer de clé ou de provider ne rechiffre **pas** automatiquement les Secrets déjà présents dans etcd : il faut une étape explicite de migration (généralement en réécrivant chaque Secret pour forcer son chiffrement avec le nouveau provider) ; `identity` (pas de chiffrement) reste en dernier recours pendant une migration initiale, pour lire les anciennes données non encore chiffrées.

### Exercice 15.1
Pourquoi un KMS externe est-il généralement préféré à une clé de chiffrement locale statique pour etcd ?

<details><summary>💡 Solution</summary>

Une clé locale statique est stockée sur le même système que les données qu'elle protège : compromettre le disque du control plane donne accès à la fois à la clé et aux données chiffrées. Un KMS externe garde la clé maîtresse dans un système séparé avec sa propre gouvernance d'accès et sa rotation automatisée — une compromission du control plane seul ne suffit plus à déchiffrer les données.
</details>

### Exercice 15.2
Tu changes de clé de chiffrement dans la configuration. Que deviennent les Secrets déjà chiffrés avec l'ancienne clé, et pourquoi faut-il une étape de migration ?

<details><summary>💡 Solution</summary>

Ils restent chiffrés avec l'**ancienne** clé — le changement de configuration n'affecte que les **nouvelles** écritures. Il faut une migration explicite (relire puis réécrire chaque Secret existant) pour qu'ils soient effectivement rechiffrés avec la nouvelle clé ; sans cette étape, l'ancienne clé doit rester disponible indéfiniment pour pouvoir encore déchiffrer les anciennes données.
</details>

### Exercice 15.3
Pourquoi le provider `identity` (aucun chiffrement) reste-t-il listé en dernier pendant une migration vers le chiffrement ?

<details><summary>💡 Solution</summary>

Au moment d'activer le chiffrement pour la première fois, les Secrets déjà existants dans etcd sont encore **non chiffrés**. Le provider `identity` en dernier recours permet à l'API server de continuer à **lire** ces anciennes données non chiffrées pendant la période de transition, le temps que la migration les réécrive effectivement avec le nouveau provider de chiffrement.
</details>

# Partie 5 — GitOps, multi-cluster et opérations

## Module 16 — GitOps et Argo CD

### Push vs pull : un changement d'architecture, pas juste d'outil
Un pipeline CI/CD classique (*Networking and Cloud Intermédiaire*, Module 18) **pousse** les changements vers le cluster : la CI détient des identifiants avec le droit d'écrire dans le cluster de production — une surface d'attaque significative si la CI est compromise. En **GitOps**, c'est l'inverse : un controller **à l'intérieur du cluster** (Argo CD, Flux) **tire** en continu l'état désiré depuis Git et l'applique — aucun système externe n'a besoin d'un accès en écriture au cluster.

### Argo CD en pratique
```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: api
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/mon-org/manifests
    targetRevision: main
    path: overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: prod
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```
```bash
argocd app get api
argocd app sync api
argocd app history api
argocd app rollback api <id-revision>
```

### `selfHeal` : la dérive d'état, en continu
`selfHeal: true` reprend exactement le concept de **dérive d'état** vu avec Terraform (*Networking and Cloud Intermédiaire*, Module 10) — sauf qu'ici, la détection et la correction sont **continues**, pas seulement à la demande d'un `plan` : si quelqu'un modifie manuellement une ressource dans le cluster, Argo CD **annule silencieusement** ce changement pour revenir à ce que déclare Git. C'est une discipline forte (plus de modification manuelle « juste pour dépanner vite ») autant qu'une garantie de cohérence.

### Git devient le journal d'audit complet
Chaque changement d'infrastructure passe par une **pull request** : qui a changé quoi, quand, pourquoi (message de commit), avec revue par les pairs — l'historique Git **est** l'historique des changements du cluster, consultable et rejouable (`git revert` = rollback).

### Exercice 16.1
Différence entre un pipeline CI/CD qui pousse vers le cluster et un controller GitOps qui tire depuis Git ?

<details><summary>💡 Solution</summary>

Dans le modèle push, la CI détient des identifiants avec accès en écriture au cluster de production — une compromission de la CI expose directement le cluster. Dans le modèle pull (GitOps), le controller tourne **à l'intérieur** du cluster et va lui-même chercher l'état désiré dans Git ; aucun système externe n'a besoin d'un accès en écriture au cluster, réduisant la surface d'attaque.
</details>

### Exercice 16.2
Explique `selfHeal: true` et son lien avec la détection de dérive Terraform (*Networking and Cloud Intermédiaire*, Module 10).

<details><summary>💡 Solution</summary>

C'est le même concept de dérive — l'état réel du cluster divergeant de ce qui est déclaré comme source de vérité — mais appliqué en continu plutôt qu'à la demande : Terraform détecte la dérive au prochain `plan` exécuté manuellement, alors qu'Argo CD avec `selfHeal` la détecte et la corrige automatiquement dès qu'elle survient, sans attendre une action humaine.
</details>

### Exercice 16.3
Pourquoi Git devient-il un journal d'audit complet des changements d'infrastructure avec GitOps ?

<details><summary>💡 Solution</summary>

Puisque **toute** modification de l'état désiré doit passer par un commit (et généralement une pull request revue) dans le dépôt Git source de vérité, l'historique Git enregistre automatiquement qui a changé quoi, quand et pourquoi — sans nécessiter un système de journalisation séparé, et avec la possibilité de revenir à n'importe quel état antérieur via `git revert`.
</details>

## Module 17 — Multi-cluster : stratégies et Cluster API

### Pourquoi plusieurs clusters plutôt qu'un seul géant
Les mêmes raisons qui justifiaient les comptes cloud séparés (*Networking and Cloud Expert*, Module 11 : rayon d'impact, conformité, isolation) s'appliquent à l'échelle d'un cluster Kubernetes : un cluster par **environnement** (dev/staging/prod), par **région** (latence, résidence des données), ou par **équipe/tenant** (isolation forte, quotas indépendants) limite la portée d'une erreur de configuration ou d'une compromission à un seul périmètre plutôt qu'à l'ensemble.

### Cluster API : déclarer des clusters comme on déclare des Pods
Provisionner un cluster à la main (`kubeadm` nœud par nœud) ne passe pas à l'échelle au-delà de quelques clusters. **Cluster API** étend le modèle déclaratif de Kubernetes **au cycle de vie des clusters eux-mêmes** :
```yaml
apiVersion: cluster.x-k8s.io/v1beta1
kind: Cluster
metadata:
  name: cluster-prod-eu
spec:
  clusterNetwork:
    pods:
      cidrBlocks: ["10.244.0.0/16"]
  infrastructureRef:
    kind: AWSCluster
    name: cluster-prod-eu
```
Un cluster de **management** (lui-même Kubernetes) gère ainsi le provisionnement, la mise à l'échelle et les mises à jour de nombreux clusters **cibles**, via les mêmes principes de boucle de réconciliation vus au Module 4 — appliqués ici aux clusters plutôt qu'aux Pods.

### Le défi : la découverte de services au-delà d'un cluster
CoreDNS (palier 2, Module 10) ne résout que des noms **à l'intérieur** d'un cluster. Un service tournant sur le cluster A n'a, par défaut, **aucun moyen** d'être découvert par nom depuis le cluster B — il faut un mécanisme dédié (API Multi-Cluster Services, ou l'extension multi-cluster d'un service mesh, Module 11) pour étendre la découverte de services et, le cas échéant, le mTLS au-delà des frontières d'un seul cluster.

### Exercice 17.1
Donne une raison de répartir des charges sur plusieurs clusters Kubernetes plutôt que sur un seul cluster partagé géant.

<details><summary>💡 Solution</summary>

Limiter le **rayon d'impact** : une erreur de configuration RBAC, un quota mal posé, ou une compromission touchant un cluster reste cantonnée à ce cluster précis, plutôt que de risquer d'affecter toutes les équipes et environnements partageant un unique cluster — la même logique que les comptes cloud multiples (*Networking and Cloud Expert*, Module 11), appliquée au niveau Kubernetes.
</details>

### Exercice 17.2
Qu'apporte Cluster API par rapport à un provisionnement manuel de chaque cluster via `kubeadm` ?

<details><summary>💡 Solution</summary>

Cluster API déclare le cycle de vie d'un cluster (création, mise à l'échelle, mise à jour) de façon **déclarative**, géré par une boucle de réconciliation — exactement comme un Deployment déclare l'état désiré de ses Pods. Provisionner manuellement via `kubeadm` nœud par nœud ne passe pas à l'échelle dès qu'on gère plus de quelques clusters, et ne bénéficie d'aucune réconciliation automatique en cas de dérive.
</details>

### Exercice 17.3
Pourquoi la découverte de services entre deux clusters distincts est-elle plus complexe qu'au sein d'un seul cluster ?

<details><summary>💡 Solution</summary>

CoreDNS, par défaut, ne connaît que les Services déclarés **dans son propre cluster** — un Service du cluster A n'a aucune existence dans le DNS du cluster B. Il faut un mécanisme dédié (API Multi-Cluster Services, extension multi-cluster d'un service mesh) pour synchroniser cette information de découverte au-delà des frontières naturelles d'un cluster, ce que l'architecture de base de Kubernetes ne prévoit pas nativement.
</details>

## Module 18 — Mises à jour de cluster

### L'ordre n'est jamais négociable
Le plan de contrôle est **toujours** mis à jour en premier, puis les nœuds workers — jamais l'inverse. La politique de compatibilité de version de Kubernetes garantit qu'un kubelet peut être en retard de quelques versions mineures sur l'API server, **jamais en avance** : un plan de contrôle plus ancien ne comprendrait pas forcément les objets envoyés par des kubelets plus récents.

### Mettre à jour un nœud sans interruption
La séquence reprend directement le Module 6 du palier 2 :
```bash
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data
# mise à jour effective du kubelet/OS sur node-1
kubectl uncordon node-1
```
Répétée **nœud par nœud**, cette rotation ne cause aucune interruption **à condition que** les applications aient suffisamment de réplicas, une anti-affinité ou un topology spread adapté, et un PodDisruptionBudget cohérent (palier 2, Modules 3 et 6) — sans ces garde-fous déjà en place, un `drain` peut tout de même causer une coupure.

### Toujours tester sur un cluster non-prod d'abord
Un upgrade majeur peut retirer des **API dépréciées** (une CRD en `v1beta1`, par exemple, cf. Module 5) : exécuter `kubectl get --raw /apis` avant l'upgrade, ou un outil dédié de détection d'API dépréciées, permet de corriger les manifestes concernés **avant** que l'upgrade ne les rende silencieusement invalides.

### Exercice 18.1
Pourquoi met-on toujours à jour le plan de contrôle avant les nœuds workers, jamais l'inverse ?

<details><summary>💡 Solution</summary>

La politique de compatibilité de version de Kubernetes garantit qu'un kubelet peut être légèrement en retard par rapport à l'API server, mais pas en avance. Si un nœud worker était mis à jour en premier, son kubelet pourrait envoyer des informations ou attendre un comportement qu'un plan de contrôle plus ancien ne sait pas encore gérer.
</details>

### Exercice 18.2
Décris la séquence pour mettre à jour un nœud worker sans interruption, en supposant des réplicas et des PDB adéquats.

<details><summary>💡 Solution</summary>

`kubectl drain` (évince proprement les Pods en respectant les PDB), effectuer la mise à jour du nœud, puis `kubectl uncordon` pour le rendre à nouveau planifiable — répété nœud par nœud, jamais plusieurs à la fois si cela risque de descendre sous le `minAvailable` des applications concernées.
</details>

### Exercice 18.3
Pourquoi vérifier les API dépréciées avant une mise à jour majeure de version est-il une étape critique ?

<details><summary>💡 Solution</summary>

Une nouvelle version de Kubernetes peut **retirer complètement** le support d'anciennes versions d'API (pas seulement les déprécier). Un manifeste encore écrit avec cette ancienne `apiVersion` deviendrait silencieusement inapplicable après l'upgrade — vérifier et migrer ces manifestes en amont évite une panne découverte seulement après coup, au pire moment.
</details>

## Module 19 — Reprise après sinistre pour Kubernetes

### Ce qu'un instantané etcd couvre, et ce qu'il ne couvre pas
Un instantané etcd (Module 1) restaure la définition de **tous** les objets Kubernetes — Deployments, Services, Secrets, CRD. Il ne restaure **jamais** le contenu des **PersistentVolumes** (palier 2, Module 7) : les données réelles d'une base de données, par exemple, vivent sur un disque cloud totalement séparé d'etcd.

### Velero : sauvegarder les deux à la fois, de façon cohérente
```bash
velero backup create prod-backup --include-namespaces prod
velero backup describe prod-backup --details
velero restore create --from-backup prod-backup
```
Velero sauvegarde **à la fois** les manifestes Kubernetes (comme le ferait un export etcd ciblé) **et** déclenche des **snapshots** des volumes persistants associés — une sauvegarde cohérente de l'application entière, pas seulement de sa définition.

### Le plan ne vaut que ce que vaut sa dernière restauration testée
Reprend directement le principe du **chaos engineering** et des **game days** (*Networking and Cloud Expert*, Module 14) : un plan de reprise jamais testé par une restauration réelle n'est qu'une hypothèse. Le vrai test : restaurer `prod-backup` dans un cluster **séparé**, vérifier que l'application démarre et que les données sont cohérentes — et mesurer le temps réellement nécessaire, à comparer au **RTO** documenté (*Networking and Cloud Intermédiaire*, Module 15).

### Exercice 19.1
Pourquoi sauvegarder uniquement etcd n'est-il pas une reprise après sinistre suffisante pour une application avec des PersistentVolumes ?

<details><summary>💡 Solution</summary>

etcd restaure la **définition** des objets (le PVC existera à nouveau, avec sa taille et sa StorageClass déclarées) mais pas le **contenu** réel du disque associé, qui vit en dehors d'etcd. Une restauration etcd seule redonnerait une base de données avec sa structure Kubernetes intacte, mais un disque vide ou absent.
</details>

### Exercice 19.2
Qu'est-ce que Velero sauvegarde et restaure, que ne couvre pas un simple instantané etcd ?

<details><summary>💡 Solution</summary>

Velero combine la sauvegarde des manifestes Kubernetes **et** le déclenchement de snapshots des volumes persistants associés, de façon coordonnée — restaurant ainsi une application complète (sa définition **et** ses données), alors qu'un instantané etcd seul ne couvre que la définition.
</details>

### Exercice 19.3
En t'appuyant sur le cadre RTO/RPO, explique pourquoi un plan de reprise pour un cluster doit être testé par un vrai exercice de restauration plutôt que simplement documenté.

<details><summary>💡 Solution</summary>

Le RTO documenté (temps de restauration visé) n'est qu'une estimation tant qu'elle n'a pas été mesurée en conditions réelles — une procédure de restauration peut comporter des étapes manuelles oubliées, des dépendances non anticipées, ou simplement prendre bien plus longtemps que prévu. Seul un exercice de restauration réel, dans un environnement séparé, révèle le RTO **effectif** et permet de corriger le plan avant qu'un incident réel ne force à le découvrir dans l'urgence.
</details>

# Partie 6 — Synthèse

## Module 20 — Projet de synthèse : une plateforme Kubernetes complète

### Le brief
Sur un cluster `kind` multi-nœuds, construis une plateforme qui recombine l'ensemble du palier :

1. Un **CRD + Operator** minimal `BackupSchedule` (Modules 5-6) : le controller traduit chaque instance en CronJob (recap palier 2, Module 5), et supprime le CronJob si la ressource est supprimée.
2. Une **politique Kyverno** (Module 8) exigeant : un label `team` sur chaque Pod, et une **signature cosign valide** (Module 13) pour toute image venant de ton registre.
3. **Cilium** installé (Module 10), avec une `CiliumNetworkPolicy` L7 limitant un service `frontend` à des `GET` sur `/api/.*` d'un service `api`.
4. Un **service mesh** (Istio ou Linkerd, Modules 11-12) activé sur le namespace applicatif, avec un `VirtualService` répartissant 90/10 le trafic entre deux versions de `api` (canary), et une vérification du mTLS actif.
5. **Falco** (Module 14) avec une règle personnalisée détectant un shell lancé dans le namespace de production.
6. Toute la configuration ci-dessus déclarée dans un **dépôt Git**, synchronisée par une **Application Argo CD** (Module 16) avec `selfHeal: true` — démontre la correction automatique d'une modification manuelle.
7. Une **sauvegarde Velero** (Module 19) du namespace applicatif (manifestes + volumes), **restaurée avec succès** dans un second cluster `kind`, avec le temps de restauration mesuré et comparé à un RTO cible que tu te fixes.
8. Un **runbook de mise à jour** de cluster (Module 18) : ordre des opérations, étapes `drain`/`uncordon` nœud par nœud, vérification préalable des API dépréciées.

### Pourquoi ce projet
Il recombine tout le palier : internals et extension (M1-M8), réseau et mesh (M9-M12), chaîne d'approvisionnement et runtime (M13-M15), opérations (M16-M19). Si tu le mènes à bien et sais expliquer **pourquoi** chaque brique est là, tu as le niveau expert — et tu as, de fait, construit une maquette réduite de ce que fait tourner une plateforme Kubernetes de production sérieuse.

<details><summary>💡 Solution guidée (vue d'ensemble)</summary>

```
Dépôt Git (source de vérité)
 └─ overlays/prod/
     ├─ crd-operator/              # BackupSchedule + son controller (image signée)
     ├─ policies/                   # ClusterPolicy Kyverno (labels + signature)
     ├─ network/                     # CiliumNetworkPolicy L7
     ├─ mesh/                         # VirtualService (canary 90/10)
     └─ falco/                         # règle personnalisée

Argo CD (dans le cluster) ──pull continu──> applique tout ce qui précède
     └─ selfHeal: true → toute modification manuelle hors Git est annulée automatiquement

Vérifications :
  kubectl get backupschedules,cronjobs -n prod        # l'operator a bien créé le CronJob
  kubectl run test -n prod --image=monapp:non-signee    # rejeté par Kyverno (signature)
  hubble observe --namespace prod --verdict DROPPED       # confirme le blocage L7 hors /api/GET
  istioctl authn tls-check <pod> ; for i in {1..20}; do curl api; done | sort | uniq -c   # ~90/10
  # Simuler un shell suspect :
  kubectl exec -n prod <pod> -- sh                          # Falco doit émettre une alerte WARNING

Velero :
  velero backup create prod-backup --include-namespaces prod
  # sur un second cluster kind :
  velero restore create --from-backup prod-backup
  # mesurer le temps total, comparer au RTO cible documenté
```
</details>

## Cheat-sheet

| Catégorie | Repères clés |
|---|---|
| etcd | Raft, majorité, nombre impair de membres, `snapshot save/restore` |
| API server | Authn → Authz (RBAC) → Admission (mutating puis validating) → etcd |
| Scheduler | filtrage → scoring ; `schedulerName` pour un scheduler dédié |
| Controller | informer (watch+cache), réconciliation par niveau, idempotence |
| CRD | nouveau type d'API ; `served`/`storage` ; sans controller = juste de la donnée |
| Operator | encode le savoir-faire opérationnel (Day 2) ; controller-runtime/Kubebuilder |
| Webhooks | mutating avant validating ; `failurePolicy: Fail` (sûr, fragile) vs `Ignore` |
| Policy as code | OPA/Gatekeeper (Rego) ou Kyverno (YAML) ; `Audit` avant `Enforce` |
| CNI | crée veth + IPAM ; changer de CNI = reconstruction, jamais à chaud |
| Cilium/eBPF | tables de hachage ≠ règles séquentielles ; NetworkPolicy L7 ; Hubble |
| Service mesh | sidecar + control plane ; mTLS auto, traffic management, observabilité — pas gratuit |
| SBOM/signature | SBOM = inventaire, signature = provenance ; cosign + Sigstore |
| Falco | détection runtime (vs prévention à l'admission) ; contexte K8s natif |
| KMS etcd | 1er provider chiffre, `identity` en dernier recours ; rotation = migration explicite |
| GitOps | pull (Argo CD/Flux) ≠ push (CI classique) ; `selfHeal` = anti-dérive continue |
| Multi-cluster | rayon d'impact réduit ; Cluster API = déclaratif ; découverte cross-cluster à part |
| Upgrade | control plane d'abord ; `drain`/`uncordon` nœud par nœud ; vérifier les API dépréciées |
| DR Kubernetes | etcd ≠ données des PV ; Velero = manifestes + snapshots ; tester, pas supposer |

## Glossaire

| Terme | Définition |
|---|---|
| **Raft** | algorithme de consensus d'etcd (élection de leader, réplication par majorité) |
| **Admission control** | étape du pipeline API server qui mute puis valide un objet avant persistance |
| **Informer** | mécanisme watch + cache utilisé par les controllers pour réagir aux changements |
| **CRD** | Custom Resource Definition, nouveau type d'objet dans l'API Kubernetes |
| **Operator** | CRD + controller encodant le savoir-faire opérationnel d'une application |
| **Admission webhook** | service HTTP personnalisé appelé pendant l'admission (mutating/validating) |
| **Policy as code** | règles de conformité déclaratives appliquées via l'admission (OPA/Kyverno) |
| **IPAM** | composant d'un plugin CNI qui distribue les adresses IP aux Pods |
| **Sidecar** | conteneur proxy injecté dans chaque Pod par un service mesh |
| **mTLS** | authentification et chiffrement mutuels entre deux parties |
| **SBOM** | inventaire complet des composants et dépendances d'une image |
| **Sigstore / cosign** | infrastructure et outil de signature d'images sans gestion manuelle de clé |
| **Runtime security** | détection de comportements anormaux pendant l'exécution (Falco) |
| **GitOps** | Git comme source de vérité, réconcilié en continu par un controller dans le cluster |
| **Cluster API** | gestion déclarative du cycle de vie des clusters Kubernetes eux-mêmes |
| **RTO / RPO (cluster)** | temps de restauration visé / perte de données tolérée, appliqués à un cluster entier |
