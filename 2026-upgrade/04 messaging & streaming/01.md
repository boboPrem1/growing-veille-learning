# Partie 1 — Penser en événements

## Module 1 — Pourquoi la messagerie ? Du couplage synchrone à l'asynchrone

### Le problème de l'appel direct
Un service qui appelle un autre service en HTTP (synchrone) crée un **couplage fort** : si le second est lent ou indisponible, le premier attend, échoue, ou doit implémenter lui-même des tentatives et un repli — exactement le constat qui justifiait déjà les files d'attente dans *Networking and Cloud Intermédiaire*, Module 14. Ce cours reprend ce fil et le creuse pour en faire une compétence à part entière.

### Découpler avec un broker de messages
```
Appel direct (synchrone) :
  Service Commandes ──HTTP──> Service Notifications
  (si Notifications est lent/down, Commandes attend ou échoue)

Avec un broker (asynchrone) :
  Service Commandes ──publie──> [ Broker ] ──livre──> Service Notifications
  (Commandes publie et continue ; le broker garde le message jusqu'à ce que Notifications soit prêt)
```
Le service producteur n'a plus besoin de connaître **qui** consomme l'événement, ni **combien** de consommateurs existent, ni **quand** ils le traiteront — c'est l'inversion de dépendance appliquée à la communication inter-services.

### Ce que l'asynchrone gagne, et ce qu'il complique
| Gain | Nouvelle complexité |
|---|---|
| Résilience : une panne du consommateur ne bloque pas le producteur | Cohérence éventuelle : le consommateur traite l'événement **après coup**, jamais instantanément |
| Absorption des pics (le broker lisse la charge) | Débogage plus difficile : le trajet d'une donnée n'est plus un simple appel traçable d'un coup d'œil |
| Plusieurs consommateurs indépendants pour un même événement | Idempotence requise (Module 14) : un message peut être livré plus d'une fois |

### Exercice 1.1
Un service de paiement appelle en HTTP synchrone un service d'envoi d'e-mails de confirmation. Explique ce qui se passe si le service d'e-mails tombe en panne, puis comment un broker de messages changerait ce comportement.

<details><summary>💡 Solution</summary>

En appel direct, le service de paiement **attend** la réponse du service d'e-mails ; si ce dernier est en panne, l'appel échoue ou expire, ce qui peut faire échouer (ou ralentir inutilement) le paiement lui-même — alors que l'envoi d'un e-mail n'a rien à voir avec la validité du paiement. Avec un broker, le service de paiement **publie** un événement « paiement confirmé » et continue immédiatement ; le message reste dans le broker jusqu'à ce que le service d'e-mails (une fois rétabli) vienne le consommer.
</details>

### Exercice 1.2
Cite un gain et une complexité nouvelle introduits par le passage d'un appel synchrone à un événement asynchrone.

<details><summary>💡 Solution</summary>

Gain, par exemple : la panne d'un consommateur n'empêche plus le producteur de continuer son travail. Complexité, par exemple : la cohérence devient « éventuelle » — le consommateur traite l'information avec un léger délai, jamais de façon strictement instantanée comme un appel synchrone bloquant.
</details>

### Exercice 1.3
Pourquoi un même événement « commande créée » peut-il légitimement avoir plusieurs consommateurs indépendants (facturation, notification, analytique) sans que le producteur n'en sache rien ?

<details><summary>💡 Solution</summary>

Le producteur publie l'événement vers le broker sans connaître ni le nombre ni l'identité de ceux qui le liront — c'est précisément le découplage recherché. N'importe quel nouveau service peut s'abonner plus tard au même flux d'événements sans la moindre modification du service producteur, ce qu'un appel HTTP direct ne permettrait pas sans ajouter explicitement un nouvel appel pour chaque nouveau consommateur.
</details>

## Module 2 — Patterns de messagerie : queue vs pub/sub

### Deux modèles de distribution, deux usages
| Modèle | Principe | Effet sur le message |
|---|---|---|
| **File d'attente (queue)** | chaque message est consommé par **un seul** destinataire parmi un groupe de travailleurs | le message disparaît de la file une fois traité (répartition de charge) |
| **Publish/Subscribe (pub/sub)** | chaque message est livré à **tous** les abonnés indépendants | chaque abonné reçoit sa propre copie, indépendamment des autres |

### Une image simple
```
Queue (répartition de charge) :
  Producteur → [ File ] → Travailleur A  (reçoit le message 1)
                        → Travailleur B  (reçoit le message 2)
  (un message = un seul traitant)

Pub/Sub (diffusion) :
  Producteur → [ Sujet ] → Abonné Facturation   (reçoit SA copie)
                         → Abonné Notification   (reçoit SA copie)
                         → Abonné Analytique      (reçoit SA copie)
  (un message = autant de copies que d'abonnés)
```

### Kafka fait les deux à la fois, via les groupes de consommateurs
C'est l'un des points les plus souvent mal compris de Kafka, et il sera détaillé au Module 6 : un même **topic** Kafka se comporte comme une **queue** à l'intérieur d'un groupe de consommateurs (les messages s'y répartissent entre les instances du groupe) et comme du **pub/sub** entre plusieurs groupes de consommateurs différents (chaque groupe reçoit sa propre copie complète du flux).

### Exercice 2.1
Une plateforme de traitement d'images doit répartir un flux de tâches entre 5 workers, chaque tâche ne devant être traitée qu'une seule fois. Queue ou pub/sub ?

<details><summary>💡 Solution</summary>

**Queue** : on veut répartir la charge, chaque tâche allant à un seul worker disponible, pas la dupliquer vers les 5 à la fois.
</details>

### Exercice 2.2
Un événement « nouvel utilisateur inscrit » doit déclencher à la fois l'envoi d'un e-mail de bienvenue, la création d'un profil analytique, et une entrée dans le CRM commercial. Queue ou pub/sub ?

<details><summary>💡 Solution</summary>

**Pub/sub** : les trois traitements sont indépendants et doivent **chacun** recevoir l'événement complet — ce n'est pas une répartition de charge entre traitants interchangeables, mais une diffusion vers trois consommateurs aux rôles différents.
</details>

### Exercice 2.3
Explique, en une phrase, comment Kafka peut se comporter à la fois comme une queue et comme du pub/sub.

<details><summary>💡 Solution</summary>

À l'intérieur d'un même groupe de consommateurs, les messages d'un topic se répartissent entre les instances comme une queue ; entre plusieurs groupes de consommateurs distincts, chaque groupe reçoit sa propre copie complète du flux, comme du pub/sub.
</details>

## Module 3 — Panorama des brokers : Kafka, RabbitMQ, NATS, SQS/SNS

### Les familles, et ce qui les distingue vraiment
| Broker | Famille | Point fort | Point faible relatif |
|---|---|---|---|
| **Kafka** | log distribué, rejouable | très haut débit, conservation longue des messages, rejeu possible | plus lourd à opérer, latence par message un peu plus élevée que NATS |
| **RabbitMQ** | broker de queues traditionnel (AMQP) | routage très flexible (exchanges), mature | pas conçu pour conserver un historique rejouable à grande échelle |
| **NATS** | messagerie légère, cloud native | ultra-léger, latence minimale, simplicité opérationnelle | moins de garanties de persistance par défaut (JetStream l'ajoute, Module 17) |
| **SQS / SNS** | managé, cloud (AWS) | zéro opération (géré par le fournisseur) | lié à un fournisseur cloud, moins de contrôle fin |

### La question qui tranche le plus souvent : rejouer l'historique ou pas ?
C'est la différence la plus structurante pour choisir : Kafka **conserve** les messages consommés (ils ne disparaissent pas après lecture, contrairement à une queue classique) et permet de **rejouer** le flux depuis n'importe quel point passé — utile pour reconstruire un état, déboguer un incident, ou brancher un nouveau consommateur qui doit « rattraper » l'historique. RabbitMQ et NATS « simple » (sans JetStream) suppriment le message une fois qu'il est accusé-réception.

### Pourquoi ce cours se concentre sur Kafka, avec NATS en complément
Kafka domine très largement l'écosystème **streaming** (et c'est la techno explicitement citée dans le paysage CNCF pour cette catégorie) ; NATS illustre l'alternative **légère**, pertinente quand Kafka serait disproportionné. RabbitMQ et SQS/SNS sont mentionnés ici pour le panorama, mais ne sont pas couverts en pratique dans ce cours.

### Exercice 3.1
Une équipe veut pouvoir rejouer trois mois d'historique de transactions pour reconstruire un tableau de bord après un bug découvert tardivement. Quel type de broker privilégier, et pourquoi ?

<details><summary>💡 Solution</summary>

Un broker de type **log distribué comme Kafka**, qui conserve les messages après consommation et permet de repositionner un consommateur à n'importe quel offset passé — une file d'attente classique (RabbitMQ, SQS) aurait déjà supprimé ces messages une fois accusés-réception, rendant le rejeu impossible sans une architecture de stockage séparée.
</details>

### Exercice 3.2
Une petite flotte de capteurs IoT doit publier des mesures toutes les secondes avec une latence minimale, sans besoin de conserver un historique long. Quel broker serait naturellement adapté ?

<details><summary>💡 Solution</summary>

**NATS** : sa légèreté et sa latence minimale conviennent bien à de la télémétrie haute fréquence sans besoin de rejeu d'historique — déployer Kafka pour ce seul besoin serait disproportionné en complexité opérationnelle.
</details>

### Exercice 3.3
Pourquoi la capacité à « rejouer » un flux de messages est-elle une question structurante dans le choix d'un broker, plus que le simple débit ?

<details><summary>💡 Solution</summary>

Le débit se dimensionne généralement par la configuration (plus de partitions, plus de brokers). La capacité de rejeu, elle, est une propriété **architecturale** du broker : un système conçu pour supprimer les messages consommés ne peut pas être reconfiguré après coup pour les conserver indéfiniment — c'est un choix à faire en amont, en fonction du besoin réel (reconstruire un état, déboguer, brancher un nouveau consommateur en retard).
</details>

# Partie 2 — Kafka : les fondamentaux

## Module 4 — Architecture : brokers, topics, partitions

### Les briques de base
| Terme | Définition |
|---|---|
| **Broker** | un serveur Kafka ; un cluster en contient un ou plusieurs |
| **Topic** | un flux nommé d'événements (ex : `commandes.creees`) |
| **Partition** | une **division** d'un topic ; l'unité réelle de parallélisme et d'ordonnancement |
| **Réplication** | chaque partition est dupliquée sur plusieurs brokers pour la résilience (approfondi au palier 2) |

### Un topic n'est pas un fichier unique : c'est un ensemble de journaux ordonnés
```
Topic "commandes.creees" (3 partitions)
 ├─ Partition 0 : [msg0][msg1][msg4][msg7]...
 ├─ Partition 1 : [msg2][msg5][msg8]...
 └─ Partition 2 : [msg3][msg6][msg9]...
```
Chaque partition est un **journal append-only** : les messages y sont ajoutés dans l'ordre d'arrivée et numérotés par un **offset** croissant (0, 1, 2...), jamais modifiés ni réordonnés après écriture.

### Pourquoi plusieurs partitions
Une seule partition limite le débit du topic à ce qu'**un seul** processus peut lire ou écrire. Plusieurs partitions permettent de **paralléliser** la lecture et l'écriture — au prix d'une garantie importante à retenir dès maintenant : **l'ordre n'est garanti qu'à l'intérieur d'une partition**, jamais entre partitions différentes d'un même topic (creusé au Module 15).

### Exercice 4.1
Un topic a 4 partitions. Que se passe-t-il, en termes d'ordre, pour deux messages envoyés vers des partitions différentes ?

<details><summary>💡 Solution</summary>

Aucun ordre n'est garanti entre eux : Kafka ne garantit l'ordre **qu'à l'intérieur** d'une même partition. Deux messages dans des partitions différentes peuvent être lus dans un ordre quelconque par les consommateurs.
</details>

### Exercice 4.2
Pourquoi un seul broker avec une seule partition limite-t-il mécaniquement le débit maximal d'un topic ?

<details><summary>💡 Solution</summary>

Une seule partition ne peut être écrite et lue que de façon séquentielle par un nombre limité de processus à la fois (un seul consommateur actif par partition au sein d'un groupe, Module 6) — le débit total du topic plafonne donc à ce qu'un seul flux séquentiel peut traiter, quel que soit le nombre de machines disponibles par ailleurs.
</details>

### Exercice 4.3
Qu'est-ce qu'un offset, et pourquoi ne décrit-il la position d'un message que relativement à **sa** partition ?

<details><summary>💡 Solution</summary>

L'offset est le numéro d'ordre croissant d'un message **au sein d'une partition précise** (0, 1, 2...) — chaque partition a sa propre numérotation indépendante, qui recommence à 0. Un offset n'a donc de sens que combiné au couple (topic, partition) auquel il appartient ; le même nombre d'offset existe dans chaque partition, pour des messages complètement différents.
</details>

## Module 5 — Producteurs : clés, partitionnement, acks

### Comment un message choisit sa partition
```python
producteur.send("commandes.creees", key=f"client-{id_client}".encode(), value=evenement)
```
- **Sans clé** : répartition round-robin (ou par lots) entre les partitions — simple, mais aucune garantie d'ordre entre messages liés.
- **Avec clé** : Kafka applique un **hachage** de la clé pour toujours router vers la **même** partition — tous les événements d'un même `client-id`, par exemple, resteront dans l'ordre les uns par rapport aux autres.

> 💡 Choisir la bonne clé est la décision de modélisation la plus importante d'un pipeline Kafka — elle détermine ce qui reste ordonné et ce qui ne l'est pas (voir Module 15). Pour FlowCart, la clé naturelle est l'identifiant de commande ou de client.

### Les accusés de réception (acks) : un compromis durabilité/latence
| Valeur | Comportement | Risque |
|---|---|---|
| `acks=0` | le producteur n'attend **aucune** confirmation | perte silencieuse possible si le broker échoue juste après réception |
| `acks=1` | confirmation du broker **leader** de la partition seulement | perte possible si le leader tombe avant la réplication (palier 2) |
| `acks=all` (`-1`) | confirmation après réplication sur toutes les répliques synchronisées | le plus sûr, légèrement plus lent |

Pour un flux de commandes (FlowCart), `acks=all` est le choix par défaut raisonnable : perdre un événement de commande coûte bien plus cher qu'un peu de latence.

### Exercice 5.1
Pourquoi envoyer tous les événements d'un même client avec sa clé client garantit-il leur ordre relatif ?

<details><summary>💡 Solution</summary>

Kafka hache la clé pour toujours router vers la **même** partition, et l'ordre n'est garanti qu'à l'intérieur d'une partition (Module 4). En utilisant systématiquement la même clé pour un même client, tous ses événements atterrissent dans la même partition et y sont donc lus dans l'ordre exact où ils ont été écrits.
</details>

### Exercice 5.2
Pour quel type de donnée `acks=0` serait-il acceptable, malgré le risque de perte ?

<details><summary>💡 Solution</summary>

Une donnée à très haut volume et à faible valeur individuelle, où perdre occasionnellement un message est sans conséquence réelle — par exemple des métriques de monitoring échantillonnées très fréquemment, où la tendance globale compte plus qu'un point isolé.
</details>

### Exercice 5.3
Pourquoi `acks=all` ne protège-t-il pleinement contre la perte qu'une fois combiné à un facteur de réplication supérieur à 1 (notion approfondie au palier 2) ?

<details><summary>💡 Solution</summary>

`acks=all` attend la confirmation de **toutes les répliques synchronisées** d'une partition — mais si cette partition n'a qu'**une seule** réplique (facteur de réplication 1, le cas par défaut d'un cluster mono-broker comme celui de ce palier), il n'y a tout simplement rien d'autre à répliquer : la garantie se réduit à celle d'`acks=1`. La vraie protection contre la perte de broker vient de la combinaison `acks=all` **et** d'un facteur de réplication ≥ 3, vue au palier 2.
</details>

## Module 6 — Consommateurs et groupes de consommateurs

### Le consommateur lit, il ne retire rien
Contrairement à une file d'attente classique, **lire** un message Kafka ne le **supprime pas** du topic — le consommateur avance simplement son propre pointeur de lecture (l'offset, Module 7). D'autres consommateurs (ou le même, plus tard) peuvent relire le même message.

### Groupes de consommateurs : répartir le travail automatiquement
Plusieurs instances d'un consommateur partageant le même **group.id** se répartissent **automatiquement** les partitions d'un topic entre elles :
```
Topic "commandes.creees" (3 partitions), groupe "service-notifications" (2 instances)
 Instance A → Partition 0, Partition 1
 Instance B → Partition 2
```
Si une 3ᵉ instance rejoint le groupe, Kafka **rééquilibre** automatiquement (chaque instance reçoit idéalement 1 partition). Si une instance tombe, ses partitions sont **réattribuées** aux instances survivantes.

### La règle à retenir : jamais plus d'instances actives que de partitions
Avec 3 partitions et 4 instances dans le même groupe, la 4ᵉ instance reste **inactive**, sans aucune partition assignée — elle sert de redondance passive (prête en cas de panne d'une autre), mais ne traite jamais rien tant que les 3 premières tournent.

### Exercice 6.1
Un topic à 6 partitions est consommé par un groupe de 3 instances. Combien de partitions chaque instance reçoit-elle, en moyenne ?

<details><summary>💡 Solution</summary>

**2 partitions par instance** (6 partitions / 3 instances), en supposant un rééquilibrage classique à répartition égale.
</details>

### Exercice 6.2
Pourquoi une 4ᵉ instance ajoutée à un groupe consommant un topic à 3 partitions ne traite-t-elle jamais rien tant que les 3 premières fonctionnent ?

<details><summary>💡 Solution</summary>

Une partition ne peut être assignée qu'à **une seule** instance active à la fois au sein d'un même groupe de consommateurs (c'est ce qui garantit qu'aucun message n'est traité deux fois en parallèle par erreur, voir Module 14). Avec seulement 3 partitions, au maximum 3 instances peuvent être actives simultanément — toute instance supplémentaire reste en attente, prête à prendre le relais si une des 3 tombe.
</details>

### Exercice 6.3
Deux équipes différentes (facturation et notifications) veulent chacune consommer **l'intégralité** du flux `commandes.creees`, indépendamment l'une de l'autre. Comment configurer leurs consommateurs ?

<details><summary>💡 Solution</summary>

Chaque équipe doit utiliser un **`group.id` différent** (par exemple `facturation` et `notifications`). Deux groupes distincts reçoivent chacun leur propre copie complète du flux — c'est le comportement pub/sub entre groupes évoqué au Module 2, indépendant de la répartition en queue qui se produit, elle, à l'intérieur de chaque groupe.
</details>

## Module 7 — Offsets et garanties de livraison

### Le commit : où en est réellement un consommateur
Un consommateur **committe** (enregistre) régulièrement l'offset jusqu'où il a traité un flux, dans un topic interne dédié de Kafka (`__consumer_offsets`). C'est ce qui permet à un consommateur redémarré — ou à une autre instance qui hérite de ses partitions après une panne — de **reprendre exactement où il s'était arrêté**, plutôt que de repartir de zéro ou de perdre sa progression.

### Les trois garanties possibles, selon QUAND on committe
| Garantie | Comportement | Quand committer |
|---|---|---|
| **Au plus une fois** (at-most-once) | un message peut être **perdu**, jamais traité deux fois | committer **avant** de traiter le message |
| **Au moins une fois** (at-least-once) | un message peut être **traité deux fois**, jamais perdu | committer **après** avoir traité le message (le défaut recommandé) |
| **Exactement une fois** (exactly-once) | ni perte, ni duplication | mécanisme transactionnel dédié (approfondi au palier 2) |

```
Au plus une fois :  commit → [crash ici = message jamais traité] → traitement
Au moins une fois : traitement → [crash ici = message retraité au redémarrage] → commit
```

### Le choix par défaut, et pourquoi
**Au moins une fois** est le choix standard pour la grande majorité des pipelines (dont FlowCart à ce palier) : perdre un événement de commande est presque toujours pire que le traiter deux fois — **à condition** que le traitement soit **idempotent** (Module 14), sans quoi une double livraison deviendrait un vrai bug (facturer deux fois, par exemple).

### Exercice 7.1
Un consommateur committe son offset **avant** de traiter le message, puis plante pendant le traitement. Que se passe-t-il au redémarrage ?

<details><summary>💡 Solution</summary>

Le message est considéré comme déjà traité (l'offset a avancé avant le crash) — au redémarrage, le consommateur reprend **après** ce message, qui n'a pourtant jamais été réellement traité. C'est une perte silencieuse : le scénario « au plus une fois ».
</details>

### Exercice 7.2
Pourquoi « au moins une fois » est-il le choix par défaut recommandé pour la plupart des pipelines, malgré le risque de doublons ?

<details><summary>💡 Solution</summary>

Dans la majorité des cas métier, retraiter un même événement par erreur est un problème gérable (et évitable via l'idempotence, Module 14), alors que **perdre silencieusement** un événement (une commande, un paiement) est généralement bien plus coûteux et difficile à détecter après coup.
</details>

### Exercice 7.3
Pourquoi la garantie « exactement une fois » nécessite-t-elle un mécanisme dédié, plutôt qu'un simple choix de moment de commit ?

<details><summary>💡 Solution</summary>

Le simple choix du moment de commit (avant/après traitement) ne peut produire que l'une des deux garanties « au plus » ou « au moins » une fois — il reste toujours une fenêtre où un crash exact au mauvais instant cause soit une perte, soit un doublon. Éliminer les deux risques simultanément exige un mécanisme transactionnel liant atomiquement la lecture, le traitement et l'écriture (producteur idempotent et transactions Kafka, vus au palier 2).
</details>

## Module 9 — Écrire un producteur

### Installer la bibliothèque cliente
```bash
pip install confluent-kafka
```

### Un producteur simple
```python
# producteur.py
import json
from confluent_kafka import Producer

conf = {"bootstrap.servers": "localhost:9092"}
producteur = Producer(conf)

def on_delivery(err, msg):
    if err is not None:
        print(f"Échec de livraison : {err}")
    else:
        print(f"Livré sur {msg.topic()} [{msg.partition()}] offset {msg.offset()}")

evenement = {
    "commande_id": "cmd-1042",
    "client_id": "client-77",
    "montant": 15990,
    "devise": "XOF",
}

producteur.produce(
    topic="commandes.creees",
    key=evenement["client_id"].encode("utf-8"),
    value=json.dumps(evenement).encode("utf-8"),
    callback=on_delivery,
)
producteur.flush()      # attend que tous les messages en attente soient effectivement envoyés
```

### `flush()` vs `poll()` : ne pas bloquer pour rien
`produce()` est **asynchrone** : il place le message dans un buffer interne et revient immédiatement ; la confirmation arrive plus tard via le `callback`. `flush()` bloque jusqu'à ce que tout soit envoyé (utile en fin de script) ; dans une application qui tourne en continu, on préfère appeler régulièrement `producteur.poll(0)` pour déclencher les callbacks sans bloquer le flux principal.

### Configurer les acks (rappel Module 5)
```python
conf = {
    "bootstrap.servers": "localhost:9092",
    "acks": "all",
    "enable.idempotence": True,   # évite les doublons côté PRODUCTEUR en cas de nouvelle tentative réseau
}
```

### Exercice 9.1
Écris un producteur qui envoie 5 événements de commande vers `commandes.creees`, avec l'identifiant client comme clé.

<details><summary>💡 Solution</summary>

```python
for i in range(5):
    evenement = {"commande_id": f"cmd-{i}", "client_id": "client-77", "montant": 1000 * i}
    producteur.produce(
        "commandes.creees",
        key=b"client-77",
        value=json.dumps(evenement).encode("utf-8"),
    )
producteur.flush()
```
</details>

### Exercice 9.2
Pourquoi `produce()` ne garantit-il rien tout seul, sans `flush()` ni `poll()` ?

<details><summary>💡 Solution</summary>

`produce()` place seulement le message dans un buffer local et revient immédiatement, sans attendre la confirmation du broker. Si le programme se termine (ou plante) avant que ce buffer soit vidé vers le réseau, le message peut ne **jamais** être réellement envoyé — `flush()` (ou des appels réguliers à `poll()`) est nécessaire pour que l'envoi et sa confirmation aient réellement lieu.
</details>

### Exercice 9.3
À quoi sert `enable.idempotence: True` côté producteur, et en quoi diffère-t-il de l'idempotence côté consommateur (Module 14) ?

<details><summary>💡 Solution</summary>

Côté producteur, l'idempotence évite qu'une **nouvelle tentative réseau** (après un timeout, par exemple, alors que le message était en fait bien arrivé) ne crée un doublon **à l'écriture** dans la partition. L'idempotence côté consommateur (Module 14) traite un problème différent : éviter qu'un même message, relu deux fois côté lecture (garantie « au moins une fois », Module 7), ne produise un effet dupliqué dans le système qui le consomme.
</details>

## Module 10 — Écrire un consommateur

### Un consommateur simple
```python
# consommateur.py
import json
from confluent_kafka import Consumer

conf = {
    "bootstrap.servers": "localhost:9092",
    "group.id": "service-notifications",
    "auto.offset.reset": "earliest",   # d'où partir si aucun offset committé n'existe encore
    "enable.auto.commit": False,         # on committe nous-mêmes, APRÈS traitement (Module 7)
}
consommateur = Consumer(conf)
consommateur.subscribe(["commandes.creees"])

try:
    while True:
        msg = consommateur.poll(1.0)
        if msg is None:
            continue
        if msg.error():
            print(f"Erreur : {msg.error()}")
            continue

        evenement = json.loads(msg.value())
        print(f"Commande reçue : {evenement['commande_id']} (partition {msg.partition()}, offset {msg.offset()})")
        # ... traitement métier (envoyer la notification) ...

        consommateur.commit(msg)      # commit APRÈS traitement réussi : "au moins une fois"
finally:
    consommateur.close()
```

### `auto.offset.reset` : que faire sans position connue
Si aucun offset n'a jamais été committé pour ce `group.id` (premier démarrage, ou groupe totalement nouveau) :
- **`earliest`** : repart du **tout début** conservé du topic ;
- **`latest`** : ne lit que les messages **à partir de maintenant**, ignore tout l'historique.
Pour FlowCart, `earliest` a du sens pour ne manquer aucune commande passée lors d'un premier déploiement.

### `consommateur.close()` : libérer proprement les partitions
Fermer explicitement le consommateur déclenche un **rééquilibrage immédiat** (Module 6) vers les instances restantes du groupe, au lieu d'attendre le délai d'expiration (`session.timeout.ms`) qui serait utilisé si le processus plantait brutalement.

### Exercice 10.1
Lance le consommateur ci-dessus dans un terminal, puis le producteur de l'exercice 9.1 dans un autre. Que s'affiche-t-il ?

<details><summary>💡 Solution</summary>

Le consommateur affiche les 5 commandes au fur et à mesure de leur réception, avec leur partition et leur offset — tous dans la **même** partition puisqu'ils partagent la clé `client-77` (rappel Module 5).
</details>

### Exercice 10.2
Arrête le consommateur (Ctrl+C) après avoir lu 2 messages sur 5, puis relance-le. Que se passe-t-il ?

<details><summary>💡 Solution</summary>

Le consommateur reprend exactement après le dernier offset **committé** (2), et relit donc les 3 messages restants — grâce au commit explicite après traitement (`enable.auto.commit: False` + `commit()` manuel), aucun message n'est perdu malgré l'arrêt.
</details>

### Exercice 10.3
Pourquoi choisir `auto.offset.reset: earliest` plutôt que `latest` pour le premier déploiement du service de notifications de FlowCart ?

<details><summary>💡 Solution</summary>

`earliest` garantit que le tout premier démarrage du service traite **l'historique complet** déjà présent dans le topic, sans rater aucune commande passée avant son déploiement. `latest` ignorerait tout ce qui existait déjà, ce qui conviendrait seulement à un consommateur qui n'a besoin que des événements **futurs** (un tableau de bord en direct, par exemple, qui n'a pas besoin de rejouer l'historique).
</details>

# Partie 4 — Concevoir un pipeline fiable

## Module 12 — Modéliser les événements

### Nommer : un vocabulaire métier, pas technique
Un bon nom de topic décrit un **fait métier survenu**, au passé : `commandes.creees`, `commandes.payees`, `commandes.expediees` — jamais une commande impérative (`creer-commande`) ni un nom d'implémentation (`table-commandes-update`). Convention courante : `domaine.evenement` en minuscules, séparé par des points.

### Granularité : un topic par type d'événement, pas un fourre-tout
```
❌ Un seul topic "commandes" avec un champ "type": "creee" | "payee" | "expediee"
✅ Trois topics distincts : commandes.creees, commandes.payees, commandes.expediees
```
Séparer les événements par topic permet à chaque consommateur de ne s'abonner qu'à ce qui le concerne réellement, applique des politiques de rétention différenciées (Module 13, approfondi au palier 2), et évite qu'un pic sur un type d'événement ne pollue le lag mesuré sur un autre (Module 16).

### Le contenu d'un événement : fait accompli, horodaté, auto-suffisant
```json
{
  "evenement_id": "evt-9f2c...",
  "commande_id": "cmd-1042",
  "client_id": "client-77",
  "montant": 15990,
  "devise": "XOF",
  "horodatage": "2026-10-04T14:32:00Z"
}
```
- **`evenement_id`** : identifiant unique de l'événement lui-même (distinct de `commande_id`) — indispensable pour l'idempotence (Module 14) ;
- **auto-suffisant** : un consommateur ne devrait pas avoir besoin de rappeler un autre service pour comprendre l'événement — inclure les données nécessaires directement, au prix d'une légère duplication, plutôt que de recréer un couplage synchrone que la messagerie était censée éliminer (Module 1).

### Exercice 12.1
Pourquoi `commande-creee` est-il un meilleur nom de topic que `creer-commande` ?

<details><summary>💡 Solution</summary>

`creer-commande` sonne comme une **instruction** à exécuter (un impératif, plus proche d'une commande RPC), alors qu'un événement Kafka décrit un **fait déjà survenu**. `commande-creee`, au passé, reflète correctement la sémantique : quelque chose s'est produit, et le topic en informe qui veut l'écouter.
</details>

### Exercice 12.2
Pourquoi séparer `commandes.creees` et `commandes.payees` en deux topics plutôt qu'un seul topic `commandes` avec un champ `type` ?

<details><summary>💡 Solution</summary>

Chaque consommateur peut s'abonner uniquement au type d'événement qui le concerne (le service de facturation n'a besoin que de `commandes.payees`, pas de filtrer lui-même un flux mélangé). Cela permet aussi des politiques de rétention et de partitionnement distinctes par type, et isole le `LAG` mesuré de chaque flux (un pic sur les créations n'affecte pas la mesure sur les paiements).
</details>

### Exercice 12.3
Pourquoi inclure `evenement_id` en plus de `commande_id` dans la charge utile ?

<details><summary>💡 Solution</summary>

`commande_id` identifie la commande métier, qui peut légitimement générer **plusieurs** événements distincts au fil du temps (créée, payée, expédiée). `evenement_id` identifie cet **événement précis**, nécessaire pour qu'un consommateur puisse détecter s'il a déjà traité exactement ce même événement — la base technique de l'idempotence côté consommateur (Module 14).
</details>

## Module 13 — Gestion des erreurs : retries et dead-letter

### Le traitement d'un message peut échouer pour deux raisons très différentes
| Type d'échec | Exemple | Bonne réaction |
|---|---|---|
| **Transitoire** | la base de données est momentanément indisponible | **réessayer**, avec un délai croissant |
| **Permanent (message invalide)** | le JSON est malformé, un champ obligatoire manque | **ne jamais réessayer** indéfiniment — isoler le message |

### Nouvelles tentatives avec backoff
```python
import time

def traiter_avec_retry(evenement, max_tentatives=3):
    for tentative in range(1, max_tentatives + 1):
        try:
            traiter(evenement)
            return True
        except ErreurTransitoire as e:
            attente = 2 ** tentative      # 2s, 4s, 8s...
            print(f"Tentative {tentative} échouée, nouvel essai dans {attente}s")
            time.sleep(attente)
    return False
```

### Le piège du « message poison »
Si un message est **structurellement invalide**, le réessayer indéfiniment ne le réparera jamais — il **bloque** le traitement de tous les messages suivants de la même partition (puisqu'on ne committe qu'après succès, Module 7). C'est le même problème déjà rencontré pour les files de travail (*Networking and Cloud Intermédiaire*, Module 14) : il faut une **dead-letter**.

### Dead-letter : isoler sans bloquer
```python
def traiter_message(msg):
    try:
        if not traiter_avec_retry(json.loads(msg.value())):
            raise ErreurPermanente("échec après tentatives")
    except (json.JSONDecodeError, ErreurPermanente) as e:
        producteur_dlq.produce(
            "commandes.creees.dlq",
            key=msg.key(),
            value=msg.value(),
            headers={"erreur": str(e).encode()},
        )
        producteur_dlq.flush()
    consommateur.commit(msg)   # on committe MÊME en cas d'échec définitif, pour ne pas bloquer la suite
```
Une **alerte** sur l'arrivée d'un message dans `commandes.creees.dlq` est indispensable : sans elle, ces échecs s'accumulent silencieusement (même observation que pour les architectures événementielles cloud, *Networking and Cloud Intermédiaire*, Module 14).

### Exercice 13.1
Pourquoi réessayer indéfiniment un message au JSON malformé est-il une mauvaise stratégie ?

<details><summary>💡 Solution</summary>

Un message malformé est une erreur **permanente** : aucune nouvelle tentative, aussi nombreuse soit-elle, ne le rendra valide. Le réessayer en boucle bloque indéfiniment le traitement de la partition (tant qu'on ne committe pas, Module 7), empêchant tous les messages suivants, pourtant valides, d'être traités.
</details>

### Exercice 13.2
Pourquoi committe-t-on l'offset même pour un message envoyé en dead-letter, plutôt que de le laisser bloquer le flux ?

<details><summary>💡 Solution</summary>

Le message a été définitivement traité, dans le sens où une décision finale a été prise à son sujet (l'isoler en DLQ pour investigation). Committer permet au consommateur d'avancer vers les messages suivants ; ne pas committer referait indéfiniment échouer le même message problématique à chaque relecture, bloquant toute la partition.
</details>

### Exercice 13.3
Pourquoi une alerte sur l'arrivée de messages en dead-letter est-elle indispensable, et pas seulement « bonne pratique » ?

<details><summary>💡 Solution</summary>

Sans alerte, les messages en DLQ s'accumulent silencieusement — personne ne sait qu'une partie du flux de commandes n'est jamais traitée correctement, jusqu'à ce qu'un client se plaigne ou qu'un audit tardif révèle le problème, bien après que l'impact métier se soit déjà produit.
</details>

## Module 14 — Idempotence côté consommateur

### Le rappel qui compte : « au moins une fois » implique des doublons possibles
Rappel du Module 7 : avec la garantie par défaut, un message peut être **relivré** (après un crash juste avant le commit, un rééquilibrage de groupe, une nouvelle tentative applicative). Un traitement qui n'est pas pensé pour cela produira un doublon réel — facturer deux fois un même paiement, par exemple.

### Rendre un traitement idempotent : vérifier avant d'agir
```python
def traiter_paiement(evenement):
    if deja_traite(evenement["evenement_id"]):
        print(f"Événement {evenement['evenement_id']} déjà traité, ignoré")
        return
    enregistrer_paiement(evenement)
    marquer_traite(evenement["evenement_id"])
```
`deja_traite` et `marquer_traite` s'appuient typiquement sur une contrainte d'**unicité** en base de données sur `evenement_id` (Module 12) : une deuxième tentative d'insertion du même `evenement_id` échoue proprement, sans dupliquer l'effet métier.

### Une alternative : des opérations naturellement idempotentes
Certaines opérations sont idempotentes **par construction**, sans vérification explicite : `DEFINIR le statut de la commande à "payée"` donne le même résultat qu'on l'exécute une ou dix fois, contrairement à `AJOUTER 15990 au solde du client`, qui, lui, dépend du nombre d'exécutions. Concevoir ses traitements comme des **affectations d'état** plutôt que des **incréments** élimine le problème à la racine, quand c'est possible.

### Exercice 14.1
Un service de facturation exécute `solde_client += montant` à chaque réception de l'événement `commandes.payees`. Pourquoi est-ce dangereux avec la garantie « au moins une fois », et comment corriger ?

<details><summary>💡 Solution</summary>

Si l'événement est relivré (commit manqué après un crash, par exemple), `solde_client += montant` s'exécute une seconde fois et double le montant crédité — une vraie erreur métier. Correction : vérifier `evenement_id` avant d'appliquer l'incrément (idempotence explicite), ou modéliser l'opération différemment (enregistrer chaque paiement individuellement avec son `evenement_id` en clé unique, puis calculer le solde comme une somme — une ré-insertion du même `evenement_id` est alors rejetée par la contrainte d'unicité sans dupliquer l'effet).
</details>

### Exercice 14.2
Pourquoi `DEFINIR le statut à "payée"` est-il naturellement idempotent, contrairement à un incrément ?

<details><summary>💡 Solution</summary>

Affecter une valeur fixe produit toujours le **même état final**, qu'on l'exécute une ou plusieurs fois — exécuter `statut = "payée"` dix fois de suite laisse le statut à "payée", sans effet cumulatif. Un incrément (`+= montant`), lui, change de résultat à chaque exécution supplémentaire : l'idempotence n'est alors obtenue qu'en ajoutant une vérification explicite.
</details>

### Exercice 14.3
Sur quoi repose typiquement la vérification `deja_traite(evenement_id)` en pratique ?

<details><summary>💡 Solution</summary>

Une contrainte d'**unicité** sur la colonne `evenement_id` dans la table où l'effet du traitement est enregistré : une tentative d'insertion avec un `evenement_id` déjà présent échoue proprement au niveau de la base de données elle-même, offrant une garantie robuste même en cas de traitements concurrents, plutôt qu'une simple vérification applicative qui pourrait être sujette à une condition de course.
</details>

## Module 15 — Garanties d'ordonnancement

### Rappel structurant : l'ordre n'existe qu'à l'intérieur d'une partition d'un topic
Reprise directe du Module 4, avec une conséquence qu'il faut formuler précisément : Kafka garantit l'ordre **uniquement entre les messages d'une même partition d'un même topic**. Deux topics sont deux journaux indépendants, lus par des requêtes distinctes : **aucun ordre n'est garanti entre eux**, même avec la même clé et le même nombre de partitions.

Pour FlowCart, cela veut dire que `commandes.payees` peut être lu **avant** `commandes.creees` pour une même commande — la séparation en trois topics (Module 12) a un prix.

### Deux réponses possibles
| Stratégie | Principe | Contrepartie |
|---|---|---|
| **Un seul topic**, clé = `commande_id` | tous les événements d'une commande vont dans la même partition et sont lus dans l'ordre d'écriture | on perd les avantages de topics séparés par type (Module 12) |
| **Topics séparés**, consommateur tolérant au désordre | le consommateur ne suppose aucun ordre entre topics : état par commande, mise en attente ou nouvelle tentative si l'étape précédente n'est pas encore vue, ou fusion monotone de l'état (technique vue au palier 3) | un peu plus de logique côté consommateur |

FlowCart garde trois topics : son consommateur ne doit donc **jamais** supposer qu'il verra `creee` avant `payee`.

### La clé reste indispensable : l'ordre au sein d'un topic
Utiliser la même clé (`commande_id`) reste utile : elle garantit l'ordre de tous les événements d'un **même topic** pour une même commande (par exemple deux événements `payee` successifs pour une commande dont le premier paiement a échoué, puis réussi).

### Le piège classique : changer la clé en cours de route
```
❌ commandes.payees partitionné par commande_id un jour, par client_id le lendemain
→ les événements d'une même commande ne sont plus dans la même partition : l'ordre au sein du topic est perdu
```
Pour conserver l'ordre au sein d'un topic, la **même clé** doit être utilisée de façon constante pour ce topic.

### Augmenter les partitions : attention à l'ordre existant
Ajouter des partitions à un topic **déjà en production** change la fonction de hachage clé → partition pour les **nouveaux** messages, sans redistribuer les anciens : une même clé peut se retrouver, après l'ajout, associée à une partition différente de celle utilisée jusque-là. Décider du nombre de partitions **en amont**, avec une marge de croissance raisonnable, évite cette surprise plutôt que de la corriger après coup (creusé au palier 2).

### Exercice 15.1
Pour qu'un consommateur lise tous les événements d'une même commande dans l'ordre exact où ils ont été écrits, que faut-il garantir ?

<details><summary>💡 Solution</summary>

Qu'ils soient écrits dans le **même topic** avec la **même clé** (`commande_id`) : ils atterrissent alors dans la même partition, où l'ordre est garanti. Avec trois topics séparés (comme FlowCart), cette garantie n'existe pas entre `creee`, `payee` et `expediee`.
</details>

### Exercice 15.2
FlowCart publie `creee`, `payee` et `expediee` sur trois topics distincts, avec la même clé `commande_id`. Pourquoi `service_notifications` ne peut-il pas supposer qu'il lira `creee` avant `payee`, et comment s'en protéger ?

<details><summary>💡 Solution</summary>

Ce sont trois journaux indépendants lus via des requêtes distinctes : leur ordre de lecture relatif n'est pas défini, même avec la même clé et le même nombre de partitions. Le service doit donc tolérer le désordre : tenir un état par commande (n'afficher « expédiée » que si l'étape précédente a été vue, sinon mettre en attente ou réessayer), ou fusionner l'état de façon monotone (le rang d'étape le plus élevé l'emporte — technique du palier 3).
</details>

### Exercice 15.3
Pourquoi vaut-il mieux décider du nombre de partitions d'un topic à l'avance plutôt que de l'augmenter après coup une fois en production ?

<details><summary>💡 Solution</summary>

Augmenter le nombre de partitions change la fonction de hachage clé → partition pour les messages **futurs**, sans redistribuer l'historique déjà écrit — une même clé peut alors se retrouver associée à une partition différente de celle utilisée précédemment, cassant potentiellement les garanties d'ordre dont dépendaient déjà des consommateurs en production.
</details>

## Module 16 — Observabilité de base : lag et throughput

### Le lag : la métrique la plus importante d'un pipeline de streaming
Déjà introduit au Module 11 via la CLI, le **lag** (combien de messages restent à lire par rapport à ce qui a été écrit) est l'équivalent, pour un pipeline Kafka, de ce qu'est la file d'attente HTTP pour un serveur web — le signal numéro un qu'un consommateur ne suit plus le rythme.
```bash
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group service-notifications
```
```
TOPIC              PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
commandes.creees   0          1042            1050            8
commandes.creees   1          998             998             0
```

### Lag qui croît vs lag qui oscille
Un lag qui **oscille** autour d'une valeur stable (il monte un peu lors d'un pic, puis redescend) est normal — le consommateur absorbe la charge. Un lag en **croissance continue** signale que le consommateur est structurellement trop lent par rapport au débit du producteur : il faudra soit optimiser le traitement, soit ajouter des instances au groupe (jusqu'à la limite du nombre de partitions, Module 6).

### Débit (throughput) : messages par seconde, des deux côtés
Suivre le débit de production et de consommation côte à côte permet de voir si un déséquilibre est **ponctuel** (un pic de commandes un jour de promotion) ou **structurel** (le débit de consommation plafonne toujours en dessous de celui de production). Ce module reste volontairement sommaire : le monitoring Prometheus complet d'un cluster Kafka est traité au palier 2.

### Exercice 16.1
Interprète ce résultat de `kafka-consumer-groups.sh --describe`, mesuré trois fois à 10 minutes d'intervalle : lag = 50, puis 200, puis 600. Que faire ?

<details><summary>💡 Solution</summary>

Le lag **croît de façon continue**, pas une simple oscillation ponctuelle : le groupe de consommateurs traite structurellement moins vite que le débit de production. Il faut soit optimiser le traitement (réduire le temps par message), soit ajouter des instances au groupe (tant que le nombre de partitions le permet, Module 6), soit augmenter le nombre de partitions si la limite est déjà atteinte.
</details>

### Exercice 16.2
Pourquoi un lag qui oscille (monte puis redescend) n'est-il généralement pas un problème, contrairement à un lag qui croît continûment ?

<details><summary>💡 Solution</summary>

Une oscillation reflète une absorption normale des pics de charge — le consommateur prend un peu de retard lors d'un afflux ponctuel, puis le rattrape une fois le pic passé. Une croissance continue, elle, indique que le débit de consommation est **structurellement** inférieur au débit de production : le retard ne se résorbe jamais tout seul et continuera de s'accumuler indéfiniment.
</details>

### Exercice 16.3
Pourquoi le lag est-il comparé, dans ce module, à la file d'attente d'un serveur web ?

<details><summary>💡 Solution</summary>

Dans les deux cas, la métrique révèle un **déséquilibre entre l'arrivée et le traitement** : une file d'attente HTTP qui grossit signale que le serveur reçoit des requêtes plus vite qu'il ne les traite ; un lag Kafka qui grossit signale que des messages arrivent plus vite que le consommateur ne les traite. C'est le même type de signal d'alerte, appliqué à deux contextes différents.
</details>

# Partie 5 — NATS, l'alternative légère

## Module 17 — NATS : concepts et cas d'usage

### Core NATS : pub/sub pur, au plus simple
```bash
docker run -d --name nats -p 4222:4222 nats:2.10
```
```python
import asyncio
import nats

async def main():
    nc = await nats.connect("nats://localhost:4222")

    async def handler(msg):
        print(f"Reçu sur {msg.subject}: {msg.data.decode()}")

    await nc.subscribe("commandes.creees", cb=handler)
    await nc.publish("commandes.creees", b'{"commande_id": "cmd-1"}')
    await asyncio.sleep(1)
    await nc.close()

asyncio.run(main())
```
Par défaut (« Core NATS »), un message **non reçu** par un abonné connecté au moment de la publication est **perdu** — aucune persistance, aucun rejeu. C'est un choix délibéré : la simplicité et la latence minimale priment sur la durabilité.

### JetStream : quand NATS a besoin de persistance
**JetStream** ajoute à NATS une couche de persistance et de rejeu, se rapprochant des garanties de Kafka — tout en restant nettement plus léger à opérer :
```python
js = nc.jetstream()
await js.add_stream(name="COMMANDES", subjects=["commandes.*"])
await js.publish("commandes.creees", b'{"commande_id": "cmd-1"}')

sub = await js.pull_subscribe("commandes.creees", "service-notifications")
messages = await sub.fetch(10)
for msg in messages:
    print(msg.data.decode())
    await msg.ack()
```

### Sujets (subjects) et wildcards : un routage plus fin que de simples noms de topics
```
commandes.creees
commandes.payees
commandes.*        ← correspond à "commandes.creees" ET "commandes.payees"
commandes.>         ← correspond à "commandes.creees.urgent" ET tout ce qui suit "commandes."
```
Un abonné peut s'abonner à un **motif** plutôt qu'à un nom exact — une flexibilité de routage native que Kafka n'offre pas au même niveau (un consommateur Kafka s'abonne à des topics nommés explicitement, ou via une expression régulière côté client, mais le broker lui-même n'a pas cette notion de hiérarchie de sujets).

### Exercice 17.1
Lance NATS, abonne-toi à `commandes.creees`, publie un message, et vérifie sa réception.

<details><summary>💡 Solution</summary>

```bash
docker run -d --name nats -p 4222:4222 nats:2.10
```
Utilise le script Python ci-dessus : le handler affiche le message publié juste après l'abonnement.
</details>

### Exercice 17.2
Pourquoi un message Core NATS publié **avant** qu'un abonné ne se connecte est-il définitivement perdu ?

<details><summary>💡 Solution</summary>

Core NATS ne persiste rien par défaut : un message est transmis uniquement aux abonnés **déjà connectés** au moment précis de la publication, puis disparaît. Sans JetStream, il n'existe aucun journal où un abonné arrivant plus tard pourrait aller le relire.
</details>

### Exercice 17.3
Un abonné veut recevoir à la fois `commandes.creees` et `commandes.payees` sans s'abonner deux fois séparément. Quel motif de sujet utiliser ?

<details><summary>💡 Solution</summary>

`commandes.*` — le wildcard `*` correspond à exactement un niveau de hiérarchie, couvrant ici `commandes.creees` et `commandes.payees` en un seul abonnement.
</details>

## Module 18 — Kafka vs NATS : bien choisir

### Une grille de décision, pas un vainqueur absolu
| Critère | Kafka | NATS (+ JetStream) |
|---|---|---|
| Débit à très grande échelle | référence du marché | très bon, légèrement en retrait au sommet |
| Latence minimale | bonne | meilleure (conçu pour ça dès l'origine) |
| Rejeu d'historique long | natif, cœur du design | possible avec JetStream, moins central |
| Écosystème (connecteurs, traitement de flux) | très riche (Kafka Connect, Streams, ksqlDB) | plus restreint |
| Simplicité opérationnelle | plus lourd | nettement plus léger |
| Routage par motif de sujet | non (au niveau broker) | natif |

### Pour FlowCart : pourquoi Kafka reste le bon choix à ce stade
FlowCart a besoin de **conserver** un historique de commandes rejouable (reconstruire un état, déboguer, brancher de nouveaux consommateurs en retard — Module 3), et visera au palier 2 un **traitement de flux** (agrégation temps réel) où l'écosystème Kafka (Kafka Streams/ksqlDB) est nettement plus mature. NATS resterait pertinent pour un besoin différent **au sein** de la même plateforme — par exemple de la télémétrie interne à très haute fréquence, sans besoin de rejeu.

### Exercice 18.1
Une application de chat doit notifier en temps réel les utilisateurs connectés d'un nouveau message, sans jamais avoir besoin d'historique rejouable. Kafka ou NATS ?

<details><summary>💡 Solution</summary>

**NATS** (Core, sans JetStream) : latence minimale, aucun besoin de persistance ni de rejeu — exactement le cas d'usage pour lequel NATS a été conçu, et Kafka serait une complexité opérationnelle disproportionnée.
</details>

### Exercice 18.2
Pourquoi FlowCart reste-t-il sur Kafka plutôt que NATS à ce stade du projet fil rouge ?

<details><summary>💡 Solution</summary>

FlowCart a besoin d'un historique de commandes **rejouable** sur la durée (reconstruire un état, déboguer, brancher de nouveaux consommateurs en retard) et visera, au palier 2, du traitement de flux avec un écosystème mature (Kafka Streams/ksqlDB) — deux besoins où Kafka est structurellement plus adapté que NATS à ce stade.
</details>

### Exercice 18.3
Une même plateforme peut-elle légitimement utiliser Kafka **et** NATS simultanément, pour des besoins différents ? Donne un exemple.

<details><summary>💡 Solution</summary>

Oui — rien n'impose un choix unique à l'échelle de toute une plateforme. Par exemple, FlowCart pourrait garder Kafka pour le flux de commandes (rejouable, traité en continu), tout en utilisant NATS pour notifier en temps réel l'interface d'administration qu'une nouvelle commande vient d'arriver (latence minimale, aucun besoin de rejeu pour ce seul affichage).
</details>

## Module 19 — Sécurité de base : authentification et chiffrement en transit

### Par défaut, un cluster Kafka local n'authentifie personne
Les exemples de ce cours tournent en `PLAINTEXT`, sans authentification ni chiffrement — acceptable pour apprendre en local, **jamais** pour un cluster exposé au-delà d'un poste de développement isolé.

### Chiffrer le trafic : SSL/TLS
```properties
# config broker (extrait)
listeners=SSL://:9093
ssl.keystore.location=/etc/kafka/secrets/kafka.keystore.jks
ssl.keystore.password=motdepasse
```
```python
conf = {
    "bootstrap.servers": "kafka:9093",
    "security.protocol": "SSL",
    "ssl.ca.location": "/chemin/vers/ca-cert",
}
```
Même principe que le TLS déjà vu pour HTTPS (*Networking and Cloud Fundamentals*, Module 9) : chiffrer ce qui circule sur le réseau entre clients et brokers.

### Authentifier : SASL
**SASL** (Simple Authentication and Security Layer) ajoute une **identité** vérifiée côté client, au-dessus du chiffrement TLS :
```python
conf = {
    "bootstrap.servers": "kafka:9093",
    "security.protocol": "SASL_SSL",
    "sasl.mechanism": "PLAIN",
    "sasl.username": "service-notifications",
    "sasl.password": "...",
}
```
Sans authentification, **n'importe quel** client réseau capable d'atteindre le broker peut produire ou consommer n'importe quel topic — une absence totale de moindre privilège (*Networking and Cloud Fondamentals*, Module 20). Le contrôle **fin** de qui a le droit de faire quoi sur quel topic (les ACL Kafka) est approfondi au palier 3, aux côtés du mTLS et de la sécurisation complète du cluster.

### Exercice 19.1
Pourquoi un cluster Kafka en `PLAINTEXT` sans authentification est-il acceptable en développement local mais jamais en production ?

<details><summary>💡 Solution</summary>

En local, le broker n'est accessible qu'à la machine elle-même, sans surface d'exposition réseau réelle. En production, un broker joignable sur le réseau sans authentification ni chiffrement laisserait n'importe quel client capable de l'atteindre lire ou écrire n'importe quel topic, et le trafic (potentiellement des données sensibles) circulerait en clair, interceptable par quiconque a accès au réseau intermédiaire.
</details>

### Exercice 19.2
Quelle différence entre ce que TLS protège et ce que SASL ajoute ?

<details><summary>💡 Solution</summary>

TLS chiffre le trafic en transit (confidentialité et intégrité), empêchant l'interception ou la modification en chemin — mais ne dit rien sur **qui** se connecte. SASL ajoute une couche d'**authentification** par-dessus : le client doit prouver une identité vérifiée avant que la connexion ne soit acceptée.
</details>

### Exercice 19.3
Sans authentification configurée, que peut faire n'importe quel client réseau capable d'atteindre le broker ?

<details><summary>💡 Solution</summary>

Produire et consommer **n'importe quel** topic, sans restriction — aucune notion de moindre privilège n'est appliquée. C'est pourquoi l'authentification (SASL) et, au-delà, des autorisations fines par topic (ACL, approfondies au palier 3) sont indispensables dès qu'un cluster dépasse le cadre d'un poste de développement isolé.
</details>

## Cheat-sheet

| Catégorie | Repères clés |
|---|---|
| Concepts | queue = répartition, pub/sub = diffusion ; Kafka = log distribué rejouable |
| Architecture | broker → topic → partitions ; ordre garanti SEULEMENT dans une partition |
| Producteur | clé = routage + ordre ; `acks=0/1/all` ; `enable.idempotence` ; `flush()`/`poll()` |
| Consommateur | `group.id` = répartition entre instances ; `auto.offset.reset` earliest/latest |
| Groupes | 1 partition = 1 instance active max ; groupes différents = copies indépendantes |
| Garanties | au plus une fois (commit avant) / au moins une fois (commit après, par défaut) / exactly-once (palier 2) |
| Fiabilité | retry + backoff pour le transitoire ; dead-letter pour le permanent ; toujours committer après DLQ |
| Idempotence | vérifier `evenement_id`, ou modéliser en affectation d'état plutôt qu'en incrément |
| Observabilité | `LAG` = premier réflexe ; croissance continue = problème structurel |
| CLI | `kafka-topics.sh`, `kafka-console-producer/consumer.sh`, `kafka-consumer-groups.sh --describe` |
| NATS | Core = pub/sub pur, sans persistance ; JetStream = persistance + rejeu ; sujets avec wildcards `*`/`>` |
| Sécurité | TLS = chiffrement en transit ; SASL = authentification ; sans eux, aucun moindre privilège |

## Glossaire

| Terme | Définition |
|---|---|
| **Broker** | un serveur Kafka |
| **Topic** | flux nommé d'événements, divisé en partitions |
| **Partition** | journal ordonné append-only, unité de parallélisme et d'ordonnancement |
| **Offset** | position d'un message au sein d'une partition précise |
| **Groupe de consommateurs** | ensemble d'instances se répartissant automatiquement les partitions d'un topic |
| **Lag** | nombre de messages écrits mais pas encore lus par un groupe |
| **Acks** | niveau de confirmation attendu par un producteur avant de considérer un envoi réussi |
| **Au moins une fois** | garantie de livraison tolérant les doublons mais jamais la perte |
| **Idempotence** | propriété d'un traitement produisant le même résultat, qu'il soit exécuté une ou plusieurs fois |
| **Dead-letter (DLQ)** | flux dédié isolant les messages dont le traitement échoue de façon permanente |
| **JetStream** | extension de NATS ajoutant persistance et rejeu |
| **Sujet (subject)** | nom hiérarchique de routage dans NATS, supportant les wildcards |
