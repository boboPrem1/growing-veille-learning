## Chapitre 1 — Comprendre NestJS

⏱ 30 min

🎯 **Objectifs** : expliquer ce que Nest apporte par rapport à Express, citer ses quatre idées fondatrices et savoir quand l'utiliser (ou non).

### 1.1 Le problème : la liberté d'Express devient un piège à l'échelle

Express et Fastify sont volontairement minimalistes : ils reçoivent une requête et appellent ta fonction. Tout le reste est à ta charge :

- Où mettre la validation ? la logique métier ? l'accès aux données ?
- Comment partager une connexion à la base entre vingt fichiers ?
- Comment tester un handler sans démarrer un serveur ?

Chaque équipe invente ses propres réponses. Résultat : des projets qui ne se ressemblent pas, un onboarding long et du code difficile à tester.

**NestJS apporte une architecture** (structure, conventions, injection de dépendances) **au-dessus d'un serveur HTTP existant.**

### 1.2 Ce qu'est NestJS

- Un framework Node.js « progressif », écrit en **TypeScript** (JavaScript possible).
- Une architecture **inspirée d'Angular** : modules, injection de dépendances, décorateurs.
- Il s'exécute **sur Express** (par défaut) **ou Fastify** grâce à un adaptateur.
- Un écosystème de packages officiels `@nestjs/*` : configuration, TypeORM, Swagger, JWT, files d'attente, microservices…
- Pas seulement du HTTP : **REST, GraphQL, WebSockets, microservices** (TCP, Redis, NATS, Kafka, RabbitMQ, gRPC) et applications « standalone » (scripts, workers).

### 1.3 Quatre idées à retenir

1. **Modularité** — l'application est un arbre de **modules**. Chaque module regroupe ce qui concerne une fonctionnalité (tâches, utilisateurs, paiements…) et choisit ce qu'il montre au reste de l'application.
2. **Injection de dépendances (DI)** — une classe ne crée pas ses collaborateurs, elle les **déclare** dans son constructeur et Nest les lui fournit. Conséquences : couplage faible, tests faciles (on remplace une dépendance par un faux).
3. **Décorateurs et métadonnées** — `@Controller()`, `@Get()`, `@Injectable()`… annotent tes classes. Nest lit ces annotations pour construire les routes et le graphe de dépendances.
4. **Agnosticisme de plateforme** — ta logique métier ne dépend ni d'Express ni de Fastify, ni même de HTTP : le même service peut être appelé depuis une route REST, un message Kafka ou une tâche planifiée.

### 1.4 Quand (ne pas) choisir NestJS

| NestJS est un bon choix quand… | Un outil plus léger suffit quand… |
|---|---|
| Plusieurs développeurs travaillent sur le même back-end | Tu écris un script ou un micro-service de trois routes |
| L'application va grandir (domaines, intégrations, équipes) | Tu prototypes en quelques heures et jetteras le code |
| Tu veux des conventions claires et une forte testabilité | L'équipe maîtrise déjà une micro-stack maison (Fastify, Hono + bibliothèques) |
| Tu combines HTTP, files de messages, WebSockets ou GraphQL | Le temps de démarrage ou la taille du bundle sont critiques (edge, fonctions minuscules) |

### 1.5 NestJS 12 en bref

NestJS 12 est sorti le 28 août 2026. Ce que tu dois savoir pour ce cours :

- 🆕 **Paquets ESM-first.** Les paquets Nest sont publiés en ESM. Une application CommonJS continue de fonctionner grâce à `require(esm)` (Node 20.19+ / 22.12+).
- 🆕 **`nest new` te laisse choisir** entre un projet **ESM** (choix par défaut, tests avec **Vitest**) et un projet **CommonJS** (tests avec **Jest**). Les nouveaux projets utilisent **oxlint** et **Prettier**.
- 🆕 **Rspack remplace webpack** dans le CLI (bundling de monorepos) ; `tsc` reste le compilateur par défaut.
- 🆕 **Standard Schema** : en plus de `class-validator`, les décorateurs `@Body()`, `@Query()`, `@Param()` acceptent une option `schema` (Zod, Valibot, ArkType).
- 🆕 Petites nouveautés utiles : `errorCode` dans les exceptions HTTP, logs structurés, diagnostic des conflits de routes, arrêt gracieux avec Express, SDK d'observabilité `@nestjs/observe`.

Les **concepts** de ce cours sont les mêmes qu'en v10 et v11 ; les encadrés 🆕 signalent ce qui a changé.

### ✅ À retenir

- Nest = **structure + conventions + DI** au-dessus d'Express/Fastify.
- Quatre piliers : **modules, injection de dépendances, décorateurs, agnosticisme de plateforme**.
- Ce n'est pas un outil pour chaque besoin : pour un script de trois routes, c'est trop lourd.

## Chapitre 2 — Installer et explorer un premier projet

⏱ 60 min

🎯 **Objectifs** : installer le CLI, générer un projet, comprendre chaque fichier généré, lancer le serveur en mode watch et utiliser les commandes du CLI.

### 2.1 Versions de Node.js

Deux seuils distincts :

| Ce que tu fais | Node.js minimum |
|---|---|
| **Exécuter** une application Nest 12 | v20.19+ ou v22.12+ (branche 22) |
| **Générer** du code avec le CLI (`nest new`, `nest g`, `nest upgrade`) | v22.22.3+, v24.15+ ou v26+ |

💡 Le plus simple : installer **la dernière LTS active**, qui satisfait les deux. Un gestionnaire de versions (fnm, nvm, Volta) évite bien des soucis.

```bash
node -v
```

### 2.2 Installer le CLI et créer le projet

```bash
npm i -g @nestjs/cli
nest --version
nest new tasks-api
```

Le CLI te pose quelques questions :

1. **Gestionnaire de paquets** : npm, yarn, pnpm ou bun.
2. **Système de modules** : **ESM** (par défaut, tests avec Vitest) ou **CommonJS** (tests avec Jest).
3. **NestJS Observe** (plateforme d'observabilité officielle) : réponds **non** pour ce cours. Pour sauter les questions : `nest new tasks-api --no-observe`.

🆕 **ESM ou CommonJS ?** Ce cours suit l'option **ESM**.

| | ESM (défaut) | CommonJS |
|---|---|---|
| `package.json` | `"type": "module"` | pas de champ `type` |
| Imports relatifs | `./app.module.js` (extension `.js` **obligatoire**, même pour un fichier `.ts`) | `./app.module` |
| Démarrage dans `main.ts` | `await bootstrap();` | `bootstrap();` |
| `__dirname` | `import.meta.dirname` | `__dirname` |
| Tests | Vitest (`vi.fn()`) | Jest (`jest.fn()`) |

⚠️ **Jest + Nest 12** : Jest ne sait charger les paquets ESM de Nest 12 qu'à partir de **Node 24.9**. En dessous, tu obtiens l'erreur `ERR_REQUIRE_ASYNC_MODULE`. Si tu choisis CommonJS + Jest, utilise Node ≥ 24.9 pour lancer les tests.

### 2.4 Anatomie des quatre fichiers de `src/`

**`main.ts`** — le point d'entrée : il crée l'application et écoute sur un port.

```ts
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module.js';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  await app.listen(process.env.PORT ?? 3000);
}
await bootstrap();
```

`NestFactory.create(AppModule)` construit le graphe de dépendances à partir du **module racine**, puis renvoie l'application.

**`app.module.ts`** — le module racine : il déclare ce qui compose l'application.

```ts
import { Module } from '@nestjs/common';
import { AppController } from './app.controller.js';
import { AppService } from './app.service.js';

@Module({
  imports: [],
  controllers: [AppController],
  providers: [AppService],
})
export class AppModule {}
```

**`app.controller.ts`** — reçoit les requêtes HTTP.

```ts
import { Controller, Get } from '@nestjs/common';
import { AppService } from './app.service.js';

@Controller()
export class AppController {
  constructor(private readonly appService: AppService) {}

  @Get()
  getHello(): string {
    return this.appService.getHello();
  }
}
```

**`app.service.ts`** — contient la logique.

```ts
import { Injectable } from '@nestjs/common';

@Injectable()
export class AppService {
  getHello(): string {
    return 'Hello World!';
  }
}
```

Remarque le `constructor(private readonly appService: AppService)` du controller : **c'est de l'injection de dépendances**. Le controller ne fait jamais `new AppService()` ; il déclare son besoin, Nest fournit l'instance.

### 2.6 Décorateurs et métadonnées : la « magie » démystifiée

Un **décorateur** est une fonction qui annote une classe, une méthode ou un paramètre. Le `tsconfig.json` généré active deux options :

```json
"experimentalDecorators": true,
"emitDecoratorMetadata": true
```

Avec `emitDecoratorMetadata`, TypeScript **écrit dans le JavaScript compilé les types** des paramètres de constructeur des classes décorées. Nest les lit au démarrage :

```
AppController  →  constructor(appService: AppService)
                  métadonnée « design:paramtypes » = [AppService]
                  →  Nest sait qu'il doit injecter une instance d'AppService
```

Deux conséquences pratiques à retenir dès maintenant :

1. Une classe qui reçoit des dépendances doit être **décorée** (`@Controller()`, `@Injectable()`, `@Module()`…).
2. Les types utilisés dans les constructeurs doivent être des **classes**, pas des interfaces : les interfaces disparaissent à la compilation, il n'y a plus rien à lire à l'exécution.

### 2.7 Le CLI : les commandes à connaître

| Commande | Effet |
|---|---|
| `nest g module tasks` | Génère un module (`g` = `generate`) |
| `nest g controller tasks` | Génère un controller et l'enregistre dans le module voisin |
| `nest g service tasks` | Génère un service et l'enregistre dans le module voisin |
| `nest g resource tasks` | Génère module + controller + service + DTO + entité (CRUD complet) |
| `nest g pipe` / `filter` / `guard` / `interceptor` / `decorator` | Génère le composant correspondant |
| `--dry-run` (`-d`) | **Simule** : affiche ce qui serait créé sans toucher aux fichiers |
| `--no-spec` | Ne génère pas le fichier de test |
| `nest info` | Affiche les versions (système, CLI, paquets Nest) |
| `nest upgrade` | Migre un projet v11 vers v12 |

### 2.8 Hygiène de projet

- Le CLI initialise un dépôt Git : fais un premier commit tout de suite.
- Les fichiers `.env` contiendront des secrets : vérifie qu'ils sont dans `.gitignore` (chapitre 10).
- Lance `npm run lint` et `npm run format` de temps en temps : le projet est livré avec les deux.

- `nest new` → projet prêt à l'emploi ; `npm run start:dev` pour travailler.
