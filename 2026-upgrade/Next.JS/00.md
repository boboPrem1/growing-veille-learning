## 1. Comprendre Next.js

> 🎯 **Objectifs** : expliquer ce que Next.js apporte à React · connaître le vocabulaire du rendu · distinguer App Router et Pages Router · décrire le trajet d'une page.

### 1.1 Next.js en une phrase

**Next.js est un framework full-stack construit sur React.** React fournit les composants ; Next.js fournit tout le reste pour livrer une application web : routing, rendu côté serveur, récupération de données, API, optimisation des images et des polices, bundler (Turbopack), outils de développement et options de déploiement.

### 1.2 React seul, ou React avec Next.js ?

| Besoin | React seul (ex. Vite) | Avec Next.js |
|---|---|---|
| Routing | Bibliothèque à ajouter | Intégré, basé sur les dossiers |
| Premier affichage et SEO | HTML quasi vide, tout dépend du JavaScript | HTML déjà rendu côté serveur |
| Données | `useEffect` + `fetch` dans le navigateur | `await` directement dans un composant serveur |
| Backend / API | Serveur séparé | Route Handlers et Server Actions dans le même projet |
| Images, polices, scripts | Optimisation manuelle | `next/image`, `next/font`, `next/script` |
| Build et bundling | À configurer | Turbopack préconfiguré |

### 1.3 Le vocabulaire du rendu

| Terme | Définition courte |
|---|---|
| **CSR** (Client-Side Rendering) | Le navigateur reçoit du JavaScript et construit la page lui-même |
| **Rendu serveur** | Le serveur génère le HTML : la page s'affiche avant que le JavaScript soit chargé |
| **Prérendu** | Le HTML est généré **à l'avance** (au build ou lors d'une revalidation), puis servi tel quel, par exemple depuis un CDN |
| **Hydratation** | React « branche » les événements sur le HTML reçu pour le rendre interactif |
| **Streaming** | Le serveur envoie la page **par morceaux**, au fur et à mesure qu'ils sont prêts |
| **Shell statique** | La partie d'une page prérendue à l'avance ; le reste est streamé à la requête |

Autrefois, Next.js te demandait de choisir **par page** : statique *ou* dynamique. Aujourd'hui, tu composes **à l'intérieur d'une même page** : un en-tête statique, une liste mise en cache, un panier calculé à la requête. C'est l'idée centrale de ce cours (module 7).

### 1.4 App Router ou Pages Router ?

| | `app/` : **App Router** | `pages/` : Pages Router |
|---|---|---|
| Statut | Recommandé pour tout nouveau projet | Historique, toujours supporté |
| Composants | Server Components par défaut | Composants hydratés côté client (pas de Server Components) |
| Layouts | Imbriqués et persistants | Via `_app` |
| Données | `await` dans les composants | `getServerSideProps`, `getStaticProps` |

**Ce cours couvre uniquement l'App Router.** Si tu croises `getServerSideProps` dans un tutoriel, c'est du Pages Router.

### 1.5 Le trajet d'une page

```text
Navigateur ── GET /blog/3 ──▶ Serveur Next.js
                                1. rend les Server Components → « RSC payload »
                                2. produit le HTML initial (shell statique + parties streamées)

Navigateur ◀── HTML + RSC payload + JavaScript des Client Components
   a. affiche tout de suite le HTML (encore non interactif)
   b. réconcilie arbre serveur et arbre client grâce au RSC payload
   c. hydrate les Client Components → la page devient interactive

Clic sur un <Link> → seul le RSC payload de la nouvelle route est chargé
                     (pas de rechargement complet de la page)
```

> 💡 Le **RSC payload** est une description compacte de l'arbre de composants rendu côté serveur. React s'en sert dans le navigateur pour mettre à jour le DOM.

## 2. Installer et explorer un projet

> 🎯 **Objectifs** : créer un projet avec `create-next-app` · lire l'arborescence · utiliser les scripts npm · repérer `next.config.ts`.

### 2.1 Prérequis système

- **Node.js ≥ 20.9** (vérifie avec `node -v`). Node 18 n'est plus supporté.
- **TypeScript ≥ 5.1** (installé par le template).
- Systèmes : macOS, Windows (WSL compris) et Linux.

### 2.2 Créer le projet

```bash
npx create-next-app@latest mon-app
```

Le terminal pose alors quelques questions :

```text
What is your project named? mon-app
Would you like to use the recommended Next.js defaults?
    Yes, use recommended defaults      ← choisis celui-ci
    No, reuse previous settings
    No, customize settings
```

Les réglages recommandés activent **TypeScript, ESLint, Tailwind CSS, App Router, Cache Components**, sans dossier `src/`, avec l'alias d'import `@/*` et un fichier `AGENTS.md` ; Turbopack est le bundler par défaut. Pour tout accepter sans question :

```bash
npx create-next-app@latest mon-app --yes
```

> 💡 Avec un autre gestionnaire de paquets : `pnpm create next-app`, `yarn create next-app` ou `bun create next-app`.

### 2.3 Lancer le serveur de développement

```bash
cd mon-app
npm run dev
```

Ouvre <http://localhost:3000>. Modifie `app/page.tsx`, enregistre : le navigateur se met à jour **sans rechargement** (Fast Refresh).

### 2.4 Anatomie du projet

```text
mon-app/
├── app/                    ← l'App Router : tes routes vivent ici
│   ├── favicon.ico
│   ├── globals.css         ← styles globaux (+ Tailwind)
│   ├── layout.tsx          ← layout racine (obligatoire)
│   └── page.tsx            ← page d'accueil : URL "/"
├── public/                 ← fichiers statiques servis à la racine (/next.svg…)
├── AGENTS.md               ← consignes pour les agents de code (optionnel)
├── eslint.config.mjs       ← configuration ESLint
├── next.config.ts          ← configuration de Next.js
├── next-env.d.ts           ← généré par Next.js : ne pas modifier
├── package.json            ← dépendances et scripts
├── postcss.config.mjs      ← Tailwind, via PostCSS
└── tsconfig.json           ← configuration TypeScript
```

> 💡 Le contenu exact varie légèrement d'une version du template à l'autre.

### 2.5 Les scripts npm

| Commande | Rôle |
|---|---|
| `npm run dev` | Serveur de développement (Turbopack, Fast Refresh) |
| `npm run build` | Build de production : prérendu et optimisations |
| `npm run start` | Sert le build de production |
| `npm run lint` | Lance ESLint |

> ⚠️ **Piège** : depuis Next.js 16, `next build` n'exécute **plus** le linter. Lance `npm run lint` toi-même (et en CI). Turbopack est le bundler par défaut ; `next dev --webpack` permet de revenir à Webpack si une dépendance l'exige.

### 2.6 Le fichier `next.config.ts`

```ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
}

export default nextConfig
```

- **`cacheComponents`** active le modèle de rendu et de cache du module 7 (`'use cache'`, shell statique, `<Suspense>`).
- **`partialPrefetching`** précharge le « shell » de chaque route liée : la navigation devient quasi instantanée (module 4).

### 2.7 Alias d'import et dossier `public`

```tsx
import Footer from '@/app/ui/footer' // « @/ » = racine du projet
```

Un fichier `public/logo.png` est servi à l'URL `/logo.png`.

### 2.8 La documentation de ta version, hors-ligne

Ta version de Next.js embarque sa propre documentation dans `node_modules/next/dist/docs/`. Le fichier `AGENTS.md` y fait référence pour que les agents de code (Claude Code, Cursor, Copilot…) travaillent avec la doc de **ta** version plutôt qu'avec leurs souvenirs.

## 3. Le routing par les fichiers

> 🎯 **Objectifs** : créer des pages et des layouts · utiliser les segments dynamiques · organiser un projet sans changer les URLs · connaître les fichiers spéciaux.

### 3.1 Le principe

Next.js utilise un **routing par le système de fichiers** : la structure du dossier `app/` *est* la structure des URLs.

- Un **dossier** = un **segment d'URL**.
- Un fichier **`page.tsx`** rend la route **publique**. Sans lui, le dossier n'est pas accessible.
- Un fichier **`layout.tsx`** définit une interface partagée par la page et ses enfants.

```text
app/
├── layout.tsx            → enveloppe toutes les pages
├── page.tsx              → /
├── about/
│   └── page.tsx          → /about
└── blog/
    ├── layout.tsx        → enveloppe /blog et tout ce qui est en dessous
    ├── page.tsx          → /blog
    └── [id]/
        └── page.tsx      → /blog/1, /blog/2, …
```

### 3.2 Ta première page

```tsx
// app/about/page.tsx
export default function AboutPage() {
  return <h1>À propos</h1>
}
```

Une page est un composant React exporté **par défaut**. Visite `/about` : c'est tout.

### 3.3 Les layouts

Le **layout racine** `app/layout.tsx` est obligatoire et doit contenir les balises `<html>` et `<body>` :

```tsx
// app/layout.tsx
import type { Metadata } from 'next'
import './globals.css'

export const metadata: Metadata = {
  title: 'Mon site Next.js',
  description: 'Construit pendant le cours Fundamentals',
}

export default function RootLayout({
  children,
}: {
  children: React.ReactNode
}) {
  return (
    <html lang="fr">
      <body>{children}</body>
    </html>
  )
}
```

Les layouts s'**imbriquent** : chaque `layout.tsx` enveloppe ses segments enfants via la prop `children`.

```tsx
// app/blog/layout.tsx
export default function BlogLayout({ children }: { children: React.ReactNode }) {
  return (
    <section>
      <p>📚 Section blog</p>
      {children}
    </section>
  )
}
```

Ici, `app/layout.tsx` enveloppe `app/blog/layout.tsx`, qui enveloppe `app/blog/page.tsx` et `app/blog/[id]/page.tsx`.

> 💡 **Les layouts persistent** : quand tu navigues entre deux pages qui partagent un layout, celui-ci garde son état et ne se re-rend pas.

### 3.4 Segments dynamiques

Entoure le nom d'un dossier de crochets pour capturer une partie de l'URL :

| Dossier | URL | `params` |
|---|---|---|
| `app/blog/[id]/page.tsx` | `/blog/42` | `{ id: '42' }` |
| `app/shop/[...slug]/page.tsx` | `/shop/a/b/c` | `{ slug: ['a', 'b', 'c'] }` |
| `app/docs/[[...slug]]/page.tsx` | `/docs` puis `/docs/a/b` | `{ slug: undefined }` puis `{ slug: ['a', 'b'] }` |

`[...slug]` (*catch-all*) ne reconnaît pas `/shop` seul ; `[[...slug]]` (*optional catch-all*) le reconnaît.

```tsx
// app/blog/[id]/page.tsx
export default async function PostPage({ params }: PageProps<'/blog/[id]'>) {
  const { id } = await params
  return <h1>Article n°{id}</h1>
}
```

```tsx
// app/blog/[id]/loading.tsx   ← à ajouter dès maintenant, l'explication suit
export default function Loading() {
  return <p>Chargement…</p>
}
```

Trois points à retenir :

1. **`params` est une `Promise`** : on l'attend avec `await` (ou avec `use()` dans un Client Component). L'accès synchrone n'est plus possible depuis Next.js 16.
2. **`PageProps<'/blog/[id]'>`** est un type global qui te donne `params` correctement typé. Il est généré par `next dev`, `next build` ou `npx next typegen` : si ton éditeur ne le trouve pas, lance une fois le serveur de dev. `LayoutProps<'/…'>` existe pour les layouts.
3. **Les valeurs de `params` sont toujours des chaînes** (ou des tableaux de chaînes) : convertis-les toi-même si tu attends un nombre.

> ⚠️ **Pourquoi ce `loading.tsx` ?** Avec Cache Components, `params` est une *donnée de requête* : Next.js ne la connaît pas au moment du build. Sans frontière de chargement autour de l'`await`, tu obtiendrais une erreur « blocking route ». Le fichier `loading.tsx` crée cette frontière. Le module 7 détaille le mécanisme.

### 3.5 Les paramètres de recherche (`?q=next`)

La page reçoit aussi `searchParams`, **également une `Promise`** :

```tsx
// app/blog/page.tsx
import { Suspense } from 'react'

export default function BlogPage(props: PageProps<'/blog'>) {
  return (
    <Suspense fallback={<p>Chargement…</p>}>
      <Results searchParams={props.searchParams} />
    </Suspense>
  )
}

async function Results({
  searchParams,
}: Pick<PageProps<'/blog'>, 'searchParams'>) {
  const { q } = await searchParams // string | string[] | undefined
  return <p>Recherche : {q ?? 'aucune'}</p>
}
```

Comme `params`, `searchParams` dépend de la requête : on l'attend **sous un `<Suspense>`** (module 7). Dans un Client Component, le hook `useSearchParams()` s'utilise lui aussi sous un `<Suspense>`.

### 3.6 Organiser son code sans changer les URLs

| Convention | Exemple | Effet |
|---|---|---|
| **Groupe de routes** `(nom)` | `app/(marketing)/pricing/page.tsx` → `/pricing` | Le dossier n'apparaît **pas** dans l'URL ; il permet de partager un layout entre quelques routes |
| **Dossier privé** `_nom` | `app/blog/_components/` | Exclu du routing |
| **Colocation** | `app/blog/post-card.tsx` | Un fichier n'est une route que s'il s'appelle `page` ou `route` : tu peux ranger tes composants à côté |

```text
app/
├── layout.tsx             ← layout racine (html, body)
├── (marketing)/
│   ├── layout.tsx         ← layout propre aux pages marketing (imbriqué dans la racine)
│   ├── pricing/page.tsx   → /pricing
│   └── about/page.tsx     → /about
└── (app)/
    ├── layout.tsx         ← un autre layout (une barre latérale, par exemple)
    └── dashboard/page.tsx → /dashboard
```

### 3.7 Les fichiers spéciaux

| Fichier | Rôle |
|---|---|
| `layout.tsx` | Interface partagée et persistante |
| `page.tsx` | Interface propre à une route (la rend publique) |
| `loading.tsx` | État de chargement : frontière `<Suspense>` automatique autour de la page |
| `error.tsx` | Interface d'erreur (frontière d'erreur, Client Component) |
| `not-found.tsx` | Interface « introuvable » (404) |
| `global-error.tsx` | Erreur survenue dans le layout racine |
| `route.ts` | Endpoint d'API |
| `template.tsx` | Comme un layout, mais **remonté** à chaque navigation |
| `default.tsx` | Page de secours des routes parallèles (palier 2) |

Ces fichiers s'emboîtent dans un ordre précis, du plus extérieur au plus intérieur :

```text
layout
└─ template
   └─ error        (frontière d'erreur)
      └─ loading   (frontière Suspense)
         └─ not-found   (frontière « introuvable »)
            └─ page  (ou un layout imbriqué)
```

> 💡 **Conséquence** : un `error.tsx` n'attrape **pas** les erreurs du `layout.tsx` situé dans le **même** segment, puisqu'il se trouve à l'intérieur. Place-le dans le segment parent, ou utilise `global-error.tsx` pour le layout racine (module 8).

## 4. Navigation

> 🎯 **Objectifs** : naviguer avec `<Link>` · comprendre le préchargement · mettre en évidence le lien actif · naviguer par code (`useRouter`, `redirect`).

### 4.1 `<Link>` : la navigation côté client

```tsx
import Link from 'next/link'

export default function Menu() {
  return (
    <nav>
      <Link href="/">Accueil</Link>
      <Link href="/blog">Blog</Link>
      <Link href={`/blog/${42}`}>Article 42</Link>
    </nav>
  )
}
```

`<Link>` étend la balise `<a>` et apporte :

- une **transition côté client** : pas de rechargement complet, les layouts partagés sont conservés, l'état n'est pas perdu ;
- le **préchargement** (*prefetch*) de la page cible ;
- la gestion du **défilement** (retour en haut de page).

> ⚠️ Un `<a href="/blog">` classique provoque un rechargement complet et aucun préchargement. Réserve `<a>` aux liens **externes**.

### 4.2 Le préchargement

En **production**, Next.js précharge les routes dont le `<Link>` entre dans la zone visible : au clic, l'affichage est quasi instantané. En développement, le préchargement est désactivé : pour le voir à l'œuvre, teste avec `npm run build` puis `npm run start`.

Avec `partialPrefetching` (activé dans un nouveau projet), le routeur précharge par défaut le **shell** de chaque route, c'est-à-dire sa partie statique.

```tsx
import Link from 'next/link'

export default function Liens() {
  return (
    <>
      {/* Aucun préchargement */}
      <Link href="/blog" prefetch={false}>Blog</Link>

      {/* Précharge aussi le contenu mis en cache qui dépend de l'URL */}
      <Link href="/blog/42" prefetch>Article 42</Link>
    </>
  )
}
```

> ⚠️ `prefetch` (ou `prefetch={true}`) peut coûter **un appel serveur par lien**. Réserve-le aux liens importants, pas à une liste de 500 éléments.

### 4.3 Mettre en évidence le lien actif

Il faut lire l'URL courante : c'est le rôle du hook `usePathname()`, utilisable uniquement dans un **Client Component**.

```tsx
// app/ui/main-nav.tsx
'use client'

import Link from 'next/link'
import { usePathname } from 'next/navigation'

const links = [
  { href: '/', label: 'Accueil' },
  { href: '/blog', label: 'Blog' },
  { href: '/about', label: 'À propos' },
]

export default function MainNav() {
  const pathname = usePathname()

  return (
    <nav className="flex gap-4">
      {links.map(({ href, label }) => {
        const active = href === '/' ? pathname === '/' : pathname.startsWith(href)
        return (
          <Link
            key={href}
            href={href}
            aria-current={active ? 'page' : undefined}
            className={active ? 'font-bold underline' : 'text-gray-500'}
          >
            {label}
          </Link>
        )
      })}
    </nav>
  )
}
```

Utilise-le dans le layout racine, **entouré d'un `<Suspense>`** :

```tsx
// app/layout.tsx (extrait)
import { Suspense } from 'react'
import MainNav from '@/app/ui/main-nav'

// …
<body>
  <header className="border-b p-4">
    <Suspense fallback={<nav className="h-6" />}>
      <MainNav />
    </Suspense>
  </header>
  <main className="p-4">{children}</main>
</body>
```

> ⚠️ **Pourquoi `<Suspense>` ?** Pour une route dynamique comme `/blog/[id]`, l'URL exacte n'est pas connue au moment du prérendu. Avec Cache Components, `usePathname()` doit donc se trouver sous une frontière `<Suspense>`, sinon Next.js affiche une erreur. Le *fallback* (ici un `<nav>` vide de même hauteur, pour éviter un saut de mise en page) est inclus dans le shell statique.

### 4.4 Naviguer par code

**Dans un Client Component**, avec `useRouter()` :

```tsx
// app/ui/search-box.tsx
'use client'

import { useRouter } from 'next/navigation'

export default function SearchBox() {
  const router = useRouter()

  return (
    <form
      onSubmit={(e) => {
        e.preventDefault()
        const q = new FormData(e.currentTarget).get('q') as string
        router.push(`/blog?q=${encodeURIComponent(q)}`)
      }}
    >
      <input name="q" placeholder="Rechercher…" />
    </form>
  )
}
```

Méthodes utiles : `router.push(url)`, `router.replace(url)` (sans nouvelle entrée d'historique), `router.back()`, `router.forward()`, `router.refresh()` et `router.prefetch(url)`.

> 💡 Importe `useRouter` depuis **`next/navigation`**, jamais depuis `next/router` (Pages Router). Et préfère `<Link>` dès que c'est possible.

**Côté serveur**, avec `redirect()` :

```tsx
// app/blog/[id]/page.tsx (extrait)
import { redirect } from 'next/navigation'

export default async function Page({ params }: PageProps<'/blog/[id]'>) {
  const { id } = await params
  if (id === '0') redirect('/blog') // interrompt le rendu et redirige
  return <h1>Article {id}</h1>
}
```

`redirect()` fonctionne dans les Server Components, les Route Handlers et les Server Actions ; `permanentRedirect()` produit une redirection permanente (308). Pour des redirections **fixes**, déclare-les plutôt dans `next.config.ts` :

```ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  async redirects() {
    return [{ source: '/ancien-blog', destination: '/blog', permanent: true }]
  },
}

export default nextConfig
```

### 4.5 Un retour visuel pendant la navigation

Sur réseau lent, le préchargement peut ne pas être terminé au moment du clic. Le hook `useLinkStatus()` indique qu'une navigation est en cours ; il doit être utilisé **dans un composant rendu à l'intérieur d'un `<Link>`** :

```tsx
// app/ui/link-spinner.tsx
'use client'

import { useLinkStatus } from 'next/link'

export default function LinkSpinner() {
  const { pending } = useLinkStatus()
  return pending ? <span aria-hidden>⏳</span> : null
}
```

```tsx
<Link href="/blog">
  Blog <LinkSpinner />
</Link>
```

## 5. Server Components et Client Components

> 🎯 **Objectifs** : savoir où s'exécute chaque composant · choisir entre Server et Client · composer les deux · protéger le code serveur.

### 5.1 Le modèle mental

Dans l'App Router, **tous les composants sont des Server Components par défaut** (layouts et pages compris). Ils s'exécutent **uniquement sur le serveur**, au build ou à la requête ; leur code n'est **pas envoyé** au navigateur. Tu ajoutes `'use client'` **uniquement** aux morceaux qui ont besoin d'interactivité.

### 5.2 Qui fait quoi ?

| Tu as besoin de… | Server Component | Client Component |
|---|---|---|
| Lire une base de données ou une API, utiliser des secrets | ✅ | ❌ |
| Réduire le JavaScript envoyé au navigateur | ✅ | ❌ |
| `useState`, `useEffect`, `useRef`, contexte React | ❌ | ✅ |
| Gestionnaires d'événements (`onClick`, `onChange`…) | ❌ | ✅ |
| API du navigateur (`window`, `localStorage`, géolocalisation) | ❌ | ✅ |
| Hooks personnalisés qui reposent sur ce qui précède | ❌ | ✅ |

**Règle pratique** : commence en Server Component. Ne passe en Client Component que pour la **feuille** interactive (le bouton, pas toute la page).

### 5.3 Écrire un Client Component

```tsx
// app/ui/counter.tsx
'use client'

import { useState } from 'react'

export default function Counter() {
  const [count, setCount] = useState(0)
  return <button onClick={() => setCount(count + 1)}>{count} likes</button>
}
```

La directive `'use client'` se place **tout en haut du fichier**, avant les imports. Elle déclare une **frontière** : ce fichier et tout ce qu'il importe rejoignent le bundle envoyé au navigateur. Inutile de la répéter dans chaque composant enfant.

> 💡 Un Client Component est quand même **prérendu en HTML** sur le serveur. `'use client'` ne signifie pas « rendu uniquement dans le navigateur », mais « hydraté et interactif dans le navigateur ».

### 5.4 Passer des données du serveur au client

On passe les données par **props** :

```tsx
// app/page.tsx  (Server Component)
import LikeButton from '@/app/ui/like-button'

export default function Page() {
  const post = { title: 'Mon article', likes: 12 } // en vrai : chargé depuis une API ou une base (module 6)

  return (
    <article>
      <h1>{post.title}</h1>
      <LikeButton initialLikes={post.likes} />
    </article>
  )
}
```

```tsx
// app/ui/like-button.tsx  (Client Component)
'use client'

import { useState } from 'react'

export default function LikeButton({ initialLikes }: { initialLikes: number }) {
  const [likes, setLikes] = useState(initialLikes)
  return <button onClick={() => setLikes(likes + 1)}>❤️ {likes}</button>
}
```

> ⚠️ Les props doivent être **sérialisables** : types de base, tableaux, objets simples, et quelques types riches comme `Date` ou `Promise`. Une fonction ordinaire ou une instance de classe ne passe pas. Et tout ce que tu passes en props **atterrit dans le navigateur** : n'y mets jamais de secret.

### 5.5 Imbriquer un Server Component dans un Client Component

Un Client Component ne peut pas *importer* un Server Component, mais il peut en recevoir un **via `children`** (ou une autre prop). Le serveur rend le Server Component à l'avance et le passe comme un « trou » :

```tsx
// app/ui/modal.tsx  (Client Component)
'use client'

import { useState } from 'react'

export default function Modal({ children }: { children: React.ReactNode }) {
  const [open, setOpen] = useState(false)

  return (
    <>
      <button onClick={() => setOpen(true)}>Voir le panier</button>
      {open && <div role="dialog">{children}</div>}
    </>
  )
}
```

```tsx
// app/page.tsx  (Server Component)
import Modal from '@/app/ui/modal'
import Cart from '@/app/ui/cart' // un Server Component

export default function Page() {
  return (
    <Modal>
      <Cart />
    </Modal>
  )
}
```

### 5.6 Les providers de contexte

Le contexte React n'existe pas dans les Server Components. On crée donc un **Client Component** qui reçoit `children` :

```tsx
// app/theme-provider.tsx
'use client'

import { createContext } from 'react'

export const ThemeContext = createContext('light')

export default function ThemeProvider({ children }: { children: React.ReactNode }) {
  return <ThemeContext.Provider value="dark">{children}</ThemeContext.Provider>
}
```

```tsx
// app/layout.tsx (extrait)
<body>
  <ThemeProvider>{children}</ThemeProvider>
</body>
```

> 💡 Place les providers **le plus bas possible** dans l'arbre (autour de `{children}`, pas autour de `<html>`) : Next.js optimise mieux les parties statiques.

### 5.7 Protéger le code serveur

- **Variables d'environnement** : seules celles préfixées par `NEXT_PUBLIC_` sont incluses dans le bundle client. Les autres valent une chaîne vide côté navigateur.
- **Le package `server-only`** transforme une importation accidentelle en erreur :

```ts
// lib/data.ts
import 'server-only'

export async function getSecretData() {
  // clé d'API, requête SQL, etc.
}
```

Si ce fichier est importé depuis un Client Component, la compilation échoue. Son pendant `client-only` protège le code qui touche à `window`.

### 5.8 Les erreurs classiques

| Symptôme | Cause | Solution |
|---|---|---|
| Message indiquant qu'un hook comme `useState` ne fonctionne que dans un Client Component | Hook ou événement utilisé dans un Server Component | Ajoute `'use client'` sur la **feuille** concernée |
| `window is not defined` | Code navigateur exécuté pendant le rendu serveur | Déplace-le dans un `useEffect` ou un gestionnaire d'événement |
| Erreur sur une fonction passée à un Client Component | Prop non sérialisable | Passe des données, pas des fonctions (ou une Server Action, palier 2) |
| Un composant d'une bibliothèque tierce plante dans un Server Component | La bibliothèque n'a pas de `'use client'` | Enveloppe-la dans ton propre Client Component qui la réexporte |
| Un Client Component `async` est refusé | Un Client Component ne peut pas être `async` | Charge les données côté serveur et passe-les en props, ou utilise `use()` |

## 6. Récupérer des données

> 🎯 **Objectifs** : charger des données dans un Server Component · éviter les cascades de requêtes · comprendre l'erreur « blocking route » et ses deux solutions · connaître les options côté client.

Les exemples utilisent l'API publique [JSONPlaceholder](https://jsonplaceholder.typicode.com) (`/posts`, `/posts/1`, `/posts/1/comments`) : gratuite et sans clé.

### 6.1 `await` directement dans le composant

Un Server Component peut être `async`. Pas de `useEffect`, pas d'état de chargement à gérer à la main :

```tsx
// app/blog/page.tsx
type Post = { id: number; title: string; body: string }

export default async function BlogPage() {
  const res = await fetch('https://jsonplaceholder.typicode.com/posts')
  const posts: Post[] = await res.json()

  return (
    <ul>
      {posts.slice(0, 10).map((post) => (
        <li key={post.id}>{post.title}</li>
      ))}
    </ul>
  )
}
```

Tu peux aussi interroger directement une **base de données** ou un ORM ; le code et les identifiants restent sur le serveur :

```tsx
import { db } from '@/lib/db' // ORM de ton choix (palier 2)

export default async function Page() {
  const posts = await db.post.findMany()
  // …
}
```

> 💡 Les `fetch` identiques d'un même arbre de rendu sont **mémoïsés** : plusieurs composants peuvent demander la même donnée sans multiplier les requêtes. Pour un accès sans `fetch` (ORM), utilise `React.cache` (§ 6.4).
>
> 💡 Dans ce modèle, `fetch` n'est **pas** mis en cache par défaut.

### 6.2 L'erreur que tu vas rencontrer (et c'est normal)

Lance le code ci-dessus dans un projet neuf. Le dev overlay affiche un message du type **« Uncached data was accessed outside of `<Suspense>` »** (diagnostic `blocking-route`).

**Pourquoi ?** Au build, Next.js essaie de prérendre la page pour produire un *shell statique*. Or la page attend une donnée **non mise en cache** : impossible de savoir à l'avance ce que renverra l'API. Sans indication de ta part, la page entière serait bloquée tant que la donnée n'est pas arrivée (écran vide pour l'utilisateur). Next.js préfère t'obliger à choisir.

**Deux solutions**, selon la nature de la donnée :

| La donnée est… | Solution | Résultat |
|---|---|---|
| **Identique pour tous** pendant un certain temps (liste d'articles, catalogue…) | La **mettre en cache** avec `'use cache'` | Incluse dans le shell statique : page instantanée |
| **Propre à la requête** ou toujours fraîche | L'entourer de **`<Suspense>`** | Le shell affiche un *fallback*, la donnée est **streamée** ensuite |

**Solution A : mettre en cache.**

```ts
// lib/posts.ts
import { cacheLife } from 'next/cache'

export type Post = { id: number; userId: number; title: string; body: string }

export async function getPosts(): Promise<Post[]> {
  'use cache'
  cacheLife('hours') // considéré comme frais environ une heure, puis régénéré

  const res = await fetch('https://jsonplaceholder.typicode.com/posts')
  if (!res.ok) throw new Error('Impossible de charger les articles')
  return res.json()
}
```

```tsx
// app/blog/page.tsx
import { getPosts } from '@/lib/posts'

export default async function BlogPage() {
  const posts = await getPosts() // mis en cache : OK, aucune erreur

  return (
    <ul>
      {posts.slice(0, 10).map((p) => (
        <li key={p.id}>{p.title}</li>
      ))}
    </ul>
  )
}
```

**Solution B : streamer avec `<Suspense>`.**

```tsx
// app/blog/page.tsx
import { Suspense } from 'react'

export default function BlogPage() {
  return (
    <>
      <h1>Blog</h1> {/* dans le shell : affiché tout de suite */}
      <Suspense fallback={<p>Chargement des articles…</p>}>
        <LatestPosts />
      </Suspense>
    </>
  )
}

async function LatestPosts() {
  // Pas de cache : données fraîches à chaque requête
  const res = await fetch('https://jsonplaceholder.typicode.com/posts')
  const posts: { id: number; title: string }[] = await res.json()

  return (
    <ul>
      {posts.slice(0, 10).map((p) => (
        <li key={p.id}>{p.title}</li>
      ))}
    </ul>
  )
}
```

Le module 7 approfondit ce modèle.

### 6.3 Requêtes en séquence ou en parallèle

Dans un même composant, deux `await` à la suite s'exécutent **l'un après l'autre**. Si les requêtes sont indépendantes, lance-les ensemble :

```tsx
// extrait : les données sont gérées selon § 6.2
export default async function Page({ params }: PageProps<'/artist/[username]'>) {
  const { username } = await params

  // ❌ Séquentiel : getAlbums attend la fin de getArtist
  // const artist = await getArtist(username)
  // const albums = await getAlbums(username)

  // ✅ Parallèle : les deux requêtes démarrent en même temps
  const [artist, albums] = await Promise.all([
    getArtist(username),
    getAlbums(username),
  ])

  return <h1>{artist.name} ({albums.length} albums)</h1>
}
```

- Si une requête échoue, `Promise.all` échoue en bloc ; `Promise.allSettled` laisse chaque requête réussir ou échouer séparément.
- Quand une requête **dépend** d'une autre (l'id de l'artiste pour charger ses playlists), la cascade est inévitable : isole alors la seconde dans un composant sous `<Suspense>` pour ne pas bloquer le reste de la page.

### 6.4 Réutiliser une donnée avec `React.cache`

Pour un accès **sans `fetch`** (ORM, SDK…), enveloppe la fonction avec `React.cache` : plusieurs composants peuvent l'appeler pendant **une même requête** et partager un seul résultat.

```ts
// lib/user.ts
import { cache } from 'react'
import { db } from '@/lib/db' // ORM de ton choix

export const getUser = cache(async (id: string) => {
  return db.user.findUnique({ where: { id } })
})
```

> 💡 `React.cache` ne vit que le temps d'**une requête** : il n'y a aucun partage entre deux visiteurs. Ne le confonds pas avec `'use cache'` (module 7), qui conserve le résultat **entre les requêtes**.

### 6.5 Récupérer des données côté client

Parfois, il faut charger des données **dans le navigateur** : interactions fréquentes, *polling*, état purement client. Deux options :

- une bibliothèque comme **SWR** ou **TanStack Query** (cache, rechargement, états de chargement) ;
- l'API React **`use()`**, pour lire une promesse démarrée côté serveur :

```tsx
// app/blog/page.tsx  (Server Component)
import { Suspense } from 'react'
import Posts from '@/app/ui/posts'
import { getPosts } from '@/lib/posts' // la fonction de la solution A

export default function Page() {
  const posts = getPosts() // ⚠️ pas de await : on transmet la promesse

  return (
    <Suspense fallback={<p>Chargement…</p>}>
      <Posts posts={posts} />
    </Suspense>
  )
}
```

```tsx
// app/ui/posts.tsx  (Client Component)
'use client'

import { use } from 'react'

export default function Posts({
  posts,
}: {
  posts: Promise<{ id: number; title: string }[]>
}) {
  const allPosts = use(posts)
  return (
    <ul>
      {allPosts.slice(0, 10).map((p) => (
        <li key={p.id}>{p.title}</li>
      ))}
    </ul>
  )
}
```

### 6.6 Bonnes pratiques de sécurité

- **Ne transmets au client que le strict nécessaire** : ce que tu passes en props d'un Client Component est visible de l'utilisateur. Sélectionne les champs au lieu d'envoyer une ligne de base de données entière.
- **Garde les secrets côté serveur** (`server-only`, variables sans `NEXT_PUBLIC_`).
- **Vérifie l'authentification et les droits là où tu accèdes aux données**, pas seulement dans l'interface : un composant masqué n'est pas une protection (la couche d'accès aux données est au programme du palier 2).

## 7. Le modèle de rendu

> 🎯 **Objectifs** : comprendre ce qu'est le shell statique · classer n'importe quel code en *prévisible*, *en cache*, *dynamique* ou *instable* · corriger l'erreur « blocking route » · utiliser `'use cache'`, `cacheLife` et `<Suspense>`.

C'est **le** module à maîtriser : il explique la plupart des erreurs que tu rencontreras avec une application Next.js récente.

### 7.1 L'idée centrale

Avec Cache Components, **toutes les routes sont dynamiques par défaut** : le rendu a lieu à la requête. Mais au moment de `next build`, Next.js **prérend un maximum de chaque page**. Le résultat est le **shell statique** (HTML + RSC payload), que l'on peut servir directement depuis un CDN. Tout ce qui ne peut pas être calculé à l'avance est remplacé par un *fallback* (`<Suspense>`), puis **streamé** à la requête, dans la même réponse HTTP.

Ce mécanisme s'appelle le **Partial Prerendering (PPR)** ; c'est le comportement par défaut.

```text
GET /blog/3
┌───────────────────────────────────────┐
│ En-tête                   (statique)  │ ← dans le shell : servi instantanément
│ Article                   (en cache)  │ ← dans le shell : idem ('use cache')
│ ░░░ Commentaires… ░░░     (fallback)  │ ← remplacé en streaming par le vrai contenu
└───────────────────────────────────────┘
```

### 7.2 Les quatre familles de code

| Famille | Exemples | Exécuté… | Dans le shell ? | Que faire ? |
|---|---|---|---|---|
| **Prévisible** | JSX pur, imports, calculs purs, lecture d'un fichier fixe avec `fs.readFileSync` | Au build | ✅ oui | Rien |
| **En cache** | Fonction ou composant marqué `'use cache'` | Au build, puis à la revalidation | ✅ oui (si la durée de vie n'est pas trop courte) | Ajouter `'use cache'` + `cacheLife` |
| **Dynamique** | `fetch` ou requête SQL non cachés, `cookies()`, `headers()`, `searchParams`, `params` inconnus au build | À chaque requête | ❌ seul le *fallback* y figure | Entourer de `<Suspense>` |
| **Instable** | `Math.random()`, `Date.now()`, `new Date()`, `crypto.randomUUID()` | — | ❌ erreur si non traité | `await connection()` + `<Suspense>`, ou `'use cache'` |

### 7.3 La règle d'or

> Tout ce qui dépend de la **requête** ou de **données non mises en cache** doit être soit **mis en cache** (`'use cache'`), soit **entouré de `<Suspense>`**. Sinon, Next.js signale un problème de type **`blocking-route`**, en développement comme au build.

Pourquoi cette sévérité ? Sans elle, un seul `await` mal placé bloquerait la page entière et ruinerait l'intérêt du shell statique. Next.js préfère te le dire tout de suite.

### 7.4 Mettre en cache avec `'use cache'`

La directive `'use cache'` met en cache la **valeur de retour** d'une fonction ou d'un composant `async`. On l'applique à deux niveaux.

**Niveau donnée** : une fonction qui charge ou calcule quelque chose.

```ts
// lib/users.ts
import { cacheLife } from 'next/cache'
import { db } from '@/lib/db' // ORM de ton choix

export async function getUsers() {
  'use cache'
  cacheLife('hours')
  return db.user.findMany()
}
```

**Niveau interface** : un composant, une page ou un layout entier.

```tsx
// app/ui/footer.tsx
import { cacheLife } from 'next/cache'

export default async function Footer() {
  'use cache'
  cacheLife('days')

  return <footer>© {new Date().getFullYear()} Mon site</footer>
}
```

Ce qu'il faut savoir :

- **`cacheLife`** fixe la durée de vie : profils prédéfinis (`'minutes'`, `'hours'`, `'days'`, `'weeks'`…) ou valeurs personnalisées. Associe-le à chaque `'use cache'` ; sans lui, un profil `default` s'applique.
- Les **arguments** de la fonction (et les valeurs capturées) font partie de la **clé de cache** : `getPost('1')` et `getPost('2')` ont chacun leur entrée.
- À l'intérieur d'une fonction en cache, **ne lis pas** `cookies()`, `headers()` ni `searchParams` : lis-les *à l'extérieur* et passe les valeurs en arguments (variante avancée `'use cache: private'`, palier 2).
- Arguments et valeurs de retour doivent être **sérialisables**.
- Placée tout en haut d'un fichier, la directive met en cache **toutes les fonctions exportées** de ce fichier.
- Par défaut, le cache serveur est **en mémoire** et propre à chaque instance du serveur. Le cache durable et partagé (`'use cache: remote'`) relève du palier 3.
- Le cache est lié à un **déploiement** : un nouveau déploiement repart d'un cache vide.
- `cacheTag` et la revalidation à la demande sont au programme du palier 2.

> ⚠️ Avec Cache Components, les exports de segment `export const dynamic`, `export const revalidate` et `export const fetchCache` ne sont plus utilisés : `'use cache'` et `cacheLife` les remplacent.

### 7.5 Streamer avec `<Suspense>`

Pour les données qui doivent rester **fraîches** ou **propres à la requête**, enveloppe le composant concerné :

```tsx
import { Suspense } from 'react'

async function LatestPosts() {
  // Pas de cache : frais à chaque requête
  const res = await fetch('https://jsonplaceholder.typicode.com/posts')
  const posts: { id: number; title: string }[] = await res.json()

  return (
    <ul>
      {posts.slice(0, 5).map((p) => (
        <li key={p.id}>{p.title}</li>
      ))}
    </ul>
  )
}

export default function Page() {
  return (
    <>
      <h1>Mon blog</h1> {/* dans le shell : s'affiche tout de suite */}
      <Suspense fallback={<p>Chargement des articles…</p>}>
        <LatestPosts />
      </Suspense>
    </>
  )
}
```

> 💡 **Plus la frontière `<Suspense>` est proche de la donnée, plus le shell statique est grand.** N'enveloppe pas toute la page si seul un widget est dynamique.
>
> 💡 `<Suspense>` ne rend pas un composant dynamique à lui seul : un composant purement synchrone se termine au prérendu, qu'il soit enveloppé ou non.

### 7.6 Les données de requête (*runtime data*)

`cookies()`, `headers()`, `searchParams` et les `params` que Next.js ne connaît pas au build sont des **données de requête** : elles n'existent que lorsqu'un visiteur arrive. Tout composant qui les lit doit se trouver sous `<Suspense>`.

```tsx
import { cookies } from 'next/headers'
import { Suspense } from 'react'

async function Greeting() {
  const theme = (await cookies()).get('theme')?.value ?? 'light'
  return <p>Ton thème : {theme}</p>
}

export default function Page() {
  return (
    <>
      <h1>Tableau de bord</h1>
      <Suspense fallback={<p>Chargement…</p>}>
        <Greeting />
      </Suspense>
    </>
  )
}
```

**Cas des `params`.** Trois stratégies :

```tsx
// (a) Page entière : un loading.tsx à côté de la page
//     app/blog/[id]/loading.tsx → export default function Loading() { return <p>Chargement…</p> }

// (b) Plus fin : transmettre la promesse et l'attendre sous un <Suspense>
// app/shop/[slug]/page.tsx
import { Suspense } from 'react'

export default function Page({ params }: PageProps<'/shop/[slug]'>) {
  return (
    <div>
      <h1>Boutique</h1> {/* dans le shell */}
      <Suspense fallback={<p>Chargement…</p>}>
        {params.then(({ slug }) => (
          <Product slug={slug} />
        ))}
      </Suspense>
    </div>
  )
}

function Product({ slug }: { slug: string }) {
  return <h2>Produit : {slug}</h2>
}

// (c) generateStaticParams : voir ci-dessous
```

**(c) `generateStaticParams`.** Si tu connais à l'avance certaines valeurs (par exemple les 10 premiers articles), cette fonction les prérend au build. `params` y est alors **connu**, et un `await params` direct devient possible tant que le reste de la page est en cache (c'est ce que fait le mini-blog du module 13). Les valeurs absentes de la liste sont rendues à la demande.

> 💡 Dans un **layout**, évite d'attendre `params` tout en haut du composant : passe la promesse plus bas et attends-la sous un `<Suspense>`, pour que le reste du layout reste dans le shell.

### 7.7 Valeurs aléatoires et heure courante

`Math.random()`, `Date.now()`, `new Date()` ou `crypto.randomUUID()` donnent un résultat différent à chaque exécution : Next.js refuse de les figer par accident dans le shell. Deux options :

```tsx
import { connection } from 'next/server'
import { cacheLife } from 'next/cache'
import { Suspense } from 'react'

// Option A : une valeur différente à chaque requête
async function RequestId() {
  await connection() // « ce composant dépend de la requête »
  return <p>Requête n° {crypto.randomUUID()}</p>
}

// Option B : une valeur partagée, figée jusqu'à la revalidation
async function VersionId() {
  'use cache'
  cacheLife('days')
  return <p>Version : {crypto.randomUUID()}</p>
}

export default function Page() {
  return (
    <>
      <Suspense fallback={<p>…</p>}>
        <RequestId />
      </Suspense>
      <VersionId />
    </>
  )
}
```

> ⚠️ **Le piège du footer** : le classique `© {new Date().getFullYear()}` déclenche cette erreur. Mets le footer dans un composant `'use cache'`, comme au § 7.4.

### 7.8 Voir ce qui se passe

- **Le dev overlay**, en développement, signale les problèmes (*insights*) : `blocking-route`, heure courante ou valeur aléatoire non maîtrisée… avec des pistes de correction.
- **Le résumé de `next build`** indique le mode de rendu de chaque route :

```text
○  (Static)            prerendered as static content
◐  (Partial Prerender) prerendered as static HTML with dynamic server-streamed content
ƒ  (Dynamic)           server-rendered on demand
```

- **Les Next.js DevTools** (l'icône Next.js affichée en développement) indiquent si la route courante est statique ou dynamique.

### 7.9 Et si ton projet n'a pas Cache Components ?

Si `cacheComponents` n'est pas activé dans `next.config.ts` (projet créé avec une version antérieure ou avec des réglages personnalisés), tu es dans le **modèle précédent** :

- une page est **prérendue statiquement** tant qu'elle n'utilise pas d'API dynamique (`cookies()`, `headers()`, `searchParams`…) ; sinon elle devient entièrement dynamique ;
- il n'y a pas d'erreur `blocking-route`, mais le choix « statique ou dynamique » s'applique à la **page entière** ;
- `'use cache'` n'est pas disponible : on utilise les exports de segment (`export const dynamic`, `export const revalidate`) ;
- le reste du cours (routing, composants, erreurs, API, styles…) s'applique tel quel.

Pour un nouveau projet, **active Cache Components** : c'est le modèle recommandé depuis la 16.4. Pour migrer un projet existant, consulte le guide *Migrating to Cache Components* de la documentation.

## 8. Chargement, erreurs et pages 404

> 🎯 **Objectifs** : afficher des états de chargement pertinents · gérer erreurs attendues et inattendues · créer des pages « introuvable » · connaître `global-error`.

### 8.1 Les états de chargement

Le fichier **`loading.tsx`** crée automatiquement une frontière `<Suspense>` autour de `page.tsx` et de ses enfants. L'utilisateur voit le layout et ce squelette immédiatement, puis le contenu le remplace.

```tsx
// app/blog/loading.tsx
export default function Loading() {
  return (
    <ul className="space-y-3" aria-busy="true">
      {Array.from({ length: 5 }).map((_, i) => (
        <li key={i} className="h-5 animate-pulse rounded bg-gray-200" />
      ))}
    </ul>
  )
}
```

Deux précisions importantes :

- Un squelette **utile** ressemble au contenu final (titre, photo de couverture, structure) : l'utilisateur comprend que l'application répond.
- `loading.tsx` enveloppe la **page**, pas le layout du même segment. Un layout qui lit des données de requête ou non cachées ne bénéficie donc pas du `loading.tsx` voisin : place un `<Suspense>` plus près de l'accès concerné, ou déplace le chargement dans la page.

### 8.2 Deux familles d'erreurs

| Famille | Exemples | Traitement |
|---|---|---|
| **Attendues** | Formulaire invalide, ressource introuvable, réponse 4xx d'une API | Les **modéliser** : valeur de retour, `notFound()`, message affiché |
| **Inattendues** | Bug, base de données injoignable | Les **lancer** (`throw`) : une frontière d'erreur (`error.tsx`) prend le relais |

### 8.3 `error.tsx`

```tsx
// app/blog/error.tsx
'use client' // obligatoire : une frontière d'erreur est un Client Component

import { useEffect } from 'react'

export default function BlogError({
  error,
  retry,
}: {
  error: Error & { digest?: string }
  retry: () => void
}) {
  useEffect(() => {
    console.error(error) // à remplacer par un service de supervision
  }, [error])

  return (
    <div role="alert">
      <h2>Oups, une erreur est survenue</h2>
      <button onClick={() => retry()}>Réessayer</button>
    </div>
  )
}
```

À retenir :

- **`retry()`** (stable depuis Next.js 16.3) relance le chargement **et** le rendu du segment, Server Components compris. L'ancien `reset()` existe toujours, mais se contente d'effacer l'état d'erreur sans recharger.
- En production, `error.message` est **générique** pour les erreurs venues du serveur (pas de fuite d'informations). `error.digest` est un identifiant qui permet de retrouver l'erreur dans les logs serveur.
- `error.tsx` n'attrape **pas** les erreurs du `layout.tsx` du même segment (§ 3.7), ni celles des **gestionnaires d'événements** : pour ces dernières, utilise un `try/catch` et un état.
- Les erreurs « remontent » vers la frontière parente la plus proche : tu peux mettre un `error.tsx` à plusieurs niveaux.

### 8.4 Les pages introuvables

```tsx
// app/blog/[id]/page.tsx (extrait)
import { notFound } from 'next/navigation'

export default async function Page({ params }: PageProps<'/blog/[id]'>) {
  const { id } = await params
  const post = await getPost(id) // voir module 6
  if (!post) notFound() // affiche le not-found.tsx le plus proche

  return <h1>{post.title}</h1>
}
```

```tsx
// app/blog/[id]/not-found.tsx
import Link from 'next/link'

export default function NotFound() {
  return (
    <div>
      <h1>Article introuvable</h1>
      <Link href="/blog">← Retour au blog</Link>
    </div>
  )
}
```

Un `app/not-found.tsx` à la racine devient la **page 404 globale** (pour toute URL qui ne correspond à aucune route).

### 8.5 `global-error.tsx`

Pour les erreurs survenues dans le **layout racine**, on utilise `app/global-error.tsx`. Il remplace tout le layout quand il s'active : il doit donc définir ses propres `<html>` et `<body>`.

```tsx
// app/global-error.tsx
'use client'

export default function GlobalError({
  retry,
}: {
  error: Error & { digest?: string }
  retry: () => void
}) {
  return (
    <html lang="fr">
      <body>
        <h2>Une erreur critique est survenue</h2>
        <button onClick={() => retry()}>Réessayer</button>
      </body>
    </html>
  )
}
```

> 💡 `global-error.tsx` n'hérite pas de tes styles globaux, et il ne peut pas exporter `metadata` (utilise la balise `<title>` de React si besoin). C'est une **dernière ligne de défense** : si tu dois l'utiliser souvent, le problème est ailleurs.

### 8.6 Une frontière d'erreur pour un seul composant

Depuis Next.js 16.3, `catchError` crée une frontière d'erreur **locale**, utilisable n'importe où dans l'arbre, qui n'entre pas en conflit avec `notFound()` ni `redirect()` :

```tsx
// app/ui/widget-boundary.tsx
'use client'

import { catchError, type ErrorInfo } from 'next/error'

function Fallback(props: { title: string }, { error, retry }: ErrorInfo) {
  return (
    <div role="alert">
      <h3>{props.title}</h3>
      <p>{error.message}</p>
      <button onClick={() => retry()}>Réessayer</button>
    </div>
  )
}

export default catchError(Fallback)
```

```tsx
<WidgetBoundary title="Statistiques indisponibles">
  <Stats />
</WidgetBoundary>
```

## 9. Route Handlers et Server Actions

> 🎯 **Objectifs** : créer une API avec `route.ts` · connaître ses règles · découvrir les Server Actions et savoir quand les préférer.

### 9.1 Route Handlers : une API dans ton projet

Un **Route Handler** est un fichier `route.ts` qui répond à des requêtes HTTP avec les API web standard `Request` et `Response`. Chaque méthode HTTP est une fonction exportée : `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`.

```ts
// app/api/health/route.ts   →   GET /api/health
export async function GET() {
  return Response.json({ status: 'ok' })
}
```

**Lire des paramètres de requête :**

```ts
// app/api/posts/route.ts   →   GET /api/posts?limit=5
import type { NextRequest } from 'next/server'
import { getPosts } from '@/lib/posts'

export async function GET(request: NextRequest) {
  const raw = Number(request.nextUrl.searchParams.get('limit'))
  const limit = Math.min(Math.max(raw || 10, 1), 100) // entre 1 et 100, 10 par défaut

  const posts = await getPosts()
  return Response.json(posts.slice(0, limit))
}
```

**Recevoir des données (POST) :**

```ts
// app/api/subscribe/route.ts   →   POST /api/subscribe
export async function POST(request: Request) {
  const body = await request.json().catch(() => null)

  if (!body || typeof body.email !== 'string' || !body.email.includes('@')) {
    return Response.json({ error: 'E-mail invalide' }, { status: 400 })
  }

  // … enregistrer l'e-mail (base de données, service de newsletter…)
  return Response.json({ ok: true }, { status: 201 })
}
```

**Route dynamique typée :**

```ts
// app/api/posts/[id]/route.ts   →   GET /api/posts/3
import type { NextRequest } from 'next/server'

export async function GET(
  _req: NextRequest,
  ctx: RouteContext<'/api/posts/[id]'>
) {
  const { id } = await ctx.params
  return Response.json({ id })
}
```

**Tester :**

```bash
curl http://localhost:3000/api/health
curl "http://localhost:3000/api/posts?limit=3"
curl -X POST http://localhost:3000/api/subscribe \
  -H "Content-Type: application/json" \
  -d '{"email":"awa@example.com"}'
```

### 9.2 Les règles à connaître

- Un **même segment** ne peut pas contenir à la fois un `route.ts` et un `page.tsx`. L'emplacement habituel des API est `app/api/…`.
- Un Route Handler n'a **ni layout**, ni navigation côté client : c'est le niveau de routage le plus bas.
- Une méthode HTTP non exportée renvoie automatiquement une réponse **405**.
- **Avec Cache Components**, un `GET` suit le même modèle que les pages : il est **prérendu au build** s'il n'accède à rien de dynamique (comme `/api/health`), et s'exécute **à la requête** dès qu'il lit la requête (`request.url`, en-têtes, cookies), une base non cachée ou `Math.random()`. Pour mettre une donnée en cache, place `'use cache'` dans une **fonction d'aide** appelée par le handler (comme `getPosts()`), pas directement dans son corps.
- Les autres méthodes (`POST`, `PUT`…) ne sont **jamais** mises en cache.

### 9.3 Server Actions : un aperçu

Une **Server Action** est une fonction asynchrone qui s'exécute **sur le serveur** et qu'on appelle directement depuis un formulaire ou un composant, sans écrire d'endpoint.

```ts
// app/contact/actions.ts
'use server'

export async function sendMessage(formData: FormData) {
  const email = formData.get('email')
  const message = formData.get('message')

  // validation et enregistrement (base de données, e-mail…) : palier 2
  console.log('Nouveau message', { email, message })
}
```

```tsx
// app/contact/page.tsx
import { sendMessage } from './actions'

export default function ContactPage() {
  return (
    <form action={sendMessage}>
      <input name="email" type="email" required />
      <textarea name="message" required />
      <button type="submit">Envoyer</button>
    </form>
  )
}
```

Le formulaire fonctionne même **sans JavaScript** dans le navigateur (amélioration progressive).

| | **Route Handler** | **Server Action** |
|---|---|---|
| Usage typique | API consommée par un **tiers** : application mobile, webhook, service externe | **Mutation** déclenchée par ton **interface** : formulaire, bouton |
| Appel | Requête HTTP (`fetch`, `curl`…) | Fonction appelée depuis un formulaire ou un composant |
| Réponse | `Response` (JSON, texte, flux…) | Valeur sérialisable, redirection, revalidation |
| Contrat public | ✅ URL stable, méthodes HTTP | ❌ Détail d'implémentation de ton application |

**Règle pratique** : pour ton interface, une Server Action ; pour un consommateur externe, un Route Handler.

> ⚠️ **Piège** : une Server Action reste joignable par une requête HTTP. Comme pour un Route Handler, **valide toujours les entrées et vérifie les droits** (palier 2).

## 10. Styles, polices, images et métadonnées

> 🎯 **Objectifs** : styliser avec Tailwind ou les CSS Modules · charger des polices et des images de façon optimisée · soigner le SEO avec l'API de métadonnées.

### 10.1 Tailwind CSS (par défaut)

Le template installe **Tailwind CSS** : on écrit des classes utilitaires directement dans le JSX.

```tsx
export default function Card({ children }: { children: React.ReactNode }) {
  return <div className="rounded-lg border p-4 shadow-sm">{children}</div>
}
```

Tailwind est branché dans `app/globals.css` (qui commence par `@import 'tailwindcss';`) ; ce fichier est importé **une fois**, dans le layout racine. Pour personnaliser le thème, suis la documentation de Tailwind.

### 10.2 CSS Modules

Un fichier `*.module.css` produit des noms de classes **locaux** au composant : pas de collision possible.

```css
/* app/ui/card.module.css */
.card {
  border: 1px solid #ddd;
  border-radius: 8px;
  padding: 1rem;
}
```

```tsx
// app/ui/card.tsx
import styles from './card.module.css'

export default function Card({ children }: { children: React.ReactNode }) {
  return <div className={styles.card}>{children}</div>
}
```

> 💡 Choisis **un** style principal (Tailwind *ou* CSS Modules) et tiens-t'y : mélanger sans règle rend le code difficile à maintenir.

### 10.3 Les polices avec `next/font`

```tsx
// app/layout.tsx
import { Inter } from 'next/font/google'

const inter = Inter({ subsets: ['latin'], display: 'swap' })

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="fr" className={inter.className}>
      <body>{children}</body>
    </html>
  )
}
```

Les fichiers de police sont téléchargés **au build** et servis depuis **ton domaine** : aucune requête vers Google depuis le navigateur de tes visiteurs, et pas de saut de mise en page. Pour une police locale :

```tsx
import localFont from 'next/font/local'

const brand = localFont({ src: './fonts/brand.woff2' })
```

> 💡 Avec Tailwind, utilise l'option `variable` (par exemple `variable: '--font-inter'`) pour exposer la police comme variable CSS.

### 10.4 Les images avec `next/image`

Le composant `<Image>` étend `<img>` : images redimensionnées à la demande, formats modernes, chargement différé, aucun décalage de mise en page.

```tsx
import Image from 'next/image'
import hero from './hero.jpg' // import statique : largeur et hauteur déduites

export default function Hero() {
  return <Image src={hero} alt="Plage au coucher du soleil" priority />
}
```

Pour une image **distante**, donne `width` et `height` à la main (Next.js ne peut pas les deviner) et **autorise l'hôte** dans la configuration :

```tsx
<Image
  src="https://images.example.com/photos/paysage.jpg"
  alt="Paysage de montagne"
  width={800}
  height={600}
/>
```

```ts
// next.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  images: {
    remotePatterns: [
      { protocol: 'https', hostname: 'images.example.com', pathname: '/photos/**' },
    ],
  },
}

export default nextConfig
```

Pour une image qui remplit son conteneur, utilise `fill` et `sizes` :

```tsx
<div className="relative h-64 w-full">
  <Image
    src={hero}
    alt="Plage au coucher du soleil"
    fill
    sizes="(max-width: 768px) 100vw, 768px"
    className="object-cover"
  />
</div>
```

- **`alt` est obligatoire** (accessibilité, et texte de repli).
- **`priority`** sert pour l'image principale visible dès l'arrivée (celle qui détermine le *LCP*) ; les autres sont chargées au défilement.
- **`remotePatterns`** est aussi une **mesure de sécurité** : seuls les hôtes listés peuvent être optimisés.

### 10.5 Les métadonnées et le SEO

Next.js génère les balises `<head>` à partir d'un objet `metadata` exporté par un `layout.tsx` ou un `page.tsx` (Server Components uniquement).

```tsx
// app/layout.tsx
import type { Metadata } from 'next'

export const metadata: Metadata = {
  title: { default: 'Mini-blog', template: '%s | Mini-blog' },
  description: 'Un blog pour apprendre Next.js',
  openGraph: {
    title: 'Mini-blog',
    description: 'Un blog pour apprendre Next.js',
    type: 'website',
  },
}
```

Avec `title.template`, une page qui exporte `title: 'Blog'` devient « Blog | Mini-blog ». Pour des métadonnées qui **dépendent des données**, exporte `generateMetadata` :

```tsx
// app/blog/[id]/page.tsx (extrait)
import type { Metadata } from 'next'

export async function generateMetadata({
  params,
}: PageProps<'/blog/[id]'>): Promise<Metadata> {
  const { id } = await params
  const post = await getPost(id) // voir module 6
  return { title: post?.title ?? 'Article introuvable' }
}
```

> ⚠️ **Avec Cache Components**, les données utilisées par `generateMetadata` suivent les mêmes règles que celles de la page : mets-les en cache (comme `getPost`). Une page entièrement statique ne peut pas avoir de métadonnées qui dépendent de données non cachées ou de la requête.

Des **fichiers spéciaux** placés dans `app/` complètent le tableau : `favicon.ico`, `icon.png`, `apple-icon.png`, `opengraph-image.png` (ou `.tsx` pour une image générée par code), `robots.ts` et `sitemap.ts` :

```ts
// app/sitemap.ts
import type { MetadataRoute } from 'next'

export default function sitemap(): MetadataRoute.Sitemap {
  return [
    { url: 'https://mon-site.com', lastModified: '2026-10-01' },
    { url: 'https://mon-site.com/blog', lastModified: '2026-10-01' },
  ]
}
```

> 💡 Certains robots d'indexation ne gèrent pas le streaming des métadonnées. Next.js les reconnaît à leur *user agent* et leur sert une page rendue à la volée, métadonnées incluses dans le `<head>`. Veille donc à ce que les sources de données utilisées au prérendu restent **joignables à l'exécution**.

### 11.2 Les variables d'environnement

Next.js charge automatiquement les fichiers `.env*` à la racine du projet. Par ordre de **priorité décroissante** :

1. `process.env` (variables déjà définies dans le système ou la plateforme)
2. `.env.development.local` / `.env.production.local`
3. `.env.local` (non lu en mode test)
4. `.env.development` / `.env.production`
5. `.env`

```bash
# .env.local  (ne jamais le versionner)
API_SECRET=abc123
NEXT_PUBLIC_SITE_URL=https://mon-site.com
```

```ts
const secret = process.env.API_SECRET            // serveur uniquement
const siteUrl = process.env.NEXT_PUBLIC_SITE_URL // aussi disponible dans le navigateur
```

Les quatre règles :

1. **Sans préfixe**, une variable n'existe que **côté serveur** (côté navigateur, elle est vide).
2. **Avec `NEXT_PUBLIC_`**, la valeur est **injectée dans le JavaScript au build** : elle est publique, et **figée au moment du build**. La modifier après coup n'a aucun effet côté client tant que tu ne reconstruis pas.
3. Pour une valeur `NEXT_PUBLIC_*` destinée au navigateur, écris le nom complet : un accès dynamique comme `process.env[nom]` n'est pas injecté.
4. **Ne versionne jamais** `.env.local`. Commite plutôt un fichier `.env.example` listant les noms (sans valeurs).

Pour échouer **tôt et clairement** quand une variable manque :

```ts
// lib/env.ts
import 'server-only'

function required(name: string): string {
  const value = process.env[name]
  if (!value) throw new Error(`Variable d'environnement manquante : ${name}`)
  return value
}

export const env = {
  apiSecret: required('API_SECRET'),
}
```

```ts
// lib/posts.ts
import { cacheLife } from 'next/cache'

const API = 'https://jsonplaceholder.typicode.com'

export type Post = { id: number; userId: number; title: string; body: string }
export type PostComment = {
  id: number
  postId: number
  name: string
  email: string
  body: string
}

// Liste partagée par tous les visiteurs → mise en cache
export async function getPosts(): Promise<Post[]> {
  'use cache'
  cacheLife('hours')

  const res = await fetch(`${API}/posts`)
  if (!res.ok) throw new Error(`Échec du chargement des articles (${res.status})`)
  return res.json()
}

// Un article → mis en cache (l'id fait partie de la clé de cache)
export async function getPost(id: string): Promise<Post | null> {
  'use cache'
  cacheLife('hours')

  const res = await fetch(`${API}/posts/${id}`)
  if (res.status === 404) return null
  if (!res.ok) throw new Error(`Échec du chargement de l'article ${id} (${res.status})`)
  return res.json()
}

// Commentaires : volontairement SANS cache → ils seront streamés sous <Suspense>
export async function getComments(postId: string): Promise<PostComment[]> {
  const res = await fetch(`${API}/posts/${postId}/comments`)
  if (!res.ok) throw new Error('Échec du chargement des commentaires')
  return res.json()
}
```

<details>
<summary>Réponses</summary>

1. Un fichier **`page.tsx`** (ou `route.ts`). Un dossier qui ne contient qu'un `layout.tsx` n'est pas accessible (404) : le layout se contente d'envelopper ses segments enfants.
2. Les balises **`<html>`** et **`<body>`**. Le layout racine est obligatoire.
3. Parce que `params` est une **`Promise`** (ses valeurs ne sont connues qu'à la requête, sauf si `generateStaticParams` les fournit). Dans un Client Component : `use(params)` ou le hook `useParams()`.
4. *Client* : `useState`/gestionnaires d'événements ; API du navigateur (`localStorage`, `window`). *Serveur* : accès à une base de données ou à des secrets ; réduction du JavaScript envoyé au navigateur.
5. Uniquement dans le fichier du **bouton** (la feuille interactive). La page reste un Server Component : moins de JavaScript, et les données restent côté serveur.
6. Un problème **`blocking-route`** : la page attend des données non cachées et ne peut pas produire de shell statique. Solutions : **`'use cache'` + `cacheLife`** (donnée partagée) ou **`<Suspense>` avec un fallback** (donnée fraîche, streamée).
7. (a) **en cache** ; (b) **dynamique** ; (c) **instable** (`connection()` + `<Suspense>`, ou `'use cache'`) ; (d) **prévisible**.
8. `error.tsx` : erreurs **inattendues** d'un segment (Client Component, bouton `retry`). `not-found.tsx` : ressource introuvable, après `notFound()` ou pour une URL inconnue (404). `global-error.tsx` : erreurs du **layout racine** ; il le remplace et doit définir `<html>` et `<body>`.
9. Pour une **API consommée par un tiers** (application mobile, webhook, service externe) qui a besoin d'une URL et d'un contrat HTTP stables. Pour une mutation déclenchée par ton interface, une Server Action suffit.
10. Celle préfixée par **`NEXT_PUBLIC_`**. Sa valeur est **figée au build**.
11. Pour une route dynamique, l'URL exacte n'est **pas connue au prérendu** : `usePathname()` lit une donnée de requête. Sans `<Suspense>`, la route ne peut pas produire son shell statique.
12. `○` : **Static** (prérendue). `◐` : **Partial Prerender** (shell statique + parties streamées). `ƒ` : **Dynamic** (rendue à la demande).

</details>

**Barème.** 10 à 12 bonnes réponses : tu es prêt pour le palier 2. 7 à 9 : relis les modules correspondants. Moins de 7 : refais les ateliers 5 à 7 avant de continuer.

### 15.2 Les dix règles d'or du palier 1

1. Le **dossier** définit l'URL ; **`page.tsx`** la rend publique.
2. Les composants sont **serveur par défaut** ; `'use client'` seulement sur les **feuilles** interactives.
3. `params`, `searchParams`, `cookies()` et `headers()` sont **asynchrones**.
4. Tout accès à des données **non cachées** ou **propres à la requête** va sous `<Suspense>` (ou un `loading.tsx`).
5. Une donnée **partagée** se met en cache : `'use cache'` + `cacheLife`.
6. `Math.random()` et `Date.now()` : `connection()` ou `'use cache'`.
7. Un **secret** ne va jamais dans un Client Component ; `NEXT_PUBLIC_` signifie **public**.
8. `<Link>` pour naviguer en interne ; `next/navigation` pour les hooks de navigation.
9. Prévois `loading.tsx`, `error.tsx` et `not-found.tsx` pour chaque section importante.
10. **Teste le build de production** (`npm run build` + `npm run start`) avant de déployer.

## Annexe A. Glossaire

| Terme | Définition |
|---|---|
| **App Shell** | Version réutilisable, indépendante de l'URL, du shell statique d'une route dynamique dont les `params` ne sont pas connus au build |
| **Bundle** | Fichiers JavaScript/CSS envoyés au navigateur |
| **Client Component** | Composant hydraté et interactif dans le navigateur (`'use client'`) |
| **Donnée de requête** (*runtime data*) | Donnée qui n'existe qu'à la requête : `cookies()`, `headers()`, `searchParams`, `params` inconnus au build |
| **Fallback** | Interface affichée par `<Suspense>` en attendant le contenu |
| **Hydratation** | Attachement des événements React au HTML reçu |
| **PPR** (Partial Prerendering) | Shell statique prérendu + parties dynamiques streamées dans la même réponse |
| **Préchargement** (*prefetch*) | Chargement anticipé d'une route avant le clic |
| **Prérendu** | Génération du HTML à l'avance (build ou revalidation) |
| **RSC payload** | Description compacte de l'arbre rendu côté serveur, utilisée par React dans le navigateur |
| **Route Handler** | Fichier `route.ts` qui répond à des requêtes HTTP |
| **Segment** | Un morceau d'URL, correspondant à un dossier de `app/` |
| **Server Action** | Fonction exécutée sur le serveur, appelée depuis l'interface |
| **Server Component** | Composant exécuté uniquement sur le serveur (par défaut dans l'App Router) |
| **Shell statique** | Partie d'une page prérendue à l'avance et servable depuis un CDN |
| **Streaming** | Envoi progressif de la page, morceau par morceau |
| **Suspense** | Composant React qui affiche un fallback pendant qu'un contenu se charge |
| **Turbopack** | Bundler de Next.js, par défaut en développement et en production depuis la 16 |

## Annexe B. Pièges des anciens tutoriels

| `next lint` | `eslint` (ou Biome) lancé via un script npm |
| `images.domains` | `images.remotePatterns` |
| `reset()` dans `error.tsx` | `retry()` (stable depuis 16.3) |
