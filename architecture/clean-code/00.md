# Clean Code — Plan d'apprentissage complet

> "Any fool can write code that a computer can understand. Good programmers write code that humans can understand." — Martin Fowler

Ce plan couvre l'intégralité du Clean Code, inspiré principalement de **Robert C. Martin** (*Clean Code*, 2008) et des meilleures pratiques de l'industrie. Chaque chapitre correspond à un fichier dédié.

---

## 01 — Nommage (Meaningful Names)

- Pourquoi le nommage est la compétence n°1
- Règles d'or du nommage : intention, clarté, cohérence
- Nommer les variables, constantes, booléens
- Nommer les méthodes et fonctions (verbes d'action)
- Nommer les classes et interfaces (noms, pas de suffixes inutiles)
- Nommer les packages et modules
- Conventions par langage (Java, JS, Python)
- Longueur du nom vs portée de la variable
- Éviter les abréviations, encodages, préfixes inutiles
- Renommage et refactoring : quand et comment
- Exemples ❌/✅ complets

## 02 — Fonctions (Functions)

- Règle n°1 : une fonction fait UNE seule chose
- Taille idéale d'une fonction (5-20 lignes)
- Niveaux d'abstraction cohérents (Step-down Rule)
- Nombre d'arguments (0 idéal, 3 max)
- Éviter les flag arguments (booléens en paramètre)
- Éviter les effets de bord (side effects)
- Command-Query Separation (CQS)
- Early return et Guard Clauses
- DRY appliqué aux fonctions
- Fonctions et exceptions vs codes d'erreur
- Exemples ❌/✅ complets

## 03 — Commentaires (Comments)

- Pourquoi les commentaires sont souvent un signe d'échec
- Les bons commentaires : quand commenter est légitime
  - Commentaires légaux (licence)
  - Commentaires d'intention (le "pourquoi")
  - Clarification de code complexe inévitable
  - TODO / FIXME avec discipline
  - Javadoc sur les API publiques
- Les mauvais commentaires : ce qu'il faut supprimer
  - Commentaires redondants
  - Commentaires trompeurs / obsolètes
  - Code commenté
  - Commentaires de fermeture (} // end if)
  - Journaux de modifications dans le fichier
- Le code auto-documenté comme alternative
- Exemples ❌/✅ complets

## 04 — Formatage (Formatting)

- Pourquoi le formatage compte (communication visuelle)
- Formatage vertical
  - Taille d'un fichier (200-500 lignes idéal)
  - Métaphore du journal : du général au détail
  - Espacement vertical (groupes logiques)
  - Ordre des méthodes (appelant avant appelé)
- Formatage horizontal
  - Longueur de ligne (80-120 caractères)
  - Indentation et alignement
  - Espaces autour des opérateurs
- Règles d'équipe et conventions partagées
- Outils de formatage automatique (Prettier, Checkstyle, Spotless)
- Exemples ❌/✅ complets

## 05 — Objets et structures de données (Objects & Data Structures)

- Abstraction de données vs exposition de données
- Objets vs structures de données (la dichotomie fondamentale)
- Loi de Déméter (Law of Demeter / "Don't talk to strangers")
- Train Wrecks (chaînes d'appels)
- Data Transfer Objects (DTO)
- Active Record vs Domain Object
- Encapsulation : quand et pourquoi
- Exemples ❌/✅ complets

## 06 — Gestion des erreurs (Error Handling)

- Exceptions vs codes de retour
- Utiliser des exceptions non vérifiées (unchecked)
- Fournir du contexte dans les exceptions
- Définir des exceptions métier
- Ne pas retourner null
- Ne pas passer null en argument
- Le pattern Try-Catch-Finally
- Wrapper les API tierces pour contrôler les exceptions
- Le pattern Special Case / Null Object
- Exemples ❌/✅ complets

## 07 — Tests (Unit Testing & TDD)

- Les 3 lois du TDD
- Anatomie d'un bon test (Arrange-Act-Assert / Given-When-Then)
- Un concept par test
- Tests lisibles : le test comme documentation
- F.I.R.S.T. : Fast, Independent, Repeatable, Self-validating, Timely
- Nommage des tests
- Test Doubles : Mocks, Stubs, Fakes, Spies
- Couverture de code : métrique utile mais pas suffisante
- Tests et refactoring : le filet de sécurité
- Anti-patterns de tests
- Exemples ❌/✅ complets

## 08 — Classes (Classes)

- Organisation d'une classe (variables, constructeur, méthodes publiques, privées)
- Taille d'une classe : Single Responsibility appliqué
- Cohésion : toutes les variables utilisées par toutes les méthodes
- Couplage faible entre classes
- Classes ouvertes à l'extension, fermées à la modification (OCP)
- Refactoring : extraire des classes à partir d'une God Class
- Classes et packages : organisation logique
- Exemples ❌/✅ complets

## 09 — Émergence et design simple (Simple Design)

- Les 4 règles du Simple Design (Kent Beck)
  1. Les tests passent tous
  2. Exprime l'intention du développeur
  3. Pas de duplication
  4. Minimise le nombre de classes et méthodes
- Émergence du design par le refactoring
- Refactoring continu vs Big Rewrite
- Quand s'arrêter de refactoriser
- Exemples ❌/✅ complets

## 10 — Concurrence (Concurrency)

- Pourquoi la concurrence est difficile
- Mythes et idées reçues
- Principes de base : SRP appliqué aux threads
- Connaître sa bibliothèque (java.util.concurrent, etc.)
- Modèles d'exécution : Producer-Consumer, Reader-Writer, Dining Philosophers
- Éviter les dépendances entre méthodes synchronisées
- Garder les sections synchronisées petites
- Tester le code concurrent (stress tests, outils d'analyse)
- Exemples ❌/✅ complets

## 11 — Smells et heuristiques (Code Smells)

- Smells dans les commentaires
- Smells dans l'environnement (build, tests)
- Smells dans les fonctions (trop d'arguments, flag arguments, code mort)
- Smells dans les noms (noms non descriptifs, encodages)
- Smells généraux
  - Code dupliqué
  - Code mort
  - Rigidité, fragilité, immobilité
  - Couplage artificiel
  - Feature Envy
  - Primitive Obsession
  - Long Method / God Class
- Catalogue complet des smells avec remèdes
- Exemples ❌/✅ complets

## 12 — Refactoring (Techniques de refactoring)

- Qu'est-ce que le refactoring (et ce que ce n'est pas)
- Quand refactoriser (règle du Boy Scout)
- Techniques fondamentales
  - Extract Method / Extract Class
  - Rename (variable, méthode, classe)
  - Inline (supprimer l'indirection inutile)
  - Move Method / Move Field
  - Replace Conditional with Polymorphism
  - Introduce Parameter Object
  - Replace Magic Number with Named Constant
- Refactoring et tests : toujours ensemble
- Refactoring progressif vs Big Bang
- Outils de refactoring dans l'IDE
- Exemples ❌/✅ complets

## 13 — Clean Code au quotidien (Pratiques d'équipe)

- La règle du Boy Scout : "Laisse le code plus propre que tu ne l'as trouvé"
- Code review orientée Clean Code
- Pair programming et mob programming
- Standards de code en équipe (linters, formatters, pre-commit hooks)
- Dette technique : identifier, mesurer, rembourser
- Clean Code et agilité
- Les limites du Clean Code : pragmatisme vs perfection
- Lectures recommandées et ressources
