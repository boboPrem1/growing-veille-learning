# Design Patterns — Plan d'apprentissage complet

> "Design patterns are recurring solutions to common problems in software design." — Gang of Four (GoF)

Ce plan couvre les **23 patterns du GoF** (*Design Patterns: Elements of Reusable Object-Oriented Software*, 1994) ainsi que des patterns modernes essentiels. Chaque pattern correspond à un fichier dédié.

---

## Prérequis

Avant d'aborder les design patterns, maîtriser :
- Programmation orientée objet (classes, héritage, interfaces, polymorphisme)
- Principes SOLID
- Notions de couplage et cohésion

---

# Partie 1 — Patterns de création (Creational)

Gèrent **comment les objets sont créés**, en découplant le code client de l'instanciation concrète.

## 01 — Singleton

- Problème : garantir qu'une classe n'a qu'une seule instance
- Implémentation classique (lazy, eager, thread-safe)
- Enum Singleton en Java (la meilleure approche)
- Cas d'utilisation : configuration, pool de connexions, logger
- Anti-pattern ? Pourquoi le Singleton est controversé
- Singleton et testabilité (injection de dépendances comme alternative)
- Exemples ❌/✅ complets

## 02 — Factory Method

- Problème : déléguer la création d'objets aux sous-classes
- Différence entre Simple Factory, Factory Method et Abstract Factory
- Le pattern dans la vraie vie (frameworks, bibliothèques)
- Quand l'utiliser vs un simple `new`
- Relation avec l'Open/Closed Principle
- Exemples ❌/✅ complets

## 03 — Abstract Factory

- Problème : créer des familles d'objets liés sans dépendre des classes concrètes
- Factory de factories : le concept
- Cas d'utilisation : thèmes UI, configurations multi-plateforme, drivers BDD
- Différence avec Factory Method
- Exemples ❌/✅ complets

## 04 — Builder

- Problème : construire des objets complexes étape par étape
- Builder classique (GoF) vs Builder fluent (Java moderne)
- Director : orchestrer la construction
- Quand utiliser Builder vs constructeur télescopique
- Builder et immutabilité
- Exemples ❌/✅ complets

## 05 — Prototype

- Problème : créer des objets en copiant un prototype existant
- Clone superficiel vs clone profond (shallow vs deep copy)
- Implémentation avec `Cloneable` en Java
- Registre de prototypes
- Cas d'utilisation : objets coûteux à créer, configurations par défaut
- Exemples ❌/✅ complets

# Partie 2 — Patterns structurels (Structural)

Gèrent **comment les objets sont composés** pour former des structures plus complexes.

## 06 — Adapter

- Problème : rendre compatibles deux interfaces incompatibles
- Adapter par classe (héritage) vs Adapter par objet (composition)
- Cas d'utilisation : intégration d'API tierces, migration de code legacy
- Adapter vs Facade vs Decorator
- Exemples ❌/✅ complets

## 07 — Bridge

- Problème : séparer l'abstraction de son implémentation
- Quand l'héritage seul ne suffit pas (explosion combinatoire)
- Composition comme alternative à l'héritage multiple
- Cas d'utilisation : drivers, renderers multi-plateforme
- Exemples ❌/✅ complets

## 08 — Composite

- Problème : traiter les objets individuels et les compositions d'objets de manière uniforme
- Structure arborescente (arbre de composants)
- Feuilles vs nœuds composites
- Cas d'utilisation : systèmes de fichiers, menus UI, expressions arithmétiques
- Exemples ❌/✅ complets

## 09 — Decorator

- Problème : ajouter des responsabilités à un objet dynamiquement, sans modifier sa classe
- Decorator vs héritage
- Chaîne de decorators (stacking)
- Cas d'utilisation : streams Java (BufferedInputStream, etc.), middleware
- Decorator vs Proxy vs Adapter
- Exemples ❌/✅ complets

## 10 — Facade

- Problème : fournir une interface simplifiée à un sous-système complexe
- Facade ne cache pas, elle simplifie
- Cas d'utilisation : bibliothèques complexes, APIs legacy, orchestration de services
- Facade vs Mediator
- Exemples ❌/✅ complets

## 11 — Flyweight

- Problème : partager efficacement des objets pour économiser la mémoire
- État intrinsèque (partagé) vs état extrinsèque (contextuel)
- Pool d'objets et cache
- Cas d'utilisation : caractères dans un éditeur de texte, particules dans un jeu, String pool Java
- Exemples ❌/✅ complets

## 12 — Proxy

- Problème : contrôler l'accès à un objet via un substitut
- Types de proxy : virtual, protection, remote, caching, logging
- Proxy vs Decorator (intention différente)
- Cas d'utilisation : lazy loading, contrôle d'accès, logging transparent
- Proxy dynamique en Java (`java.lang.reflect.Proxy`)
- Exemples ❌/✅ complets

# Partie 3 — Patterns comportementaux (Behavioral)

Gèrent **comment les objets communiquent** et se répartissent les responsabilités.

## 13 — Chain of Responsibility

- Problème : passer une requête le long d'une chaîne de handlers
- Chaque handler décide de traiter ou de passer au suivant
- Cas d'utilisation : middleware HTTP, pipeline de validation, logging multi-niveaux
- Chain of Responsibility vs Decorator
- Exemples ❌/✅ complets

## 14 — Command

- Problème : encapsuler une requête comme un objet
- Invoker, Command, Receiver : les rôles
- Undo/Redo avec l'historique de commandes
- Cas d'utilisation : boutons UI, transactions, file de tâches, macros
- Command vs Strategy
- Exemples ❌/✅ complets

## 15 — Iterator

- Problème : parcourir une collection sans exposer sa structure interne
- Iterator interne vs externe
- Iterable/Iterator en Java (`for-each`, `Stream`)
- Cas d'utilisation : collections custom, curseurs de base de données
- Exemples ❌/✅ complets

## 16 — Mediator

- Problème : réduire le couplage entre objets en centralisant la communication
- Mediator vs communication directe (n-to-n → n-to-1)
- Cas d'utilisation : chat room, contrôleur de formulaire, tour de contrôle aérien
- Mediator vs Facade (intention différente)
- Exemples ❌/✅ complets

## 17 — Memento

- Problème : sauvegarder et restaurer l'état d'un objet sans violer l'encapsulation
- Originator, Memento, Caretaker : les rôles
- Cas d'utilisation : undo/redo, sauvegardes de jeu, snapshots de transactions
- Memento et sérialisation
- Exemples ❌/✅ complets

## 18 — Observer

- Problème : notifier automatiquement des objets quand un autre change d'état
- Sujet (Observable) et Observateurs (Listeners)
- Push vs Pull model
- Cas d'utilisation : événements UI, système pub/sub, data binding
- Observer en Java (`PropertyChangeListener`, reactive streams)
- Exemples ❌/✅ complets

## 19 — State

- Problème : modifier le comportement d'un objet quand son état interne change
- State vs chaîne de if/else ou switch
- Machine à états finis
- Cas d'utilisation : lecteur audio (play/pause/stop), commande e-commerce, workflow
- State vs Strategy (même structure, intention différente)
- Exemples ❌/✅ complets

## 20 — Strategy

- Problème : définir une famille d'algorithmes interchangeables
- Encapsuler les variations derrière une interface
- Strategy vs héritage pour les variations de comportement
- Cas d'utilisation : tri, validation, calcul de prix, formatage
- Strategy avec lambdas en Java 8+
- Exemples ❌/✅ complets

## 21 — Template Method

- Problème : définir le squelette d'un algorithme, en laissant les sous-classes redéfinir certaines étapes
- Hook methods (étapes optionnelles)
- Template Method vs Strategy (héritage vs composition)
- Cas d'utilisation : frameworks (Spring, JUnit), ETL, génération de rapports
- Exemples ❌/✅ complets

## 22 — Visitor

- Problème : ajouter des opérations à des objets sans modifier leurs classes
- Double dispatch
- Cas d'utilisation : compilateurs (AST), export multi-format, calcul sur des structures complexes
- Visitor et l'Open/Closed Principle
- Limites : difficile si la hiérarchie change souvent
- Exemples ❌/✅ complets

## 23 — Interpreter

- Problème : interpréter un langage ou une grammaire
- Abstract Syntax Tree (AST)
- Cas d'utilisation : expressions régulières, DSL simples, requêtes de recherche
- Rarement utilisé directement, souvent remplacé par des parseurs
- Exemples ❌/✅ complets

# Partie 4 — Patterns modernes et complémentaires

Patterns qui ne font pas partie du GoF mais sont essentiels dans le développement moderne.

## 24 — Repository

- Problème : abstraire l'accès aux données derrière une collection-like interface
- Repository vs DAO (Data Access Object)
- Repository et Domain-Driven Design
- Cas d'utilisation : couche de persistance propre
- Exemples ❌/✅ complets

## 25 — Dependency Injection (DI)

- Problème : découpler la création des dépendances de leur utilisation
- Injection par constructeur, setter, interface
- Conteneurs DI (Spring, Guice, CDI)
- DI vs Service Locator
- Relation avec le Dependency Inversion Principle (SOLID)
- Exemples ❌/✅ complets

## 26 — MVC / MVP / MVVM

- Model-View-Controller : le pattern original
- Model-View-Presenter : évolution pour les tests
- Model-View-ViewModel : data binding
- Quand utiliser lequel
- Exemples ❌/✅ complets

## 27 — Event Sourcing & CQRS

- Event Sourcing : stocker les événements, pas l'état
- CQRS : séparer lecture et écriture
- Quand ces patterns sont justifiés (et quand ils ne le sont pas)
- Cas d'utilisation : audit, systèmes financiers, systèmes distribués
- Exemples ❌/✅ complets

## 28 — Architecture Hexagonale (Ports & Adapters)

- Problème : isoler le domaine métier de l'infrastructure technique
- Origine : Alistair Cockburn (2005)
- Le concept de Ports (interfaces du domaine) et Adapters (implémentations techniques)
- Les 3 couches : Domain, Application, Infrastructure
- Ports primaires (driving) vs Ports secondaires (driven)
- Adapters primaires (controllers, CLI, tests) vs Adapters secondaires (BDD, API externes, filesystem)
- Inversion de dépendance : l'infrastructure dépend du domaine, jamais l'inverse
- Organisation des packages / modules
- Cas d'utilisation : applications métier complexes, testabilité maximale
- Hexagonale vs architecture en couches classique (Layered)
- Relation avec DDD (Domain-Driven Design)
- Exemples ❌/✅ complets (structure de projet + code)

## 29 — Clean Architecture

- Problème : rendre le domaine métier indépendant des frameworks et de l'infrastructure
- Origine : Robert C. Martin (Uncle Bob, 2012)
- Les cercles concentriques : Entities → Use Cases → Interface Adapters → Frameworks & Drivers
- La règle de dépendance : les dépendances pointent vers l'intérieur
- Entities : règles métier universelles
- Use Cases : règles métier applicatives
- Interface Adapters : contrôleurs, presenters, gateways
- Frameworks & Drivers : la couche la plus externe
- Clean Architecture vs Hexagonale vs Onion Architecture (comparaison)
- Cas d'utilisation : applications enterprise, systèmes à longue durée de vie
- Exemples ❌/✅ complets (structure de projet + code)

## 30 — Patterns Microservices

- Problème : structurer et faire communiquer des services distribués
- API Gateway : point d'entrée unique
- Service Discovery : localiser dynamiquement les services
- Circuit Breaker : tolérance aux pannes (Resilience4j, Hystrix)
- Saga : transactions distribuées (orchestration vs chorégraphie)
- Strangler Fig : migration progressive d'un monolithe
- Sidecar / Service Mesh : communication inter-services
- Quand les microservices sont justifiés (et quand un monolithe suffit)
- Exemples ❌/✅ complets

## Ordre de lecture recommandé

| Phase | Patterns | Objectif |
|-------|----------|----------|
| **Essentiels** | Strategy, Observer, Factory Method, Singleton, Builder | Les 5 patterns les plus utilisés au quotidien |
| **Structurels clés** | Adapter, Decorator, Facade, Proxy | Composer et adapter des objets |
| **Comportementaux clés** | Template Method, Command, State, Iterator | Communication et algorithmes |
| **Création avancée** | Abstract Factory, Prototype | Patterns de création spécialisés |
| **Structurels avancés** | Composite, Bridge, Flyweight | Structures complexes |
| **Comportementaux avancés** | Chain of Responsibility, Mediator, Memento, Visitor, Interpreter | Patterns spécialisés |
| **Modernes** | Repository, DI, MVC/MVP/MVVM, Event Sourcing/CQRS | Patterns du développement actuel |
| **Architecturaux** | Hexagonale, Clean Architecture, Microservices | Architectures logicielles à grande échelle |
