# 28 — Architecture Hexagonale (Ports & Adapters)

## Définition

L'**architecture hexagonale**, aussi appelée **Ports & Adapters**, est un pattern architectural qui isole le cœur métier (domaine) de toute dépendance technique (base de données, frameworks, APIs externes, UI). Le domaine ne connaît que des **ports** (interfaces), et l'infrastructure fournit des **adapters** (implémentations concrètes).

> "Allow an application to equally be driven by users, programs, automated test or batch scripts, and to be developed and tested in isolation from its eventual run-time devices and databases." — Alistair Cockburn (2005)

Le nom "hexagonale" vient de la représentation graphique en hexagone, choisie pour montrer qu'il peut y avoir **autant de ports que nécessaire** sur les faces de l'hexagone (contrairement à l'architecture en couches qui suggère un empilement vertical).

---

## Origine et contexte

- **Auteur** : Alistair Cockburn, 2005
- **Problème initial** : les architectures classiques en couches (Layered Architecture) créent un couplage fort entre la logique métier et l'infrastructure technique
- **Constat** : quand la logique métier dépend de la base de données, du framework web ou d'une API externe, elle devient impossible à tester en isolation et difficile à faire évoluer
- **Inspiration** : le Dependency Inversion Principle (DIP) de SOLID, poussé au niveau architectural

### Le problème de l'architecture en couches classique

```
┌─────────────────────┐
│    Présentation     │  ← dépend de
├─────────────────────┤
│    Logique métier   │  ← dépend de
├─────────────────────┤
│    Accès données    │  ← dépend de
├─────────────────────┤
│    Base de données  │
└─────────────────────┘
```

Dans cette architecture, les dépendances vont **vers le bas** : la logique métier dépend de la couche d'accès aux données. Si on change de base de données, on impacte la logique métier. Si on veut tester le métier, il faut monter une base de données.

---

## Pourquoi c'est important ?

- **Testabilité** : le domaine se teste avec de simples tests unitaires, sans base de données, sans serveur HTTP, sans rien
- **Indépendance technique** : changer de base de données (PostgreSQL → MongoDB), de framework (Spring → Quarkus) ou d'API externe ne touche **jamais** le domaine
- **Focus métier** : le code le plus important (les règles métier) est isolé et protégé des détails techniques
- **Évolutivité** : ajouter un nouveau canal (API REST, GraphQL, CLI, événements) ne modifie pas le domaine
- **Longévité** : les technologies changent, le métier reste ; l'hexagonale protège ce qui a le plus de valeur

---

## Les concepts fondamentaux

### Le cœur : le domaine

Le **domaine** (ou **hexagone**) contient :
- Les **entités métier** (objets avec identité et règles métier)
- Les **value objects** (objets immuables sans identité)
- Les **règles métier** (invariants, validations, calculs)
- Les **ports** (interfaces que le domaine expose ou dont il a besoin)

Le domaine **ne connaît aucune technologie** : pas de Spring, pas de JPA, pas de Jackson, pas de HTTP. Il n'a aucune dépendance technique.

### Les ports

Un **port** est une **interface Java** définie dans le domaine. C'est un contrat qui dit ce que le domaine attend ou expose, sans dire comment.

Il existe 2 types de ports :

#### Ports primaires (driving / entrants)

Ce sont les **cas d'utilisation** du domaine — ce que le monde extérieur peut demander au domaine.

```java
// Primary port: what the application can do
public interface TaskManagementUseCase {
    Task createTask(String title, Priority priority);
    Task changeStatus(TaskId id, Status newStatus);
    List<Task> listTasksByProject(ProjectId projectId);
}
```

#### Ports secondaires (driven / sortants)

Ce sont les **dépendances** dont le domaine a besoin — ce que le domaine demande au monde extérieur, sans savoir comment c'est implémenté.

```java
// Secondary port: what the domain needs
public interface TaskRepository {
    Task save(Task task);
    Optional<Task> findById(TaskId id);
    List<Task> findByProject(ProjectId projectId);
    void delete(TaskId id);
}

// Another secondary port
public interface NotificationService {
    void notifyCreation(Task task);
}
```

### Les adapters

Un **adapter** est une **implémentation concrète** d'un port, qui fait le pont entre le domaine et une technologie spécifique.

#### Adapters primaires (driving / entrants)

Ils **appellent** le domaine. Ils traduisent une requête technique (HTTP, CLI, message) en appel de use case.

```java
// Primary adapter: translates HTTP → use case
@RestController
@RequestMapping("/api/tasks")
public class TaskRestAdapter {

    private final TaskManagementUseCase taskManagement;

    public TaskRestAdapter(TaskManagementUseCase taskManagement) {
        this.taskManagement = taskManagement;
    }

    @PostMapping
    public ResponseEntity<TaskResponseDto> create(@RequestBody TaskRequestDto dto) {
        Task task = taskManagement.createTask(dto.title(), dto.priority());
        return ResponseEntity.status(201).body(TaskResponseDto.from(task));
    }
}
```

#### Adapters secondaires (driven / sortants)

Ils **sont appelés** par le domaine (via le port). Ils traduisent une demande du domaine en opération technique.

```java
// Secondary adapter: implements the port with JPA
@Repository
public class TaskJpaAdapter implements TaskRepository {

    private final TaskJpaRepository jpaRepository;
    private final TaskEntityMapper mapper;

    public TaskJpaAdapter(TaskJpaRepository jpaRepository, TaskEntityMapper mapper) {
        this.jpaRepository = jpaRepository;
        this.mapper = mapper;
    }

    @Override
    public Task save(Task task) {
        TaskEntity entity = mapper.toEntity(task);
        TaskEntity saved = jpaRepository.save(entity);
        return mapper.toDomain(saved);
    }

    @Override
    public Optional<Task> findById(TaskId id) {
        return jpaRepository.findById(id.value()).map(mapper::toDomain);
    }

    // ...
}
```

### La règle fondamentale

**Les dépendances pointent toujours vers le domaine.**

- Les adapters primaires **dépendent** des ports primaires (use cases)
- Les adapters secondaires **implémentent** les ports secondaires (repositories, services externes)
- Le domaine ne dépend de **rien d'externe**

---

## Les 3 couches en détail

### Couche 1 — Domain (le cœur)

Contient :
- **Entités** : objets avec identité et cycle de vie (`Task`, `Project`, `User`)
- **Value Objects** : objets immuables définis par leurs attributs (`TaskId`, `Email`, `Priority`)
- **Ports primaires** : interfaces des use cases (`TaskManagementUseCase`)
- **Ports secondaires** : interfaces des dépendances (`TaskRepository`, `NotificationService`)
- **Exceptions métier** : erreurs du domaine (`TaskNotFoundException`, `InvalidStatusTransitionException`)

**Aucune annotation technique** : pas de `@Entity`, `@Component`, `@JsonProperty`, rien.

```java
// Domain entity — NO technical annotation
public class Task {

    private final TaskId id;
    private String title;
    private Status status;
    private Priority priority;
    private final LocalDateTime createdAt;

    public Task(TaskId id, String title, Priority priority) {
        if (title == null || title.isBlank()) {
            throw new IllegalArgumentException("Title cannot be empty");
        }
        this.id = id;
        this.title = title;
        this.priority = priority;
        this.status = Status.TODO;
        this.createdAt = LocalDateTime.now();
    }

    public void changeStatus(Status newStatus) {
        if (!this.status.canTransitionTo(newStatus)) {
            throw new InvalidStatusTransitionException(this.status, newStatus);
        }
        this.status = newStatus;
    }

    public boolean isOverdue(LocalDate today) {
        // pure business rule
        return this.status != Status.DONE
            && this.createdAt.toLocalDate().plusDays(30).isBefore(today);
    }

    // getters (no public setters — state changes through business methods)
    public TaskId getId() { return id; }
    public String getTitle() { return title; }
    public Status getStatus() { return status; }
    public Priority getPriority() { return priority; }
    public LocalDateTime getCreatedAt() { return createdAt; }
}
```

```java
// Value Object — immutable, identified by its value
public record TaskId(UUID value) {
    public TaskId {
        Objects.requireNonNull(value, "ID cannot be null");
    }

    public static TaskId generate() {
        return new TaskId(UUID.randomUUID());
    }
}
```

```java
// Business enum with transition rules
public enum Status {
    TODO, IN_PROGRESS, IN_REVIEW, DONE, CANCELLED;

    public boolean canTransitionTo(Status target) {
        return switch (this) {
            case TODO -> target == IN_PROGRESS || target == CANCELLED;
            case IN_PROGRESS -> target == IN_REVIEW || target == TODO || target == CANCELLED;
            case IN_REVIEW -> target == DONE || target == IN_PROGRESS;
            case DONE, CANCELLED -> false;
        };
    }
}
```

### Couche 2 — Application (orchestration)

Contient l'**implémentation des use cases** (ports primaires). Cette couche orchestre les appels entre le domaine et les ports secondaires. Elle ne contient **aucune règle métier** — celles-ci sont dans les entités.

```java
// Use case implementation — orchestrates without containing business logic
public class TaskManagementService implements TaskManagementUseCase {

    private final TaskRepository taskRepository;
    private final NotificationService notificationService;

    public TaskManagementService(TaskRepository taskRepository,
                                  NotificationService notificationService) {
        this.taskRepository = taskRepository;
        this.notificationService = notificationService;
    }

    @Override
    public Task createTask(String title, Priority priority) {
        TaskId id = TaskId.generate();
        Task task = new Task(id, title, priority);  // validation is in the entity
        Task saved = taskRepository.save(task);
        notificationService.notifyCreation(saved);
        return saved;
    }

    @Override
    public Task changeStatus(TaskId id, Status newStatus) {
        Task task = taskRepository.findById(id)
            .orElseThrow(() -> new TaskNotFoundException(id));

        task.changeStatus(newStatus);  // transition rule is in the entity

        return taskRepository.save(task);
    }

    @Override
    public List<Task> listTasksByProject(ProjectId projectId) {
        return taskRepository.findByProject(projectId);
    }
}
```

### Couche 3 — Infrastructure (adapters)

Contient **toutes les dépendances techniques** : frameworks, bases de données, APIs externes, configuration.

```java
// --- Secondary adapter: JPA persistence ---

@Entity
@Table(name = "tasks")
public class TaskEntity {
    @Id
    private UUID id;
    private String title;
    @Enumerated(EnumType.STRING)
    private String status;
    @Enumerated(EnumType.STRING)
    private String priority;
    private LocalDateTime createdAt;

    // empty constructor for JPA, getters, setters
}

public interface TaskJpaRepository extends JpaRepository<TaskEntity, UUID> {
    List<TaskEntity> findByProjectId(UUID projectId);
}

@Repository
public class TaskJpaAdapter implements TaskRepository {

    private final TaskJpaRepository jpaRepository;

    public TaskJpaAdapter(TaskJpaRepository jpaRepository) {
        this.jpaRepository = jpaRepository;
    }

    @Override
    public Task save(Task task) {
        TaskEntity entity = toEntity(task);
        TaskEntity saved = jpaRepository.save(entity);
        return toDomain(saved);
    }

    @Override
    public Optional<Task> findById(TaskId id) {
        return jpaRepository.findById(id.value()).map(this::toDomain);
    }

    @Override
    public List<Task> findByProject(ProjectId projectId) {
        return jpaRepository.findByProjectId(projectId.value())
            .stream()
            .map(this::toDomain)
            .toList();
    }

    @Override
    public void delete(TaskId id) {
        jpaRepository.deleteById(id.value());
    }

    // --- Mapping Entity ↔ Domain ---

    private TaskEntity toEntity(Task task) {
        TaskEntity entity = new TaskEntity();
        entity.setId(task.getId().value());
        entity.setTitle(task.getTitle());
        entity.setStatus(task.getStatus().name());
        entity.setPriority(task.getPriority().name());
        entity.setCreatedAt(task.getCreatedAt());
        return entity;
    }

    private Task toDomain(TaskEntity entity) {
        return new Task(
            new TaskId(entity.getId()),
            entity.getTitle(),
            Priority.valueOf(entity.getPriority())
            // full state reconstruction
        );
    }
}
```

// --- Primary adapter: REST Controller ---

@RestController
@RequestMapping("/api/tasks")
public class TaskRestAdapter {

    private final TaskManagementUseCase taskManagement;

    public TaskRestAdapter(TaskManagementUseCase taskManagement) {
        this.taskManagement = taskManagement;
    }

    @PostMapping
    public ResponseEntity<TaskResponseDto> create(@Valid @RequestBody TaskRequestDto dto) {
        Task task = taskManagement.createTask(dto.title(), dto.priority());
        return ResponseEntity.status(201).body(TaskResponseDto.from(task));
    }

    @PatchMapping("/{id}/status")
    public ResponseEntity<TaskResponseDto> changeStatus(
            @PathVariable UUID id,
            @RequestBody ChangeStatusDto dto) {
        Task task = taskManagement.changeStatus(new TaskId(id), dto.status());
        return ResponseEntity.ok(TaskResponseDto.from(task));
    }

    @GetMapping("/project/{projectId}")
    public ResponseEntity<List<TaskResponseDto>> listByProject(@PathVariable UUID projectId) {
        List<Task> tasks = taskManagement.listTasksByProject(new ProjectId(projectId));
        List<TaskResponseDto> dtos = tasks.stream()
            .map(TaskResponseDto::from)
            .toList();
        return ResponseEntity.ok(dtos);
    }
}

### Le câblage des beans

Le domaine ne connaît pas Spring, donc les use cases ne sont pas annotés `@Service`. Le câblage se fait dans la couche infrastructure :

```java
@Configuration
public class BeanConfig {

    @Bean
    public TaskManagementUseCase taskManagementUseCase(
            TaskRepository taskRepository,
            NotificationService notificationService) {
        return new TaskManagementService(taskRepository, notificationService);
    }

    @Bean
    public ProjectManagementUseCase projectManagementUseCase(
            ProjectRepository projectRepository) {
        return new ProjectManagementService(projectRepository);
    }
}
```

## Inversion de dépendance : le mécanisme clé

### ❌ Architecture en couches : le domaine dépend de l'infrastructure

```
Controller  →  Service  →  JpaRepository
                  ↓
              dépend de JPA, Spring Data, PostgreSQL
```

Le service connaît JPA directement. Si on change de base de données, on modifie le service.

### ✅ Architecture hexagonale : l'infrastructure dépend du domaine

```
Controller  →  UseCase (interface)  ←  Service (implémente)
                                          ↓
                                    Repository (interface du domaine)
                                          ↑
                                    JpaAdapter (implémente, dans infrastructure)
```

Le service ne connaît qu'une **interface** (`TaskRepository`). L'implémentation JPA est dans l'infrastructure et **implémente** l'interface du domaine. Le sens des dépendances est **inversé**.

```java
// DOMAIN — defines the contract
public interface TaskRepository {
    Task save(Task task);
    Optional<Task> findById(TaskId id);
}

// INFRASTRUCTURE — implements the contract with a technology
@Repository
public class TaskJpaAdapter implements TaskRepository {
    // uses Spring Data JPA internally
    // but exposes the domain interface
}
```

### Dépendances Maven/Gradle

Pour enforcer l'isolation, on peut utiliser des modules Maven séparés :

```xml
<!-- domain/pom.xml — NO technical dependency -->
<dependencies>
    <!-- Nothing, or just pure Java utilities -->
</dependencies>

<!-- application/pom.xml — depends only on domain -->
<dependencies>
    <dependency>
        <groupId>com.taskflow</groupId>
        <artifactId>domain</artifactId>
    </dependency>
</dependencies>

<!-- infrastructure/pom.xml — depends on domain + application + frameworks -->
<dependencies>
    <dependency>
        <groupId>com.taskflow</groupId>
        <artifactId>domain</artifactId>
    </dependency>
    <dependency>
        <groupId>com.taskflow</groupId>
        <artifactId>application</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-data-jpa</artifactId>
    </dependency>
</dependencies>
```

## La testabilité : le bénéfice majeur

### Tester le domaine sans AUCUNE infrastructure

```java
class TaskTest {

    @Test
    void should_create_a_task_with_todo_status() {
        Task task = new Task(TaskId.generate(), "Deploy to production", Priority.HIGH);

        assertEquals(Status.TODO, task.getStatus());
        assertEquals("Deploy to production", task.getTitle());
    }

    @Test
    void should_reject_an_empty_title() {
        assertThrows(IllegalArgumentException.class, () ->
            new Task(TaskId.generate(), "", Priority.HIGH)
        );
    }

    @Test
    void should_allow_transition_from_todo_to_in_progress() {
        Task task = new Task(TaskId.generate(), "Task", Priority.MEDIUM);

        task.changeStatus(Status.IN_PROGRESS);

        assertEquals(Status.IN_PROGRESS, task.getStatus());
    }

    @Test
    void should_reject_transition_from_done_to_in_progress() {
        Task task = new Task(TaskId.generate(), "Task", Priority.LOW);
        task.changeStatus(Status.IN_PROGRESS);
        task.changeStatus(Status.IN_REVIEW);
        task.changeStatus(Status.DONE);

        assertThrows(InvalidStatusTransitionException.class, () ->
            task.changeStatus(Status.IN_PROGRESS)
        );
    }
}
```

Aucun mock, aucun framework, aucune base de données. Du Java pur. **C'est ça la puissance de l'hexagonale.**

### Tester les use cases avec des mocks simples

```java
class TaskManagementServiceTest {

    private TaskRepository taskRepository;
    private NotificationService notificationService;
    private TaskManagementService service;

    @BeforeEach
    void setUp() {
        taskRepository = mock(TaskRepository.class);
        notificationService = mock(NotificationService.class);
        service = new TaskManagementService(taskRepository, notificationService);
    }

    @Test
    void should_create_and_save_a_task() {
        when(taskRepository.save(any(Task.class)))
            .thenAnswer(invocation -> invocation.getArgument(0));

        Task result = service.createTask("My task", Priority.HIGH);

        assertEquals("My task", result.getTitle());
        verify(taskRepository).save(any(Task.class));
        verify(notificationService).notifyCreation(any(Task.class));
    }

    @Test
    void should_throw_exception_if_task_not_found() {
        TaskId id = TaskId.generate();
        when(taskRepository.findById(id)).thenReturn(Optional.empty());

        assertThrows(TaskNotFoundException.class, () ->
            service.changeStatus(id, Status.IN_PROGRESS)
        );
    }
}
```

### Tester avec un adapter in-memory (pas de mock)

Alternative aux mocks : un adapter in-memory pour les tests d'intégration du domaine.

```java
// Test adapter — in-memory storage
public class TaskInMemoryAdapter implements TaskRepository {

    private final Map<TaskId, Task> store = new HashMap<>();

    @Override
    public Task save(Task task) {
        store.put(task.getId(), task);
        return task;
    }

    @Override
    public Optional<Task> findById(TaskId id) {
        return Optional.ofNullable(store.get(id));
    }

    @Override
    public List<Task> findByProject(ProjectId projectId) {
        return store.values().stream()
            .filter(t -> t.getProjectId().equals(projectId))
            .toList();
    }

    @Override
    public void delete(TaskId id) {
        store.remove(id);
    }
}
```

## Hexagonale vs architecture en couches classique (Layered)

| Critère | Architecture en couches | Architecture hexagonale |
|---|---|---|
| **Direction des dépendances** | Haut → bas (présentation → données) | Extérieur → intérieur (infra → domaine) |
| **Domaine** | Dépend de la couche données | Ne dépend de rien |
| **Changement de BDD** | Impacte le service | N'impacte que l'adapter |
| **Testabilité du domaine** | Nécessite des mocks lourds / BDD | Tests unitaires purs |
| **Ajout d'un canal** (CLI, GraphQL) | Modifie potentiellement le service | Ajoute un adapter, c'est tout |
| **Complexité initiale** | Faible | Moyenne (plus de fichiers et d'interfaces) |
| **Applications simples (CRUD)** | Suffisante | Over-engineering |
| **Applications métier complexes** | Devient ingérable | Brille |

### Quand utiliser l'architecture hexagonale

**✅ Utiliser quand :**
- Le domaine métier est **complexe** (règles métier riches, workflows)
- L'application a une **longue durée de vie** (5+ ans)
- Plusieurs **canaux d'entrée** (REST, GraphQL, CLI, événements, batch)
- La **technologie peut changer** (migration BDD, changement de framework)
- La **testabilité du domaine** est critique
- L'équipe est **suffisamment expérimentée**

**❌ Éviter quand :**
- L'application est un **simple CRUD** sans logique métier
- C'est un **prototype** ou un **POC**
- L'équipe est **petite et junior** (overhead d'apprentissage)
- Le projet a une **durée de vie courte**

## Relation avec DDD (Domain-Driven Design)

L'architecture hexagonale et DDD sont **complémentaires** :

| Concept DDD | Correspondance hexagonale |
|---|---|
| **Bounded Context** | Un hexagone = un bounded context |
| **Aggregate** | Entité racine dans le domaine |
| **Repository** | Port secondaire |
| **Domain Service** | Logique dans la couche domaine |
| **Application Service** | Use case (couche application) |
| **Anti-Corruption Layer** | Adapter secondaire qui traduit un modèle externe |

```java
// Aggregate Root (DDD) in the hexagonal domain
public class Project {

    private final ProjectId id;
    private String name;
    private final List<Task> tasks = new ArrayList<>();

    public void addTask(Task task) {
        if (tasks.size() >= 100) {
            throw new TaskLimitReachedException(id);
        }
        tasks.add(task);
    }

    public int completedTaskCount() {
        return (int) tasks.stream()
            .filter(t -> t.getStatus() == Status.DONE)
            .count();
    }

    public double completionPercentage() {
        if (tasks.isEmpty()) return 0.0;
        return (double) completedTaskCount() / tasks.size() * 100;
    }
}
```

## Exemple complet : un deuxième adapter sans toucher au domaine

Le vrai test de l'hexagonale : **ajouter un canal d'entrée** (CLI) ou **changer de technologie** (MongoDB) **sans modifier une seule ligne du domaine**.

### Ajout d'un adapter CLI (nouveau port primaire)

```java
// New primary adapter: CLI with Picocli
// Domain and application DO NOT change
@Command(name = "task", description = "Task management")
public class TaskCliAdapter implements Runnable {

    private final TaskManagementUseCase taskManagement;

    public TaskCliAdapter(TaskManagementUseCase taskManagement) {
        this.taskManagement = taskManagement;
    }

    @Command(name = "create")
    public void create(
            @Option(names = "--title", required = true) String title,
            @Option(names = "--priority", defaultValue = "MEDIUM") String priority) {

        Task task = taskManagement.createTask(title, Priority.valueOf(priority));
        System.out.println("Task created: " + task.getId().value());
    }

    @Command(name = "status")
    public void changeStatus(
            @Option(names = "--id", required = true) String id,
            @Option(names = "--status", required = true) String status) {

        Task task = taskManagement.changeStatus(
            new TaskId(UUID.fromString(id)),
            Status.valueOf(status)
        );
        System.out.println("Status changed: " + task.getStatus());
    }

    @Override
    public void run() {}
}
```

### Changement de base de données (nouvel adapter secondaire)

```java
// New secondary adapter: MongoDB instead of JPA
// Domain and application DO NOT change
@Repository
public class TaskMongoAdapter implements TaskRepository {

    private final MongoTemplate mongoTemplate;

    public TaskMongoAdapter(MongoTemplate mongoTemplate) {
        this.mongoTemplate = mongoTemplate;
    }

    @Override
    public Task save(Task task) {
        TaskDocument doc = toDocument(task);
        mongoTemplate.save(doc, "tasks");
        return task;
    }

    @Override
    public Optional<Task> findById(TaskId id) {
        TaskDocument doc = mongoTemplate.findById(id.value().toString(), TaskDocument.class, "tasks");
        return Optional.ofNullable(doc).map(this::toDomain);
    }

    @Override
    public List<Task> findByProject(ProjectId projectId) {
        Query query = Query.query(Criteria.where("projectId").is(projectId.value().toString()));
        return mongoTemplate.find(query, TaskDocument.class, "tasks")
            .stream()
            .map(this::toDomain)
            .toList();
    }

    @Override
    public void delete(TaskId id) {
        Query query = Query.query(Criteria.where("_id").is(id.value().toString()));
        mongoTemplate.remove(query, TaskDocument.class, "tasks");
    }

    // mapping Document ↔ Domain (private)
    private TaskDocument toDocument(Task task) { /* ... */ }
    private Task toDomain(TaskDocument doc) { /* ... */ }
}
```

**Résultat** : on a changé de PostgreSQL à MongoDB sans modifier une seule ligne dans `domain/` ou `application/`. Seul l'adapter dans `infrastructure/` a changé.

## Pièges courants à éviter

### 1. Laisser fuir les annotations techniques dans le domaine

```java
// ❌ BAD — JPA annotation in the domain
@Entity
@Table(name = "tasks")
public class Task {
    @Id
    @GeneratedValue
    private Long id;
    // ...
}

// ✅ GOOD — pure domain, JPA entity separated in infrastructure
// domain/model/Task.java — no annotation
public class Task {
    private final TaskId id;
    // ...
}

// infrastructure/adapter/out/persistence/TaskEntity.java — JPA annotations
@Entity
@Table(name = "tasks")
public class TaskEntity {
    @Id
    private UUID id;
    // ...
}
```

### 2. Mapping anémique (entités sans logique)

```java
// ❌ BAD — anemic domain, logic is in the service
public class Task {
    private Status status;
    public void setStatus(Status status) { this.status = status; }  // public setter without validation
}

public class TaskService {
    public void changeStatus(TaskId id, Status newStatus) {
        Task task = repo.findById(id).orElseThrow();
        // business rule is in the SERVICE instead of the ENTITY
        if (task.getStatus() == Status.DONE) {
            throw new IllegalStateException("Cannot change the status of a completed task");
        }
        task.setStatus(newStatus);
    }
}

// ✅ GOOD — business logic is in the entity
public class Task {
    public void changeStatus(Status newStatus) {
        if (!this.status.canTransitionTo(newStatus)) {
            throw new InvalidStatusTransitionException(this.status, newStatus);
        }
        this.status = newStatus;
    }
}
```

### 3. Exposer les entités du domaine dans l'API

```java
// ❌ BAD — domain entity serialized directly to JSON
@GetMapping("/{id}")
public Task getTask(@PathVariable UUID id) {
    return taskManagement.findById(new TaskId(id));
}

// ✅ GOOD — a DTO specific to the infrastructure layer
@GetMapping("/{id}")
public TaskResponseDto getTask(@PathVariable UUID id) {
    Task task = taskManagement.findById(new TaskId(id));
    return TaskResponseDto.from(task);  // explicit mapping
}
```

### 4. Mettre trop de logique dans la couche application

```java
// ❌ BAD — the service computes priority (this is a business rule)
public class TaskManagementService {
    public Task createTask(String title, int urgency, int importance) {
        Priority priority;
        if (urgency > 8 && importance > 8) priority = Priority.CRITICAL;
        else if (urgency > 5) priority = Priority.HIGH;
        else priority = Priority.MEDIUM;
        // ...
    }
}

// ✅ GOOD — computation belongs in the domain
public enum Priority {
    LOW, MEDIUM, HIGH, CRITICAL;

    public static Priority compute(int urgency, int importance) {
        if (urgency > 8 && importance > 8) return CRITICAL;
        if (urgency > 5) return HIGH;
        return MEDIUM;
    }
}
```

### 5. Over-engineering un CRUD simple

```java
// ❌ OVER-ENGINEERING for a simple read
// domain/port/in/
public interface ListProductsUseCase {
    List<Product> listAll();
}
// domain/port/out/
public interface ProductRepository {
    List<Product> findAll();
}
// application/
public class ListProductsService implements ListProductsUseCase {
    public List<Product> listAll() {
        return productRepository.findAll();  // just a pass-through
    }
}
// infrastructure/adapter/in/rest/
public class ProductRestAdapter { /* ... */ }
// infrastructure/adapter/out/persistence/
public class ProductJpaAdapter implements ProductRepository { /* ... */ }

// → 5 classes for a simple SELECT * FROM products
// → Hexagonal is not justified here if this is ALL the app does
```

## Checklist Architecture Hexagonale

Pour chaque projet, vérifiez :

### Domaine
- [ ] Le package `domain` n'a **aucune dépendance** vers Spring, JPA, Jackson, etc.
- [ ] Les entités contiennent des **règles métier** (pas de modèle anémique)
- [ ] Les ports primaires expriment des **cas d'utilisation métier** (pas des opérations CRUD)
- [ ] Les ports secondaires sont des **interfaces** définies dans le domaine
- [ ] Les exceptions sont **métier** (`InsufficientBalanceException`, pas `SQLException`)

### Application
- [ ] Les services **orchestrent** sans contenir de logique métier
- [ ] Les services n'ont aucune dépendance technique directe

### Infrastructure
- [ ] Les adapters primaires **traduisent** (HTTP → use case, pas de logique métier)
- [ ] Les adapters secondaires **implémentent** les ports du domaine
- [ ] Les DTOs sont dans l'infrastructure, pas dans le domaine
- [ ] Le mapping Entity ↔ Domain est dans l'adapter, pas dans le domaine
- [ ] La configuration Spring (`@Bean`) câble le tout

### Tests
- [ ] Les entités du domaine se testent **sans aucun framework**
- [ ] Les use cases se testent avec des **mocks** ou des **adapters in-memory**
- [ ] Un changement d'adapter (JPA → Mongo) ne casse **aucun test du domaine**

## Résumé

L'architecture hexagonale protège ce qui a le **plus de valeur** — la logique métier — en l'isolant de tout ce qui est technique et changeant.

| Concept | Rôle |
|---|---|
| **Domaine** | Entités, value objects, règles métier, ports (interfaces) |
| **Port primaire** | Ce que le domaine sait faire (use cases) |
| **Port secondaire** | Ce dont le domaine a besoin (repositories, services externes) |
| **Adapter primaire** | Traduit une requête externe en appel use case (REST, CLI, test) |
| **Adapter secondaire** | Implémente un port avec une technologie (JPA, Mongo, SMTP) |
| **Règle de dépendance** | L'infrastructure dépend du domaine, jamais l'inverse |

**Quand l'adopter** : applications métier complexes avec une longue durée de vie, plusieurs canaux, ou des changements technologiques prévisibles.

**Quand s'en passer** : CRUD simples, prototypes, projets court terme.

> "L'architecture hexagonale n'est pas une fin en soi. C'est un outil pour protéger le métier du bruit technique." — Alistair Cockburn
