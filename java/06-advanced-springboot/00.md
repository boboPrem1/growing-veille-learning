# Phase 1 — Spring Boot Internals : comprendre la magie

### Objectifs
- Comprendre comment Spring Boot fonctionne sous le capot
- Maîtriser le mécanisme d'auto-configuration
- Créer un starter Spring Boot custom
- Comprendre le cycle de vie des beans en profondeur

### Sujets

#### 1.1 — Le conteneur Spring en profondeur
- `ApplicationContext` : types (AnnotationConfigApplicationContext, WebApplicationContext)
- Cycle de vie des beans : instanciation → populate → `@PostConstruct` → prêt → `@PreDestroy` → destruction
- `BeanPostProcessor` et `BeanFactoryPostProcessor` : intercepter la création des beans
- Scopes avancés : `singleton`, `prototype`, `request`, `session`, custom scopes
- `@Lazy` : initialisation différée et ses implications
- `@DependsOn`, `@Order`, `@Priority` : contrôler l'ordre de création
- `ObjectProvider<T>` et `@Lookup` pour les injections dynamiques

#### 1.2 — Auto-configuration démystifiée
- `@SpringBootApplication` = `@Configuration` + `@EnableAutoConfiguration` + `@ComponentScan`
- Le fichier `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`
- `@Conditional` et ses variantes : `@ConditionalOnClass`, `@ConditionalOnMissingBean`, `@ConditionalOnProperty`
- Ordre de précédence : configuration utilisateur > auto-configuration
- Debug : `--debug` flag, rapport d'auto-configuration (`CONDITIONS EVALUATION REPORT`)
- Désactiver une auto-configuration : `@SpringBootApplication(exclude = ...)`

#### 1.3 — Créer un starter custom
- Convention de nommage : `xxx-spring-boot-starter` + `xxx-spring-boot-autoconfigure`
- Structure du module autoconfigure : `@Configuration` + `@Conditional*` + `@ConfigurationProperties`
- `@EnableConfigurationProperties` et binding de propriétés typé
- Fichier `spring.factories` (legacy) vs `AutoConfiguration.imports` (Spring Boot 3+)
- Tester son starter dans un projet consommateur
- Cas d'utilisation : SDK interne, configuration d'entreprise partagée

#### 1.4 — Configuration avancée
- `@ConfigurationProperties` : binding typé, validation, nested objects, listes et maps
- `@Value` vs `@ConfigurationProperties` (quand utiliser lequel)
- Relaxed binding : `my-property` = `myProperty` = `MY_PROPERTY`
- Configuration externalisée : priorité des sources (args > env > yml > defaults)
- Secrets management : Vault (aperçu), variables d'environnement, Spring Cloud Config
- `@PropertySource` et sources de configuration custom

### Exercices
1. **Debug auto-config** — Lancer une app Spring Boot avec `--debug`, identifier 5 auto-configurations activées et 5 exclues, expliquer pourquoi
2. **Custom starter** — Créer un starter `audit-spring-boot-starter` qui enregistre automatiquement un `AuditService` loggant chaque appel de méthode `@Service`
3. **ConfigurationProperties** — Créer une configuration typée complexe : `app.features.notifications.enabled`, `app.features.notifications.channels[0].type=EMAIL`, etc.
4. **BeanPostProcessor** — Créer un `TimingBeanPostProcessor` qui mesure le temps d'initialisation de chaque bean et log ceux > 100ms

# Phase 2 — AOP, événements et programmation asynchrone

### Objectifs
- Maîtriser la programmation orientée aspect (AOP) avec Spring
- Implémenter un système d'événements applicatifs découplé
- Gérer les traitements asynchrones et la planification de tâches

### Sujets

#### 2.1 — AOP (Aspect-Oriented Programming)
- Concepts : aspect, advice, pointcut, join point, weaving
- Types d'advice : `@Before`, `@After`, `@AfterReturning`, `@AfterThrowing`, `@Around`
- Expressions pointcut : `execution()`, `within()`, `@annotation()`, `@within()`, `args()`
- `@Around` et `ProceedingJoinPoint` : le plus puissant
- Proxy JDK vs proxy CGLIB (et quand Spring utilise lequel)
- Cas d'utilisation : logging, audit, mesure de performance, contrôle d'accès, retry
- Limites : les appels internes (self-invocation) ne passent pas par le proxy
- Annotations custom + AOP = syntaxe déclarative métier (`@Auditable`, `@RateLimited`, `@Timed`)

#### 2.2 — Système d'événements Spring
- `ApplicationEvent` et `ApplicationEventPublisher`
- `@EventListener` et `@TransactionalEventListener`
- Phases transactionnelles : `AFTER_COMMIT`, `AFTER_ROLLBACK`, `AFTER_COMPLETION`, `BEFORE_COMMIT`
- Événements asynchrones avec `@Async` + `@EventListener`
- Événements typés vs événements payload (Spring 4.2+)
- Architecture event-driven interne (sans message broker)
- Cas d'utilisation : envoi d'email post-inscription, invalidation de cache, audit trail

#### 2.3 — Programmation asynchrone (`@Async`)
- `@EnableAsync` et configuration du `TaskExecutor`
- `CompletableFuture` comme type de retour
- Thread pools : `ThreadPoolTaskExecutor` (corePoolSize, maxPoolSize, queueCapacity)
- Gestion des exceptions dans les méthodes `@Async` (`AsyncUncaughtExceptionHandler`)
- Propagation du contexte de sécurité dans les threads async (`DelegatingSecurityContextExecutor`)
- Piège : `@Async` + self-invocation (même problème que AOP)

#### 2.4 — Scheduling (`@Scheduled`)
- `@EnableScheduling` et `@Scheduled` (fixedRate, fixedDelay, cron)
- Expressions cron Spring (6 champs vs 5 Unix)
- `SchedulingConfigurer` pour les schedules dynamiques
- Distributed scheduling : ShedLock pour éviter les exécutions multiples en cluster
- Cas d'utilisation : nettoyage de données, rapports quotidiens, synchronisation

### Exercices
1. **AOP Audit** — Créer un aspect `@Auditable` qui log automatiquement : méthode appelée, arguments, résultat, durée, utilisateur connecté
2. **AOP Performance** — Aspect `@Timed` qui publie les temps d'exécution comme métriques Micrometer
3. **Événements** — Système d'événements : à la création d'un `Utilisateur`, émettre un `UtilisateurCreeEvent` ; 3 listeners : envoyer email de bienvenue, créer un projet par défaut, logger l'audit
4. **Async + Schedule** — Tâche planifiée quotidienne qui génère un rapport de statistiques de manière asynchrone et publie un événement à la fin

# Phase 3 — Spring Data avancé

### Objectifs
- Aller au-delà du CRUD avec Spring Data JPA
- Maîtriser les Specifications pour les requêtes dynamiques
- Gérer le multi-datasource et les stratégies de migration
- Optimiser les performances de la couche données

### Sujets

#### 3.1 — Specifications et requêtes dynamiques
- `Specification<T>` et `JpaSpecificationExecutor<T>`
- Composition de specifications (`and()`, `or()`, `not()`)
- Criteria API sous-jacente
- Filtrage dynamique complexe (search API avec critères multiples optionnels)
- Alternative : QueryDSL (aperçu)

#### 3.2 — Projections et performance
- Interface-based projections (closed vs open)
- Class-based projections (DTO projections)
- `@Query` avec constructeur DTO (`SELECT new com.app.dto.TacheResume(...)`)
- `@EntityGraph` : contrôle du fetch strategy par requête
- `@BatchSize` et `@Fetch(FetchMode.SUBSELECT)` pour le N+1
- Pagination performante (keyset pagination vs offset)
- Read-only transactions (`@Transactional(readOnly = true)`) et leur impact

#### 3.3 — Multi-datasource
- Configurer 2+ DataSource dans une même application
- `@Primary` et qualifiers pour les datasources
- Entity managers et transaction managers par datasource
- Cas d'utilisation : base de lecture (replica) + base d'écriture, base legacy + base nouvelle

#### 3.4 — Auditing et soft delete
- Spring Data JPA Auditing : `@CreatedDate`, `@LastModifiedDate`, `@CreatedBy`, `@LastModifiedBy`
- `AuditorAware<T>` : fournir l'utilisateur courant
- Soft delete avec `@Where(clause = "deleted = false")` et `@SQLDelete`
- Envers (Hibernate Envers) : audit historique complet des entités (aperçu)

#### 3.5 — Migrations de schéma
- Flyway : conventions de nommage (`V1__init.sql`), repeatable migrations, callbacks
- Liquibase : changelog XML/YAML, changesets, rollback
- Flyway vs Liquibase : critères de choix
- Bonnes pratiques : migrations idempotentes, jamais de modification d'une migration appliquée, données de test

### Exercices
1. **Specifications** — Créer une API de recherche : `GET /api/taches/search?titre=deploy&statut=EN_COURS&priorite=HAUTE&dateMin=2025-01-01` avec des `Specification<Tache>` composables
2. **Projections** — Endpoint `GET /api/taches/resume` qui retourne uniquement `id`, `titre`, `statut` via une interface projection (sans charger l'entité complète)
3. **Multi-datasource** — Configurer une base `write-db` (PostgreSQL) et une base `read-db` (replica) ; router les `@Transactional(readOnly = true)` vers la replica
4. **Flyway** — Mettre en place Flyway avec : `V1__create_tables.sql`, `V2__add_projets.sql`, `V3__add_utilisateurs.sql`, migration de données incluse

# Phase 4 — Spring Security avancé

### Objectifs
- Aller au-delà du JWT basique
- Implémenter OAuth2 / OpenID Connect
- Maîtriser la sécurité fine (method security, row-level security)
- Sécuriser une application en production

### Sujets

#### 4.1 — OAuth2 et OpenID Connect
- OAuth2 : les 4 flows (Authorization Code, Client Credentials, PKCE, Device)
- OpenID Connect (OIDC) : couche d'identité sur OAuth2
- Spring Security OAuth2 Resource Server : valider les JWT émis par un Identity Provider
- Spring Security OAuth2 Client : login via Google, GitHub, Keycloak
- Keycloak comme Identity Provider (setup Docker, realms, clients, rôles)
- JWT claims et authorities mapping

#### 4.2 — Method Security avancée
- `@PreAuthorize` avec SpEL : `@PreAuthorize("hasRole('ADMIN') or #userId == authentication.principal.id")`
- `@PostAuthorize` : filtrer le résultat après exécution
- `@PreFilter` / `@PostFilter` : filtrer les collections
- Custom `PermissionEvaluator` pour `hasPermission()`
- ACL (Access Control Lists) — aperçu
- Row-level security : l'utilisateur ne voit que ses données

#### 4.3 — Sécurité avancée
- CORS : configuration fine (`CorsConfigurationSource`)
- CSRF : quand le désactiver (API stateless) et quand le garder (app server-side rendered)
- Rate limiting : implémentation avec Bucket4j ou Redis
- Headers de sécurité : `Content-Security-Policy`, `X-Frame-Options`, `Strict-Transport-Security`
- Brute force protection : verrouillage de compte après N tentatives
- Audit de sécurité : logger toutes les tentatives d'authentification

#### 4.4 — Multi-tenancy
- Concepts : tenant isolation (database, schema, row-level)
- Row-level : discriminator column + Hibernate Filter
- Schema-level : `@TenantId` (Hibernate 6+)
- Résolution du tenant : header, subdomain, JWT claim
- Cas d'utilisation : application SaaS

### Exercices
1. **Keycloak** — Installer Keycloak (Docker), créer un realm `taskflow`, configurer un client, et connecter Spring Security comme Resource Server
2. **Method security** — `@PreAuthorize` sur les services : un utilisateur ne peut modifier/supprimer que ses propres tâches, un admin peut tout faire
3. **Rate limiting** — Limiter les endpoints publics à 10 req/min par IP avec Bucket4j + Redis
4. **Multi-tenancy** — Implémenter l'isolation row-level : chaque tenant a un `tenantId` dans le JWT, les requêtes sont automatiquement filtrées

# Phase 5 — Programmation réactive avec WebFlux

### Objectifs
- Comprendre le modèle réactif vs le modèle servlet classique
- Maîtriser les fondamentaux de Project Reactor (Mono, Flux)
- Créer des endpoints réactifs avec Spring WebFlux
- Accéder aux données de manière réactive (R2DBC)

### Sujets

#### 5.1 — Fondamentaux réactifs
- Programmation impérative vs réactive
- Reactive Streams : `Publisher`, `Subscriber`, `Subscription`, `Processor`
- Backpressure : le consommateur contrôle le flux
- Project Reactor : `Mono<T>` (0 ou 1 élément) et `Flux<T>` (0 à N éléments)
- Opérateurs essentiels : `map`, `flatMap`, `filter`, `zip`, `merge`, `concat`, `switchIfEmpty`, `onErrorResume`
- Hot vs cold publishers
- Schedulers : `Schedulers.parallel()`, `Schedulers.boundedElastic()`

#### 5.2 — Spring WebFlux
- `@RestController` réactif : retourner `Mono<T>` et `Flux<T>`
- Functional endpoints : `RouterFunction` et `HandlerFunction`
- WebClient : client HTTP réactif (remplace RestTemplate)
- Server-Sent Events (SSE) pour le streaming temps réel
- WebFlux vs Spring MVC : quand choisir lequel
- Piège : bloquer dans un pipeline réactif (le crime mortel)

#### 5.3 — Accès aux données réactif
- R2DBC : Reactive Relational Database Connectivity
- Spring Data R2DBC : `ReactiveCrudRepository`
- Pas de lazy loading, pas de relations automatiques (contrairement à JPA)
- Transactions réactives avec `@Transactional`
- MongoDB réactif avec `ReactiveMongoRepository` (aperçu)

#### 5.4 — Tests réactifs
- `StepVerifier` : tester les `Mono` et `Flux` pas à pas
- `WebTestClient` : tester les endpoints WebFlux
- Tester le timing et le backpressure

### Exercices
1. **Reactor Kata** — Série de 20 exercices sur les opérateurs Reactor (map, flatMap, zip, error handling, retry, timeout)
2. **API réactive** — Réécrire un contrôleur simple en WebFlux retournant `Mono<TacheDto>` et `Flux<TacheDto>`
3. **WebClient** — Consommer une API externe (GitHub API) de manière réactive avec WebClient, gérer les erreurs et le retry
4. **SSE** — Endpoint `GET /api/taches/stream` qui émet un Server-Sent Event à chaque nouvelle tâche créée (temps réel)

# Phase 6 — Spring Batch et traitements de masse

### Objectifs
- Comprendre l'architecture de Spring Batch
- Implémenter des jobs de traitement par lots (ETL)
- Gérer les reprises sur erreur et le partitionnement
- Planifier et monitorer les jobs

### Sujets

#### 6.1 — Architecture Spring Batch
- Concepts : Job, Step, ItemReader, ItemProcessor, ItemWriter
- `JobRepository` : persistance de l'état des jobs
- `JobLauncher` : démarrer un job programmatiquement ou par schedule
- Chunk-oriented processing : lire N, traiter N, écrire N
- Tasklet : pour les étapes simples (pas de chunk)

#### 6.2 — Readers, Processors, Writers
- Readers built-in : `FlatFileItemReader` (CSV), `JdbcCursorItemReader`, `JpaPagingItemReader`, `JsonItemReader`
- Writers built-in : `FlatFileItemWriter`, `JdbcBatchItemWriter`, `JpaItemWriter`
- Custom ItemProcessor : transformation, filtrage, enrichissement
- Composite readers/writers pour les traitements multi-sources

#### 6.3 — Gestion des erreurs et reprise
- Skip policy : ignorer les lignes en erreur (avec compteur max)
- Retry policy : retenter N fois avant de skip
- Listeners : `StepExecutionListener`, `ItemReadListener`, `SkipListener`
- Restart et recovery : reprendre un job qui a échoué là où il s'était arrêté
- Job parameters et idempotence

#### 6.4 — Performance et partitionnement
- Multi-threaded step : traiter les chunks en parallèle
- Partitioning : diviser les données et traiter en parallèle
- Remote partitioning (aperçu)
- Dimensionnement : chunk size, page size, commit interval

### Exercices
1. **Import CSV** — Job qui lit un CSV de 10 000 tâches, valide le format, transforme et insère en base (chunk size 100)
2. **Export rapport** — Job qui lit les tâches de la base, calcule des statistiques par projet, et génère un CSV de rapport
3. **Reprise sur erreur** — Job avec skip policy : les lignes invalides sont loggées dans un fichier d'erreurs, le job continue
4. **Partitioning** — Partitionner le job d'import par plage d'IDs (4 partitions parallèles), mesurer le gain de performance

# Phase 7 — GraalVM Native et performance avancée

### Objectifs
- Compiler une application Spring Boot en image native (GraalVM)
- Comprendre les implications et limitations du mode natif
- Optimiser le temps de démarrage et la consommation mémoire
- Profiler et optimiser une application en production

### Sujets

#### 7.1 — GraalVM Native Image
- Ahead-of-Time (AOT) vs Just-in-Time (JIT) compilation
- Spring Boot 3 et le support natif (`spring-boot-starter-parent` + GraalVM)
- `mvn -Pnative native:compile` : compiler en binaire natif
- Temps de démarrage : ~50ms vs ~2-5s en JIT
- Empreinte mémoire : ~50MB vs ~200MB+ en JIT
- Limitations : pas de reflection dynamique (sans configuration), pas de CGLIB proxies
- AOT processing : Spring génère le code à la compilation
- Tracing agent pour détecter les usages de reflection

#### 7.2 — Virtual Threads (Project Loom)
- Java 21+ : virtual threads vs platform threads
- `spring.threads.virtual.enabled=true`
- Impact sur le modèle thread-per-request de Spring MVC
- Quand virtual threads rendent WebFlux moins nécessaire
- Structured concurrency (aperçu)

#### 7.3 — Profiling et optimisation
- Spring Boot Actuator : health, metrics, env, beans, conditions, httptrace
- Custom health indicators et custom metrics
- JVM profiling : JFR (Java Flight Recorder), async-profiler
- Heap dump analysis : Eclipse MAT
- GC tuning : G1GC, ZGC, choix du garbage collector
- Connection pooling : HikariCP (configuration fine : maximumPoolSize, minimumIdle, connectionTimeout)
- Startup optimization : lazy initialization, class data sharing (CDS)

#### 7.4 — Caching avancé
- Stratégies : cache-aside, write-through, write-behind, read-through
- Spring Cache avec Caffeine (in-process, L1) + Redis (distributed, L2)
- Cache hierarchique : L1 local + L2 distribué
- TTL, eviction policies, cache stampede protection
- `@Cacheable(condition, unless, key, keyGenerator)`
- Cache invalidation patterns dans un cluster

### Exercices
1. **Native build** — Compiler une app Spring Boot en image native, comparer le temps de démarrage et la mémoire avec le JAR classique
2. **Virtual threads** — Activer les virtual threads, benchmark sous charge (1000 req/s) vs thread pool classique
3. **Custom actuator** — Créer un `HealthIndicator` custom (vérifier une API externe) et un compteur métrique `taches.creees.total`
4. **Cache L1+L2** — Implémenter un cache Caffeine (L1, 1min TTL) + Redis (L2, 10min TTL), mesurer le hit ratio et la latence

# Phase 10 — Production-Ready : patterns et bonnes pratiques

### Objectifs
- Appliquer les patterns d'architecture dans une app Spring Boot
- Maîtriser les bonnes pratiques de production
- Construire une application complète intégrant tous les acquis

### Sujets

#### 10.1 — Architecture hexagonale avec Spring Boot
- Mapper les couches : `domain/` (entities, ports), `application/` (use cases), `infrastructure/` (adapters Spring)
- Les ports sont des interfaces Java (pas d'annotation Spring dans le domain)
- Les adapters sont des `@Component`, `@Repository`, `@RestController`
- Tester le domain en isolation complète (sans Spring)
- Package structure hexagonale concrète

#### 10.2 — CQRS léger avec Spring
- Séparer les services de commande (écriture) et de requête (lecture)
- Read models optimisés (projections, vues dénormalisées)
- `@Transactional(readOnly = true)` systématique sur les queries
- Quand aller plus loin (event sourcing, bases séparées)

#### 10.3 — Bonnes pratiques de production
- Feature flags : Togglz ou FF4j
- Graceful shutdown (`server.shutdown=graceful`)
- Liveness vs readiness probes pour Kubernetes
- Structured logging avec corrélation ID
- Configuration externalisée et secrets (jamais de secrets dans le code)
- Versioning d'API : URI (`/v1/`, `/v2/`) vs header (`Accept-Version`)
- Backward compatibility : additive changes only
- Database migrations sans downtime (expand-contract pattern)

#### 10.4 — Documentation et maintenabilité
- Architecture Decision Records (ADR) : documenter les décisions
- OpenAPI comme contrat (contract-first vs code-first)
- README et runbook : comment démarrer, déployer, debugger
- Diagrammes C4 pour documenter l'architecture

### Exercices
1. **Hexagonal** — Restructurer une API Spring Boot en architecture hexagonale stricte : le package `domain` n'a aucune dépendance Spring
2. **CQRS léger** — Séparer `TacheCommandService` (create, update, delete) et `TacheQueryService` (findById, search, rapport) avec des modèles de lecture optimisés
3. **Feature flags** — Implémenter un feature flag `NOUVELLE_UI_DASHBOARD` avec Togglz, testable par header ou par utilisateur
4. **ADR** — Rédiger 3 ADRs : choix de la base de données, choix REST vs GraphQL, stratégie de cache
